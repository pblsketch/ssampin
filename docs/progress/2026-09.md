## 🔢 학생 번호 무결성 수정 — 과제·설문·생기부 근거 5건 (2026-09-08)

앞선 세션이 재현만 해 둔 5건([분석](../03-analysis/student-number-integrity-20260908.analysis.md) · [핸드오프](../03-analysis/student-number-integrity.handoff.md))을 실제로 고쳤다. **ADR-097.**

**뿌리 두 가지**

1. **배열 위치를 학생 번호로 썼다** — 비활성 학생을 거른 뒤 `index + 1`. 2번이 전출하면 3번이 2번이 된다.
2. **번호만으로 학생을 이었다** — 학생 id·학년·반이 명시돼 있어도 마지막에 번호만 비교. 1반 3번의 제출물이 2반 3번 칸에도 붙었다.

**만든 규칙 2개(단일 출처)**

- `src/domain/rules/rosterNumbering.ts` — 담임 `studentNumber` / 수업반 `number` 를 하나로 모으고, **유효·고유한 번호는 절대 안 바꾸고** 없거나 겹친 것만 미사용 번호로 채운다. ★번호 계산을 **전체 명렬표에서 먼저** 하고 그다음 거른다 — 그래야 전출 학생 번호가 빈 자리로 남는다.
- `src/domain/rules/submissionMatching.ts` — 학생 id → 학년·반·번호 → 번호 순. **양쪽에 소속이 있는데 다르면 번호가 같아도 안 잇는다.** 소속 없는 구형 제출물은 같은 번호 학생이 둘 이상이면 **추측하지 않고** `unmatched` 로 돌린다.

## 생기부 초안이 교사 평가로 열린다 — 평가 맨 앞, 첫 문장 '~하는 학생임.' (2026-09-08, ADR-094)

오너 요청: "교사 평가가 지금은 맨 뒤에 들어가는데 맨 앞에 들어가게. 시스템 프롬프트도 바꾸고, 초안 화면의
`동기·질문 → 과정 → 결과 → 교사 평가` 순서도 평가를 맨 앞으로. 교사 평가는 '~하는 학생임.' 으로 끝나게."
결정 [ADR-094](../03-decisions/ADR-094.md) · 서버 프롬프트 판본 **1 → 2**. **커밋·푸시 안 함(저장소 쪽).**

**세 곳이 같은 순서를 말하게 했다.** 프롬프트 한 곳만 고치면 화면 범례와 어긋난다(ADR-072 실측: 프롬프트로는 규정을 못 막는다).

- **1층 프롬프트(서버 시크릿 `RECORD_PROMPT_L1`)** — 저장소에 본문이 없다. 배급 함수에서 판본 1 을 내려받아
  6개 절을 고치고 판본 2 로 올렸다. §2 시점("평가로 **맺는다**" → "평가로 **연다**", 끝에서 되풀이 금지) ·
  §3 문체(첫 문장 어미 `~하는 학생임.` 고정, `~확인됨`·`~관찰됨`·`~보임` 금지, 근거 없는 칭찬 금지, 역량은 분야와 함께) ·
  §6 골격(평가를 화살표 맨 앞으로) · §8 행특(옛 "평가어를 앞세우지 말라"를 _장면 없는 평가어 나열 금지_ 로 좁힘) ·
  §9 예시 2편(마지막 평가 문장을 첫 문장으로 옮기고 `~하는 학생임.` 으로 고쳐 씀) · §11 출력 형식.
- **2층 사용자 턴** — `NARRATIVE_MARK_INSTRUCTION` 이 `[평가] [동기] [과정] [결과]` 를 요구하고, 순서와 첫 문단
  어미를 매 요청 **끝에서** 다시 말한다(최신성). `recordDraftPack` 초안·분량 조절·[다시 표시] 세 꾸러미가 이 문장 하나를 공유한다.

## 명령줄에서 프롬프트를 뺐다 — 두 CLI 다 stdin 으로 (2026-09-07)

[ADR-089](../03-decisions/ADR-089.md) 후속 6. 같은 날 이미지 첨부 작업(ADR-090)이 끝나 겹침이
풀리면서 바로 착수했다. 계획서 `.omc/plans/record-draft-codex-argv-20260907.md`. **미커밋.**

**왜 했나.** 명령줄은 같은 컴퓨터의 다른 프로그램이 읽을 수 있는데(작업 관리자 "명령줄" 열,
`Get-CimInstance Win32_Process`, 백신·EDR 텔레메트리), 거기 실리던 것은 규정만이 아니라
**선생님이 넣은 학생 근거 본문**이었다. 이름 가림은 그 반 명단 안에서만 작동하므로
**다른 반 학생 이름은 가려지지 않은 채** 실릴 수 있었다. 세 갈래 중 **유일하게 학생
개인정보가 걸린 것**이라 미루지 않고 분리만 했던 항목이다.

**측정 먼저 (저장소 밖 `E:\test\ownai-stdin-spike`)**

| CLI               | 방법                                                         | 결과                                        |
| ----------------- | ------------------------------------------------------------ | ------------------------------------------- |
| claude 2.1.258    | `-p --input-format stream-json` + stdin 한 줄, 첨부 **없이** | exit 0 · 7초 · 응답 도착                    |
| codex-cli 0.153.4 | `codex exec … -` + stdin                                     | exit 0 · 6초 · `turn.completed` · 응답 도착 |

★**저장소가 여러 곳에 적어 둔 "stdin 을 닫지 않으면 codex 는 무한 대기한다"는 사실이지만
이번 경우가 아니다.** 그 실측은 stdin 을 **열어 둔 채 아무것도 안 준** 경우다. 써 넣고 곧바로
`end()` 하면 둘 다 정상이다. 머리말 세 곳이 이 구분 없이 "그래서 인자로 넘긴다"의 근거로
쓰이고 있어 함께 고쳤다 — 안 고치면 다음 세션이 "실측 근거"라 믿고 되돌린다.
★codex 1차 시도는 사용량 한도로 실패했는데 그때도 `thread.started`·`turn.started` 는 찍혔다.
**stdin 은 읽혔다**는 뜻이고 무한 대기도 없었다(3초 종료). 한도 풀린 뒤 재측정해 완주를 봤다.

**적용**

- **claude — 항상 stdin.** 첨부가 있을 때만 열던 경로(ADR-090)를 **항상**으로. 목적이 명령줄
  노출 제거라 첨부 유무와 무관하다.
- **codex — 버전 조건부.** `CODEX_STDIN_MIN = '0.153.4'`(**실측한 버전만 적는다**). 그 아래는
  옛 경로 유지 — 구버전에서 `-` 가 프롬프트 **글자로** 읽히면 조용한 오작동이고, 그건 명령줄
  노출보다 나쁘다. ★`OWN_AI_VERSION_FLOOR` 는 **올리지 않았다**(올리면 구버전 선생님이
  코덱스를 아예 못 쓴다).
- **codex 는 규정까지 함께 빠진다** — 시스템 자리가 없어 규정을 프롬프트 앞에 붙이는데 그
  덩어리 전체가 stdin 으로 가기 때문이다. claude 는 규정이 `--append-system-prompt` 옵션이라
  **여전히 명령줄에 남는다**(파일로 넘기는 길은 규정을 디스크에 쓰는 것이라 D7 에 더 나쁘다).
- **러너 실행 시간 상한 신설**(`RUN_TIMEOUT_MS = 10분`). 그전에는 상한이 **아예 없어서**
  CLI 가 멈추면 선생님이 [중단]을 누를 때까지 무기한 매달렸다. 인용되던 "184초"는 앱
  안전장치가 아니라 저장소 밖 스파이크 하네스의 타임아웃이었다.

**★가드가 조용히 무력화되는 것을 막았다 (이번 작업의 핵심)**

`ownAiEgress.test.ts`(저장소의 실명 유출 1순위 가드)는 `commandLineText(buildClaudeArgv(...))`
로 실명을 찾고 있었다. 프롬프트가 stdin 으로 옮겨 가면 **argv 에 본문이 없어서 이유가 틀린 채
항상 통과**한다. 그래서:

- `claudeOutbound()` 로 **argv + stdin 합본**을 재게 했다.
- 새 단언마다 **짝**을 붙였다 — "argv 에 없다" 옆에 반드시 **"그래도 stdin 에는 있다"**.
  이게 없으면 "어디에도 없어서" 참인 경우와 구분되지 않는다.
- codex 도 같은 짝으로 고정하고 **두 경로가 같은 글을 보낸다**(조립을 `buildCodexStdinText`
  한 자리에서 한다)를 단언한다. 구버전 폴백 경로도 테스트로 고정했다.

## 생기부 규정 배급 문 잠그기 — 한도·관측·만료 캐시 (2026-09-07)

배급 창구(`ssampin-record-prompt`)를 점검하다 **인증 헤더 없이도 함수 본문까지 들어간다**는 걸
실호출로 확인했다(`verify_jwt = false`). 다른 14개 함수가 쓰는 공용 횟수 제한을 이 함수만 안
쓰고 있었다. 앱 기능은 미출시지만 **엔드포인트는 이미 살아 있어서 현재형 위험**이었다.
합의 계획(RALPLAN 4라운드) → 구현. 결정 기록: [ADR-089](../03-decisions/ADR-089.md) ·
계획 `.omc/plans/ralplan-record-prompt-leak-20260907.md`. **미커밋.**

**한 것**

- **서버 한도** — 설치본 분당 10·하루 200, IP 분당 60. 분당·일간을 **두 호출로 나눠** 안내
  문구를 가른다. 새 마이그레이션 0건(있는 표를 `endpoint` 값으로 나눠 씀).
- **3단 스위치**(`RECORD_PROMPT_RATELIMIT` = `off`/`observe`/`enforce`). `off` 는 429 만이
  아니라 **DB 왕복까지** 멈춘다. 값이 이상하면 소리를 내고 `observe` 로 간다.
- **차단 관측** — 공용 헬퍼는 차단 시 아무것도 안 남긴다(`rateLimit.ts` 가 insert 전에 return).
  그래서 `record-prompt-blocked` 로 따로 1행 남긴다. 헬퍼를 `max: 1` 로 재사용해 IP 당 분당
  1행으로 스스로 묶인다.
- **만료 캐시 폴백(24시간)** — 서버가 죽어도 초안이 안 멈춘다. 상한을 둔 이유는 규정이 학사
  기재요령에 매인 문서라 무한정 낡은 걸 쓰면 폐지된 규정으로 초안을 쓰는 셈이라서.
- **판별 유니온 반환형 + `promptVersion` 저장** — 서버는 전부터 판본을 주는데 앱이 버리고
  있었다. 이제 어느 규정으로 만든 초안인지 남는다.
- **사유별 안내 + [이어 하기] 60초 쿨다운** — 그 버튼은 큐를 즉시 다시 부르므로 문구만으로는
  재시도 폭주를 못 막는다.
- **문서** — 쌤핀 서버가 남기는 설치 식별자·접속 IP·시각을 `/docs`·개인정보처리방침(한/영)에
  적었다. ★**코덱스 세션 파일 잔존은 오너 결정으로 사용자 문서에서 뺐다**(ADR-089 D12,
  ADR-084 를 뒤집는 결정 — 누락 아님). 내부 QA 체크리스트에는 남겼다.
- **덤으로 실제 버그 수정** — `internalErrorResponse(e)` 를 인자 1개로 부르고 있어 500 로그에
  함수 이름 없이 오류가 `undefined` 로 찍혔다. `tsconfig.json` 의 `include` 가 `["src"]` 라
  타입 검사가 이 파일을 아예 안 봐서 오래 살아남았다.

**검증**

- `npx tsc --noEmit` → **0 errors** ✔
- `npm run lint` → **0 errors**(경고 137은 기존, 내가 만든 것 0) ✔
- `npm run test` → **712파일 9,629개 통과** ✔ 새 테스트 19개 추가(메타 계약 + 헬퍼 동작),
  기존 mock 갱신.
- `npm run regression-check` → **62/62 통과** ✔
- `cd landing && npm run docs:check && npm run build` → **exit 0** ✔

★중간에 게이트가 두 번 빨간불이었는데 **둘 다 이미지 첨부 세션(ADR-090)의 진행 중 상태**였다.
내 변경 파일 목록에 없었고, 그 세션이 마무리하면서 스스로 고쳤다 — ⒜ `ownAiPort.noServer.test.ts`
mock 에 `createFsAttachmentStore` 누락(6실패) ⒝ `useAssistStore.ts` 에 +74줄이 들어가 REGRESSION
#57 의 패턴 거리가 4,266자 > 창 4,000자가 됨(그쪽에서 5,000으로 넓힘). **동시 세션에서는
"내 탓"으로 돌리기 전에 `git status` 와 mtime 부터 볼 것.**

**배포 완료 (2026-09-07) — 세 모드를 실제로 켜 보고 확인**

게이트가 초록이어도 배포·시크릿은 따로 해야 산다. 그래서 **모드마다 배포하고 실호출로 쟀다.**
현장에 이 기능을 담은 앱이 0대라(v2.4.9 는 기능 구현 **전**에 출시) 피해 없이 잴 수 있는 창이었다.

| 단계              | 확인                                        | 결과                                                                    |
| ----------------- | ------------------------------------------- | ----------------------------------------------------------------------- |
| (0) 프롬프트 배급 | 상태·크기만(본문 안 받음)                   | `status=200 bytes=10753` ✔                                              |
| (1) `off`         | 15연발 전부 200 **AND 5분 내 행 0**         | 전부 200 · **0행** ✔ 429 만이 아니라 **DB 왕복까지** 멈춘다             |
| (2) `observe`     | 12연발 전부 200 **AND blocked ≥ 1**         | 전부 200 · `record-prompt` **32행** · `record-prompt-blocked` **1행** ✔ |
| (3) `enforce`     | 카운터 비운 뒤 12연발 → 1~10:200, 11~12:429 | **정확히 일치** ✔ 429 본문 `{"retryAfterKind":"minute"}`                |

★(2)의 32행이 설계와 정확히 맞는다: 통과 10건 × 3행(분당 2 + 일간 1) + 한도 넘은 2건의 일간
1행씩 = 32. 그리고 차단이 2번인데 **blocked 는 1행** — `max: 1` 자기 제한이 의도대로 작동한다.

**최종 상태: `enforce`.** 시크릿 다이제스트를 `sha256('enforce')` 와 대조해 값이 잘리거나
뭉개지지 않았음을 확인했다(`c1f1005e…`). 시험 흔적 행은 전부 삭제(잔여 0).

★**계획 초안은 `observe` 로 끝내자고 했는데 오너 결정으로 `enforce` 로 바꿨다**(ADR-089 D7).
근거: 두 모드의 **관측 데이터가 완전히 같고**(통과도 차단도 양쪽 다 기록된다) 차이는 429 를
돌려주느냐뿐인데, 현장 앱이 0대라 켜도 피해가 없다. `observe` 로 두면 **사는 것 없이 문만
계속 열어 두는** 셈이었다.

**잔여**

- 실기기 QA: 30명 연속 생성 시 행 증가가 학생 수(90)가 아니라 **3행**인지(캐시 건전성).
  1시간을 넘겨 재fetch 하면 6행도 정상이다.
- 함수 로그에서 `mode=enforce` 부팅 줄과 `rate-limit unavailable`(fail-open 발동) 부재 확인 —
  대시보드에서 눈으로 볼 것.
- (다) 명령줄 노출은 **별도 작업 단위**(ADR-089 후속 6). ★다른 세션이 이미지 첨부로
  `promptViaStdin`·`imagePaths` 를 넣는 중이라 **착수 전 대조 필수.**

### 계획 검토가 잡아낸 기존 결함 3건 (C0 - 새 기능보다 먼저 고침)

셋 다 **검증 게이트 4종이 전부 초록인 채** 있었고, 각각 수정을 빼면 새 테스트가 실패하는 것을 확인했다.

1. **초점만 빠져도 저장이 거부된 글이 사라졌다.** 되돌리기 효과가 `focused` 를 의존 목록에 두고
   있어 초점 이탈만으로 다시 돈다. 저장이 거부되면 `draft.content` 는 옛 글이라 방금 쓴 글이
   화면에서 없어지고 붉은 오류만 남았다. **이 기능의 전제를 무너뜨리는 결함이었다.**
2. **[반영]이 실패해도 무반응.** `applyVersion` 에 `try/catch` 가 없어 한도 초과로 던지면
   `markApplied` 도 큐 진행도 안 돌았다.
3. **[다시 표시] 중복 실행 잠금이 `useState` 라 뚫렸다.**

### 이번에 지킨 것

- 조절 대상은 **화면의 현재 글**(3축 키 등록부). 저장이 거부된 글은 디스크에 없다.

### ✅ T2 근거 창고 주제 분류 + 탐구 흐름 완료 (2026-09-04) — 병렬 세션 (핵심)

낱장을 **주제(탐구 흐름)** 로 묶어, 초안이 활동 나열이 아니라 하나의 서사가 되게 한다.

- **주제 축 = 칩 줄**(오너 결정): 영역 탭 아래 `전체 | 미분류 N | 주제… | + 새 주제`.

  창고가 이미 [학생목록 | 근거목록] 2열이라 주제마다 칼럼을 두면 근거 본문이 반토막 나기 때문.

  수행평가 이름으로 주제를 만들면 그 루브릭 요소 이름이 키워드로 자동으로 실린다.
- **흐름 화면**(`InquiryThreadPanel`, 근거 목록 **위에 펼치는 인라인** — 모달 아님, 오너 결정):

  로직 미변경을 테스트로 잠갔다. 0건이면 문구를 안 건드린다.

## 🔒 옆핀 개인정보 보호 2단계 — 위젯 칸 PIN 잠금 (2026-09-01, **실기기 확인 완료**)

옆핀에서는 그대로 보였다. 옆핀이 `WidgetCard` 를 안 거치고 본문을 직접 그리기 때문이다.

| 무엇                    | 자리                                                                           |
| ----------------------- | ------------------------------------------------------------------------------ |
| 해제 상태를 상태 기계로 | `SidePinRuntimeState.pinUnlockedAt` + `pin-unlocked`/`pin-locked` 이벤트       |
| 사건 기반 재잠금        | `protect-released` 와 `close-requested(force)` 에서 `pinUnlockedAt: null`      |
| 잠금 단방향 전파        | `usePinStore.lock()` → `pin:locked` → 옆핀. **푸는 방향 통로는 만들지 않았다** |

**★ 왜 해제 상태를 창(상태 기계)이 드는가** — 패널 창은 접힌 뒤 **10초면 파괴된다.**
화면이 기억하면 그때 증발해 **스칠 때마다 PIN 을 다시 묻고**, 그러면 선생님이 PIN 자체를
꺼 버려 대시보드 보호까지 0이 된다. 계획서 §6.1 이 v1 을 무너뜨린 발견이 이것이다.

**🚨 리뷰가 잡은 결함 1건 — [지금 가리기]가 잠그지 않았다**
`close-requested(force)` 가 `pinUnlockedAt` 을 그대로 뒀다. **그 단추를 누르는 순간은
"누가 온다"는 뜻인데**, 그 사람이 손잡이를 스치면 잠근 위젯 4종이 그대로 열렸다(최대 12시간).
재잠금 사건에 포함시켰다. 게이트 4종·실기기 어느 쪽으로도 안 잡히는 자리였다.

**🚨 실기기에서 결함 1건 — "잠기긴 하는데 비밀번호를 입력해도 안 열려"**

리뷰 지적(임시 해제 플래그가 재잠금을 넘길 수 있다)을 고치면서 **과잉 교정으로 기능을 깨뜨렸다.**
"통로가 있으면 창이 정본"이라며 즉시 열기를 `onUnlocked === undefined` 조건으로 감쌌는데,
`onUnlocked` 는 **항상 있는 함수**라 그 조건이 절대 참이 되지 않았다. 그래서 안쪽 IPC 가
없으면(옛 preload·브라우저 모드) **PIN 을 맞춰도 조용히 아무 일도 안 일어났다.**

→ **무조건 먼저 연다.** 창이 답을 주면 그 값이 이어받아 패널이 파괴돼도 살아남고,
안 주면 이 창에서만 열린 채로 남는다. 어느 쪽이든 **잠긴 채로 갇히지 않는다.**

★ **교훈: "통로가 있는가"를 콜백이 있는가로 판단하면 안 된다.** 콜백은 늘 있고,
없는 것은 그 **안쪽**이다. 그리고 **여는 쪽이 막히는 실패는 잠기는 쪽이 막히는 실패보다
사용자에게 먼저 보인다** — 안전한 기본값을 고를 때 그 비대칭을 함께 봐야 한다.

**계획에서 벗어난 것** — §6.7 의 "창 쪽 칸별 지도" 대신 **화면에서 합쳤다**
(`mergeEditorActivity`). `SidePinApp` 이 이미 두 칸을 알고 있어 통신 규약도 창 쪽 상태도
안 바꾸고 같은 결과를 얻는다. 리뷰에서 `reportEditorActivity` 호출 지점이 하나뿐임을 확인했다.

**두 결함의 공통 원인**: 판단을 **테스트가 볼 수 없는 자리**에 두었다.
① 창을 실제로 다루는 것은 `sidePinWindow.ts` 인데 도메인 테스트만 봤다.
② 폴링 판정을 `main.ts` 안에 두어 어떤 테스트도 못 봤다.
→ 판정을 순수 함수 `stepPresentationWatch` 로 빼고 테스트 6건을 붙였다.
**"발표를 30초 안에 끝내도 두 번째 확인에서 바로 되돌아온다"** 가 테스트로 박혀 있어
누가 최소 유지 시간을 다시 넣으면 빨간불이 뜬다.

★ **교훈**: 명령 이름을 믿지 말고 **그 명령이 실제로 무슨 일을 하는지** 읽을 것.
그리고 "되돌아올 수 있는가(D2)"는 **사람이 직접 누른 경우**에 필요한 것이지,

**🚨 리뷰가 잡은 결함 1건 — 게이트 4종도 실기기 4종도 못 잡았다**

| 신고되지 않았지만 있던 것                                   | 왜                                                                                                                                                                                                                                                 |
| ----------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **메모를 쓰다가 발표하면 옆핀이 다시는 자동으로 안 접힌다** | 화면이 보호를 보고 편집기를 닫으며 `'idle'` 을 보내는데, `onEditorActivityChanged` 가 `!isSidePinResponsive` 라고 **그 보고를 통째로 버렸다.** 다시 보내 주는 곳이 없어 보호가 풀린 뒤에도 `'editing'` 이 남고, `shouldHoldOpen` 이 영영 참이 된다 |

**순한 등급을 만들면서 생긴 자리다.** `force-protect` 는 스스로 `editorActivity` 를 `'idle'` 로
밀어 버려 이 구멍이 없었는데, `soft-protect` 는 쓰던 글을 지키려고 **일부러 안 지운다.**
→ 보호 중에도 **내려가는 보고(`editing → idle`)만은 받아 적도록** 고쳤다(창은 안 건드린다).
올라가는 보고는 받지 않는다 — 숨어 있는 동안 새로 쓸 방법이 없고, 받아 두면 풀리는 순간 접힘이 막힌다.

**⚠️ "쓰던 글이 살아 있다"의 정확한 뜻** — **패널 창을 파괴하지 않는다**는 뜻이다.
편집기가 닫히면서 **아직 저장 안 된 마지막 몇 글자**(저장 지연 이내)는 잃는다.
먼저 저장하고 닫도록 고쳐 봤으나 ① 저장을 기다리면 **보호 후에도 한 박자 내용이 화면에 남고**(P3 위반)
② 화면 갱신이 무한히 겹쳤다. 화면을 먼저 치우는 쪽을 택했다.
**이 동작은 잠금·절전에서도 원래부터 같았다** — 발표 감지가 만든 문제가 아니다.
제대로 고치려면 저장을 effect 바깥으로 옮겨야 한다(후속).
