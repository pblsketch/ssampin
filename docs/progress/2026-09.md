### ✅ T2 근거 창고 주제 분류 + 탐구 흐름 완료 (2026-09-04) — 병렬 세션 (핵심)

낱장을 **주제(탐구 흐름)** 로 묶어, 초안이 활동 나열이 아니라 하나의 서사가 되게 한다.
창고의 분류 축이 생기부 영역 탭 하나뿐이라 근거 12건이 한 줄로 늘어서고, 그게 몇 개의 이야기인지는
교사 머릿속에만 있었다. 그 구조가 "활동 나열형" 세특을 만들고 있었다(분석 §3).

- **주제 축 = 칩 줄**(오너 결정): 영역 탭 아래 `전체 | 미분류 N | 주제… | + 새 주제`.
  **칩이 곧 끌어다 놓는 과녁**이고 체크해서 한 번에 묶을 수도 있다. 칸반 세로 칼럼을 안 쓴 이유는
  창고가 이미 [학생목록 | 근거목록] 2열이라 주제마다 칼럼을 두면 근거 본문이 반토막 나기 때문.
- **주제 이름 후보 1순위 = 수행평가 이름**(`AssessmentPlanItem.title`·`Rubric.title`) → 과제 제목 →
  성취기준 키워드(T3 착지로 실제 동작). 루브릭 **요소** 이름은 주제 이름이 아니라 매칭 키워드로만.
  수행평가 이름으로 주제를 만들면 그 루브릭 요소 이름이 키워드로 자동으로 실린다.
- **흐름 화면**(`InquiryThreadPanel`, 근거 목록 **위에 펼치는 인라인** — 모달 아님, 오너 결정):
  시간순 줄기(슬롯 라벨) · 빈 고리 힌트 3종 · 역량 키워드 칩(분야 붙이기 유도) · 다음 탐구 메모 · 주제 닫기.
- **"이것도 이 주제?"**: `threadSuggest.ts`(순수) 문자열 포함 검사. **AI 없음.** 양방향 —
  주제에서 본 미분류 후보, 미분류 근거에서 본 주제 후보.
- **초안 화면**: "이 주제로" 고르기 → 그 주제 근거 건수 + AI 요청문 복사. 인앱 [AI 초안] 버튼은 안 만듦(Phase 4).
- **브릿지**(별도 레포 `2ccb32c`): `get_inquiry_threads`(읽기 전용·탈식별) 신설 ·
  `get_record_evidence(threadToken)` — 그 주제 근거만, **다른 학생 흐름 토큰은 거부**.
- **관찰 알림 문구**에 "미분류 근거 N건". ★**누구를 부를지는 안 바꿨다**(ADR-072 결정 6) — 선정
  로직 미변경을 테스트로 잠갔다. 0건이면 문구를 안 건드린다.
- **T4 인수인계 처리**: 성취기준 원문을 점검기에 넘기는 배선 → **성취기준 복사 검사가 이제 실제로 돈다**

## 🗓️ 상담예약 — 결번 뒤 학생 번호가 한 칸씩 밀림 (2026-09-03, 게이트 4종 통과)

**신고** — "32명 반에서 16번이 자퇴로 빠졌고 명렬표에도 반영했는데, 상담예약에서 그 번호부터
하나씩 앞으로 당겨져 나온다."

**원인** — 예약이 들고 오는 "번호"는 명렬표의 출석번호(`studentNumber`)인데,
`ConsultationDetail` 은 **활성 학생 배열의 위치**로 학생을 찾고 있었다
(`nonVacant[studentNumber - 1]`, `nonVacant.map((s, i) => ({ number: i + 1 }))`).
중간 번호가 비면 위치와 번호가 어긋나 그 번호부터 전원이 한 칸씩 밀린다.
예약 링크(`landing`)가 내려받는 대상 번호는 원래부터 `studentNumber` 라서 정상이었다 —
밀린 곳은 **교사 화면 3곳**이다.

| 자리                    | 증상                                           |
| ----------------------- | ---------------------------------------------- |
| 예약자 이름 표시        | 17번 예약에 18번 학생 이름 (엑셀·캘린더 포함)  |
| 미신청 학생 목록        | 31명이 1~31번으로 표시 (17번 이후 이름 어긋남) |
| 예약에서 상담 기록 쓰기 | **다른 학생에게 기록이 저장됨** (데이터 오염)  |

**수정** — 위치 대신 번호로 찾는다.

- `consultationRules.ts` 에 순수 함수 2개 추가: `buildStudentNumberIndex`(출석번호 → 학생
  조회표, 활성 우선 · 번호 없거나 0 이하면 제외) · `listUnbookedStudents`(미신청 목록, 번호 오름차순).

- 회귀 테스트 6건 추가(16번 결번 명렬표 32명 시나리오 고정).

**검증** — `npx tsc --noEmit` 0건 · `npm run lint` 0 error(경고 135건은 기존) ·
`npm run test` 648파일 8,552건 통과 · `npm run regression-check` 55/55.

**★남은 확인** — 예약 링크에 보이는 마지막 번호가 **32번**이면 이 수정으로 끝이고,
**31번**이면 명렬표의 학번(출석번호) 값 자체가 재부여된 것이라 별건이다.

**★ 왜 해제 상태를 창(상태 기계)이 드는가** — 패널 창은 접힌 뒤 **10초면 파괴된다.**
화면이 기억하면 그때 증발해 **스칠 때마다 PIN 을 다시 묻고**, 그러면 선생님이 PIN 자체를
꺼 버려 대시보드 보호까지 0이 된다. 계획서 §6.1 이 v1 을 무너뜨린 발견이 이것이다.

**🚨 리뷰가 잡은 결함 1건 — [지금 가리기]가 잠그지 않았다**
`close-requested(force)` 가 `pinUnlockedAt` 을 그대로 뒀다. **그 단추를 누르는 순간은
"누가 온다"는 뜻인데**, 그 사람이 손잡이를 스치면 잠근 위젯 4종이 그대로 열렸다(최대 12시간).
재잠금 사건에 포함시켰다. 게이트 4종·실기기 어느 쪽으로도 안 잡히는 자리였다.

**🚨 실기기에서 결함 1건 — "잠기긴 하는데 비밀번호를 입력해도 안 열려"**

리뷰 지적(임시 해제 플래그가 재잠금을 넘길 수 있다)을 고치면서 **과잉 교정으로 기능을 깨뜨렸다.**
"통로가 있으면 창이 정본"이라며 즉시 열기를 `onUnlocked === undefined` 조건으로 감쌌는데,
`onUnlocked` 는 **항상 있는 함수**라 그 조건이 절대 참이 되지 않았다. 그래서 안쪽 IPC 가
없으면(옛 preload·브라우저 모드) **PIN 을 맞춰도 조용히 아무 일도 안 일어났다.**

→ **무조건 먼저 연다.** 창이 답을 주면 그 값이 이어받아 패널이 파괴돼도 살아남고,
안 주면 이 창에서만 열린 채로 남는다. 어느 쪽이든 **잠긴 채로 갇히지 않는다.**

★ **교훈: "통로가 있는가"를 콜백이 있는가로 판단하면 안 된다.** 콜백은 늘 있고,
없는 것은 그 **안쪽**이다. 그리고 **여는 쪽이 막히는 실패는 잠기는 쪽이 막히는 실패보다
사용자에게 먼저 보인다** — 안전한 기본값을 고를 때 그 비대칭을 함께 봐야 한다.

**계획에서 벗어난 것** — §6.7 의 "창 쪽 칸별 지도" 대신 **화면에서 합쳤다**
(`mergeEditorActivity`). `SidePinApp` 이 이미 두 칸을 알고 있어 통신 규약도 창 쪽 상태도
안 바꾸고 같은 결과를 얻는다. 리뷰에서 `reportEditorActivity` 호출 지점이 하나뿐임을 확인했다.

**검증** — `tsc` 0 · `lint` 0 error(경고 135건은 기존) · `test` **644파일 8,522 통과**
(신규: 가드 10건 · REGRESSION #65 렌더 11건 · 배선 6건 · 도메인 재잠금 7건) ·
`regression-check` **54/54**(신규 #65). 최종 **8,524 통과**.

★ **REGRESSION #65 는 grep 이 아니라 렌더 테스트다.** `import` 한 줄만 남고 JSX 에서 가드가
빠져도 grep 은 초록이 된다 — 같은 폴더의 기존 privacy 테스트가 자기 한계를 그렇게 적어 두었다.

누가 최소 유지 시간을 다시 넣으면 빨간불이 뜬다.

**🚨 리뷰가 잡은 결함 1건 — 게이트 4종도 실기기 4종도 못 잡았다**

**순한 등급을 만들면서 생긴 자리다.** `force-protect` 는 스스로 `editorActivity` 를 `'idle'` 로
밀어 버려 이 구멍이 없었는데, `soft-protect` 는 쓰던 글을 지키려고 **일부러 안 지운다.**

올라가는 보고는 받지 않는다 — 숨어 있는 동안 새로 쓸 방법이 없고, 받아 두면 풀리는 순간 접힘이 막힌다.

**⚠️ "쓰던 글이 살아 있다"의 정확한 뜻** — **패널 창을 파괴하지 않는다**는 뜻이다.

② 화면 갱신이 무한히 겹쳤다. 화면을 먼저 치우는 쪽을 택했다.
**이 동작은 잠금·절전에서도 원래부터 같았다** — 발표 감지가 만든 문제가 아니다.
제대로 고치려면 저장을 effect 바깥으로 옮겨야 한다(후속).
