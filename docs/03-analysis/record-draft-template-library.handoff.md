## 1. 왜 이 일을 하는가

사용자는 한국어 교사이자 쌤핀 제품 오너다. 현재 AI 생기부 초안이 하나의 시스템 프롬프트와 고정된 순서로 작성되어 수업과 학생의 차이를 충분히 드러내지 못한다고 지적했다. 사용자가 제시한 방법은 ① 복수 템플릿 선택 ② 구성 요소 모듈 조합 ③ 자기만의 커스텀 프롬프트 입력이다.

대학 학종 가이드북·실제 학생부 사례·교사 연수 자료를 조사한 뒤, 사용자는 방향에 동의하고 새 세션이 테스트 설계·구현·검증까지 빠짐없이 수행할 수 있는 핸드오프를 요청했다. 따라서 처음부터 아이디어를 다시 묻거나 문구만 바꾸고 종료하지 않는다. 다만 연구 제안의 세부 기본값·저장 구조·서버 배급 방식이 모두 확정된 것은 아니다. 작은 구현 선택은 근거를 기록하며 진행하고, 운영 권한이 필요한 일은 구체적인 변경안과 검증을 먼저 준비한다.

목표는 단순히 문장을 다르게 보이게 하는 것이 아니다. **같은 사실을 보존하면서 실제 수업·개인 수행에 맞는 기록 초점을 선택하게 하는 것**이다. 문장 어미 무작위 변경, 동의어 치환, 과장된 역량 평가, 활동 사이의 가짜 인과관계는 해결책이 아니다.

## 3. 이어갈 제품 방향

### 기본 선택과 사용자 제작

- 기본 흐름: **작성 초점 선택 → 필요한 요소만 조정 → 내 작성 방식으로 저장**.
- 8종: 성취·수행 / 개념 적용 / 근거 비교·판단 / 질문·검증 / 피드백·수정 / 설계·창작·문제 해결 / 협업·기여 / 관심 탐색·선택.
- 행특은 `생활·관계 종합`이라는 영역별 기본 구성을 따로 두고 필요한 초점을 결합한다.
- 독립 설정: 기록 초점 / 시작 방식(교사 판단·수행 장면·실제 질문) / 묶기(대표 하나·실제로 이어진 과정·독립 수행을 성취별로).
- 수업 맥락(내용·수행 방법·제공된 기준), 학생 개인 근거, 서술 초점을 분리한다. 맥락은 선택 정보이며 기존 자료를 우선 사용한다. 관찰 본문 입력을 막는 추가 필수 폼을 만들지 않는다.
- 사용자 지시는 강조점·문체·구성을 조절한다. 공통 규정·사실성·개인정보 보호를 끄는 시스템 프롬프트 교체 기능으로 만들지 않는다.
- 모듈은 문장 조각이 아니다. 목적·필요 근거·생략 조건·허용 영역·금지 추론을 함께 가진다. 모듈 하나가 반드시 문단 하나일 필요는 없다.
- 처음부터 모든 설정을 펼치지 않는다. 기존 공통 AI 패널 안에서 간단한 선택을 제공하고 조합/커스텀은 상세 설정으로 둔다.

### 보존할 계약

- 원본 근거·기존 초안·사용자 편집 내용을 자동 덮어쓰지 않는다. 비교 후 교사가 명시적으로 반영한다.
- 본문 우선, 장면·주제 선택, 여러 학생·여러 날짜 입력, 담임/교과 양쪽 진입점을 보존한다.
- 성취기준 원문 전송 금지 등 기존 외부 전송 계약을 확인한다. 개인 이름·학번 마스킹과 기재 금지 근거 제외를 새 입력 경로에도 적용한다.
- 학생 진술·교사 관찰·산출물·교사 판단의 출처를 보존한다. 자기평가만으로 독립 수행이나 교사 확인을 꾸미지 않는다.
- 동기·성장·갈등·후속 탐구·진로 연결은 근거가 있을 때만. 팀 성과를 개인 성과로 바꾸지 않는다.
- 최종 바이트는 앱이 계산한다. 미저장 편집 글을 분량 조절의 원본으로 사용한다. 생성과 분량 조절 모두 요청 시작 시 대상을 고정한다.

ADR-094는 **사용자가 채택한 기존 결정**이다. 새 방향으로 변경되는 부분은 후속 ADR에서 명시하고 기존 문서를 조용히 뒤집지 않는다. 기존형·기존 초안은 보존하며 새 작성 방식에서 순서와 어미를 선택할 수 있도록 설계한다. ADR 번호는 현재 마지막 번호를 다시 확인하고 예약 번호를 피한다.

서버 L1과 클라이언트 지시가 충돌하면 UI만 선택 가능해지고 생성 결과는 그대로일 수 있다. 운영 시크릿 본문을 로그·문서·저장소로 유출하지 않고 안전한 방법으로 확인할 필요가 있다. 접근 불가 시 이 부분을 미확인으로 적는다. 상충하는 운영 규정을 둔 채 사용자 지시로 무시하도록 시켜 해결했다고 주장하지 않는다.

공통 규정 / 템플릿 구성 / 사용자 지시의 경계를 먼저 설계한다. 규정 판본·템플릿 판본·적용 설정은 추적할 수 있어야 하지만 비공개 L1 원문을 초안에 저장하지 않는다. 구버전 앱·신규 앱과 규정 판본의 조합, 캐시 만료 전 요청, 규정 수신 실패를 포함한 배포 순서와 되돌리기 전략을 마련한다.

## 5. 순차 실행 계획과 각 단계의 종료 증거

### S0. 상태 파악 및 기준선

- dirty main의 기존 변경 목록과 실행 중인 앱/서버를 기록한다. 다른 세션의 쌤도구·자기평가서 작업을 덮어쓰거나 프로세스를 종료하지 않는다.
- 위 파일부터 호출 경로를 따라 생성/축약/보충, 쌤핀 AI/내 AI, 담임/교과 흐름을 지도화한다.
- 기존 관련 테스트를 실행해 통과/기존 실패를 구분한다. 옛 테스트 수를 현재 증거로 복사하지 않는다.
- 산출물: 관련 파일·문제 원인·기준선 결과. 이 단계에서 멈추지 않고 S1로 진행한다.

### S1. 상세 설계 및 테스트 명세

- `docs/01-plan/features/record-draft-template-library.plan.md`, `docs/02-design/features/record-draft-template-library.design.md` 작성.
- 초기 범위에 기본 8종·행특 구성·모듈 조합·사용자 지시·내 방식 저장/복제/수정/삭제를 포함한다. 공유 마켓·대학별 합격 최적화·실제 학생부 예시 수록은 범위 밖이다.
- 설정 적용 범위와 기본값, 사용자 방식 저장 위치·충돌 처리·기본 복구, 삭제된 방식으로 만든 기존 초안의 재현 정보, 구데이터 기본값을 결정한다. 학생 원문을 재사용 템플릿에 저장하지 않는다.
- 시작/묶기와 모듈의 충돌, 근거 부족 시 안내·생략·다른 초점 추천, 사용자 지시 충돌의 실제 적용값을 정의한다.

- 아래 AC와 QA를 자동 테스트/실제 화면/실제 모델 평가로 배정하고 기대 결과를 먼저 기록한다.
- 산출물: 실행 가능한 설계, AC-테스트 대응표, 필요한 ADR. 근거가 충분한 로컬 작업마다 승인을 반복 요청하지 않는다.

### S2. 도메인과 저장 구현

- 순수 타입·기본 카드·조합/검증·지시 조립을 구현하고 의미 있는 단위 테스트를 추가한다.
- 기존 의존 방향과 저장/동기화 규칙을 따른다. 새 영속 파일이면 잠금·동기화 목록·누락 필드·손상 데이터·구버전 읽기 처리를 확인한다.
- 고정 지시 충돌을 제거하되 공통 규정·마스킹·제외 근거 처리와 기존형을 유지한다.
- 산출물: 관련 단위/저장 테스트 결과와 변경 설명.

### S3. 공통 UI와 실행 연결

- 간단 선택, 상세 조합, 추가 지시, 내 방식 관리 및 실제 적용 설정 요약을 구현한다. 모든 UI 한국어, sp-\* 토큰.
- 생성/축약/보충에서 설정의 유지 또는 변경 정책을 명시한다. 실행 중 설정 변경은 진행 중 요청을 바꾸지 않는다.
- 학생 전환·본문 수정·패널 닫기·중단·재시도에서 다른 대상에 결과를 반영하지 않도록 기존 실행 계약과 연결한다.
- 쌤핀 AI/내 AI 모두 같은 검증된 구성 계약을 받는지 확인한다.
- 산출물: 컴포넌트/통합 테스트, 담임·교과 실제 화면 증거.

### S4. 실제 모델 비교와 수동 QA

- 아래 가상 근거 묶음으로 기존형 대비 새 방식 생성 실험을 수행한다. 실제 학생 개인정보 사용 금지.
- 모델·공급자·날짜·규정/템플릿 판본·설정·근거 ID·결과·평정 근거를 보존하되 시크릿 원문/토큰/실명을 기록하지 않는다.
- 호출 수와 예상 비용을 먼저 제한하고, 이미 허용된 환경에서 수행한다. 유료 호출 승인이 필요한 환경이면 가상/모의 검증까지 먼저 끝내고 필요한 실제 검증만 명확히 요청한다.
- 실제 공급자 접근 불가 시 모의 테스트를 실제 품질 검증으로 대체 표기하지 않는다. 공급자별 확인 범위를 구분한다.
- 산출물: `docs/03-analysis/record-draft-template-library.qa.md`, 가상 입력/출력 비교 자료, 화면 증거, 실패 수정·재검증 기록.

### S5. 전체 검증·문서·인계

- `npx tsc --noEmit`, `npm run lint`, `npm run test`, `npm run regression-check`, `npm run build` 실행. 명령·종료 코드·핵심 수치와 로그 경로 기록.
- 사용자 행동이 바뀌므로 `landing/src/content/docs.ts`의 공개 가이드 갱신, 필요한 스크린샷 준비. `cd landing`에서 `npm run docs:check`, `npm run build` 확인. 다른 세션 변경 보존.
- Electron 실제 실행 및 설치본/패키지 검증의 확인 범위를 구별한다. 설치본 검증이 미실행이면 출시 검증 완료라고 하지 않는다.

- 서버 변경이 필요하면 비공개 적용물·판본·적용 순서·호환성·되돌리기·검증 방법을 준비한 뒤 운영 적용 승인을 마지막에 요청한다. push/배포를 임의 수행하지 않는다.

## 7. 테스트 설계 상세

### 자동 테스트

- 기존 후보: `src/domain/services/__tests__/recordDraftPack.test.ts`, `src/domain/rules/__tests__/narrativeParagraphs.test.ts`, `src/domain/rules/__tests__/recordLengthGoal.test.ts`, `src/adapters/stores/__tests__/useRecordDraftsStore.test.ts`, `src/adapters/components/RecordDraft/__tests__/RecordDraftAiPanel.test.tsx`, `src/infrastructure/ownAi/__tests__/RecordPromptClient.test.ts`.
- 프롬프트 문자열이 특정 문구를 포함한다는 검사만으로 끝내지 않는다. 설정 전파, 상충 지시 부재, 개인정보 차단, 대상 고정, 저장 호환성을 검사한다.
- 조합 전체의 무의미한 전수 검사 대신 정상 기본값 + 위험한 경계 조합을 다룬다. 저장 실패/늦은 응답/캐시 구버전은 결정적인 모의 테스트로 재현한다.

### 실제 생성 평가용 가상 입력

1. 두 작품 비교 메모·비평문: T3, T1, T5 비교(전후 없는 T5가 성장을 발명하지 않는지).
2. 주장 글 초안·교사/동료 피드백·수정본: T5, T3, T1 비교.
3. 문학 작품 시점 변경·창작 설명: T6, T3, T1 비교.
4. 개념을 이용한 현상 설명과 실제 검토: T2, T4, T1 비교.
5. 모둠 산출물만 있는 기록 / 개인 기여가 추가된 기록의 쌍: T7.
6. 진로 변경 전후의 탐색 / 관심 직업명만 있는 기록의 쌍: T8.
7. 일상 생활 관찰과 단일 사건: 행특. 단일 사건을 인격 전체로 일반화하지 않는지.
8. 서로 무관한 두 과제: 실제 연결 없음에도 하나의 탐구 동기로 묶는지.
9. 관찰 한 줄, 질문 없음, 미완성 탐구, 자기평가만 있음, 금지 근거 포함의 경계 입력.

최소 1~4의 비교는 총 12개 결과로 초점 차이를 확인하고, 5~9의 위험 조건도 평가한다. 확률적 실패가 의심되는 사례는 재실행하여 단발 성공에 의존하지 않는다. 비교 전 rubric을 고정한다: 사실 보존·개인 귀속·교과 수행의 구체성·초점 적합성·불필요한 요소 생략·학생 간 차이·교사 수정 필요량. 점수만 남기지 말고 판단을 뒷받침하는 부분을 기록한다. 새 사실/개인정보 유출/타학생 반영은 즉시 실패이며 문체 점수로 상쇄하지 않는다. 모델의 자동 평가는 보조로만 사용한다.

### 실제 화면 순서

담임에서 근거 선택 → 초점 선택 → 상세 설정 → 내 방식 저장 → 생성 → 바이트/형광펜 확인 → 편집 글과 비교 → 명시 반영 → 앱 재실행 후 설정/본문 확인. 교과 진입에서도 반복한다. 별도 시나리오로 생성 중 학생 전환·본문 수정·중단·패널 닫기·네트워크 실패·삭제된 사용자 방식·구데이터를 검증한다. Playwright 사용 시 로컬 HTTP 서버를 사용하고 다른 세션 포트를 점유하지 않는다.
