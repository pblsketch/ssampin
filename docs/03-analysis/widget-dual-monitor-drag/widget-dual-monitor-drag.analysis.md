# 위젯 듀얼 모니터 드래그 신고 — 근거 기반 원인 분석

- 작성일: 2026-08-18
- 신고 내용: 듀얼 모니터에서 위젯 헤더 **우측 상단**을 잡고 주모니터로 끌었더니
  ① **좌측 상단을 잡은 것처럼** 인식되고 ② 위젯이 **최대 절반만** 주모니터로 넘어가
  두 모니터에 반씩 걸친 채 더 이상 이동하지 않음.
- 상태: **코드 근거 확보 / 최종 확정은 신고자 환경 정보 3건 필요** (아래 §5)

---

## 1. 결론 먼저

증상 두 가지는 서로 다른 버그가 아니라 **하나의 원인에서 동시에 나오는 짝**이다.

> **위젯이 커서보다 "느리게" 따라온다 → 커서가 위젯 위를 미끄러진다.**

- 위젯이 커서 이동량의 일정 비율(예: 절반)만 움직이면,
  커서는 잡았던 지점(우측 상단)에서 점점 위젯의 **왼쪽 방향으로 밀려난다** → 증상 ①
- 커서가 주모니터 끝까지 가도 위젯은 그 비율만큼만 이동 → **"최대 절반"** 에서 멈춤 → 증상 ②

"정확히 절반"이라는 표현은 **두 모니터의 배율 차이가 2배(예: 100% ↔ 200%)** 일 때 나오는
전형적인 수치다. 즉 **모니터별 화면 배율(DPI) 불일치**가 1순위 용의자다.

## 2. 확정된 사실 (코드로 검증)

### 2-1. 위젯 드래그 경로는 두 개뿐이고, 서로 완전히 다르다

| 모드           | 누가 창을 움직이나                            | 코드                                            |
| -------------- | --------------------------------------------- | ----------------------------------------------- |
| 일반 위젯 모드 | **Chromium(OS)** — `-webkit-app-region: drag` | `src/adapters/components/Widget/Widget.tsx:444` |
| 바탕화면 모드  | **쌤핀이 직접** — 마우스 훅 + `SetWindowPos`  | `electron/desktopWidgetManager.ts:980~1020`     |

- 일반 모드에는 드래그용 IPC 채널이 **존재하지 않는다**(`electron/preload.ts` 전수 확인).
  즉 일반 모드의 이동은 100% Chromium 내부 동작이며, 우리 코드가 개입하지 않는다.
- 바탕화면 모드는 위젯 창을 바탕화면(WorkerW)의 **자식 창**으로 붙이기 때문에
  `-webkit-app-region: drag`가 무력화되어 직접 구현했다 (`Widget.tsx:84` 주석).

**→ 어느 모드였는지에 따라 조사 대상이 완전히 갈린다. 이것이 첫 번째로 확인할 것이다.**

### 2-2. 최근 "화면 밖 이탈 방지" 커밋은 이번 신고의 원인이 아니다

```
git merge-base --is-ancestor f2cd0b02 v2.4.0  →  v2.4.0 does NOT have clamp
```

- 경계 제한(clamp) 기능은 커밋 `f2cd0b02`(2026-08-17 22:08)에 들어왔고 **아직 푸시조차 안 됐다.**
- 신고자가 쓸 수 있는 최신 버전은 v2.4.0(2026-08-15)이며 이 코드가 **없다**.
- **따라서 "반만 가고 멈춤"을 clamp 탓으로 돌리면 오진이다.** 원인은 그 이전부터 있던 것.

### 2-3. 바탕화면 모드 드래그 계산 자체는 "차이값(delta)" 방식이라 이론상 어긋나지 않는다

```ts
// electron/desktopWidgetManager.ts:986
const dx = p.x - dragState.startMouse.x; // 커서 이동량 (마우스 훅 좌표)
const rawX = dragState.startWidget.x + dx; // 시작 위치 + 이동량
```

잡은 지점의 오프셋을 따로 저장하지 않고 **"시작 위치 + 커서가 움직인 만큼"** 으로 계산하므로,
좌표계만 일치하면 어디를 잡든 offset은 자동 보존된다.
→ **증상 ①은 "offset을 잃어버린 버그"가 아니라, 위젯이 커서를 못 따라간 결과로 봐야 한다.**
(이 구분이 중요하다. offset 버그로 오진하면 엉뚱한 곳을 고치게 된다.)

### 2-4. 그런데 "좌표계 일치"가 모니터 배율이 다르면 깨질 수 있는 지점이 있다

드래그 한 번에 세 종류의 좌표가 섞인다.

| 값                           | 출처                                                                | 좌표계                                  |
| ---------------------------- | ------------------------------------------------------------------- | --------------------------------------- |
| `startMouse`, `p`            | Win32 저수준 마우스 훅                                              | 프로세스 DPI 인식 수준에 따른 화면 좌표 |
| `startWidget`, `startBounds` | `screen.dipToScreenRect(window, …)` (`desktopWidgetManager.ts:838`) | 실제 물리 픽셀                          |
| 이동 반영                    | `SetWindowPos` (`electron/platform/win32Desktop.ts:2026`)           | **부모(WorkerW) 클라이언트 좌표**       |

세 가지가 모두 같은 축척이어야 1:1로 따라온다. 확인된 취약점 2가지:

1. **`dipToScreenRect(window, …)`는 "그 창이 올라가 있는 모니터" 기준으로 환산한다.**
   위젯이 두 모니터에 걸쳐 있는 순간에는 반대편 모니터 영역까지 잘못된 배율로 환산된다.
   드래그 중에는 `startBounds`를 시작 시점에 한 번만 재므로 이동 중 재환산 사고는 없지만,
   **경계를 넘는 순간 Windows가 DPI 변경(WM_DPICHANGED)을 통보해 Chromium이 창 크기를
   스스로 다시 잡는다.** 이때 훅 드래그와 Chromium이 서로 창을 밀며 다투면
   위젯이 경계에 붙어 더 나아가지 못하는 상태가 만들어질 수 있다. → 증상 ② 설명 가능.

2. **`SetWindowPos`에 화면 좌표를 그대로 넘긴다.** 바탕화면 모드의 위젯은 WorkerW의
   **자식 창**이고, Win32에서 자식 창의 `SetWindowPos` 좌표는 화면 좌표가 아니라
   **부모 클라이언트 좌표**다. 두 좌표계는 부모(=가상 화면)의 원점이 (0,0)일 때만 일치한다.
   **보조 모니터가 주모니터의 왼쪽/위쪽에 배치되면 가상 화면 원점이 음수가 되어 어긋난다.**
   코드에는 이 변환(`ScreenToClient`)이 드래그 경로에 **없다**
   (`ScreenToClient`는 바탕화면 아이콘 판정에만 쓰인다 — `win32Desktop.ts:1668`).
   → 이 경우 이동량이 아니라 **위치가 통째로 한 모니터만큼 어긋난다**. 증상과는 결이 다르지만,
   듀얼 모니터 배치가 "보조가 왼쪽"이면 반드시 함께 검증해야 한다.

### 2-5. 곁가지로 확인된 별개 결함 (이번 신고와 무관, 기록용)

`electron/main.ts:1215` `getDefaultWidgetBounds()`는 주모니터의 **크기(workAreaSize)** 만 쓰고
**원점(workArea.x/y)** 을 무시한다. 주모니터가 가상 화면 원점이 아닌 배치(보조가 왼쪽/위)에서는
위젯 첫 표시 위치가 엉뚱한 모니터로 갈 수 있다.

## 4. 배율 차이가 왜 "정확히 절반"을 만드는가 (산수)

주모니터 100%, 보조 200%라 하자. 커서를 보조 모니터에서 왼쪽으로 1000px(물리) 옮기면

- 훅이 보고하는 이동량과 창에 적용되는 이동량의 축척이 2배 어긋나는 경로가 하나라도 있으면
  창은 500px만 움직인다.
- 커서가 주모니터 끝(더 갈 데 없음)에 닿았을 때 위젯은 **절반 지점**에 있다 →
  "최대 절반만 이동, 반씩 걸쳐 있음"과 정확히 일치.
- 그리고 이동 중 내내 커서는 위젯보다 500px 앞서므로, 처음 잡은 우측 상단이
  점점 좌측으로 밀린다 → "좌측 상단을 잡은 것처럼".

## 5. 확정을 위해 신고자에게 받아야 할 것 (3가지)

1. **위젯 모드** — 설정 → 위젯에서 "바탕화면 모드"가 켜져 있는지 (일반 위젯인지).
2. **모니터 배치와 배율** — Windows 설정 → 시스템 → 디스플레이에서
   ① 두 모니터의 **배율(%)** 각각 ② 주모니터가 **왼쪽인지 오른쪽인지** ③ 해상도.
   (배율이 서로 다르면 1순위 가설 확정에 가깝다.)
3. **진단 로그** — 바탕화면 모드인 경우에만 존재:
   `%APPDATA%\쌤핀\native-desktop-diag.log` 의 `[7-C] drag` 줄들.

   ```
   [7-C] drag start mouse=(…) widget=(…) size=(…) workAreas=N
   [7-C] drag move #N mouse=(x,y) delta=(dx,dy) newPos=(X,Y) moveOk=true
   ```

   여기서 **`delta`(커서가 움직인 양)와 `newPos`의 실제 변화량을 비교**하면
   축척이 어긋나는지 한 줄로 판명된다. 1:1이면 가설 1·3 기각, 2:1이면 확정.

## 6. 임시 안내 (신고자에게 지금 줄 수 있는 우회책)

- 두 모니터의 **배율을 동일하게** 맞추면 증상이 사라질 가능성이 높다 (1순위 가설이 맞다면).
- 또는 위젯을 주모니터로 옮기고 싶을 때는 드래그 대신 **위젯을 껐다가 주모니터에서 다시 켜는** 방법.
- 챗봇이 안내한 "앱 재시작 / 항상 위에 / 아이콘 모드"는 이 증상과 **무관하다.**
  (KB 답변 교정 필요 — 위치 이동 문제에 가시성 문제 해법을 안내하고 있다.)

## 7. 미출시 clamp 코드에 대한 선제 경고 (f2cd0b02)

지금 신고의 원인은 아니지만, **이 코드가 출시되면 듀얼 모니터에서 새 증상을 만들 수 있다.**

`clampWidgetBoundsToWorkArea`는 **모니터 하나의 작업 영역만** 기준으로 삼는다
(`desktopWidgetManager.ts:1002` — `findBestWorkAreaForBounds`로 가장 많이 겹치는 모니터 1개 선택).
드래그 중 위젯이 경계를 넘어 겹침이 뒤집히는 순간 기준 모니터가 **바뀌고**,
두 모니터의 작업 영역 세로 위치(`workArea.y`, 작업표시줄 위치·해상도 차이)가 다르면
`minY = workArea.y` 강제 때문에 **위젯이 세로로 튄다.**

→ 실기기 확인 항목에 "**배율·해상도가 다른 듀얼 모니터에서 경계를 가로지르는 드래그**"를
반드시 넣어야 한다. 현재 커밋 메시지의 검증 범위에는 이 항목이 없다.

## 8. 2차 조사 (2026-08-18) — 신고자 회신 없이 확정하는 경로

### 8-1. 오너 PC가 신고 조건과 동일한 환경이다

`EnumDisplayMonitors` + `GetDpiForMonitor`(per-monitor aware)로 실측:

| 모니터          | 물리 해상도 | 배율               | 물리 좌표            |
| --------------- | ----------- | ------------------ | -------------------- |
| DISPLAY1 (주)   | 2880×1800   | **175%** (dpi 168) | (0,0)–(2880,1800)    |
| DISPLAY2 (보조) | 1920×1080   | **100%** (dpi 96)  | (2880,0)–(4800,1080) |

- 가상 화면 원점 = **(0,0)** → §2-4-2(자식 창 좌표계) 어긋남은 **이 배치에서는 발생하지 않는다.**
  (보조가 왼쪽/위인 배치에서만 문제. 오너 PC로는 그 가설을 검증할 수 없음 — 별도 항목으로 남긴다.)
- 배율비 **1.75배**. 위젯이 커서 이동량의 1/1.75 = **57%**만 따라오면
  사용자 표현 "최대 절반만 이동"과 사실상 일치한다.

### 8-2. 기존 진단 로그: 아직 이 버그를 밟은 적이 없다

`%APPDATA%\ssampin\native-desktop-diag.log` — `[7-C] drag` 기록 55건 분석:

- drag 시작 시 위젯 x 좌표 분포: 1097 / 1180 / 1376 / 1391 / 1430 / 1433 / 2154 / 2165
- **최대 2165** → 위젯이 모니터 경계(2880)를 넘은 드래그는 **한 건도 없다.**
- 기록된 모든 이동은 `newPos = startWidget + delta`로 **정확히 1:1** (예: `delta=(179,16)` → `newPos`가 정확히 그만큼 이동).
  → 같은 배율 안에서는 계산이 옳다. 문제는 경계를 넘을 때만 드러난다.
- 이 로그로 오너가 **바탕화면 모드 사용자**임도 확인됨.

### 8-3. 코드에서 특정한 결함 — 드래그 중 "출발 모니터 크기"를 매 프레임 강제

`electron/desktopWidgetManager.ts` drag hot path:

```ts
win32.moveWidget(
  cachedWidgetHwnd,
  newX,
  newY,
  dragState.startBounds.width, // ← 드래그 시작 시점 물리 크기 (출발 모니터 배율 기준)
  dragState.startBounds.height,
);
```

`startBounds`는 drag 시작 시 `dipToScreenRect`로 잰 **physical** 크기다. 배율이 다른 모니터로
넘어가면 Windows가 `WM_DPICHANGED`로 창 크기를 다시 잡는데, 우리 코드는 매 MOUSEMOVE마다
**출발 모니터 기준 크기를 도로 밀어넣는다.** 오너 환경 기준 위젯 폭이 732 ↔ 418 물리픽셀
사이를 오가게 된다(418 DIP 위젯 기준).

이 한 가지가 두 증상을 모두 설명한다:

- 위젯이 갑자기 좁아지면, 우측 상단을 잡고 있던 커서가 위젯 **왼쪽**으로 튄다 → 증상 ①
- Windows와 우리 코드가 서로 창을 밀어내 경계에서 진행이 막힌다 → 증상 ②

### 8-4. 계측 보강 (이번 커밋 대상)

기존 로그는 **"어디로 옮겨달라고 요청했는지"(`newPos`)만** 남기고
**"실제로 어디에 놓였는지"** 를 남기지 않아, 재현해도 판독이 불가능했다. 다음을 추가:

- `describeApplied()` — `GetWindowRect`로 **실제 적용된 위치·크기**를 읽어
  요청값과의 오차(`posErr`, `sizeErr`) + 그 순간의 **모니터 배율**을 기록.
- `drag start` — 출발 모니터 배율, 작업 영역 원점(`workAreaOrigin`) 기록.
  원점이 (0,0)이 아니면 §2-4-2 가설 후보.
- `drag move` — 30회마다 요청값 vs 실제값 대조(FFI 비용 때문에 sampling 유지).
- `drag end` — **`totalDelta`(커서 이동량) vs `actualTravel`(위젯 실제 이동량) + `ratio`**.

### 8-5. 판정 기준 (재현 후 이 한 줄만 보면 된다)

```
[7-C] drag end … totalDelta=(dx,dy) actualTravel=(tx,ty) ratio=(rx,ry) … sizeErr=(dw,dh) scale=…
```

| 관측                                       | 판정                                                                               |
| ------------------------------------------ | ---------------------------------------------------------------------------------- |
| `ratio` ≈ **1.000** 이고 `sizeErr` = (0,0) | 바탕화면 모드는 결백 → 신고자는 **일반 위젯 모드**였고 원인은 Chromium 쪽 (가설 2) |
| `ratio` ≈ **0.571 또는 1.75**              | 배율비 그대로 → 축척 불일치 **확정** (가설 1)                                      |
| `sizeErr` 이 0이 아니고 요동               | §8-3 크기 강제 충돌 **확정**                                                       |
| `posErr` 이 일정한 상수                    | 자식 창 좌표계 어긋남 (가설 3)                                                     |

### 8-6. 재현 절차 (오너 PC, 약 30초)

1. `npm run electron:dev`
2. 위젯 켜기 → 설정에서 **바탕화면 모드** 켜기 (기존 로그상 이미 켜져 있을 가능성 높음)
3. 위젯을 **보조 모니터(오른쪽, 100%)로 옮긴 뒤**, 헤더 **우측 상단**을 잡고
   **주모니터(왼쪽, 175%)로 천천히 끌기** → 놓기
4. 반대 방향으로도 한 번
5. `%APPDATA%\ssampin\native-desktop-diag.log`의 마지막 `[7-C] drag end` 줄 판독

## 9. 오너 PC 실측 — 바탕화면 모드 (2026-08-18)

> **읽는 순서 안내** — §9~§14는 두 세션이 나란히 조사하며 각자 기록한 구간이라
> 같은 실측을 두 번 적은 곳이 있다(§9와 §10). 결론은 §13(원인)과 §14(수정)에 정리돼 있다.

경계를 가로지르는 드래그 3회 실측. **바탕화면 모드는 결백하다.**

```
drag end totalDelta=(2302,-9)   actualTravel=(2302,0)   ratio=(1.000,0.000)  posErr=(0,0) sizeErr=(0,0)
drag end totalDelta=(-2281,107) actualTravel=(-2281,107) ratio=(1.000,1.000) posErr=(0,0) sizeErr=(0,0)
drag end totalDelta=(2256,-145) actualTravel=(2256,-107) ratio=(1.000,0.738) posErr=(0,0) sizeErr=(0,0)
```

- **X축 ratio가 3회 모두 정확히 1.000** → 축척 불일치(가설 1) **기각**.
- **posErr 전 구간 (0,0)** → 자식 창 좌표계 어긋남(가설 3) **기각**.
  (`workAreaOrigin=(0,0)` 이므로 애초에 발생 조건이 아님. 보조가 좌/상단인 배치는 미검증으로 남음.)
- **sizeErr 전 구간 (0,0)** → §8-3에서 내가 지목한 "드래그 중 크기 강제 충돌" **기각**.
  바탕화면 모드의 위젯은 WorkerW의 자식 창이라 Windows가 `WM_DPICHANGED`를 보내지 않는다.
  즉 다툴 상대가 애초에 없었다. **§8-3은 틀린 가설이었다.**
- Y축 ratio가 1이 아닌 건 clamp가 아니라 위젯이 화면 상단(y=0)에 닿아 멈춘 것 — 정상.

### 9-1. 대신 드러난 사실 — 모니터를 넘어도 물리 크기가 그대로다

```
drag start widget=(1430,0) size=(1478x1722) scale=1.75   ← 175% 모니터에서 출발
drag end   actual=(3732,0,  1478x1722)      scale=1      ← 100% 모니터 도착, 크기 동일
```

도착한 보조 모니터는 1920×**1080**인데 위젯 높이는 **1722** — **모니터보다 1.6배 크다.**
아래로 642px, 오른쪽으로 410px 화면 밖으로 나간 채 끝났다.

신고 문구 "**주모니터에는 절반만 뜨고**"는 *위치가 덜 간 것*이 아니라
**위젯이 그 모니터에 안 들어갈 만큼 커진 것**일 수 있다. 조사 방향을 위치 → **크기**로 옮긴다.

### 9-2. 다음 검증 — 일반 위젯 모드

일반 모드는 Chromium이 창을 옮기고, 바탕화면 모드와 달리 **DIP 크기를 유지**하려 하므로
경계를 넘는 순간 창을 **1.75배로 다시 잰다**(예상). 창은 좌상단 기준으로 커지므로
우측 상단을 잡고 있던 커서가 창 왼쪽에 놓인다 → 신고 증상 ①과 일치.

계측 추가: `electron/main.ts` `logWidgetGeometry()` — 위젯 `move`(150ms throttle) / `resize`(무조건)
시점의 DIP·physical 크기와 그 순간 배율을 `[dpi-probe]`로 기록.
**드래그 도중 `RESIZE` 줄이 찍히면 그게 결정적 증거다.**

## 11. 일반 위젯 모드 재현 (04:53) — 크기 폭발 확인

### 11-1. 관측 로그 (핵심 3줄)

```
[dpi-probe] move   dip=(1149,285,1920x1032) physical=(2383,285,1920x1032) scale=1    desktopMode=normal
[dpi-probe] RESIZE dip=(815,223,1098x591)   physical=(1426,390,1922x1035) scale=1.75 desktopMode=normal
[dpi-probe] RESIZE dip=(815,223,1921x1033)  physical=(1426,390,3362x1808) scale=1.75 desktopMode=normal
```

경계를 넘는 순간 **크기 변경이 15ms 간격으로 두 번** 일어난다.

1. **1차** — Windows가 `WM_DPICHANGED`로 창을 175% 기준으로 다시 잰다.
   논리(DIP) 크기 1920×1032 → **1098×591** (= 1920/1.75), **실제 크기는 1922×1035로 유지.**
   이것이 올바른 동작이다 (화면에서 차지하는 물리적 넓이가 안 변함).
2. **2차** — Electron이 창의 **DIP 크기를 원래대로(1921×1033) 되돌린다.**
   그 결과 **실제 크기가 3362×1808로 1.75배 폭발한다.**

되돌림은 우리 코드가 아니다: 우리 쪽에서 크기를 다시 넣는 경로는
`scheduleWidgetBoundsSave`(저장만 함, 500ms 디바운스) · `ensureWidgetBoundsWithinDisplays`
(축소만 함, 디스플레이 이벤트에서만 호출) · `setWidgetLayout`(IPC 트리거)뿐이고,
15ms 안에 이전 DIP 크기를 기억해 재적용하는 코드는 없다.
Electron `BrowserWindow`의 크기 단위가 DIP이고 DPI 변경 시 DIP 크기를 유지하는 설계 때문이다.

### 11-2. 신고 문구와 숫자가 일치한다

되돌림 직후 위젯의 실제 가로 범위 = **1426 ~ 4788**. 주모니터는 2880에서 끝난다.

|                                   | 픽셀                   | 비율    |
| --------------------------------- | ---------------------- | ------- |
| 주모니터(0~2880)에 걸친 부분      | 1426~2880 = **1454px** | **43%** |
| 보조모니터(2880~4800)에 걸친 부분 | 2880~4788 = **1908px** | **57%** |

> 신고: "주모니터에는 절반만 뜨고 나머지 절반이 다른 모니터에 뜹니다"

**증상 ② 확정** — 위치가 덜 간 것이 아니라, **위젯이 그 모니터에 안 들어갈 만큼 커진 것**이다.
주모니터(2880×1800)보다 위젯(3362×1808)이 크므로 **아무리 끌어도 완전히 옮길 수 없다.**

**증상 ① 확정** — 창이 좌상단을 기준으로 1.75배 커지므로, 우측 상단을 잡고 있던 커서가
상대적으로 창 가운데~왼쪽에 놓인다. "좌측 상단을 잡은 것처럼"과 일치.

### 11-3. 두 모드의 차이가 설명된다

|                | 배율 변경 통지                                            | 크기 변화          | 결과                         |
| -------------- | --------------------------------------------------------- | ------------------ | ---------------------------- |
| 바탕화면 모드  | **없음** (WorkerW의 자식 창이라 부모 DPI 컨텍스트를 따름) | 없음 (`sizeErr=0`) | 커서를 1:1로 따라감 — 무혐의 |
| 일반 위젯 모드 | **있음** (최상위 창)                                      | **1.75배 폭발**    | 화면 밖으로 넘침 — **원인**  |

### 11-4. 악화 조건

위젯이 보조 모니터의 **작업 영역을 꽉 채운 크기**(1920×1032 = 보조 work area 그대로)였다.
이 상태에서 배율이 더 높은 모니터로 넘어가면 반드시 그 모니터보다 커진다.
레이아웃 단축키(전체/절반 등)로 화면을 채운 뒤 옮기는 사용 패턴에서 항상 재현된다.

### 11-5. 미출시 clamp(f2cd0b02)로는 해결되지 않는다

`ensureWidgetBoundsWithinDisplays`(크기 축소 + 위치 보정)는 존재하지만 호출 시점이
**`display-added` / `display-removed` / `display-metrics-changed` / 모드 전환**뿐이다.
**"위젯이 다른 모니터로 이동했을 때"는 호출되지 않는다.** 따라서 이 신고는 그대로 남는다.

### 11-6. 수정 방향 (제안)

드래그가 끝난 뒤(`moved` 이벤트) 위젯이 올라간 모니터의 작업 영역에 들어가는지 검사하고,
넘치면 `fitWidgetSizeToWorkArea` + `clampWidgetBoundsToWorkArea`로 맞춘다.

- **드래그 중에 하면 안 된다** — 드래그와 보정이 서로 창을 밀어낸다 (§8-3에서 겪은 실패 유형).
- 무조건 축소가 아니라 **"새 모니터에 안 들어갈 때만"** 축소한다.
  배율이 높은 모니터에서 물리적으로 커지는 것 자체는 정상 동작이며 축소하면 오히려 손해다.
- 축소 후 크기를 저장할지 여부는 제품 결정 사항 (사용자가 정한 크기를 앱이 바꾸는 것이므로).

## 12. 일반 위젯 모드 기계 재현 (사람 손 없이)

§9-2의 예측을 확인하기 위해 **위젯과 같은 옵션의 빈 창**을 띄우고 경계를 가로질러 옮기는
프로브 3종을 만들었다 (`scripts/dpi-probe/`). 앱 전체를 띄우지 않고 창 하나만 재므로
결과가 위젯 코드가 아니라 **Chromium/Windows의 성질**임을 분리해 볼 수 있다.

| 스크립트                                   | 하는 일                                                                                             |
| ------------------------------------------ | --------------------------------------------------------------------------------------------------- |
| `widget-dpi-probe.mjs`                     | `setPosition`으로 경계를 가로지르며 DIP·물리 크기 기록                                              |
| `widget-dpi-variants.mjs`                  | `transparent`·`thickFrame`·`resizable` 조합별 거동 비교                                             |
| `real-drag-probe.mjs` + `drag-sampler.mjs` | **실제 마우스 드래그를 주입**하고, 중첩 메시지 루프에 갇히지 않도록 **별도 프로세스**에서 창을 관찰 |

### 12-1. 경계 통과 시 창이 다시 재어진다 — 예측 적중

```
step  5  dip=(1353,40,700x520)  physical=(2587,40, 700x 520)  scale=1
  RESIZE  dip=(1286,40,401x298)  physical=(2251,70, 703x 522)  scale=1.75   ← 과도 상태
  RESIZE  dip=(1286,40,701x520)  physical=(2251,70,1228x 910)  scale=1.75   ← 확정
```

**DIP 크기는 유지되고 물리 크기가 배율비(1.75배)만큼 커진다.** §9-2가 예측한 `RESIZE`가
정확히 경계에서 발생한다.

### 12-2. 그런데 실제 드래그에서는 "잡은 지점"이 보존된다 — **증상 ①은 기각**

실제 마우스 입력을 주입해 헤더 **우측 상단(창 폭의 95.7% 지점)** 을 잡고 주모니터로 끌었다.

```
 step  커서x   창left   창폭   커서-창left  폭대비%
    5   3209     2619    700          590    84.3
    7   3048     2015   1225         1033    84.3   ← 폭 700→1225 (경계 통과)
   39    480     -553   1225         1033    84.3
```

- 창이 1.75배로 커지는 순간 **커서와 왼쪽 모서리의 거리도 590→1033으로 같은 비율로 늘어난다.**
  잡은 지점 비율 **84.3%가 처음부터 끝까지 한 번도 흔들리지 않는다.**
  → Windows 드래그 루프가 DPI 변경 시 잡은 지점을 비례 보존한다. **"좌측 상단을 잡은 것처럼"은
  일반 위젯 모드에서 재현되지 않는다.**
- 창이 커서를 못 따라간 연속 구간 최대 **1단계**(주입 첫 걸음의 임계값). **"멈춤"도 재현 안 됨.**
- 95.7% → 84.3%로 한 번 줄어든 것은 드래그 시작 임계값 때문이며(주입이 한 걸음 80px씩 뛴다),
  사람 손 드래그에서는 몇 px 수준이다. 증상 설명이 되지 않는다.

**→ 가설 2(일반 모드 Chromium 결함) 기각.** 일반 위젯 모드에서 크로스-모니터 드래그는 정상이다.

### 12-3. 남은 유일한 설명 — 바탕화면 모드는 물리 크기가 그대로다

| 모드      | 경계를 넘을 때                                 | 결과                                  |
| --------- | ---------------------------------------------- | ------------------------------------- |
| 일반 위젯 | **DIP 크기 유지** (물리가 1.75배)              | 보이는 크기가 같다 — 정상             |
| 바탕화면  | **물리 크기 유지** (§9-1 실측 `sizeErr=(0,0)`) | 100% 모니터에서 **1.75배로 거대해짐** |

§9-1의 실측이 그대로 이 결론을 가리킨다:

```
drag start widget=(1430,0) size=(1478x1722) scale=1.75   ← 175% 모니터
drag end   actual=(3732,0, 1478x1722)      scale=1       ← 100% 모니터, 크기 동일
```

1920×**1080** 모니터에 높이 **1722**짜리 창 → **아래로 642px, 오른쪽으로 410px이 화면 밖.**
신고 문구 "**주모니터에는 절반만 뜨고 더 이상 안 움직인다**"는
*위치가 덜 간 것*이 아니라 **모니터에 안 들어갈 만큼 커진 것**으로 읽으면 정확히 들어맞는다.
(커서가 화면 끝에 닿으면 더 끌 수 없으니 "멈췄다"고 느껴진다.)

원인은 바탕화면 모드의 위젯이 **바탕화면(WorkerW)의 자식 창**이라 Windows가
`WM_DPICHANGED`를 보내지 않는 데 있다. 알림을 못 받으니 스스로 다시 잴 기회가 없다.
§9-1에서 확인했듯 이는 "우리 코드가 크기를 강제해서"가 아니다 — 강제를 빼도 크기는 그대로다.

### 12-4. 곁가지로 잡힌 별개 결함 — 175% 모니터에서 창을 옮길 때마다 1~2px씩 커진다

```
=== 요약 (폭 누적 증가가 0이면 래칫 없음) ===
  drift=  18  resize= 24  widget 현행 (transparent+thickFrame:false+resizable:false)
  drift=  18  resize= 24  thickFrame:true 만 바꿈
  drift=  11  resize= 16  resizable:true 만 바꿈
  drift=  18  resize= 24  transparent:false 만 바꿈
  drift=   6  resize= 18  기본 frameless
```

- 175% 모니터 위에서 `setPosition`/`setBounds`를 부를 때마다 DIP 폭이 **1~2씩 늘고 줄지 않는다**
  (700 → 왕복 2회 뒤 718). 소수 배율에서 `DIP→물리→DIP` 반올림이 한 방향으로만 쌓이는 래칫이다.
- **창 옵션을 어떻게 바꿔도 사라지지 않는다.** `transparent`·`thickFrame`은 무관하고,
  `resizable:false`만이 경계 통과 순간 DIP 폭이 401까지 무너지는 과도 상태(minWidth 640 위반)를
  만든다. 다만 이 과도 상태는 **실제 드래그에서는 나타나지 않았다**(10-2) — `setPosition` 경로만의 현상.
- **앱에 미치는 실제 경로**: 위치 저장(`scheduleWidgetBoundsSave`)이 DIP 크기를 적고,
  다음 실행에서 그 값으로 복원하며, `ensureWidgetBoundsWithinDisplays`가 읽고-고쳐-쓴다.
  소수 배율 모니터를 쓰는 사용자는 **앱을 켤 때마다 위젯이 1~2px씩 커질 수 있다.**
  이번 신고와는 별개 항목으로 기록한다.

## 13. 바탕화면 모드 기계 재현 — **원인 확정**

`scripts/dpi-probe/desktop-mode-drag-probe.mjs` — **빌드된 실제 매니저**(`dist-electron/desktopWidgetManager.js`)를
그대로 불러 위젯과 같은 옵션의 창을 바탕화면(WorkerW) 자식으로 붙이고, 드래그가 하는 일과 같은
`SetWindowPos`로 경계를 가로질렀다. 매 단계 **창의 실제 물리 rect**(`GetWindowRect`)와
**렌더러가 실제로 그리는 크기**(`devicePixelRatio`·`innerWidth/Height`)를 함께 읽었다.

```
moveWidget x= 2400 GetWindowRect=(2400,140,1232x916) getBounds(DIP)=(1166,140,1232x916)
                   display=748019706 scale=1  devicePixelRatio=1  innerSize=705x524
[2초 후 재측정]     devicePixelRatio=1  innerSize=705x524  실제 창=(3581,140,1232x916)
[실제로 그려진 영역] capturePage=403x300
```

### 13-1. 확정된 사실 3개

1. **창의 물리 크기는 그대로다** — 1232×916 유지. 일반 모드와 정반대(§12-1).
2. **Chromium은 배율 변화를 알아챈다** — `devicePixelRatio`가 1.75 → 1로 바뀐다.
   즉 "자식 창이라 아무것도 모른다"는 §9-1의 추정은 **절반만 맞았다.**
3. **그런데 화면 배치(레이아웃)는 옛 배율에 멈춘다** — 창은 1232px인데 렌더러는 여전히
   **705 CSS px**만 그린다. 실제 칠해진 영역은 **403×300**.
   → 투명 창이므로 **나머지는 그냥 빈 공간.** 위젯 UI가 창의 **약 57%**만 채운 채 남는다.

**이것이 "주모니터에는 절반만 뜬다"의 정체다.** 위치가 덜 간 것도, 창이 잘린 것도 아니라
**창은 그대로인데 그림이 옛 크기로 남아 절반만 칠해진 것**이다.
(`705/1232 = 57%` — 사용자가 "절반"이라고 표현할 만한 값이며, 배율비 1.75의 역수와 정확히 같다.)

### 13-2. 고칠 수 있다 — `setBounds` 한 번이면 레이아웃이 복구된다

```
=== 복구 시도 ===
  setBounds(같은 값 재지정) → innerSize=1232x917 dpr=1   ← 705x524에서 창 전체로 복구
```

Electron에 DIP 기준 크기를 **다시 한 번 알려주기만 해도** 렌더러가 새 배율로 다시 배치한다.
창을 -1px 흔들 필요조차 없다.

### 13-3. 그래서 무엇으로 고칠 것인가 — "보이는 크기 유지"

단순 복구(`setBounds(현재값)`)만 하면 레이아웃은 살아나지만 **창이 물리 1232px로 남아**
1920px 모니터의 64%를 차지한다(원래 2880px 모니터에서는 43%였다). 즉 **모니터를 옮길 때마다
위젯이 커졌다 작아졌다** 한다.

일반 위젯 모드가 하는 일(=Windows 표준)은 **DIP 크기 보존**이다(§12-1). 바탕화면 모드도 같게 맞춘다:

> 드래그가 끝났을 때 도착 모니터의 배율이 출발 때와 다르면,
> **드래그 시작 시점의 DIP 크기**를 그대로 유지하도록 창 크기를 다시 지정한다.
> (예: 175%에서 705×524 DIP였다면, 100% 모니터에서는 물리 705×524가 된다.)

부수 효과로 §13-2의 레이아웃 복구도 함께 일어난다 — `setBounds`가 그 자체로 재배치를 부르기 때문.

### 13-4. 정정 — §9-1과 §11-3의 표현

- §9-1 "**모니터를 넘어도 물리 크기가 그대로다 → 모니터보다 크다**"는 관측은 맞지만,
  사용자가 보는 증상의 주범은 크기 초과가 아니라 **57%만 칠해지는 레이아웃 고착**이다.
- §11-3의 "Windows가 `WM_DPICHANGED`를 보내지 않아 **알림을 못 받는다**"는 **틀렸다.**
  Chromium은 배율 변화를 인지한다(`devicePixelRatio`가 바뀐다). 빠진 것은 **크기 재계산**이다.
