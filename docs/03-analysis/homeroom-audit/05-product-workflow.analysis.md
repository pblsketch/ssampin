## A. 담임 교사 일과 시뮬레이션

### [P0] 조회 시간 (08:30) — 출결 입력 마찰이 가장 높은 구간

- **사용자 시나리오**: 담임이 08:30 조회 시간에 결석·지각 학생 3~5명을 즉시 입력해야 한다. 10분 안에 끝내야 수업에 들어간다.
- **현재 상태**: 사이드바 "담임 업무" 클릭 → 기록 탭(기본 활성) → 입력 서브탭 진입. 학생 그리드에서 해당 학생 클릭(다중 선택 가능) → 출결 카테고리에서 유형(결석/지각/조퇴/결과) 선택 → 사유(질병/인정/미인정/기타) 선택 → 교시(PeriodChipGroup, 기본 전체) → 저장 버튼 또는 Enter. 단축키(A/L/E/X 유형, Q/W/R/T 사유, 1~7 교시, Enter 저장)가 존재한다.
- **문제/기회**:
  1. 탭 구조가 최상단(명렬 관리·기록·설문·과제·상담·자리배치)과 서브탭(입력·통계·조회) 2단이다. 처음 쓰는 교사는 "기록" 탭 안에 "입력" 서브탭이 있다는 사실을 직관적으로 알기 어렵다.
  2. 출결 입력 시 유형 선택(1클릭) → 사유 선택(1클릭) → 교시(기본 전체이므로 생략 가능) → 저장(1클릭) = 최소 3클릭. 학생 선택 포함 시 학생당 총 4클릭이며, 다중 학생 선택으로 N명을 한 번에 처리할 수 있는 것은 강점이다.
  3. 단축키(A→Q→Enter)를 알면 3키로 결석-질병 일괄 처리가 가능하지만, 단축키 안내가 카테고리 선택 후 출결 섹션에만 노출되어 조회 시간에 처음 발견하기 어렵다.
  4. 앱 진입부터 입력 준비까지 클릭 수: 사이드바 1 + (기록 탭 이미 기본) 0 + 입력 서브탭 1 = 최소 2클릭. 이미 기록 탭이 기본 활성이므로 비교적 빠르다.
- **개선안**: (1) 앱 시작 시 마지막 사용 탭·서브탭을 복원하는 "세션 기억" 기능 — 조회 시간마다 같은 곳을 찾지 않도록. (2) 대시보드 위젯에 "빠른 출결 입력" 버튼 → 기록/입력 모드로 직접 딥링크. (3) 키보드 단축키를 입력 모드 상단 고정 힌트 배너로 항상 노출.
- **메트릭 제안**: 조회 시간대(08:20~09:00) 기록 저장 이벤트 수. 출결 입력 시작부터 저장까지 평균 소요 시간(세션 로그).

### [P0] 교시별 출결 정정 (10:30, 쉬는 시간) — PeriodChipGroup 직관성

- **사용자 시나리오**: 1교시 수업 후 쉬는 시간에 "5교시 조퇴 학생이 생겼다"는 연락을 받고 즉시 수정하거나 신규 입력해야 한다.
- **현재 상태**: 입력 모드에서 학생 선택 → 조퇴(E) 선택 → 사유 선택 → PeriodChipGroup에서 "5교시"만 선택(나머지 해제) → 저장. PeriodChipGroup은 "전체(기본)"와 교시 칩을 함께 표시하며, 특정 교시만 선택하면 전체 칩이 비활성화된다. 또한 기존에 저장한 기록을 수정하려면 조회 탭에서 인라인 편집(InlineRecordEditor)을 사용해야 한다.
- **문제/기회**:
  1. "전체" 기본 선택 상태에서 특정 교시만 선택하려면 전체 해제가 아니라 해당 교시 칩을 직접 클릭하면 된다. 이 동작이 직관적이지 않을 수 있다(전체 해제 → 5교시 선택으로 오해).
  2. 소급 정정(이미 "전체 결석"으로 저장된 기록을 "5교시 조퇴"로 변경)은 조회 탭의 인라인 편집이 필요한데, 입력 탭에서 바로 편집하는 경로가 없다.
  3. PeriodRowEditor(교시별 상태·사유를 행 단위로 편집)는 조회 탭의 인라인 편집에만 있고 입력 탭에는 없다. 즉 "같은 학생이 1교시 지각 + 5교시 조퇴" 같은 복합 출결을 한 번의 입력으로 처리할 수 없다.
- **개선안**: (1) PeriodChipGroup에 "전체 → 개별 선택 전환" 시 툴팁 또는 인라인 힌트("특정 교시만 선택하면 해당 교시만 기록됩니다"). (2) 입력 모드에서도 PeriodRowEditor를 표시하거나, 복합 출결 입력을 위한 "교시별 세부 입력" 토글 추가. (3) 조회 탭으로 이동하지 않고 입력 탭 우측 패널의 "오늘 기록" 섹션에서 기존 기록을 클릭해 바로 편집.
- **메트릭 제안**: 인라인 편집 사용 빈도(입력 탭 vs 조회 탭). 교시별 세부 선택 빈도.

### [P1] 쉬는 시간 (10분) — 학생 상담 빠른 입력

- **사용자 시나리오**: 쉬는 시간에 학생이 찾아와 짧게 상담한 내용을 10분 안에 기록하고 다음 수업에 들어가야 한다.
- **현재 상태**: 기록/입력 모드에서 학생 선택 → 상담 카테고리의 서브카테고리(학생상담) 선택 → 상담 방법 선택(선택사항) → 메모 입력(선택사항) → 저장. 템플릿 드롭다운에서 "학생 1:1 상담" 선택 시 메모 영역에 구조화 템플릿(상담 사유/학생 이야기/교사 소견/후속 계획)이 자동 입력된다.
- **문제/기회**:
  1. 다른 탭(예: 자리배치)에서 기록/입력 모드로 전환하려면 최상단 탭 1클릭 + 서브탭 전환이 없어도 되므로(기록 탭이 기본 입력 모드를 기억함) 비교적 빠르다.
  2. 템플릿이 `<select>` 드롭다운으로 구현되어 있어, 쉬는 시간에 마우스를 잡아야 하는 마찰이 있다. 빠른 접근을 위한 키보드 단축키(템플릿 선택)가 없다.
  3. 후속 조치(followUp) 입력이 "후속 조치 추가" 버튼 클릭 후에만 나타나 기본 숨김 처리된다. 짧은 쉬는 시간에는 놓치기 쉽다.
- **개선안**: (1) 자주 쓰는 템플릿 1~3개를 칩 형태로 카테고리 선택란 상단에 노출("최근 사용 템플릿"). (2) 후속 조치 필드를 기본 노출하되 옵션임을 흐린 텍스트로 표시.
- **메트릭 제안**: 템플릿 드롭다운 사용 빈도. 후속 조치 입력 비율.

### [P1] 점심 시간 — 학부모 전화 상담 후 기록 연동

- **사용자 시나리오**: 점심 시간에 학부모 전화를 받고, 상담 기록을 남기고, 다음 상담 일정도 잡아야 한다.
- **현재 상태**: 경로 A(빠른 기록) — 기록/입력 모드에서 학부모상담 카테고리 선택 → 전화 방법 선택 → 메모 → 저장. 경로 B(상담 예약 연동) — 상담 예약 탭 → 기존 일정 클릭 → ConsultationDetail 화면 → "기록하기" 버튼 → HomeroomPage.handleWriteRecord 호출 → 기록 탭 자동 전환 + 학생/카테고리/방법 prefill 자동 입력. prefill 구현이 `RecordPrefill` 인터페이스로 정확히 연결되어 있다(HomeroomPage.tsx L24~27, RecordsTab.tsx L40~45, InputMode.tsx L163~184).
- **문제/기회**:
  1. 경로 B의 연동 흐름(상담 예약 → 기록하기 → 기록 탭 자동 전환 + prefill)은 설계가 매끄럽다. 학생, 카테고리, 상담 방법이 자동으로 채워지므로 교사가 중복 입력할 필요가 없다.
  2. 단, prefill된 상태에서 교사가 "저장" 전에 상담 탭으로 돌아가면 prefill이 사라진다(setPrefillRecord(null)이 onPrefillConsumed에서 즉시 호출됨). 메모를 입력하다가 다른 탭을 실수로 클릭하면 prefill이 소실될 위험이 있다.
  3. 경로 B는 상담 예약 일정이 이미 생성되어 있어야 한다. 즉흥적인 전화 상담(일정 없이 전화 받은 경우)은 경로 A를 써야 하는데, 두 경로의 존재를 사용자가 알고 선택하기가 불명확하다.
- **개선안**: (1) prefill 소비를 onPrefillConsumed에서 즉시 하지 않고, 저장 성공 시점에 소비. 탭 이동 시 "기록 중인 내용이 있습니다. 계속하시겠습니까?" 경고 추가. (2) 입력 모드 상단에 "즉흥 상담? 템플릿으로 빠르게 기록" 링크로 경로 A를 안내.
- **메트릭 제안**: prefill 완료 후 실제 저장 성공률. prefill 소실(탭 이동 후 재진입) 빈도.

### [P0] 오후 수업 중 — 생활지도 다중 기록

- **사용자 시나리오**: 5교시에 학생 3명이 다툼. 쉬는 시간 10분 안에 3명 모두 생활지도 기록을 남겨야 한다.
- **현재 상태**: 입력 모드에서 3명을 동시 클릭(다중 선택, Set 누적) → 생활지도 서브카테고리 선택 → 메모 입력 → 저장. 저장 시 selectedStudents를 순회하여 각 학생에게 동일 카테고리·메모로 기록 생성(Promise.all). 키보드 전용 흐름도 가능하다.
- **문제/기회**:
  1. 다중 학생 일괄 기록(FR-STMEMO-04)은 구현 완료되어 있고, 같은 메모가 모든 학생에게 들어간다. 이것이 대부분 경우에 맞지만, "학생마다 메모가 달라야 하는 경우"(예: 각자 다른 역할)는 지원되지 않는다.
  2. 3명 선택 후 저장하면 토스트("N건 저장됨")만 표시되고 각 학생에 어떤 기록이 들어갔는지 확인하는 인라인 피드백이 없다.
  3. 중복 감지 로직(같은 날 같은 학생+카테고리+서브카테고리)이 있어 이중 저장을 방지하지만, "이미 존재해서 저장 안 됨"을 교사가 알 수 있는 명확한 피드백이 없다.
- **개선안**: (1) 저장 완료 후 입력 모드 우측 "오늘 기록" 패널에 방금 저장한 학생들의 기록이 즉시 나타나도록(현재 구현되어 있는 `dateRecords` 상태 활용). (2) 중복 스킵 발생 시 구체적 토스트("3명 중 2명 저장됨 — 김철수는 이미 같은 기록이 있음"). (3) 학생별 다른 메모가 필요한 경우를 위한 "개별 입력 모드" 옵션(현재는 없음).
- **메트릭 제안**: 한 번의 저장에서 다중 학생 선택 비율. 중복 스킵 발생 빈도.

### [P1] 종례 (15:30) — 오늘 정리 + 학부모 연락 확인

- **사용자 시나리오**: 종례 전 오늘 출결·상담 기록을 훑어보고, 학부모에게 연락해야 할 학생이 있는지 확인한다.
- **현재 상태**: 기록 탭 통계 서브탭(ProgressMode)에서 오늘 범위("이번 주")로 필터 후 요약 카드(총 기록/출결/상담/생활/기록없음) 확인. NEIS 미반영 출결, 서류 미제출, 미완료 후속 조치 경보가 자동 노출된다. ActionDashboard는 SearchMode에 포함되어 있어 조회 탭에서 접근한다.
- **문제/기회**:
  1. "오늘 기록 요약"을 보려면 통계 탭에서 기간을 "이번 주"에서 오늘 날짜로 바꿔야 한다. 오늘만 보는 "오늘 보기" 단일 버튼이 없다.
  2. NEIS 미반영 알림과 서류 미제출 알림은 통계 탭에 있고, 후속 조치 알림도 통계 탭에 있다. 그러나 "학부모 연락이 필요한 학생"이라는 통합 뷰가 없어, 교사가 여러 알림을 개별로 확인해야 한다.
  3. 종례 기록(조회/종례 교시)을 PeriodChipGroup에서 선택할 수 있으나 조회/종례 칩이 정규 교시와 같은 크기로 섞여 있어 시각적으로 구분이 약하다.
- **개선안**: (1) 통계 탭 상단에 "오늘" 빠른 필터 버튼 추가(현재: 이번주/이번달/사용자정의/전체). (2) 종례 전 체크리스트 카드(NEIS 미반영 N건 + 서류 미제출 N건 + 후속 조치 N건을 단일 배너로 묶기). (3) 대시보드 위젯에서 이미 "미완료 후속 조치"를 노출하므로 위젯과 본 페이지 간의 정보 일관성 유지.

## B. 6개 탭 우선순위와 정보 위계

### [P0] 탭 순서가 사용 빈도와 불일치

- **사용자 시나리오**: 담임 교사의 실제 사용 빈도 추정 — 기록(매일) > 명렬(학기초·전출입) > 상담(부정기) > 자리배치(월 1~2회) > 설문(주 1~2회) > 과제(주 1~2회).
- **현재 상태**: HomeroomTabBar의 탭 순서: `roster(명렬 관리) → records(기록) → survey(설문) → assignment(과제) → consultation(상담) → seating(자리배치)`. 초기 활성 탭은 `records`(HomeroomPage.tsx L21).
- **문제/기회**:
  1. 탭 순서가 시각적으로 명렬 → 기록이지만, 기록이 기본 활성이다. 시각적 순서와 기능 우선순위가 불일치한다. 처음 보는 교사는 "명렬 관리"가 더 중요한 기능으로 인식할 수 있다.
  2. 설문/과제가 상담 앞에 위치한다. 담임 교사의 업무 빈도 기준으로는 상담이 설문/과제보다 훨씬 중요하고 자주 사용된다.
  3. 자리배치가 담임 업무 탭 안에 임베드되어 있다. 자리배치는 독립 페이지로도 접근 가능해 기능이 중복 노출된다. 담임 업무 탭의 자리배치는 "담임반 좌석 보기" 정도의 경량 뷰가 더 적합할 수 있다.
- **개선안**: 탭 순서를 사용 빈도 기준으로 재배치 — `records(기록) → consultation(상담) → roster(명렬) → survey(설문) → assignment(과제) → seating(자리배치)`. 또는 기록·명렬·상담을 "핵심"으로, 설문·과제·자리배치를 "도구"로 시각적 구분.
- **메트릭 제안**: 각 탭의 체류 시간 및 클릭 빈도.

## D. 기록 입력 효율

### [P0] 출결 5명 동시 지각 기록 — 클릭 수 계산

- **사용자 시나리오**: 조회 시간에 5명이 동시에 지각. 모두 같은 사유(질병)로 기록.

- **문제/기회**:
  1. 8클릭(또는 7키입력)으로 5명 처리가 가능하다. 개별로 처리하면 5명 × 4클릭 = 20클릭이므로 60% 이상 절감이다. 이것은 핵심 경쟁력이다.
  2. 그러나 "5명 모두 선택"이 현재 그리드에서 하나씩 클릭해야 한다. 20~30명 학급에서 특정 범위(예: 1번~5번)를 드래그로 다중 선택하는 기능이 없다.
  3. 키보드 단축키가 입력 모드에서만 동작하고, 학생 그리드 영역에 포커스가 없어도 잘 동작하는지 확인 필요(document 레벨 이벤트리스너로 등록되어 있어 동작하나, INPUT/TEXTAREA에 포커스 시 단축키가 비활성화됨).
- **개선안**: (1) 그리드에서 드래그 또는 Shift+클릭으로 연속 선택 지원. (2) "전체 선택" / "번호 범위 선택" 입력창 추가(예: "1~5" 입력하면 1~5번 학생 일괄 선택).
- **메트릭 제안**: 저장 1회당 평균 선택 학생 수. 키보드 단축키 사용 비율(단축키 입력 이벤트 로그).

- **메트릭 제안**: 과제 탭 진입 후 Google 연동 클릭 비율. OfflineNotice 표시 비율.

- **문제/기회**: 학기말 종합 작업을 효율화하는 "생기부 작성 모드"(학생별 기록을 생기부 양식에 맞게 요약하는 UI)가 없다. 교사가 수동으로 타임라인을 보며 생기부에 타이핑해야 한다.
- **개선안**: 조회 탭에 "생기부 요약" 버튼 — 학생 선택 시 해당 학생의 카테고리별 기록을 문단 형태로 자동 요약(예: "출결: 결석 2회(질병), 지각 1회. 상담: 학부모상담 3회. 생활: ..."). AI 요약 기능으로 장기 발전 가능.
- **메트릭 제안**: 학기말(1~2월, 7~8월) 조회 모드 전체 기간 필터 사용 급증.

## G. 위젯 vs 본 페이지 가치 차별화

### [P1] DashboardStudentRecords 위젯 — 가치 희석 문제

- **현재 상태**: DashboardStudentRecords(269줄)는 오늘 기록 목록(카테고리 탭 전환 포함) + 미완료 후속 조치 count + "전체 보기" 링크로 구성된다. 별도 위젯 StudentRecords.tsx(1959줄)은 대시보드 임베드용으로 추정되며 기록 입력·통계·조회를 포함한 거의 완전한 기능을 가진다.
- **문제/기회**:
  1. StudentRecords.tsx(1959줄)가 대시보드에 임베드되어 있다면, 본 페이지(HomeroomPage)와 기능이 거의 중복된다. "흘낏 보기" 위젯의 본질(한눈에 상태 파악)이 희석된다.
  2. DashboardStudentRecords(269줄)는 경량 위젯으로 올바른 방향이다(오늘 기록 수 + 후속 조치). 그러나 위젯에서 직접 기록 입력은 불가능하다. "오늘 N건" 카운트를 클릭하면 기록 탭으로 이동하는 딥링크가 있는지 확인이 필요하다.
  3. 1959줄짜리 StudentRecords.tsx가 여전히 사용되는지(레거시인지) 확인이 필요하다. HomeroomPage 기반 리팩토링 후 이 파일의 역할이 명확하지 않다.
- **개선안**: (1) DashboardStudentRecords를 "흘낏 보기" 위젯으로 정리 — 오늘 기록 3건 미리보기 + 미완료 후속 조치 N건 + "빠른 기록" CTA(클릭 시 기록/입력 모드로 딥링크). (2) StudentRecords.tsx(1959줄)가 레거시라면 단계적 제거 또는 역할 명확화. (3) 위젯에서 가장 빈번한 동작(출결 입력)만 가능한 "빠른 출결" 미니 위젯 추가.
- **메트릭 제안**: 위젯에서 "전체 보기" 클릭 빈도 vs 사이드바 직접 진입 비율.

## H. 한국 담임 교사 컨텍스트

### [P0] 개인정보 보호 — PIN 잠금 충분성

- **현재 상태**: PinGuard 'studentRecords'로 담임 업무 페이지 접근이 PIN 보호된다.
- **문제/기회**:
  1. PIN 잠금은 앱 레벨 보호로, 교무실에서 잠깐 자리를 비운 경우 다른 교사가 이미 열려있는 앱으로 접근할 수 있다. 일정 시간 비활동 후 자동 잠금이 없다면 공유 PC 환경에서 취약하다.
  2. 학생 이름·전화번호·보호자 연락처가 화면에 표시되는 상황에서, 대화 중 화면을 학생이 보는 경우를 방지하는 "학생 보기 보호 모드"(이름 마스킹)가 없다.
  3. GDPR/개인정보보호법 기준으로 학생 데이터가 로컬 JSON으로만 저장되고 클라우드 동기화 시 암호화 여부가 중요하다.
- **개선안**: (1) 비활동 자동 잠금 설정(예: 5분 후 PIN 재입력 요구). (2) 상담 기록 화면에서 이름 마스킹 토글("상담 중 화면 보호 모드"). (3) GDrive 동기화 시 민감 필드(전화번호, 보호자 연락처) 별도 암호화 여부 명시.
- **메트릭 제안**: PIN 잠금 재입력 빈도(자동 잠금 후). 앱 비활동 시간 분포.

### [P0] 수업 반 선택 탭 (FR-STMEMO-10) — 미구현 확인

- **사용자 시나리오**: 교과 겸직 담임이 1학년 4개 반 수업을 담당. 각 반 학생의 출결도 개별 관리하고 싶다.
- **현재 상태**: PRD는 "[담임] [1-1] [1-2] [1-3]..." 탭을 기술한다. Design examples(code.html L118~137)에도 수업반 탭이 상단에 표시된다. 그러나 HomeroomPage.tsx와 HomeroomTabBar.tsx에는 이 수업반 탭이 없다. RecordsTab은 `activeStudents()`만 사용하여 담임반 학생만 처리한다.
- **문제/기회**: FR-STMEMO-10은 PRD에 명시된 요구사항이지만 현재 미구현 상태다. 교과 겸직 담임(한국 중·고교 담임의 100%)에게는 중요한 기능이다. 수업반 출결은 ClassManagement 페이지(AttendanceTab, ClassRosterTab 등이 존재함)에서 별도로 처리하는 구조인지 확인이 필요하다.
- **개선안**: (1) 단기: 기록 탭 상단에 "담임반 | 수업반 추가" 탭바 추가. 수업반은 기존 TeachingClass 스토어(useTeachingClassStore, 이미 InputMode에서 참조됨)를 활용. (2) ClassManagement 페이지와의 역할 분리 명확화. (3) 수업반 출결 데이터와 담임반 기록 데이터의 연동.
- **메트릭 제안**: 수업반 탭 추가 후 탭별 사용 비율.

### [P1] 상벌점 (PRD 5.7 v2.0) — 우선순위 평가

- **현재 상태**: PRD 라인 319에 "상벌점 모드 (v2.0)"가 기술되어 있으나 현재 미구현이다.
- **문제/기회**:
  1. 상벌점 제도는 학교마다 다르며(없는 학교도 많음), 전국 표준이 없다. 구현 시 학교별 커스터마이즈 필요.
  2. 생활지도 기록과 상벌점이 연동되면 가치가 높다(생활지도 기록 → 자동 벌점 부여). 단독 상벌점 관리보다 기록과의 통합이 핵심.
  3. 현재 기록의 "칭찬" 서브카테고리(PRD 5.7: 생활/학습 그룹에 칭찬 언급)가 상점 대리자 역할을 할 수 있다.
- **개선안**: 상벌점을 별도 탭이 아닌 기록 카테고리(생활지도 → 벌점 N점 연결, 칭찬 → 상점 N점 연결)의 확장으로 구현. 누계를 통계 탭에서 시각화. 학교별 기준 설정은 Settings에 추가.
- **우선순위**: P2 — 핵심 가치(빠른 출결·상담 기록)가 안정화된 후 구현.

### [P1] 학기말 데이터 마이그레이션

- **사용자 시나리오**: 3월에 새 담임반을 받아 새 명렬로 전환하고 작년 기록을 보존한다.
- **현재 상태**: 학생 데이터는 JSON 파일로 로컬 저장. 새 명렬 일괄 등록 시 기존 데이터가 덮어써진다(updateStudents 호출). 과거 기록과의 연결은 studentId 기반이며, studentId가 변경되면 과거 기록 조회가 불가능해진다.

- **개선안**: (1) "학년도 전환" 기능 — 현재 데이터를 아카이브(예: `2025-data.json`)로 백업 후 새 학기 시작. (2) StudentRecord에 schoolYear 필드 추가로 연도별 분리 조회. (3) GDrive 동기화를 통한 자동 백업.
- **메트릭 제안**: 3월 첫째 주 명렬 초기화 건수(학기초 패턴).
