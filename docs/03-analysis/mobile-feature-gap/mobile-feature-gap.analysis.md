# 쌤핀 모바일 기능 격차 분석 — 데스크톱에는 있고 모바일에는 없는 것

작성: 2026-07-03 · 성격: 분석/제안 (구현 없음)
근거: 같은 폴더의 `desktop-feature-inventory.md`(데스크톱 전수 목록), `mobile-feature-inventory.md`(모바일 전수 목록 + 데이터 아키텍처) — 모두 이 날짜의 코드 조사 기반.

---

## 0. 한 줄 결론

모바일의 데이터 배관(구글 드라이브 동기화)은 이미 데스크톱의 30개 데이터 영역 전부를 휴대폰까지 내려보내고 있다. 즉 **대부분의 격차는 "화면이 없어서"이지 "데이터가 없어서"가 아니다.** 따라서 격차 해소는 위험이 낮은 "보여주기(읽기 전용)"부터 시작해, 현장에서 손이 가는 것만 "입력(쓰기)"으로 승격하는 순서를 추천한다.

**최우선 추천 3가지: ① 주간 시간표 보기 ② 상담 예약 조회 ③ 즐겨찾기.** 셋 다 읽기 전용이라 데이터가 꼬일 위험이 없고, 교사가 PC 앞이 아닐 때 가장 자주 아쉬운 기능이다.

## 2. 무엇을 추가할 가치가 있는가 — 판단 기준

모바일의 제품 포지션은 코드 곳곳에 명시돼 있다: **"PC = 원본 데이터·설정, 모바일 = 교실/이동 중의 뷰 + 경량 입력"** (근거: mobile-feature-inventory.md §4의 코드 인용 10건). 이 포지션을 지키면서 격차를 평가하는 기준:

1. **모바일 맥락 적합성** — 교실 순회, 복도 이동, 조례/종례 직전, 퇴근 후처럼 "PC 앞이 아닌 순간"에 실제로 필요한가
2. **데이터 준비 상태** — 이미 동기화돼 폰에 내려와 있는가 (있으면 화면 작업만 남음)
3. **위험** — 쓰기를 추가하면 PC와 데이터가 충돌할 수 있는가 (읽기 전용이면 위험 0)

## 3. 추가 추천 (우선순위)

### 1순위 — 읽기 전용 3종 (저위험 · 즉시 체감)

**① 주간 시간표 보기**

- 왜: "내일 3교시가 뭐더라"는 교사가 폰을 꺼내는 1등 이유인데, 지금 모바일은 오늘 현재 교시 카드뿐이다. 데스크톱 대시보드에서도 주간 시간표가 대표 위젯이다.
- 데이터: `teacher-schedule.json` 이미 동기화·모바일 스토어(`useMobileScheduleStore`)까지 존재. **순수 화면 작업.**
- 방식: 일정 탭 세그먼트를 [일정 | 할 일]에서 [시간표 | 일정 | 할 일]로 확장하거나, 홈 현재-교시 카드를 탭하면 주간 보기로 진입. 요일×교시 그리드 1화면.
- 확장(2단계): 시간표 변동(`timetable-overrides`) 표시 — 데이터는 동기화되나 머지 계산이 의도적으로 빠져 있어, 공용 머지 로직을 모바일에서 재사용하는 별도 검토 필요.

**② 상담 예약 조회**

- 왜: 담임이 "오늘/이번 주 상담 누구지"를 확인하는 순간은 대부분 이동 중이다. 학생 연락처 조회(전화 걸기)가 이미 모바일에 있어서, 상담 목록→학생→전화로 자연스럽게 이어진다.
- 데이터: `consultations.json` 이미 동기화. 모바일 DI에 상담 리포지토리만 등록하면 됨(공용 클래스 재사용).
- 방식: 더보기 또는 일정 탭에 "상담" 목록(다가오는 순), 홈에 "오늘 상담 N건" 카드(표시/숨김 토글). 읽기 전용으로 시작.
- 주의: 학부모의 새 예약은 Supabase→PC를 거쳐 로컬 파일에 기록되므로, PC가 꺼져 있으면 폰에는 늦게 반영된다. 1단계에서는 "마지막 동기화 기준" 문구로 정직하게 표시하고, 2단계에서 모바일이 Supabase를 직접 조회하는 방안(과제 제출현황과 같은 패턴)을 검토.
- 민감정보 유의: 상담 사유 등이 보이므로 필요 시 기존 모바일 위젯 PIN 가림과 같은 계열의 가림 처리 검토.

**③ 즐겨찾기(북마크)**

- 왜: 링크는 오히려 폰에서 여는 일이 많다(공문 포털, 학교 홈페이지, 구글 폼 등).
- 데이터: `bookmarks.json` 동기화 + **모바일 DI에 리포지토리가 이미 등록돼 있음**(container.ts — 코드 확인). 남은 것은 스토어+목록 화면뿐. 3개 후보 중 가장 싸다.
- 방식: 더보기에 "즐겨찾기" 항목, 그룹별 목록 + 탭하면 새 탭 열기. 읽기 전용(등록/정리는 PC).

### 2순위 — 현장 입력(쓰기) 2종 (가치 크지만 별도 계획 필요)

**④ 수행평가 채점(루브릭) 모바일 입력**

- 왜: 수행평가는 본질적으로 "교실을 돌아다니며" 채점한다. 폰/태블릿으로 기준 탭→점수 입력이 되면 데스크톱보다 오히려 현장 적합성이 높다. 이미 v2.1.2에서 출시된 인기 기능의 자연스러운 확장.
- 데이터: `rubrics.json` 동기화. 쓰기는 기존 9개 쓰기 스토어와 같은 `triggerSaveSync` 패턴.
- 위험: 같은 파일을 PC와 폰에서 동시에 고치면 한쪽이 밀릴 수 있는 구조(파일 단위 충돌 처리)라, "수업 중엔 폰으로만 채점"이라는 사용 패턴이면 실위험은 낮지만 설계 검토는 필요. **규모가 커서 별도 계획(PDCA)으로 진행 권장.**
- 범위 제안: 1단계는 "이미 PC에서 만든 평가지에 점수만 입력" — 평가지 설계·출력은 PC 유지.

**⑤ 과제 수합 수동 체크**

- 왜: 과제 걷기야말로 교탁 앞에서 폰으로 하는 일. 지금 모바일은 제출 현황을 보기만 한다.
- 데이터: `assignments.json` 동기화. 제출 여부 토글에 쓰기 경로(triggerSaveSync)만 추가.
- 위험: 낮음(학생별 체크 토글 수준). 기존 화면(`ToolAssignmentPage`)에 토글만 추가라 비용도 작다.

### 3순위 — 로컬 도구 확충 (거의 공짜, 단 화면 적합성 확인)

**⑥ 모둠 편성기 / 자리 뽑기 / 배점 계산기 (+ 필요 시 칠판)**

- 왜: 로컬 도구 9종을 PC 컴포넌트 lazy 재사용으로 이식한 패턴(`MORE_LAZY_TOOLS` 레지스트리)이 확립돼 있어, 레지스트리에 추가하는 수준의 비용.
- 조건: 각 도구가 좁은 세로 화면에서 쓸 만한지 도구별로 확인 필요(자리 뽑기·모둠 편성기는 명단 데이터 필요 — 모바일에 이미 있음). 자리 뽑기는 "학생 화면에 노출 금지" 원칙이 있는데, 교사 폰은 학생에게 비추지 않는 개인 화면이라 원칙과 충돌하지 않음(오히려 PC 프로젝터보다 안전).
- 제외: 신호등 토론·워드클라우드 등 실시간 계열은 🚫(호스트가 Electron).

### 검토 후보 (추천 보류 — 판단 재료만)

- **생기부 초안 읽기 전용 뷰어**: 데이터는 있고(`record-drafts.json`) "이동 중에 초안 검토"라는 시나리오도 그럴듯하다. 다만 생기부는 가장 민감한 데이터라 PIN 가림 등 보호 장치와 함께 가야 하고, 편집은 PC 유지가 맞다. (AI 기능 금지 원칙과는 무관 — 생성이 아니라 이미 있는 데이터의 조회다.)
- **쌤핀 노트 읽기 뷰어**: 노트 본문 형식 렌더링 비용 대비, 이동 중 노트를 읽는 수요가 얼마나 되는지 불확실.
- **D-Day 추가/편집**: 조회는 이미 일정 탭에 있음. QuickAdd FAB에 "D-Day" 한 칸 추가하는 정도의 소형 개선.
- **학교 알리미**: 모바일에서 쓸 이유는 있으나 서버 프록시(Edge Function) 신설이 선행돼야 해 비용이 크다.
- **관찰기록 첨부 보기**: 첨부 바이너리가 동기화는 되지만 용량·렌더링 이슈 검토 필요.

| 기능                                                            | 이유                                                                                                                              |
| --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| 실시간 협업 도구 **개설**(설문·담벼락·보드·토론·서명 등)        | PC가 서버(로컬 WebSocket+터널) 역할. 폰은 서버가 될 수 없고, 학생 참여는 이미 폰 웹으로 가능 — 즉 "교실의 반쪽"은 이미 모바일이다 |

| AI 브릿지, 미니앱, 내 이모티콘, 위젯/아이콘 모드, 퀵애드 단축키 | OS/Electron 의존(🚫). 미니앱은 장기적으로 iframe 방식 검토 여지는 있으나 보안 설계가 커서 범위 밖                                 |
| Google Calendar/Tasks 모바일 직접 연동                          | 이미 PC 경유로 동기화가 성립하고, 폰에는 구글 캘린더 공식 앱이 있다 — 중복 투자                                                   |

## 5. 공통 구현 방식 (추가 작업 시의 표준 절차)

신규 도메인 "조회" 추가는 다섯 단계로 정형화된다 (기존 코드 패턴 그대로):

1. 공용 `Json*Repository`를 모바일 DI(`src/mobile/di/container.ts`)에 등록 — 클래스는 이미 존재, 저장 백엔드(IndexedDB)도 그대로
2. `stores/useMobileXxxStore.ts` 생성 — 기존 load/reload 패턴 준수 (리팩토링 보고서의 보류 항목 B-1 참고: 팩토리화하지 말고 개별 작성)
3. `reloadAllStores()` 목록에 추가 — 동기화 직후 새 데이터가 화면에 반영되도록
4. 페이지/카드 UI — `moreSub` 키 신설(기존 키 문자열 불변), 홈 카드는 표시/숨김 토글 등록
5. 쓰기로 승격할 때만 `triggerSaveSync()` 연결 — 기존 9개 쓰기 스토어와 동일 패턴

유의사항:

- UI 설계 단계에서는 frontend-design 협업 원칙 적용
- 검증 게이트(tsc/lint/vitest/regression-check) + 모바일은 실기기 확인, `cd landing && npm run docs:check`는 /docs 가이드 변경 시
- 기능 추가 시 사용자 가이드(`landing/src/content/docs.ts`) 동반 갱신
- 게이미피케이션·생성형 AI 기능 금지 원칙은 본 추천 목록과 충돌 없음(전부 기존 데이터의 조회/입력)
