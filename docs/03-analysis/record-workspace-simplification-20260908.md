# 생활기록부 작업 화면 단순화 검토 (2026-09-08)

상태: 화면 관찰에 근거한 제안. 제품 코드 수정·설계 확정·사용성 검증은 하지 않았다.

## 1. 확인 범위와 증거

- 현재 main의 미커밋 변경을 포함한 Vite 개발 화면을 Playwright로 직접 탐색했다. 담임 업무 → 생기부 초안, 수업 관리 → 테스트 학급 → 수업 기록 → 생기부 초안 → 근거 정리를 확인했다.
- Electron 프로세스는 실행 중이었지만 Windows 화면 조작 연결은 native pipe unavailable, 기존 CDP 9333은 ECONNREFUSED였다. 별도 Electron 시작 명령은 자동 승인 검토에서 blocked by policy로 거절됐다. 설치본을 직접 조작했다고 주장하지 않는다.
- 브라우저 전용 세션 `record-ux`에 합성 수업반 30명과 합성 담임 학생 30명을 넣었다. 원본 앱 자료는 수정하지 않았다. 테스트 시더는 별도 `output/playwright/record-ux-20260908/fixture`를 대상으로 실행했다. 이 폴더를 사용하는 Electron이 없음을 확인한 별도 자료이므로 전체 Electron 프로세스 검사만 `--force`로 제외했다.
- 브라우저에서는 구독 CLI 연결이 없어 전용 AI 패널은 미연결 상태다. 쌤핀 AI 도킹 배치는 테스트 스토어의 enabled/open 값을 활성화해 관찰했다. AI 요청·실제 생성·연결·동의 절차는 검증하지 않았다. 연결 후 생성·판 비교·분량 조절 도구는 현재 소스를 읽어 기능 목록에 반영했다.
- 1440×900에서 담임/교과 초안, 학급 목록 접기, 근거 보드, AI 도킹 전후를 확인했다. 1280×800 교과+AI와 1920×1080 담임+AI도 캡처했다. 폭은 브라우저 CSS px이며 Windows 배율을 따로 검증한 것은 아니다.

자료는 저장소의 `output/playwright/record-ux-20260908/`에 있다.

### 버튼 집계의 의미

`measure.js`는 button·role=tab·role=switch를 집계한다. 선택 상자·본문 입력칸은 버튼 수에 넣지 않았고, 비활성 버튼은 넣었다. 전체 DOM 수와 현재 스크롤·잘림을 고려한 노출 수를 구분했다. 겹침에 따른 가림이나 실제 사용자의 시선은 측정하지 않았다.

| 1440×900 상태                 | 기록 내부 전체 조작 요소 |  기록 내부 현재 노출 | 앱 전체 현재 노출 |
| ----------------------------- | -----------------------: | -------------------: | ----------------: |
| 교과, 학급 목록 접힘, AI 닫힘 |                       82 |                   22 |                55 |
| 교과, 학급 목록 펼침, AI 열림 |                       82 |                   15 |                53 |
| 담임, AI 닫힘                 |                       74 |                   21 |                47 |
| 근거 보드, 학급 목록 접힘     |     별도 내부 집계 안 함 | 별도 내부 집계 안 함 |                58 |

초안의 82개는 30명 목록 전체에 걸친 수치다. 한 화면에 82개가 동시에 보인다는 뜻이 아니다. AI를 열어 노출 수가 줄어든 것은 단순화가 아니라 잘림의 결과다. 측정 원문은 `*-metrics.txt`에 저장했다.

## 2. 복잡하게 느껴지는 원인

1. **글을 쓰는 단계와 준비·설정·정리 단계가 같은 비중으로 보인다.** 영역 전체 복사, 내보내기, 형광펜, 필터가 초안/근거 전환과 나란히 있다. 제목과 영역명도 반복된다.
2. **목록형 일괄 편집과 학생별 상세 작업이 섞였다.** 30명의 입력칸마다 AI·복사·상태·근거 조작이 반복되는데, 실제 상세 AI 작업 대상은 한 명이다.
3. **오른쪽 공간의 주인이 두 곳이다.** `RecordDraftSidePanel`과 `AssistDock`이 서로의 폭과 상태를 고려하지 않고 붙는다. 가로 스크롤은 접근 가능성을 일부 보전하지만 읽고 비교하는 작업에는 부담이다.
4. **근거 카드가 편집 폼처럼 보인다.** 관찰에서 정리한 카드 한 장에 영역 3개, AI 제외, 수정, 원본 보기·수정, 정리한 근거 삭제 등 7개 조작이 붙는다. 여러 카드에서 반복되므로 근거 내용의 비중이 낮아진다.
5. **담임과 교과의 진입 구조가 다르다.** 담임은 생기부가 상위 탭이고 교과는 수업 기록 내부 탭이다. 교과에는 학급 목록까지 있어 같은 기록 화면도 더 좁다.

## 3. 권장 구조

### 기본 화면은 학생 선택 + 넓은 본문

```text
수업 관리 > 흐름테스트 3-8 > 생활기록부       [기록 화면 나가기]
영역 [과목 세특 ▾]   작성 4/30   [전체 훑어보기] [내보내기 ▾]

학생 찾기 / 작성 상태 필터     흐름가온 · 과목 세특
1 흐름가온  작성 중           [근거 9건]                  [AI 도움]
2 흐름나래  검토 필요
3 흐름다솜  작성 중           ┌────────────────────────┐
…                            │ 충분히 넓은 초안 본문    │
                             │                        │
                             └────────────────────────┘
                             저장 상태 · 162/1,500B
                             [이전] [다음] [복사] [검토 완료]
```

- 학생 목록은 이름·작성 상태 위주로 좁게 유지한다. 미작성·검토 전 필터, 학생 검색, 작성 진행률을 제공한다.
- 30명을 연속 작성하는 교사를 위해 기존 목록 편집은 **전체 훑어보기**로 유지한다. 초안 여러 개를 한 번에 읽기·편집하기, 일괄 복사·내보내기, Ctrl+Enter 다음 학생 이동을 없애지 않는다. 보기 선택은 기억한다.
- 본문 아래 바이트·저장 상태·한도 초과는 항상 보인다. 초안에 문제가 있을 때 점검 결과를 바로 열 수 있게 한다.
- ‘작성 중/검토 완료’는 AI가 생성했다는 사실과 분리한다. AI 생성만으로 교사 검토 완료 상태를 만들지 않는다.
- 학급 선택은 기록 화면 머리의 선택기로 남기고, 큰 학급 목록은 집중 화면에서 접는다. 앱 전체 메뉴 축소는 사용자가 복원할 수 있게 하고 기존 표시 상태를 기억한다.
- 간단한 초안 작성에 근거 보드 방문이나 주제 지정이 필수 단계가 되지 않게 한다. 관찰 입력의 ‘본문 우선, 장면·주제 선택’도 유지한다.

### 오른쪽 보조 공간은 하나

`AI 도움` 또는 `근거 N건`을 눌렀을 때만 보조 공간을 연다. 내부에서 **근거 / AI 작업**을 바꾼다. AI 작업에는 ‘초안 만들기’, ‘분량 조절’, 필요할 때 ‘자유 질문’이 있다. 세 작업의 설정 폼을 동시에 펼치지 않는다.

쌤핀 AI 진입점으로 열어도 두 번째 패널을 추가하지 않고 같은 보조 공간으로 전환한다. 일반 대화와 생활기록부 작성은 제공 가능한 AI·기능이 다르므로 제목과 현재 학생/영역을 명확히 표시한다. 통합은 배치와 진입점의 통합이며, 구독 전용 초안을 일반 AI가 작성할 수 있다고 표시하면 안 된다.

- AI 종류·모델은 현재 선택을 한 줄에 보여 주고 눌러 바꿀 수 있게 한다. ‘고급 설정’ 깊숙이 숨기지 않는다.
- 처음에는 ‘이 학생 초안 만들기’가 중심이다. 일괄 생성은 별도 메뉴에서 대상 명단·인원과 덮어쓰기 정책을 확인한 뒤 실행한다.
- 글이 있는 경우 ‘분량 조절’은 찾기 쉬운 위치에 남기되 목표 입력은 눌렀을 때 펼친다. **현재 구현의 ‘목표 바이트가 줄이기/보충 방향을 정함’을 유지**하며 방향 선택 버튼을 재도입하지 않는다.
- 결과가 도착하면 설정 대신 결과와 비교·반영을 중심에 둔다. 판 이력·형광펜·다시 표시는 해당 결과의 도구로 배치한다.
- 비교는 320px 패널 안을 다시 두 열로 쪼개지 않는다. 본문 공간에서 원문/제안을 충분히 넓게 비교하거나 좁은 폭에서는 위아래 비교로 전환한다.
- 탭을 바꾸거나 닫았을 때 진행 중 요청을 소리 없이 잃지 않는다. 학생·영역·원문 버전을 요청에 묶고, 진행 상태·중단·결과 돌아가기를 유지한다. 다른 학생을 선택했다고 이전 결과를 새 학생에게 적용해서는 안 된다.

### 근거는 평소에 읽고, 정리할 때 보드를 연다

평소 ‘근거 9건’은 같은 학생·영역의 근거 목록을 보여 준다. ‘주제별로 정리’를 누르면 본문 공간을 보드로 전환한다. 보드에서 돌아오면 기존 학생·영역·작성 위치를 복원한다.

| 기존 기능                             | 제안 위치와 노출 방식                                                       |
| ------------------------------------- | --------------------------------------------------------------------------- |
| 관찰·과제·평가 등 근거 확인           | 근거 패널의 날짜·출처·본문 요약, 펼치면 전문                                |
| 영역 여러 개 지정                     | 카드 상세의 ‘작성 영역’ 선택. 여러 영역 지정 유지                           |
| AI 제외/해제                          | 카드 상세와 선택 항목 작업 바. **제외된 상태는 카드 겉면에도 계속 표시**    |
| 수정·원본 보기·원본과 비교            | 카드 상세에서 각각 분명한 이름으로 제공. 원본과 정리본을 자동 덮어쓰지 않음 |
| 삭제·되돌리기                         | 상세 더보기에서 삭제 대상 명시, 기존 되돌리기 유지                          |
| 주제 생성·이름 변경·닫기·다시 열기    | 보드의 주제 제목 및 더보기                                                  |
| 줄기 보기·관찰 이어 쓰기              | 주제를 선택하면 나타나는 작업 도구                                          |
| 드래그·여러 카드 선택·주제 이동       | 정리 보드 유지. 선택 시 일괄 작업 바, 키보드로도 실행 가능                  |
| AI 분류 제안·제안 원문·개별/전체 적용 | 보드의 ‘분류 도움’에서 실행, 결과가 있을 때 적용 도구 표시                  |
| 엑셀 가져오기·내보내기·직접 입력      | 근거 목록/보드의 ‘근거 추가 ▾’와 내보내기 메뉴                              |
| 판 이력·원문/제안 비교·명시적 반영    | AI 결과 보기 안에서 제공, 대상과 분량 상시 표시                             |
| 전체 학생 생성·복사·내보내기          | 전체 훑어보기 및 작업 메뉴에서 유지                                         |

카드의 기본 모습은 본문 2~3줄, 날짜·출처, 상태 배지, 상세 진입 정도로 줄인다. 더보기는 마우스 올리기만으로 나타나는 버튼으로 만들지 말고 키보드 초점·클릭으로도 접근 가능하게 한다. 중요한 경고와 AI 제외 상태는 더보기 속에 숨기지 않는다.

## 4. 다른 대안과 적용 순서

| 대안                                                    | 장점                                                       | 한계                                                             | 판단                 |
| ------------------------------------------------------- | ---------------------------------------------------------- | ---------------------------------------------------------------- | -------------------- |
| 현재 목록을 유지하며 버튼만 더보기로 이동               | 변경이 작고 익숙함                                         | 두 패널·좁은 본문·여러 단계 탐색은 남음                          | 단기 개선으로만 적합 |
| 학생별 집중 보기 + 기존 전체 목록 보기 + 보조 공간 하나 | 긴 글 읽기·근거 확인·AI 비교에 공간 확보, 일괄 작업도 보전 | 보기 전환과 실행 상태 보전 설계 필요                             | 권장                 |
| 모든 기능을 AI 대화창으로 이동                          | 첫 화면이 단순해 보임                                      | 근거 선정·정확한 바이트·검토 상태·일괄 편집의 발견성과 제어 약화 | 권장하지 않음        |

1. **첫 작업**: 두 오른쪽 패널의 동시 표시를 막는 공통 컨테이너와 상태 보전 계약을 설계한다. 학급 목록 접기/복원, 제목·버튼 줄바꿈, 반복 안내를 함께 정리한다.
2. **둘째 작업**: 학생별 집중 보기를 추가하고 기존 전체 훑어보기를 보전한다. 30명 연속 작성과 저장되지 않은 글 이동을 먼저 검증한다.
3. **셋째 작업**: 카드 조작부를 상세로 옮기고, AI 설정/결과/분량 조절을 작업 단계에 따라 펼친다.

단순 패널 조건부 렌더링만 바꾸면 진행 중 생성이 언마운트로 취소되거나 결과가 사라질 수 있다. ‘하나만 열기’에도 작업 상태의 소유 위치를 먼저 정해야 한다. 기존 ADR-085의 오른쪽 AI 패널 원칙과 겹치므로, 승인 후 설계 단계에서 변경 범위를 결정한다. 이번 검토로 새 결정을 확정하지 않는다.

## 5. 구현 전후 판단 기준

다음은 제안하는 합격 기준이며 이번에 통과시킨 테스트가 아니다.

- 1280×800, 1440×900, 1920×1080 모두에서 기록 본문·주요 버튼 접근에 페이지 가로 스크롤이 필요하지 않을 것. 보드 자체의 가로 이동은 허용하되 좁은 폭에서 주제 선택/목록 대안 제공.
- 학생별 보기에서 본문은 가급적 560 CSS px 이상 확보. 보조 패널을 더할 공간이 부족하면 학생 목록을 선택기로 바꾸고, 그래도 부족하면 패널을 별도 작업 화면으로 전환한다. 화면 전체 폭만으로 판단하지 않고 실제 남은 본문 폭을 기준으로 한다.
- 오른쪽 보조 패널은 최대 하나. 닫힌 패널의 빈 폭은 남기지 않는다.
- 기본 작업 버튼은 학생 탐색·영역/보기 선택을 제외하고 근거·AI 도움·복사·검토 완료·내보내기 등 약 5개를 목표로 한다. 숫자 자체보다 기능 발견성·읽기 폭을 우선한다.
- 전체 30명 초안 편집, 다음 학생 단축키, 상태 필터, 일괄 생성/복사/내보내기까지 접근 경로를 기능표로 대조한다.
- 분량 초과 미저장 글에서 학생/보기/AI 전환 → 원문 보전. 근거 부족 시 허구 보충 없음. 적용은 교사가 비교 후 결정.
- AI 실행 중 패널 전환·학생 변경·중단·늦게 도착한 결과 시나리오에서 잘못된 학생에 반영되는 일이 없을 것.
- 원본과 정리본 비교·명시 적용, AI 제외·해제, 다중 영역, 다중 선택, 드래그/키보드 이동, 닫힌 주제 재열기, 삭제 되돌리기 유지.
- 교사가 ‘한 학생 작성 → 근거 확인 → 분량 조절 → 비교·반영 → 다음 학생’을 수행하는 과정을 관찰해 막힌 지점과 되돌아간 횟수를 비교한다. 실제 사용자 검증 없이 클릭 수 감소나 사용성 향상을 확정하지 않는다.

## 6. 이번 검증 결과

Playwright 실행·화면 이동·PNG 캡처·이미지 직접 확인·DOM 폭과 조작 요소 계측을 수행했다. 브라우저 합성 자료 기반의 화면 검토이며 실제 AI 왕복·Electron 실기기 QA와 구분한다. 제품 코드는 수정하지 않아 tsc/lint/Vitest/regression-check는 실행하지 않았다. 향후 구현 완료 판정에는 프로젝트의 네 검증 게이트와 실제 화면 검증이 모두 필요하다.
