## 0. 결론

**쓰기(체크)는 넣지 말 것. 읽기(표시)만 소규모로 넣을 값어치가 있다.**

그리고 이 분석에서 **증빙서류보다 우선순위가 높은 문제 하나를 발견했다**(§3). 서류와 무관하지만
이번 기본값 확대로 영향 범위가 넓어졌다.

| 항목                                                | 판단                                                                                        | 근거 |

## 1. 먼저 확인 — **서류 값 자체는** 모바일을 거쳐도 안전하다

모바일에 서류 기능이 **없어서** 서류 값이 깨지는 일은 없다. 두 가지를 실측했다.

> ⚠️ 범위 주의 — 이 절은 **`documentSubmitted` 필드의 보존**만 다룬다.
> 기록(사본) **자체가 삭제되는** 별개 경로가 있고, 그건 §3-2(B)다. 서류 기능 유무와 무관한 문제다.

**(1) 병합 계약을 데스크톱과 공유한다.**
모바일도 같은 `SyncFromCloud`를 쓴다(`useMobileDriveSyncStore.ts:5,338`). 병합 채택은
`TRACKED_GROUP_FIELDS.documentGroup`(= `documents` + `documentSubmitted`)에서 파생되므로
**모바일을 거쳐도 서류 값이 소실되지 않는다.**

**(2) 모바일이 출결을 고쳐도 서류 값을 승계한다.**
`useMobileStudentRecordsStore.ts:122-127` — 기존 레코드를 스프레드해 부분 갱신한다.

```
const { attendancePeriods: _stale, ...existingBase } = existing ?? ({} as StudentRecord);
const record: StudentRecord = { ...existingBase, id: bridgeId, ... };
```

`documentSubmitted`는 `existingBase`에 실려 그대로 남는다. 주석도 이 계약을 명시한다 —
"승계 목록을 손으로 고르면 followUp/tags 같은 필드가 after에서 빠져 before→after diff가
'삭제 의도'로 오인한다".

→ **모바일에 서류 기능이 없는 것 자체는 결함이 아니라 기능 격차다.**
다만 서류와 무관한 별개 결함이 같은 경로에 있다 — §3.

## 2. 쓰기(체크)를 넣지 말아야 하는 이유

**(1) 모바일 기록 줄에는 완료 상태 표시가 하나도 없다.**

`StudentRecordsFullSheet.tsx:218-249`의 RecordRow가 그리는 것 — **날짜 · 분류 라벨 · 내용**. 끝.

- 나이스 반영: `grep -rn "reportedToNeis" src/mobile/` → **0건**
- 후속조치 완료 표시: 없음
- 서류: 없음

서류만 넣으면 **모바일에서 유일하게 튀는 요소**가 된다. 데스크톱에서 서류 배지가 정당했던 근거는
"같은 자리에 나이스 배지가 이미 있는데 서류만 숨는 비대칭"이었다(발견성 분석 §9-1). **모바일에는
그 비대칭이 없다** — 셋 다 없다. 같은 논리로 서류만 먼저 넣을 이유가 없다.

**(2) "오늘 남은 일" 카드에도 맞지 않는다.**

`TodayRemaining.tsx:14-47`이 스스로 정한 규칙:

- **남은 것만 보여준다. 다 했으면 카드가 통째로 사라진다**
- 오늘 범위 — 오늘 출결 미입력 + 마감 지남/오늘 마감 할 일

증빙서류 미제출은 **오늘 것이 아니라 누적 상태**다. 여기 넣으면 카드가 상시로 떠 있게 되고,
"다 했으면 사라진다"는 규칙이 깨진다.

**(3) 앱의 역할 분담과 어긋난다.**

사용자 가이드(`docs.ts` features/mobile): _"PC 데이터를 휴대폰으로 확인하고 **일부** 기록을 작성합니다."_

이미 같은 선례가 있다 — _"컴퓨터에서 적어 둔 '다시 확인할 날'과 관련인 이름이 할 일 목록에 함께
보입니다. **보기만 되고, 붙이거나 고치는 것은 컴퓨터 쌤핀에서 합니다.**"_

**데스크톱에서 만든 부가 정보는 모바일이 읽기만 한다** — 이미 확립된 패턴이고, 증빙서류가 딱 그 종류다.

**(4) 실사용 동선이 약하다.**

서류는 학부모가 보내거나 학생이 가져와 **교무실 책상에서** 받는다. 받는 순간 체크하려면 휴대폰이
아니라 PC 앞일 가능성이 높다. 반대로 "누가 아직 안 냈지?"를 **복도·교실에서 확인**하는 동선은
있을 법하다 → 그래서 §4는 읽기만 권한다.

## 3. ✅ 해결됨 — 모바일 저장 한 번에 서류 대상이 사라지던 문제

> **상태: 2026-08-27 수정 완료.** 아래 §3-1~3-3은 **수정 전** 상태의 기록이다(원인 분석 보존).
> 조치는 §3-5 권고대로 **브리지가 하루 전체를 집계**하도록 고쳤고, 회귀 가드는
> `src/mobile/stores/__tests__/mobileAttendanceBridgeDocumentPolicy.test.ts` (8건)가 맡는다.
> 학교급 대응(§3-7)도 함께 반영했다.

**상태: 재현 테스트로 확정.** `src/mobile/stores/__tests__/mobileAttendanceBridgeDocumentPolicy.test.ts` (5건 통과)
— 코드 읽기 추정이 아니라 실제 스토어를 돌려 확인했다.

### 3-1. 원인 — 두 모델이 어긋나 있다

|                     | 데스크톱 담임 출결                                                                  | 모바일 담임 출결                                                                                                                           |
| ------------------- | ----------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 교시                | 교시별 입력                                                                         | **0교시(조회) 하나만.** 교시 선택 UI 자체가 없다 (`TodayHub.tsx:197,343`, `AttendanceCheckPage.tsx:639` 주석 "담임 출결은 교시 개념 없음") |
| 사본(StudentRecord) | 대표 사유 + **`attendancePeriods` 전량 보존** (`useStudentRecordsStore.ts:603-615`) | **`attendancePeriods` 의도적 제거** (`useMobileStudentRecordsStore.ts:122`)                                                                |
| 저장 범위           | 편집한 것                                                                           | **저장 시 명단 전원을 브리지** (`AttendanceCheckPage.tsx:291`, 미지정 학생은 `?? 'present'`)                                               |

`requiresDocument`는 경로가 둘이다 — 교시 상세가 있으면 **OR 집약**(`attendanceDocumentPolicy.ts:88`),
없으면 **subcategory 하나로 추론**(`:92-94`). 상세가 사라지면 판정 근거가 바뀐다.

### 3-2. 확인된 결과 2가지

**(A) 하루에 사유가 섞이면 판정이 뒤집힌다 — 항상 과소 방향**

- PC: 1교시 미인정 결석 + 3교시 질병 결과 → OR 집약으로 **서류 요구 = true**
- 모바일에서 그날 저장 → 교시 상세 소멸, subcategory '결석 (미인정)'만 남음 → **false**

대표(`REPRESENTATIVE_PRIORITY` = absent > earlyLeave > late > classAbsence)는 **상태 심각도로만** 뽑고
사유는 보지 않는다. 대표가 면제 축(미인정)이면 다른 교시의 질병이 통째로 묻힌다.

방향은 **항상 과소(true→false)** 다 — 대표는 그날 교시 중 하나이므로, OR이 false면 대표도 요구일 수 없다.
과다 오류는 구조적으로 생기지 않는다. **놓치는 쪽으로만 틀린다**는 뜻이라 서류 수합에는 더 나쁜 방향이다.

**(B) 더 큰 문제 — 0교시에 안 걸린 기록은 사본이 통째로 삭제된다**

- PC: **3교시** 결과(질병)만 기록 → 서류 요구 대상
- 모바일 담임 출결은 **0교시만** 보므로 이 학생이 '출석'으로 보인다
- 저장하면 전원 루프가 이 학생을 `present`로 브리지 → **사본(`att-<studentId>-<date>`) 삭제**

서류만의 문제가 아니다. **담임 기록·통계에서 그 출결이 사라진다.**
present→삭제 자체는 의도된 동작이지만(`attendance-dual-ledger-delete.handoff.md`),
**"0교시만 보는 화면이 하루 전체를 대표한다"는 전제가 다중 교시에서 깨진다.**

### 3-3. 이번 변경과의 관계

**이 결함은 이번 증빙서류 작업이 만든 것이 아니다.** 모바일 하루-단위 모델의 기존 성질이다.
다만 **기본 대상이 '인정만'에서 '인정+질병'으로 넓어지면서 (A)에 걸릴 확률이 크게 올랐다** —
전에는 인정 사유가 섞여야 했는데 이제 질병만 섞여도 해당된다.
하루 여러 예외는 정식 지원 기능이다(가이드: "1교시 지각 → 3교시 결과 → 6교시 조퇴처럼
종류가 달라도 함께 기록됩니다").

### 3-4. ✅ 원장은 안전하다 (확인 완료) — 상한 것은 파생 사본뿐

§3-2 발견 직후 남겨 뒀던 질문("출결부 원장까지 상하나")을 확인했다. **안 상한다.**

모바일 저장은 `upsertRecord`를 타고, 교체 키가 `matchesKey`(`ManageAttendance.ts:122-132`)다 —
**`(classId/groupId, date, period)`로 교시를 포함**한다. 0교시 저장은 **0교시 레코드만** 교체하고
같은 날 3교시 레코드는 그대로 남는다.

이 사실이 대응 방향을 바꾼다.

- 진짜 출결 데이터(AttendanceRecord)는 **모든 교시가 온전하다**
- 망가지는 것은 그걸 베껴 만든 **담임 기록 사본(StudentRecord)** 하나뿐
- → **사본 만드는 규칙만 고치면 앞으로도 안 새고, 이미 틀어진 것도 원장에서 다시 만들 수 있다**

### 3-5. ✅ 채택·구현 — 화면이 아니라 브리지를 고쳤다

| 안                                   | (A) 판정 뒤집힘 | (B) 사본 삭제 | 화면 변경 | 비용   |
| ------------------------------------ | --------------- | ------------- | --------- | ------ |
| **브리지가 하루 전체를 집계** (권고) | 해결            | 해결          | 없음      | **소** |
| 모바일에 교시 선택 추가              | **미해결**      | **미해결**    | 큼        | 중~대  |
| 둘 다                                | 해결            | 해결          | 큼        | 대     |

**교시 선택기만 붙여서는 데이터가 안 고쳐진다.** 브리지가 "지금 이 교시" 값만 쓰고
`attendancePeriods`를 버리는 동작은 그대로이기 때문이다 — 화면을 고쳐도 브리지는 따로 고쳐야 한다.

**브리지 수정안** — 저장 후 그날 그 학급의 **전 교시 원장**을 읽어 `recordsByPeriod`를 만들고,
데스크톱과 같은 방식으로 대표 + `attendancePeriods`를 기록한다.

- 데이터는 이미 메모리에 있다 — `useMobileAttendanceStore.records` (전 레코드 보유)
- 같은 로직이 데스크톱에 이미 있다 — `useStudentRecordsStore.ts:574` `bridgeHomeroomDayAttendance`
  (`pickRepresentativeAttendance` + 교시 상세 보존)
- 순환 참조 문제 없음 — 모바일 기록 스토어가 이미 출결 스토어를 참조한다(`migrateExistingAttendance`)
- (B)도 함께 풀린다: 0교시가 present여도 3교시에 대표가 있으면 삭제 대상이 아니게 된다

### 3-6. ✅ 함께 조치 — 하루뷰가 다른 교시 기록을 가리지 않게 했다

브리지를 고쳐도 **표시 문제는 남는다.** 모바일 담임 출결은 0교시만 보여주므로,
3교시에 결과가 있는 학생이 화면에서는 '출석'으로 보인다. 데이터가 새지 않더라도 **화면이 사실과 다르다.**

다만 **모바일 담임 출결의 '교시 없음'은 의도된 설계**다 — 도메인에 전용 지원까지 만들어 뒀다:

```
// attendanceQuickText.ts:15,66
// (교시 개념이 없는 화면 — 모바일 담임 출결 — 은 requirePeriod:false로 전 종류 생략 허용)
// 하루 단위 상태만 저장하는 화면(모바일 담임 출결)처럼 교시 개념이 없는 호출자용.
```

가이드도 같은 방향이다 — "출결은 전원 출석을 기본으로 두고 다른 학생만 골라 바꾸는 방식".
교실에서 빠르게 쓰라고 단순화한 화면이므로, 교시 선택기 도입은 **그 설계를 되돌리는 결정**이다.

표시 문제의 선택지(가벼운 순):

1. **읽기 표시만** — 그 학생 줄에 "3교시 결과"처럼 다른 교시 기록이 있음을 알려주고, 편집은 PC에서
2. **교시 선택기 추가** — 하루 전체를 모바일에서 편집 가능. 화면이 무거워지고 의도된 단순화를 되돌린다

**조치 결과**: 1번(읽기 표시)을 채택해 구현했다 — 하루뷰(중·고)에서 그날 다른 교시에 이상 출결이
있으면 건수와 교시를 알리고, 고치는 것은 PC로 안내한다. 교시 선택이 있는 화면(수업·초등 담임)은
직접 옮겨 볼 수 있으므로 띄우지 않는다.
2번(교시 선택)은 **초등·직접설정 학교급에 한해** 채택했다 — §3-7.

### 3-7. 🔑 학교급이 판을 바꾼다 — 초등 담임은 거의 전 교시를 관리한다

오너 지적(2026-08-27): _"고등학교는 조회·종례만 보면 되지만, 초등학교는 담임이 거의 모든 교시의
출결을 관리한다."_

> **문서를 제품에 맞추거나, 지원 범위를 명시적으로 정할 것.**

### 학교급 분기 선례가 이미 있다 — 그것도 같은 이유로

```
// DashboardTimetable.tsx:111, ProgressCalendarView.tsx:63
settings.timetableColorBy ?? (settings.schoolLevel === 'elementary' ? 'subject' : 'classroom')
```

**초등은 담임이 한 교실에서 여러 과목을 가르치므로 교실이 아니라 과목으로 구분한다** — 코드가 이미
오너가 말한 그 구조를 알고 다르게 동작한다. `AddClassModal/index.tsx:28`(초등·custom은 마법사),
`ClassAssessmentManagementTab.tsx:264`도 같은 축으로 갈린다.

→ **학교급별 분기는 이 앱의 확립된 패턴이다.** 새 개념을 도입하는 게 아니다.

### 학교급별로 필요한 것이 다르다

|                                 | 중·고 담임  | 초등 담임                                       |
| ------------------------------- | ----------- | ----------------------------------------------- |
| 출결을 보는 시점                | 조회·종례   | **거의 전 교시**                                |
| 모바일 하루뷰(0교시)로 충분한가 | 대체로 충분 | **불충분 — 3교시 결과를 넣을 방법이 아예 없다** |
| 지금 모바일 담임 출결의 실효성  | 쓸 만함     | **사실상 못 씀**                                |

초등 담임에게 현재 모바일 담임 출결은 **버그가 아니라 기능 부재**다. 0교시만 쓰므로
교시별 지각·조퇴·결과를 기록할 길이 없다.

### 도메인은 이미 양쪽을 지원한다

`parseAttendanceQuickText`는 `requirePeriod` 옵션으로 **두 모드를 모두** 갖고 있다
(`attendanceQuickText.ts:15,66` — "교시 개념이 없는 화면 — 모바일 담임 출결 — 은 requirePeriod:false").
교시 모드로 켜는 데 도메인 변경이 필요 없다.

### 수정된 권고

| 순서  | 내용                                | 학교급                  | 상태    |
| ----- | ----------------------------------- | ----------------------- | ------- |
| **1** | 브리지가 하루 전체를 집계 (§3-5)    | 전체 공통               | ✅ 완료 |
| **2** | 다른 교시 기록이 있으면 화면에 표시 | 중·고 하루뷰            | ✅ 완료 |
| **3** | 초등은 교시 선택 노출               | `elementary` + `custom` | ✅ 완료 |

1번이 여전히 먼저다 — **학교급과 무관하게 데이터가 새는 것부터 막아야** 하고, 3번을 하더라도
브리지가 그대로면 교시 상세는 계속 버려진다.

**3번의 결정 사항 (구현에 반영, 근거는 코드 주석에도 남김)**

| 항목                        | 결정                       | 근거                                                                                                                                                |
| --------------------------- | -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `custom` 학교급             | **초등과 함께 노출**       | 담임 운영 방식을 알 수 없다. 안 열면 그만이지만 필요한데 없으면 기록할 방법이 없다. 수업반 추가 마법사도 `elementary \|\| custom` 을 함께 묶는 선례 |
| 초등 진입 교시              | **0교시(조회) 유지**       | 홈 '오늘 남은 일'이 그렇게 열고 중·고에는 그게 하루 전체다. 진입을 바꾸면 기존 동선이 깨진다. 목록에서 옮길 수 있게만 한다                          |
| 교시 목록에 0 포함          | **포함(이름 '조회')**      | `periodTimes` 는 1교시부터라 0이 없다. 홈과 같은 이름을 직접 붙여, 초등 담임이 조회로 돌아올 수 있게                                                |
| 빠른 텍스트 `requirePeriod` | **false 유지 (변경 없음)** | 저장 교시는 화면에서 이미 고른 값이다. 텍스트에 또 적게 하면 같은 정보를 두 번 요구하고, 둘이 어긋나면 어느 쪽을 따를지 애매해진다                  |

## 4. 넣는다면 — 읽기만, 최소로

우선순위 낮음. 데스크톱 변경의 실사용 피드백을 먼저 받아 보는 편이 낫다.

| 안     | 내용                                                                     | 비용  |
| ------ | ------------------------------------------------------------------------ | ----- |
| **M1** | 학생 상세 출결 줄에 **미제출만** 작게 표시(제출 완료·대상 아님은 무표시) | 소    |
| **M2** | 학급 기록 모아보기에 '증빙서류 미제출' 필터 한 개                        | 소~중 |
| ~~M3~~ | 체크(토글) — **권하지 않음**(§2)                                         | —     |

M1이면 "복도에서 누가 안 냈는지 확인"이라는 유일하게 그럴듯한 동선을 덮는다.
표시 규칙은 데스크톱과 같아야 한다 — 정책 게이트(`requiresDocument`)를 그대로 통과시키고,
미인정은 아예 안 그린다. 도메인 함수를 공유하므로 새 규칙을 만들 필요는 없다.

**넣지 말아야 할 것**: "오늘 남은 일" 카드 편입(§2-2), 종류별 체크리스트(신청서/보고서/증빙자료),
설정 화면의 정책 편집기(데스크톱 전용 유지).

## 5. 권고

1. **지금은 넣지 않는다.** 데이터 위험이 없고(§1), 모바일에 붙일 자리가 마땅치 않다(§2).
2. **§3을 별도 작업으로 올린다.** 서류보다 먼저다 — 사본이 삭제되면 담임 기록·통계·생기부 집계가
   함께 빈다. 다음 순서를 권한다: ① 원장(AttendanceRecord) 손상 여부 확인(§3-4) → ② 실기기 재현
   → ③ 대응 결정(모바일이 교시를 보게 할지, 브리지가 상세를 보존할지, 0교시 외 기록이 있으면
   삭제를 보류할지).
3. 데스크톱 변경이 실사용에서 자리를 잡은 뒤, 실제로 "휴대폰에서도 보고 싶다"는 요청이 오면 **M1만** 넣는다.

## 6. 이 분석의 한계

- 코드 실측 기반이다. **모바일 실기기 확인은 하지 않았다** — 특히 §3은 실제로 어떤 값이 남는지
  눈으로 봐야 확정된다.
- 모바일 사용 빈도·동선 데이터가 없다. §2-4의 동선 판단은 추론이며, 실제 요청이 오면 뒤집힐 수 있다.
