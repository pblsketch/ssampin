## 0. 조사 방법과 근거의 한계 — 먼저 읽어주세요

### Mobbin은 쓰지 못했습니다

지난 세션에서 Mobbin MCP를 연결하고 인증까지 끝냈지만, 이번 세션에서 실제로 검색을 돌리자 세 도구(`search_screens` / `search_flows` / `search_sections`)가 전부 같은 응답으로 막혔습니다.

```
Mobbin MCP requires a paid plan. Upgrade at https://mobbin.com/pricing to continue.
```

지난 세션의 `✔ Connected`와 OAuth 완료는 **"서버에 붙었다"까지만 증명**하고, 검색 권한은 계정 요금제에서 한 번 더 걸립니다. 쿼리를 바꾸거나 다시 로그인해도 뚫리는 종류가 아닙니다. 사용자 판단으로 **Mobbin 없이 대체 근거로 진행**했습니다.

### 그래서 근거를 이렇게 바꿨습니다

Mobbin은 "실제 앱 스크린샷"이 근거였습니다. 대신 아래 세 가지를 썼고, **각 주장 옆에 근거 등급을 표시**했습니다. 이걸 표시하는 이유는, 나중에 "이거 확실한 얘기였나?"를 되짚을 때 스크린샷 본 것과 제가 아는 것을 구분해야 하기 때문입니다.

| 등급       | 의미                                                                   | 신뢰도                   |
| ---------- | ---------------------------------------------------------------------- | ------------------------ |
| **[공식]** | Apple HIG · Material Design 3 · NN/g 등 공식 가이드라인 원문           | 높음 — 그대로 인용 가능  |
| **[업계]** | 업계 문서·디자인 시스템 공개 문서·제품 도움말 페이지                   | 중간 — 방향은 믿을 만함  |
| **[관측]** | 제가 아는 해당 앱의 구조. **이번 세션에서 스크린샷으로 확인하지 않음** | 낮음 — 참고용, 검증 필요 |

> **[관측] 표시가 붙은 항목은 재설계 확정 근거로 쓰지 마세요.** Mobbin을 열게 되면 그 항목부터 스크린샷으로 확인하는 게 순서입니다.

### 조사한 앱군

핸드오프 조건대로 **소비자 SNS를 제외**하고 현장 업무앱 위주로 봤습니다 — 근무 관리(Deputy · Homebase · Connecteam), 진료 현장(Epic Haiku · Epic Rover), 창고 검수(Microsoft Warehouse Management), 출석 관리(Canvas Roll Call · Acadly), 그리고 업무용 디자인 시스템(ServiceNow Horizon · SAP Fiori for iOS · Microsoft Fluent 2).

## R1. 하단 탭 구성 원칙 — 전체 IA

### 지금 상태

`App.tsx:114-119` 기준 탭은 **4개**(홈 · 학생 · 일정 · 더보기).

```ts
const tabs: TabConfig[] = [
  { key: 'home', label: '홈', icon: 'home' },
  { key: 'students', label: '학생', icon: 'group' },
  { key: 'schedule', label: '일정', icon: 'calendar_month' },
  { key: 'more', label: '더보기', icon: 'more_horiz' },
];
```

### 먼저 짚을 것 — 탭 개수는 문제가 아닙니다

[공식] Apple HIG는 아이폰에서 **탭 3~5개**를 권합니다. [공식] Material Design 3도 **3~5개**를 규정하고, 3개 미만이면 탭 대신 다른 걸 쓰고 5개를 넘기지 말라고 못박습니다. 쌤핀의 4개는 정확히 권장 범위 안입니다.

**진짜 문제는 탭 개수가 아니라 탭 뒤에 매달린 것의 불균형입니다.**

| 탭     | 뒤에 있는 목적지 수                                |
| ------ | -------------------------------------------------- |
| 홈     | 1                                                  |
| 학생   | 2 (담임 / 수업 세그먼트)                           |
| 일정   | 2 (일정 / 할 일 세그먼트)                          |
| 더보기 | **18** (`App.tsx:145-165`의 `moreSub` 유니온 타입) |

즉 겉으로는 4칸인데 실제 목적지는 4+18 = 22개이고, 그중 18개가 한 칸 뒤에 몰려 있습니다.

### 레퍼런스에서 확인한 원칙

1. **[공식] 탭은 이동 전용, 동작 버튼이 아니다.** HIG: "Use a tab bar strictly for navigation. Tab bar buttons should not be used to perform actions."
2. **[공식] 탭은 사라지거나 비활성화되면 안 된다.** HIG: "Don't remove or disable a tab when its function is unavailable." — 조건부로 나타나는 탭은 앱을 예측 불가능하게 만듭니다.
3. **[공식] 탭 vs 세그먼트의 역할 구분.** 업계에서 널리 쓰이는 정리: **탭 바는 "앱의 어디에 있나?"에 답하고, 세그먼트 컨트롤은 "이 화면의 어느 버전을 보고 있나?"에 답한다.** 예를 들어 "리스트 vs 보드"는 세그먼트, "홈 vs 프로필"은 탭입니다.
4. **[업계] 업무앱은 방문 빈도로 탭을 정한다.** 근무관리 앱군(Deputy · Homebase · Connecteam)은 매일 여러 번 쓰는 것(내 근무표, 출퇴근 찍기, 팀 메시지)을 탭에 두고, 관리자용 설정은 별도 관리 탭 하나로 묶습니다. [관측] Connecteam의 도움말 문서상 하단에 별도 Admin 탭이 존재합니다.

### 쌤핀 적용

**가장 큰 구조적 이상 신호: 매일 가장 자주 하는 일(출결 입력)이 탭에 없습니다.**

`AttendanceCheckPage`는 탭 밖 전체화면이고, 다른 화면을 거쳐야만 도달합니다. 반면 하루에 한 번도 안 여는 도구(룰렛 · 동전 · 주사위)는 더보기 안에 들어 있긴 해도 같은 계층에 평평하게 놓여 있습니다. **빈도와 계층이 뒤집혀 있습니다.**

검토할 후보 두 갈래입니다.

**A안 — 탭을 5개로 늘리고 출결을 승격**
`홈 · 학생 · 출결 · 일정 · 더보기`. 장점은 매일 하는 일이 한 번에 닿는 것. 단점은 [공식] Material 3 기준 5개일 때 비활성 탭의 텍스트 라벨은 "공간이 허락하지 않을 수 있어 주의해서 쓰라"고 되어 있어, **한국어 라벨 5개가 390px 폭에 들어가는지 실측이 필요**합니다.

**B안 — 탭은 4개 유지, 홈을 "오늘의 작업 시작점"으로 재정의**
출결은 홈에서 시간표 카드를 눌러 바로 진입. 장점은 탭 폭 문제 없음, HIG의 "탭은 이동 전용" 원칙과도 충돌 없음. 단점은 출결이 여전히 한 단계 뒤에 있음.

**판단 재료:** 선생님이 하루에 출결을 몇 번 여는지가 갈림길입니다. 수업반이 여러 개면 하루 4~6회이고, 그러면 A안 쪽이 맞습니다.

**공통으로 지킬 것:** 담임/수업 세그먼트는 "같은 화면의 다른 버전"이므로 세그먼트가 맞습니다(원칙 3에 부합). 이건 탭으로 올리지 않습니다.

### 걸러낸 패턴

- **햄버거 메뉴(좌측 서랍)로 18종 수용** — 한 손 조작 시 좌상단은 가장 닿기 어려운 자리이고, 발견성이 하단 탭보다 명확히 낮습니다.
- **조건부 탭**(담임일 때만 담임 탭 표시) — [공식] HIG가 명시적으로 금지.

## R2. 반 선택 + 날짜 이동 + 뷰 전환 — 헤더 3층 (P1)

### 지금 상태

`StudentsPage.tsx:340-479`. 헤더 안에서 세 줄이 쌓입니다.

1. **제목 + 기록보기 아이콘 + 좌석/명단 토글** (`:342-406`)
2. **반 선택 가로 스크롤 탭**
3. **날짜 이동바** (← 8월 12일 (화) → · "오늘로 가기")

여기에 App 전역 헤더와 학생 탭 세그먼트까지 더하면 **첫 학생 이름이 보이기 전에 5개 층**을 지납니다.

### 레퍼런스에서 확인한 원칙

1. **[공식] 콘텐츠 대 크롬 비율(content-to-chrome ratio)을 최대로.** NN/g는 상단 고정 영역이 잡아먹는 공간을 비율로 평가합니다. 뉴요커의 아이폰 11 Pro 기준 **13:1을 "합리적인 공간 거래"**로, Lollar Pickups의 **2:1을 "인색하다(miserly)"**고 평가했습니다. 원칙은 "Maximize the Content-to-Chrome Ratio by Keeping It Small."
2. **[공식] 고정 영역에서 줄일 수 있는 건 여백뿐.** NN/g는 탭 대상 최소 1cm × 1cm, 본문 약 16pt를 지키고 **"그 크기를 넘는 추가 세로 높이는 줄이라"**고 합니다. 즉 글자와 버튼은 그대로 두고 층 수를 줄이는 게 정답입니다.
3. **[업계] 고정 바를 쌓지 말 것.** 헤더 + 배너 + 위젯이 겹겹이 붙으면 빠르게 못 쓰게 됩니다. 고정 바에는 스크롤 중에도 필요한 것만 남깁니다.
4. **[공식] 3~5개 선택지는 세그먼트, 6개 이상은 드롭다운·필터 칩·탭.** SAP Fiori for iOS와 Fluent 2가 공통으로 두는 기준입니다.

### 쌤핀 적용

핵심 질문은 **"스크롤하는 내내 진짜로 계속 보여야 하는 게 뭔가?"**입니다. 세 줄을 이 기준으로 나누면:

| 헤더 요소       | 스크롤 중에도 필요한가                           | 판단        |
| --------------- | ------------------------------------------------ | ----------- |
| 반 선택         | **예** — 지금 누구 명단인지 모르면 오조작 위험   | 고정 유지   |
| 날짜            | **예** — 어느 날 기록인지가 데이터 정합성의 핵심 | 고정 유지   |
| 좌석/명단 토글  | 아니오 — 한 번 정하면 그 화면 내내 유지          | 접거나 이동 |
| 기록보기 아이콘 | 아니오 — 다른 화면으로 나가는 입구               | 접거나 이동 |

**적용 후보: 반 + 날짜를 한 줄로 합치고, 나머지는 스크롤 시 접기.**

한 줄 안에 `[3-2반 ▾]  ← 8/12(화) →  [⋯]` 형태로 두면 3층이 1층이 됩니다. 반 선택은 반이 6개를 넘으면 [공식] 기준상 가로 스크롤 탭보다 **드롭다운(바텀시트)**이 맞습니다. 담임반 1개 + 수업반 N개 구조라 대부분 6개를 넘습니다.

**주의할 점 — 반 선택을 드롭다운으로 바꾸면 현재 선택된 반이 화면에서 덜 눈에 띕니다.** 쌤핀은 반을 잘못 고르면 **다른 반 출결에 기록이 들어가는** 사고가 나는 앱입니다(핸드오프 §5). 그러니 드롭다운으로 바꾸더라도 선택된 반 이름은 굵게, 그리고 출결 입력 화면 진입 시 한 번 더 확인시키는 장치가 필요합니다. 이건 미관 문제가 아니라 데이터 안전 문제입니다.

### 걸러낸 패턴

- **큰 제목이 스크롤에 따라 접히는 iOS Large Title 방식** — 접히는 동안 세로 위치가 계속 움직여서, 30명 명단을 빠르게 훑는 작업과 궁합이 나쁩니다.
- **상단 검색바 상시 노출** — 한 반 30명 규모에서는 스크롤이 검색보다 빠릅니다. 공간만 먹습니다.

## R3. 다수 하위 메뉴 — 더보기 18종 (P3)

### 지금 상태

`MorePage.tsx:56-104`는 메뉴 5줄(메모 · 즐겨찾기 · 쌤도구 · 설정 · 지인 추천)이고, **쌤도구 14종은 "쌤도구"를 눌러 한 단계 더 들어가야** 나옵니다. 검색 없음, 즐겨찾기 없음, 최근 사용 없음.

즉 룰렛을 쓰려면 `더보기 → 쌤도구 → 룰렛`으로 3번 눌러야 하고, 14개 중에서 눈으로 찾아야 합니다.

### 레퍼런스에서 확인한 원칙

1. **[공식] 넘치는 항목은 More 탭으로 흘러가는 게 표준.** HIG는 탭이 넘칠 때 마지막 탭이 More가 되고 나머지를 별도 화면의 리스트로 보여준다고 규정합니다. 즉 **더보기 자체는 정상 패턴**입니다. 문제는 그 안이 평평하다는 것.
2. **[업계] 업무앱은 "고정(pin) · 즐겨찾기 · 최근 사용"으로 푼다.** 엔터프라이즈 UX 패턴 정리에서 반복되는 항목입니다 — 자주 쓰는 페이지를 앞으로 끌어올리고, 사용자가 직접 고정·즐겨찾기·바로가기를 만들 수 있게 합니다.
3. **[업계] 검색 위에 최근 항목을 붙인다.** 검색바를 맨 위에 두고 바로 아래 최근 검색·최근 사용을 노출하는 배치가 표준입니다.
4. **[업계] 초보자와 숙련자를 동시에 지원한다.** 리스트로도 되고 바로가기로도 되는 이중 경로.

### 쌤핀 적용

14종은 성격이 명확히 갈립니다. **한 화면 안에서 그룹으로 나누면 3번 누르던 게 2번이 됩니다.**

| 그룹              | 도구                                                       | 성격                         |
| ----------------- | ---------------------------------------------------------- | ---------------------------- |
| 수업 진행 중 즉시 | 신호등 · 타이머 · 랜덤뽑기 · 주사위 · 동전 · 룰렛 · 점수판 | 수업 중 1~2초 안에 꺼내야 함 |
| 수업 준비·정리    | 모둠편성 · 자리배치 · 수업기호 · 점수배분                  | 앉아서 여유 있게             |
| 수합·평가         | 과제수합 · 설문 · 루브릭 · QR                              | 결과물이 쌓이는 것           |

**적용 후보:**

## R7. 스와이프 빠른 액션 · 되돌리기 · 바텀시트 표준 (P5)

### 지금 상태

### 레퍼런스에서 확인한 원칙 — 스와이프

1. **[공식] 스와이프는 파괴적 동작에만.** NN/g: "Limit contextual swipe to destructive actions." 사용자는 스와이프를 삭제·제거로 기대하지, 추가 동작으로 기대하지 않습니다.
2. **[공식] 발견성이 근본 약점.** "Lack of signifiers makes it unclear where the contextual swipe can be used." — **핵심 동작을 스와이프 뒤에 묻으면 사용자가 발견하지 못합니다.** 스와이프는 항상 지름길이어야 하고, 유일한 경로여선 안 됩니다.
3. **[공식] 스와이프하면 내용이 가려진다.** "swiping to reveal the menu often obscures the content beyond recognition" — 대상이 맞는지 확인할 수 없게 됩니다. 명단처럼 이름이 비슷한 항목이 줄줄이 있는 화면에서 특히 위험합니다.
4. **[공식] 확인을 받거나, 쉬운 되돌리기를 제공.** 반복 동작이면 후자.
5. **[공식] 앱 안에서 스와이프 동작을 일관되게.** Spotify가 같은 제스처를 맥락에 따라 다르게 쓴 게 나쁜 사례로 지목됩니다.
6. **[업계] 방향 의미 구분** — 오른쪽에서 왼쪽(trailing)은 삭제·보관 같은 파괴적/종료 동작, 왼쪽에서 오른쪽(leading)은 고정·읽음·즐겨찾기 같은 비파괴적 지름길.
7. **[업계] 되돌리기는 스낵바로.** Gmail이 보관 후 하단 스낵바에 실행취소를 띄우는 게 모범 사례로 꼽힙니다. 단점은 **되돌리기 창이 짧아 놓칠 수 있다**는 것.

**이 축은 R1~R6과 성격이 다릅니다. 새 화면을 설계하는 게 아니라, 재설계의 전제 조건입니다.**

바텀시트가 17개 파일에 각자 구현되어 있다는 건, 앞으로 R2·R3·R4에서 "이건 바텀시트로 뺀다"고 결정할 때마다 **18번째, 19번째 구현이 늘어난다**는 뜻입니다. 재설계로 오히려 부채가 커집니다.

따라서 **순서상 R7이 먼저입니다.**

1. 바텀시트 공용 부품 1개 (모달/표준 두 모드)
2. 헤더 공용 부품 1개 (3종 통합)
3. 되돌리기 스낵바 공용 부품 1개
4. 그 위에서 R2·R3·R4 재설계

**스와이프에 대한 판단:** [공식] 원칙 1·2에 따라, 쌤핀에서 스와이프는 **삭제 계열에만** 두고 **반드시 같은 동작을 버튼이나 메뉴로도 제공**해야 합니다. 그리고 삭제에는 되돌리기 스낵바가 붙어야 합니다. 이 저장소는 과거에 데이터 소실 신고 이력이 있어서, 되돌릴 수 없는 삭제를 제스처 뒤에 두는 건 특히 위험합니다.

**색 280건에 대해:** 이건 재설계 중에 자연스럽게 줄어드는 게 아니라, 그냥 두면 늘어납니다(149 → 280이 그 증거). 공용 부품을 만들 때 그 부품 안에서 토큰만 쓰면, 부품을 쓰는 화면들이 따라옵니다.

### 걸러낸 패턴

- **양방향 스와이프에 서로 다른 4개 동작 배치** — 발견성 문제가 4배가 됩니다.
- **스와이프로 출결 상태 변경** — R4에서 이미 제외.
- **되돌리기 없는 스와이프 삭제** — [공식] 원칙 4 위반.

## R8. 라우팅과 뒤로가기 (추가 축)

### 지금 상태 — 구조 재설계의 진짜 핵심

`App.tsx:138-165`. 화면 전환이 전부 `useState`입니다.

```ts
const [activeTab, setActiveTab] = useState<MobileTab>('home');
const [studentsSeg, setStudentsSeg] = useState<StudentsSeg>('homeroom');
const [attendanceNav, setAttendanceNav] = useState<AttendanceNav | null>(null);
const [moreSub, setMoreSub] = useState< /* 18개 유니온 */ >(null);
```

**주소가 없어서 안드로이드 하드웨어 뒤로가기가 앱을 종료시킵니다.** 룰렛을 열고 뒤로가기를 누르면 이전 화면이 아니라 앱이 닫힙니다. 바텀시트를 열고 눌러도 마찬가지입니다.

한국 중·고등학교 교사 사용자층에서 안드로이드 비중을 생각하면, 이건 미관 문제가 아니라 **매일 겪는 오작동**입니다.

### 레퍼런스에서 확인한 원칙

1. **[업계] 원인은 명확합니다.** PWA에서는 Cordova식 `backbutton` 이벤트가 없습니다. 브라우저 히스토리에 항목이 없으면 뒤로가기는 그냥 앱을 닫습니다.
2. **[업계] 해법은 History API.** `history.pushState()`로 화면 전환마다 히스토리 항목을 쌓고, `popstate` 이벤트를 뒤로가기로 처리합니다. 히스토리 상태에 `depth` 같은 값을 넣어 되돌아갈 데가 있는지 판단할 수 있습니다.
3. **[업계] 다만 이 API는 함정이 많습니다.** 여러 논의에서 공통으로 "복잡하고 주의사항이 많다"고 경고합니다.

### 쌤핀 적용

**이 축이 "마감 공사가 아니라 구조 재설계"라는 사용자 결정의 실질적 내용입니다.** 색과 팝업을 통일해도 뒤로가기는 안 고쳐집니다. 라우터를 넣어야만 고쳐집니다.

주소 체계 초안(논의용):

```
/                     홈
/students/homeroom    학생 - 담임
/students/teaching    학생 - 수업
/attendance/:classId  출결 입력 (전체화면)
/schedule             일정
/schedule/todo        일정 - 할 일
/more                 더보기
/more/tools           쌤도구 목록
/more/tools/:toolId   개별 도구 (14종을 유니온 18개에서 파라미터 1개로)
```

**이렇게 하면 부수 효과가 큽니다.** `moreSub`의 18개 유니온 타입이 `:toolId` 하나로 접히고, R3에서 도구를 그룹으로 재배치하거나 새 도구를 추가할 때 `App.tsx`를 건드릴 필요가 없어집니다.

**바텀시트도 히스토리에 포함해야 합니다** — 시트를 열고 뒤로가기를 누르면 시트만 닫히는 게 안드로이드 사용자의 기대입니다. 이건 R7의 공용 바텀시트 부품 안에서 한 번만 구현하면 전부 적용됩니다. **R7과 R8은 같이 가야 하는 짝입니다.**

**위험 요소:** 라우터 도입은 "화면 조립 층만 바꾼다"는 무손상 경계선 안에 있지만, `App.tsx`가 36회 수정된 핫 패스라 다른 세션과 충돌 위험이 가장 높은 파일입니다. 착수 시점에 다른 세션이 이 파일을 만지고 있지 않은지 확인이 필요합니다.

### 걸러낸 패턴

- **뒤로가기 두 번 눌러야 종료(toast 안내)** — 라우터 없이 종료만 막는 임시방편. 근본 원인을 안 고치고 증상만 가립니다.

## 2. 조사 전체에서 반복해서 나온 원칙 5개

축을 따로 조사했는데 같은 얘기가 계속 나왔습니다. 재설계 판단 기준으로 쓸 만합니다.

1. **고정 영역은 "스크롤하는 내내 진짜 필요한 것"만.** (R2 · R4 · R6) — 나머지는 접거나 옮깁니다.
2. **기본값이 대다수에게 맞아야 한다. 커스터마이즈는 그 위에 얹는 것이지 대체재가 아니다.** (R4 · R5)
3. **제스처는 지름길이지 유일한 길이 아니다.** (R4 · R7) — 스와이프로만 되는 동작을 만들지 않습니다.
4. **탭은 "어디에 있나", 세그먼트는 "어느 버전인가", 메뉴는 "또 뭐가 있나".** (R1 · R2 · R6)
5. **빈도가 높은 작업이 얕은 계층에 있어야 한다.** (R1 · R3 · R4) — 지금 쌤핀은 이게 뒤집혀 있습니다.

## 4. 다음 세션에서 사용자가 정해야 할 것

재설계안을 만들려면 아래 결정이 필요합니다. 제가 임의로 정하지 않았습니다.

1. **탭 4개 유지 vs 5개로 늘려 출결 승격** (R1) — 판단 재료: 하루에 출결 화면을 몇 번 여시나요?
2. **반 선택을 가로 스크롤 탭에서 드롭다운으로 바꿀 것인가** (R2) — 공간은 크게 줄지만 선택된 반이 덜 눈에 띕니다. 오조작 위험과의 거래입니다.
3. **출결을 예외 입력 방식으로 바꿀 것인가** (R4) — 화면 길이 약 57% 감소(3,180px → 1,350px, 목업 실측) 대 "전원이 보이던 5버튼"의 익숙함 상실.
4. **홈 카드 숨김/순서 변경 기능을 넣을 것인가** (R5) — 넣는다면 설정에서만.
5. **작업 단위를 어떻게 자를 것인가** — 이 저장소는 한 세션 한 작업 단위 원칙이고, 라우터 도입은 그 자체로 한 단위입니다.
6. **Mobbin을 열 것인가** — 열면 [관측] 등급 항목(Fantastical 티커 뷰, Epic Rover 흐름, Connecteam 탭 구조)을 스크린샷으로 확정할 수 있습니다. 안 열어도 [공식]·[업계] 근거만으로 진행 가능합니다.
