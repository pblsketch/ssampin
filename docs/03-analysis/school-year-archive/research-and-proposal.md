# 학년도·학기 전환 · 보관함(아카이브) — 조사 보고 및 설계 제안 v0.2

작성: 2026-08-06 · v0.2: 학기 단위 전환 요구 반영(2단 시간 축) · 상태: 조사 완료, 방향 제안 (구현 착수 전 사용자 결정 필요 항목 §10)

## 1. 배경과 목표

새 학년도가 되면 교사는 가르치는 학생·과목·담임 반이 달라진다. **학기가 바뀔 때도** 시간표가 갱신되고, 특히 고교학점제 고등학교는 선택과목 수업반이 학기 단위로 통째로 바뀐다. 요구사항:

1. **기존 기록은 삭제가 아니라 보관** — 언제든 다시 열람 가능
2. **새 학년도(또는 새 학기)는 새로운 환경에서 시작**
3. **사용자 친화적 UI/UX**
4. **학기 단위 변화도 지원** — 학년도 전면 전환보다 가벼운 장치로

이를 위해 4트랙 병렬 조사를 수행했다: ①쌤핀 내부 데이터 구조 ②해외 교사용 서비스 사례 ③국내 서비스 사례 + 한국 학사·개인정보 규범 ④범용 아카이브 UX 패턴.

## 2. 결정적 내부 발견 — 쌤핀에는 "학년도" 개념이 전혀 없다

내부 코드 전수 조사 결과 (상세 근거는 §9):

- **`schoolYear` 필드가 코드베이스 어디에도 없다.** 약 50개 저장 파일(동기화 30 + 로컬 전용 20)이 전부 "현재 것 하나"만 가정한다.
- **2년차 사용 시 실제 사고가 확정돼 있다:**
  - 수업반 학생 식별키가 `학년-반-번호` 문자열(`TeachingClass.ts:22-27`) → 새 학년도에 **같은 키가 다른 학생을 가리켜** 출결·관찰·성적분석 기록이 뒤섞인다.
  - 성적 분석은 `semester: '1'|'2'`만 있고 연도가 없어(`GradeAnalysis.ts:27,79`) 2년째 1학기에 **작년 1학기와 충돌**한다.
  - 상담은 `studentNumber`만 참조 → 새 학년 같은 번호의 다른 학생과 조용히 섞인다.
- 즉 이 기능은 "있으면 좋은 편의"가 아니라 **2년차 사용을 위한 필수 인프라**다.
- 참고할 내부 선례: 학년도 경계 계산(3~8월=1학기, 9~12월=2학기, **1~2월=직전 학년도 2학기**)이 `useAiBridgeConsentStore.ts:40-58`에 유일하게 구현돼 있다. 이 규칙을 domain rule로 승격하는 것이 자연스럽다.

**공통 패턴 5가지:**

1. **"작년 반 재사용 금지, 보관 + 새로 만들기"가 업계 표준** (ClassDojo·Seesaw는 명문 권고)
2. 트리거는 **수동 + 시즌 가이드**(완전 자동은 없음)
3. 보관 = **읽기 전용 + 별도 '보관함' 목록 + 언제든 복원**
4. **삭제와 보관은 강하게 분리** (Classroom: 보관해야만 삭제 버튼이 열림)
5. 이력은 **학생 단위로 승계**, 교사 자산은 "구조 복사"로 이월

## 4. 국내 서비스 사례 + 한국 학사·개인정보 규범

- **국내 표준은 "새 클래스 수동 개설 + 전원 재가입"** — 클래스팅·하이클래스 모두 연도 속성으로 클래스를 구분하고, 지난 클래스는 삭제 전까지 계정에 남는 "소극적 보관". 전용 보관함 UI는 드물다.
- **유일한 자동 이관형이던 아이엠티처(나이스 반편성 기반 진급처리)는 2026-02-28 서비스 종료** — 종료 안내의 백업 수단이 "화면 캡처"였다는 점이 구조화된 보관·내보내기의 가치를 역설한다.
- **학년도는 법으로 고정**: 초·중등교육법 제24조① "학년도는 3월 1일부터 다음 해 2월 말일까지" → **전환 시점을 사용자에게 물을 필요 없이 2월 말~3월 초로 예측 가능**. NEIS도 학년말(2월) 마감 → 새 학년 반배정은 2월 말에야 조회 가능한 리듬.
- **학기 경계도 법정**: 시행령 제44조 — 2학기는 1학기 종료일 다음 날부터 다음 해 2월 말일까지(통상 8월 말~9월 초 개학). 고교학점제 고등학교는 선택과목 수업반이 **학기 단위로 재편성**되는 경우가 흔함 → 교과 축 데이터의 자연 수명은 학년도가 아니라 학기.
- **단, 담임 축은 학기에서 끊으면 안 됨**: 출결 통계와 학교생활기록부는 **학년도 단위** 집계(기재요령·별표 8 — [[feedback_verify_regulation_before_impl]] 확인 원칙과 동일 맥락). 담임 명렬·출결·누가기록은 1·2학기를 관통해 연속되어야 한다.
- **개인정보 관점**: 교육부 개인정보 보호지침(훈령 제476호) — 목적 달성 시 지체 없이 파기가 원칙. 학급 운영 데이터는 학년도 종료 = 목적 달성으로 해석되는 게 표준. → **"보관할 것/지울 것을 교사가 명시적으로 선택하는 정리 플로우"는 규범 친화적이며 오히려 권장 근거가 있다.** (쌤핀은 로컬 저장이라 상용 클라우드보다 유리한 위치)
- 3월 첫 2주는 고객 문의가 급증하는 시기(클래스팅 공식 공지) — 전환 UX가 나쁘면 지원 부담이 그대로 늘어난다.

주요 출처: law.go.kr(초·중등교육법 §24, 시행령 §44) · support.classting.com · 여천고 하이클래스 가정통신문 PDF(직접 판독) · iamservice.oc.toast.com(아이엠스쿨 종료 안내) · law.go.kr(교육부훈령 제476호) · privacy.moe.go.kr

## 5. UX 원칙 체크리스트 (근거 출처 병기)

1. **보관 = 숨김, 삭제 아님을 언어로 고정** — 항상 다른 동사·버튼·색. "기록은 그대로 남고 언제든 다시 볼 수 있어요" 명시 (Slack, Notion)
2. **영구 삭제는 보관을 거쳐야만 가능**(2단계 게이트) (Trello, Google Classroom)
3. **보관물 열람은 상설 진입점** — 사이드바/설정의 "지난 학년도 보관함", 무기한 보존 (Trello Archived items, Asana)
4. **복원은 원클릭 + 전체 데이터 보존 보증 문구** (Notion Unarchive 배너, Todoist)
5. **학년도 전환은 단일 버튼이 아닌 소형 마법사** — 연 1회 수행되는 드물고 큰 작업은 마법사가 정석 (NN/g Wizards, TeamSnap Archive Season, Toddle)
6. **확인 다이얼로그는 구체적 문구 + 행동형 버튼**("보관하고 새 학년도 시작") — "정말요?" 금지, 가역 작업엔 Undo (NN/g Confirmation Dialogs)
7. **전환 직후 빈 화면은 정보형 빈 상태** — "2025학년도 기록은 보관함에 안전하게 있어요 [보관함 열기]" (Pencil&Paper Empty States; 반면교사: PowerSchool은 보관 후 열람성이 깨져 "PDF로 따로 저장하라"는 불신 발생)

**가장 닮은 모델 = YNAB "Fresh Start"(가계부)**: 새해에 새 예산으로 시작하되 옛 예산은 통째 보존되어 언제든 다시 열람, **구조(카테고리·계정)는 승계하고 기록만 리셋**, "마음이 바뀌면 그냥 돌아가면 된다"는 안심 카피. (ynab.com/blog/the-logic-art-of-a-ynab-fresh-start)

## 6. 제안 설계 (요약)

### 6.1 개념 모델 — 2단 시간 축

- **학기(term)를 최소 단위로 도입**: 라벨 `'2026-1'`(학년도-학기) — 내부 선례 `useAiBridgeConsentStore.ts:40-58`의 형식 그대로(3~8월=1학기, 9~2월=2학기, 1~2월=직전 학년도). 이 계산을 domain rule로 승격.
- **두 축의 수명이 다르다:**

| 축      | 데이터                                    | 자연 수명                                                           | 전환 장치              |
| ------- | ----------------------------------------- | ------------------------------------------------------------------- | ---------------------- |
| 담임 축 | 명렬·담임 출결·누가기록·좌석·생기부 초안  | **학년도** (출결 통계·생기부가 학년도 단위 — 학기에서 끊으면 안 됨) | 학년도 마무리 마법사   |
| 교과 축 | 수업반·진도·수업 관찰기록·루브릭·성적분석 | **학기** (고교학점제 재편성, 시간표 갱신)                           | 수업반 단위 보관(경량) |

- 설정에 `settings.schoolYear` 추가(온보딩·마법사에서 결정, 기본값은 오늘 날짜로 계산). epoch 스탬프도 처음부터 **학기 입도**(`'2026-1'`)로 설계 — 학년도 입도로 만들면 학기 요구를 못 담는다.

### 6.2 두 개의 전환 장치 (경량 + 전면)

**(A) 수업반 단위 보관 — 학기 대응, 경량 (먼저 출시 가능)**

- `TeachingClass`에 `archived`/`archivedAt` 플래그 추가 — 앱 내 기존 선례 그대로(`Memo.archived`, `Notebook.archived`, `Bookmark.archivedAt`).
- 보관된 수업반은 활성 목록·위젯·입력 화면에서 사라지고, 수업반 목록 하단 "보관된 수업반" 접이식 섹션에서 **읽기 전용**으로 열람(출결·진도·관찰기록은 라이브 파일에 그대로 있으므로 기존 화면 재사용 + 읽기 전용 배지). 복원(보관 해제) 원클릭.
- **파일 이동이 없으므로 동기화 부활 문제도 없다** — 플래그가 일반 데이터처럼 동기화됨. epoch 기반 장치 없이 독립 출시 가능.
- 학기 전환 시나리오: 2학기 개학 시 "1학기에만 있던 수업반"을 골라 보관 → 새 수업반 생성(기존 흐름). 학기 시즌 배너(8월 말~9월 중순)가 이 동선을 안내.
- Additio "그룹 아카이브"·iDoceo "숨김/폴더"와 동일한 모델. 학기 중 담당 변경·폐강 등 **비정기 변화도 커버**(시즌과 무관하게 언제든 보관 가능).

**(B) 학년도 마무리 마법사 — 전면 전환 (스냅샷 아카이브)**
두 가지 선택지 중:

- **(a) 스냅샷 방식(권고)**: 전환 시점에 학생·반 스코프 파일(약 16개 + 관찰 첨부 바이너리)을 `data/archives/{2025-2}/`(당시 학기 라벨)로 통째 복사 + 매니페스트(라벨, 시각, 앱 버전, 건수) 기록 → 라이브 파일 리셋(보관된 수업반 포함 전부). 기존 backupManager 패턴 재사용 가능, 라이브 코드 무수정으로 "원형 그대로 열람" 보장. 보관함 뷰어는 라벨을 학년도로 묶어 표시.
- (b) 전 엔티티에 `schoolYear` 필드 추가: 30+ 엔티티·300+ 호출처 수정 — 위험 대비 이득 없음. **기각.**
- 담임이 학기 중 바뀌는 드문 경우(휴직·복직 등)도 마법사를 아무 때나 실행할 수 있으므로 커버된다.

### 6.3 사용자 플로우

1. **시즌 배너 2회** (기존 App.tsx 새 학기 토스트 자리 확장, 강제 없음):
   - **8월 말~9월 중순(2학기)**: "2학기 준비 — 끝난 수업반은 보관하고 새 수업반을 만들어 보세요" → 경량 동선(A)
   - **2/15~3/15(새 학년도)**: "새 학년도를 준비할 시간이에요 → [학년도 마무리 시작]" → 전면 마법사(B). 설정 > 백업 탭 옆에서 언제든 수동 실행 가능.
2. **학년도 마무리 마법사** (4단계, 진행 표시, 중간 이탈·이어하기 허용):
   - ① 안내: 무엇이 보관되고(학생·출결·기록·진도·좌석…) 무엇이 유지되는지(설정·서식·노트·즐겨찾기…) 명시
   - ② 정리 선택: 도메인별 "보관"(기본) vs "파기" — 개인정보 규범 친화 옵션, 파기는 별도 확인
   - ③ 새 학년도 프로필: 학교/담임 여부(teacherRoles)/담임 반/교시 재확인 — 미니 온보딩 재사용. 시간표 틀·수업반 틀 승계 여부 선택(Additio "구조 복사" 모델)
   - ④ 요약 + 실행: 버튼 문구 "2025학년도를 보관하고 2026학년도 시작하기". 실행 직후 **"전환 취소"**(스냅샷 원복) 제공.
3. **전환 직후 빈 상태**: 주요 화면에 "2025학년도 기록은 보관함에 있어요 [보관함 열기]".
4. **보관함 뷰어**: 사이드바/설정 상설 진입점 "지난 학년도 보관함" → 연도 선택 → **읽기 전용** 열람. MVP 범위는 교사가 실제로 다시 찾는 것 우선: 학생 명렬·누가기록·관찰기록(첨부 포함)·출결 통계·진도. 검색 지원.

### 6.4 데이터 메커니즘 (안전 순서)

1. safety backup 생성(기존 `createSafetyBackup` 재사용)
2. `data/archives/{year}/`로 대상 파일 + 바이너리(obs-attachments 등) 복사 + 매니페스트
3. 라이브 파일 리셋 — **단, 병합형 3도메인(출결·학생기록·관찰)은 단순 비우기 금지**(§7-①) → 파일에 학기 입도 epoch 스탬프(`'2026-1'`)를 도입하고 병합 규칙을 "다른 epoch끼리는 병합하지 않음, 낮은 epoch 사본은 그 기기에서 아카이브로 이동"으로 확장
4. 아카이브는 수동 백업(.ssampin-backup.json)에 자동 포함(파일명 화이트리스트 통과 확인됨), startup 스냅샷 14일 TTL과는 완전 별개의 영구 보존

### 6.5 동기화 전략 (단계적)

- **Phase 1**: 아카이브 파일 자체는 로컬 보관 + 수동 백업 포함. 라이브 리셋은 epoch 스탬프로 전 기기·모바일에 안전 전파(옛 사본 부활 차단).
- **Phase 2**: 아카이브 폴더도 Drive 업로드 → 다른 기기·새 PC에서도 보관함 열람.

### 6.6 로드맵 (시급성 반영 — 가장 가까운 전환 이벤트는 **2026년 9월 2학기 개학**)

- **P0 (기반)**: 학기 계산(`'2026-1'`) domain rule 승격 + `settings.schoolYear` + grade-analysis 연도 축 수선
- **P1 (경량, 2학기 개학 전 목표)**: **수업반 단위 보관** — `TeachingClass.archived` 플래그 + 보관 섹션 + 읽기 전용 배지 + 복원 + 2학기 시즌 배너. epoch 불필요, 독립 출시 가능.
- **P2 (전면, 2027년 2월 전 목표)**: 학년도 마무리 마법사 + 스냅샷 아카이브 + 라이브 리셋 + **동기화 epoch 가드**(학기 입도) + 빈 상태
- **P3 (열람)**: 보관함 뷰어(읽기 전용, 학년도→학기 그룹핑) + 사이드바 진입점
- **P4 (확장)**: 구조 승계 옵션 고도화 · 모바일 보관함 · 아카이브 Drive 동기화 · "학생 승계"(동일 학생 연속 담임 시 기록 연결 — rosterImportPlan 매칭 패턴 재사용)

## 7. 반드시 피해야 할 함정 (내부 조사 확정분)

① **동기화 부활**: 출결·학생기록·관찰기록은 파일 교체가 아닌 레코드 병합(`SyncFromCloud.ts:490-527`) — 그냥 비우면 다른 기기 사본이 전부 되살아난다. epoch 가드가 전면 전환(P2)의 전제조건. (수업반 보관 플래그(P1)는 파일을 비우지 않으므로 해당 없음)
② **툼스톤 축 불일치**: 관찰만 `deletedAt`이 number(ms), 나머지는 ISO 문자열 — 공통 유틸에서 통일 시도 금지.
③ **바이너리 고아**: 관찰 첨부·스티커·서식은 현행 백업에서도 제외 — 아카이브에 명시 포함 필요.
④ **원격 병행 도메인**: 상담(Supabase)·담벼락·메모공유는 로컬만 보관하면 원격과 어긋남 — Phase 분리 취급.
⑤ **electron ↔ domain 분리**: electron은 domain을 import 못 함(rootDir) — 아카이브 규칙은 backupRules처럼 의도적 미러 유지.
⑥ **렌더러에 파일 나열 IPC 없음**: 아카이브 조작에는 새 IPC 필요(`security-guards` 메타테스트 대응 포함).
⑦ **reload 시 `loaded:false` 금지**(편집 중 입력 소실) — 전환 후 스토어 리셋도 같은 함정.
⑧ **`.backup.json` 1세대는 즉시 덮임** — 대량 write 전 safety backup 선행 필수.
⑨ localStorage 명렬(`ssampin_class-rosters`)은 백업·동기화 사각지대 — 보관 범위 결정 필요.

## 10. 미결정 사항 (사용자 결정 필요)

1. **P1(수업반 단위 보관)을 2학기 개학 전 우선 출시**하는 로드맵에 동의하는지 — 전면 마법사는 내년 2월 전 완성으로 분리.
2. **아카이브 Drive 동기화 시점** — 스냅샷 아카이브는 로컬만으로 출발(권고)할지, 처음부터 기기 간 열람 필수인지. (수업반 보관 플래그는 자동으로 동기화됨)
3. **보관함 뷰어 MVP 범위** — 권고: 명렬 + 누가기록 + 관찰(첨부) + 출결 통계 + 진도. 좌석·설문·과제까지 포함할지.
4. **"파기" 옵션 노출 여부** — 규범 친화적이지만 복잡도 증가. 마법사 v1에서는 "전부 보관" 고정 + 보관함에서 연도 단위 삭제(2단계 게이트)로 시작하는 축소안도 가능.
5. **상담(Supabase 원격) 처리** — 보관 범위에서 제외하고 별도 트랙으로 미룰지.
6. 시즌 배너 노출 기간(권고: 2학기 8/25~9/15, 새 학년도 2/15~3/15).
