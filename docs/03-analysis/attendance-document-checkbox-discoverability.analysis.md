# 출결 증빙서류 체크박스 발견성 분석

작성일: 2026-08-27
계기: 사용자 피드백 — "출결 사유 입력란 아래에 증빙서류 제출 여부 체크박스가 안 보이면 어떻게 해야 하죠?"
범위: 담임 출결/기록 탭, 수업관리 출결, 설정, 모바일, 사용자 가이드
성격: 진단만. 구현·수정 없음.

## 0. 결론 먼저

피드백은 **오작동 신고가 아니라 정확한 관찰**이다. 사용자가 말한 위치(출결 사유 입력란 아래)에는
증빙서류 체크박스가 **애초에 존재한 적이 없다**. 그리고 실제로 존재하는 곳들은 전부
기본 설정에서 **가장 흔한 출결(질병 결석)에 대해 아무것도 렌더하지 않는다.**

원인은 단일 버그가 아니라 4겹이다.

| #   | 층        | 한 줄 요약                                                                                     |
| --- | --------- | ---------------------------------------------------------------------------------------------- |
| A   | 배치      | 입력 화면 4곳 전부에 체크박스 없음. 유일한 체크박스는 "수정" 진입 후 두 블록 아래              |
| B   | 기본값    | 기본 정책이 '출석인정'만 → 질병 결석은 배지·배너·검토·통계·필터 **5개 표면에서 동시에 사라짐** |
| C   | 명명      | 같은 개념을 화면마다 4가지 이름으로 부름. 화면 어디에도 "증빙서류"라는 단어가 없음             |
| D   | 도달 경로 | 켜는 스위치가 설정 5뎁스 안쪽, 그것도 "기록 알림"이라는 무관해 보이는 이름 아래                |

이 중 **B가 지배적 원인**이다. A/C/D가 없어도 B만으로 동일한 피드백이 나온다.

다만 **B의 해법은 기본값을 바꾸는 게 아니다.** 학교마다 서류 규정이 달라 앱이 정답을 고를 수 없다
(오너 결정 2026-08-27). 고쳐야 할 것은 기본값이 아니라, 정책 밖일 때 앱이 **아무 말도 하지 않는** 것이다.
**채택 방향(§9)**: 정책 매트릭스로 미리 걸러내지 말고, **모든 출결에 서류 상태를 상시 표시**하고
**제출 완료 / 미제출 / 제출 대상 아님** 3상태를 선생님이 직접 관리한다.
→ **최종 결정은 §11**(2상태 + 학교 설정). §9·§10의 3상태 안은 철회됐고 판단 근거로만 남긴다.

## 1. 근거 — A. 입력 화면에는 체크박스가 없다

출결을 **입력**하는 경로는 4개다. 네 곳 모두 사유 입력란 아래에 서류 관련 UI가 없다.

| 경로                | 파일:라인                                                                      | 사유 입력란 **바로 아래**에 있는 것                   |
| ------------------- | ------------------------------------------------------------------------------ | ----------------------------------------------------- |
| 담임 출결 탭 팔레트 | `src/adapters/components/Homeroom/Records/HomeroomAttendanceGrid.tsx:706-733`  | "비고" 텍스트 입력 → 안내 문구                        |
| 여러 날짜 일괄 입력 | `src/adapters/components/Homeroom/Records/MultiDayAttendancePanel.tsx:276-303` | "비고" → "그날 기존 출결을 지우고 새로 넣기" 체크박스 |
| 누가기록 입력기     | `src/adapters/components/Homeroom/Records/StudentRecordsEditor.tsx:580-601`    | 곧바로 "내용" textarea                                |
| 수업관리 출결       | `src/adapters/components/ClassManagement/ClassRecordInputView.tsx:599-630`     | "사유 메모" → 저장 버튼                               |

검증: 위 4개 파일에서 `서류` / `documentSubmitted` 문자열 **0건**
(`HomeroomAttendanceGrid.tsx:531`의 `document.activeElement`는 브라우저 DOM API로 무관).

체크박스가 실재하는 유일한 위치는 **인라인 수정기**다.

- `src/adapters/components/Homeroom/Records/InlineRecordEditor.tsx:319-332`
- 라벨: **"출결 서류 제출 확인"**
- 위치: 사유 칩(`:231-236`) → **메모**(`:282-294`) → **첨부 자료**(`:296-302`) → 나이스 반영(`:305-318`) → 서류(`:319`)

즉 사용자가 기대한 "사유 바로 아래"에서 **두 블록 아래**, 그리고 기록을 **저장한 뒤 다시 [수정]으로
들어가야** 나온다. 입력 시점에는 존재하지 않는 선택지다.

또한 이 체크박스는 정책 게이트를 **거치지 않는다**(`:319`의 조건은 `isAttendance && setEditDocumentSubmitted`뿐).
→ 질병 결석에서도 체크는 되지만, 체크한 결과가 배지·배너·통계 어디에도 나타나지 않는다.
**"체크는 되는데 아무 데도 안 보인다"**는 가장 나쁜 조합이다.

## 2. 근거 — B. 기본 정책이 질병 결석을 전 표면에서 숨긴다 (지배 원인)

```
// src/domain/rules/attendanceDocumentPolicy.ts:44
export const DEFAULT_ATTENDANCE_DOCUMENT_POLICY = { requiredBy: { 인정: ALL_DOC_STATUSES } };
```

`requiresDocument()`가 false면 아래 **5개 표면이 동시에** 침묵한다.

| 표면                    | 파일:라인                           | 게이트 통과 못 하면                   |
| ----------------------- | ----------------------------------- | ------------------------------------- |
| 목록 서류 배지          | `DefaultRecordListView.tsx:158-164` | 배지 자체가 렌더 안 됨                |
| 타임라인 서류 배지      | `StudentTimelineView.tsx:186-192`   | 배지 자체가 렌더 안 됨                |
| 검토 큐                 | `useReviewQueue.ts:85-98`           | 큐에서 제외 → 종류별 체크칩도 안 나옴 |
| 미제출 배너             | `AttendanceStatusBanners.tsx:50-57` | 카운트에서 제외                       |
| 통계 서류 완료율        | `ProgressMode.tsx:764, 910`         | 분모에서 제외                         |
| 조회 '서류 미제출' 필터 | `useRecordFilters.ts:142-148`       | 필터에 안 걸림                        |

`ATTENDANCE_REASONS = ['질병', '인정', '미인정', '기타']` (`RecordCategory.ts:19`) 중
실사용 빈도 1위인 **질병**이 기본값에서 빠져 있다. 진단서·처방전을 걷는 학교의 교사에게는
**앱 전체가 서류 기능을 갖고 있지 않은 것처럼 보인다.**

이건 예견된 위험이었고, 계획 단계에서 **미해결로 남아 있다.**

```
docs/01-plan/features/attendance-neis-audit-suite.plan.md:315
- [ ] D 기본 서류요구 정책 기본값 — '출석인정만 요구'가 학교 방침 기본으로 타당한지 규정 확인.
      왜 중요: 과다/과소 카운트 양방향 회귀 방지.
```

체크박스가 비어 있다. 이번 피드백이 그 미해결 질문의 **실사용 답변**이다.
(당시 배경: `AttendanceStatusBanners`가 모든 출결을 '서류 필요'로 세던 **과다 카운트**를 잡는 게 M4의 목표였고,
그 반작용으로 기본값을 최대한 보수적으로 잡았다 — plan.md:18, :265. 과다는 잡혔지만 **과소로 넘어갔다.**)

## 5. 부수 발견 (이번 피드백의 직접 원인은 아니지만 같은 뿌리)

### 5-1. 모바일 전면 미지원

`src/mobile/` 전체에서 `documentSubmitted` / `증빙` / `서류` **0건**.
m.ssampin.com에서는 서류 상태를 **보지도, 체크하지도** 못한다.

### 5-2. 두 가지 입력 방식이 서로 다른 화면에 흩어져 있다

- boolean 단일 토글 — 인라인 수정 체크박스, 배지 클릭, 배너 일괄 처리
- 종류별 3칩(신청서/보고서/증빙자료) — **`ReviewMode` 검토 화면에만 존재**

사용자 가이드(`docs.ts:575`)는 **종류별 목록만** 설명한다. 그런데 그 목록은
`조회 탭 → [검토] 세그먼트`(`SearchMode.tsx:42, 212-221`)로 전환해야 나오고,
거기서도 `requiresDocument` 통과 기록만 나온다. **가이드가 약속한 화면에 실제로 도달하기가 어렵다.**

데이터 동기화 자체는 정상이다 — 파생 불변식이 도메인·유스케이스·스토어 3곳에서 일관되게 지켜진다
(`attendanceDocumentPolicy.ts:deriveDocumentSubmitted`, `UpdateAttendancePeriods.ts:74-93`,
`ManageStudentRecords.ts:121-123`, `useStudentRecordsStore.ts:409-448`). **모델이 아니라 표면의 문제다.**

### 5-3. 코드 주석이 실제와 어긋나 진단을 오도한다

```
// AttendanceStatusBanners.tsx:12
// 출결 탭(AttendanceMode)과 통계 탭(ProgressMode)이 공유하는 단일 컴포넌트.
```

실제 사용처는 **`ProgressMode.tsx:1063` 한 곳뿐**이다.
`git log -S "AttendanceStatusBanners" -- AttendanceMode.tsx` → **커밋 0건** (한 번도 들어간 적 없음).
→ **출결 탭에는 서류 미제출 배너가 없다.** 출결을 입력하는 화면에서 서류를 상기시키는 장치가 0개라는 뜻이다.

## 6. 사용자 여정 재구성 (피드백 작성자가 실제로 겪은 것)

가정: 질병 결석에 진단서를 걷는 학교의 담임.

1. 가이드에서 "증빙서류가 필요한 출결에는 신청서·보고서·증빙자료를 종류별로 체크하는 목록이 있다"를 읽음
2. 출결 탭에서 질병 결석 입력 → 사유 칩 아래에 비고 입력칸뿐. 서류 관련 없음 → **1차 실패**
3. 저장된 기록을 조회에서 찾아 [수정] → 스크롤 → "출결 서류 제출 확인" 발견, 체크 → 저장
4. 목록으로 돌아옴 → **배지 없음**. 통계 → **서류 완료율에 안 잡힘**. 검토 → **목록에 없음** → **2차 실패**
   (정책 게이트 밖이라 체크는 저장됐지만 어디에도 표시되지 않음 — §1 마지막 문단)
5. 검토 탭에서 신청서/보고서/증빙자료 칩을 찾음 → 그 기록이 큐에 없어서 **안 보임** → **3차 실패**
6. "체크박스가 안 보이는데 어떻게 하죠?" 라고 문의

**단계마다 앱은 조용하다.** 정책 게이트 밖이라는 사실을 알려주는 문구가 한 군데도 없다.

## 7. 개선 방향 후보 — **제약: 학교마다 서류 규정이 다르다**

> **상태: §9로 대체됨(2026-08-27).** 오너가 '정책 게이트를 표시 경로에서 걷어내고 모든 출결에
> 3상태를 상시 표시'하는 방향을 택했다. 아래 A~H는 정책 게이트를 **전제로** 한 안이므로
> A·B는 §9에 흡수되고 F(이름 통일)만 독립 유효하다. 판단 근거로 남겨 둔다.

### 7-0. 제약이 바꾸는 것

오너 결정(2026-08-27): **기본값을 규정 근거로 재확정하는 안(구 7-1)은 폐기.**
학교마다 서류 규정이 달라 앱이 정답을 고를 수 없다.

이 제약은 문제를 좁히는 게 아니라 **다시 정의한다.**

> 앱이 규정을 알 수 없다면, 고쳐야 할 것은 **기본값**이 아니라 **침묵**이다.
> 지금 앱은 모르는 걸 모른다고 말하지 않고, 그냥 아무것도 안 그린다.

따라서 아래 안은 전부 **규정 가정 0**을 만족한다. 어떤 학교가 무엇을 걷는지 앱은 끝까지 모른 채로 동작한다.

### 7-3. 권고 조합 — **A + B + F, 이어서 C**

세 개를 합치면 §6 여정의 실패 3곳이 순서대로 닫힌다. 셋 다 소규모이고 규정을 하나도 가정하지 않는다.

| §6 실패                                    | 닫는 안 | 닫히는 방식                                                                          |
| ------------------------------------------ | ------- | ------------------------------------------------------------------------------------ |
| 2차 실패 — 체크했는데 배지·통계에서 사라짐 | **A**   | 체크한 기록은 정책 밖이어도 배지가 남는다. 선생님이 한 일이 화면에서 지워지지 않는다 |
| 1·3차 실패 — 왜 없는지 알 수 없음          | **B**   | 체크박스 바로 옆에서 "안 세는 중"이라고 말하고, 바꾸는 곳으로 데려간다               |
| 가이드의 단어가 화면에 없음                | **F**   | "증빙서류"로 검색·훑기가 가능해진다                                                  |

**C(행동 학습)는 A·B 적용 후 별도 단위.** A·B만으로 "보이고 도달 가능"해지므로,
C는 "매번 설정 가는 수고"를 줄이는 최적화다. 먼저 넣으면 A·B 없이 토스트만 뜨는 어색한 상태가 된다.

**D는 실사용 확인 후 판단.** 매트릭스(사유×상태)로 표현 안 되는 규정을 실제로 쓰는 학교가 있는지가
채택 조건이다. 스키마 확장은 동기화 계약을 건드리므로 추측으로 착수하지 않는다.

**E·G는 A·B와 목적이 겹친다.** A·B가 "필요한 순간에 필요한 자리"에서 해결하므로,
상시 칩(E)·초기 배너(G)는 화면 예산 대비 이득이 작다. A·B 적용 후에도 문의가 이어지면 재검토.

## 9. 방향 재검토 — **모든 출결에 서류 상태를 상시 표시 + 3상태 관리** (오너 안, 2026-08-27)

> **상태: §11로 철회됨.** '대상 아님' 상태를 빼기로 하면서 2상태로 되돌아갔다. 근거로만 남긴다.

### 9-0. 제안 내용

> "질병 결석이든 질병 지각이든 **기본으로 증빙서류 제출 여부를 표시**하게 하는 게 나은 것 같다.
> 그리고 **서류를 제출하였는지, 제출 대상이 아닌지**를 체크해서 관리하게 하는 거지."

정리하면 — 정책 매트릭스로 **미리 걸러내지 말고**, 모든 출결에 서류 칸을 만들고
선생님이 상태를 직접 정한다. 상태는 3개다.

| 상태               | 의미                              |
| ------------------ | --------------------------------- |
| **미제출**         | 서류를 걷어야 하는데 아직 안 받음 |
| **제출 완료**      | 받음                              |
| **제출 대상 아님** | 이 출결은 서류를 걷지 않음        |

§7의 A~H는 **정책 게이트를 전제로** 그 주변을 손보는 안이었다. 9안은 **게이트 자체를 표시 경로에서 걷어낸다.**
§7-3 권고(A+B+F)는 이 안에 흡수된다 — A(표시/집계 분리)는 9안의 부분집합이고, B(안내 문구)는 상태가
눈에 보이면 불필요해진다. F(이름 통일)만 독립적으로 유효하다.

### 9-1. 이 방향이 옳은 근거

**(1) 지금 나이스 배지와 서류 배지가 비대칭이다.**

`DefaultRecordListView.tsx:150-165` — 같은 자리, 같은 부품(`RecordCompletionBadge`), 다른 규칙:

```
나이스 배지  → 조건 없음.  모든 출결 기록에 무조건 표시
서류 배지    → requiresDocument(record, policy) 통과한 기록에만 표시
```

둘 다 "출결 하나를 마무리하려면 해야 하는 일"이다. 한쪽은 항상 보이고 한쪽은 조건부로 숨는 이유가
데이터 모델 밖에 없다. **9안은 이 비대칭을 없앤다** — 일관성 근거가 코드 안에 이미 있다.

**(2) 규정 차이를 앱이 판단하지 않는다.**

정책 매트릭스는 (사유 × 상태) 16칸으로 학교 규정을 **근사**한다. 근사가 맞는 학교는 편하고,
안 맞는 학교는 손댈 방법이 없었다. 9안은 **기록 단위로 선생님이 정하므로 근사 오차가 0**이다.
"3일 이상 질병 결석만 진단서" 같은 매트릭스로 표현 불가능한 규정도 그냥 된다.

**(3) '제출 대상 아님'이 지금 없는 정보를 만든다.**

현재 모델에서 배지가 없는 상태는 **두 가지가 겹쳐 있다** — "서류 안 걷는 출결"과 "아직 확인 안 함".
구분이 안 되니 선생님도 앱도 어디까지 처리했는지 알 수 없다.
'대상 아님'은 **선생님이 판단을 마쳤다는 기록**이다. 이게 검토 큐를 실제로 비울 수 있게 한다.

### 9-2. 반드시 먼저 풀어야 할 문제 — 초기 상태

**이게 9안의 성패를 가른다.** 새 기록과 **기존 기록 전부**의 출발 상태를 무엇으로 둘 것인가.

기존 기록은 대부분 `documentSubmitted: false`다(`emit-entity-samples.mjs:220`이 그 형태).
이걸 그대로 **'미제출'로 해석하면 M4가 고쳤던 과다 카운트가 그대로 부활한다.**

> plan.md:18 — "서류 배너가 `category==='attendance' && !documentSubmitted` **부정 필터**로
> **모든** 출결 기록을 '서류 필요'로 집계"

즉 학기 초에 열면 지난 기록 전부가 주황색 '미제출'로 뜨고 검토 큐가 터진다.
**M4 이전 상태로 되돌아가는 것**이므로 이건 반드시 피해야 한다.

세 가지 출발점을 비교했다.

| 안      | 초기 상태                    | 학기 초 화면            | 과다 카운트 | 발견성 | 판정                     |
| ------- | ---------------------------- | ----------------------- | ----------- | ------ | ------------------------ |
| **i**   | 전부 '미제출'                | 지난 기록 전부 주황     | **재발**    | 최고   | ✗ M4 회귀                |
| **ii**  | 전부 '미정'(4번째 중립 상태) | 회색 '서류?' 배지       | 없음        | 높음   | △ 상태가 4개로 늘어 복잡 |
| **iii** | **정책이 초기값만 제안**     | 대부분 회색 '대상 아님' | 없음        | 높음   | **○ 권고**               |

**iii 권고 이유** — 정책 매트릭스를 **없애지 않고 "정답"에서 "초기값 제안"으로 강등**한다.

- 정책 대상(기본: 출석인정) → **'미제출'**로 시작
- 나머지(질병 결석·지각 등) → **'제출 대상 아님'**으로 시작
- **어느 쪽이든 배지는 보인다** → 오너가 요구한 "기본으로 표시" 충족
- 선생님이 배지를 눌러 언제든 뒤집는다 → 학교 규정 차이를 기록 단위로 흡수
- 이미 정책을 켜 둔 학교(v2.4.x 출시분)의 설정이 **그대로 살아난다** — 마이그레이션 부담 0
- 집계(배너·검토 큐)는 **'미제출'만** 센다 → 과다 카운트 재발 없음

배지 순환: `대상 아님(회색) → 미제출(주황) → 제출(초록) → 대상 아님`

### 9-3. 데이터·동기화 변경 실측

**표현 방식 권고 — 기존 boolean 유지 + 필드 하나 추가.**

```
documentSubmitted?: boolean      (기존 유지)
documentNotRequired?: boolean    (신규)

파생 순서(도메인 순수 함수 1곳):
  documentNotRequired === true  →  '제출 대상 아님'
  documentSubmitted   === true  →  '제출 완료'
  그 외                          →  '미제출'
```

enum 신규 필드(`documentStatus`) 대신 이 방식을 권고하는 이유: `documentSubmitted`를 남겨두면
**구버전 앱·AI 브릿지·내보내기가 그대로 동작**한다. 순서가 정해진 파생이라 모순 조합이 생길 수 없다.

**손대야 하는 곳 — 전부 실측했다.**

| 위치                                                            | 무엇을                                                  | 안 하면                                                                                                               |
| --------------------------------------------------------------- | ------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `StudentRecord.ts:56` `TRACKED_GROUP_FIELDS.documentGroup`      | `documentNotRequired` 추가 (한 줄)                      | 코드 주석의 경고 그대로: **"스탬프는 찍히는데 병합이 채택 안 함"** → 기기 간 동기화에서 '대상 아님'이 조용히 사라진다 |
| `scripts/emit-entity-samples.mjs:79-80` `ENTITY_FIELD_CONTRACT` | mirrored 에 추가 + 샘플 갱신                            | 계약 메타테스트 실패(`entitySampleContract.meta.test.ts` 가드 A/B)                                                    |

**좋은 소식**: 스탬프(`ManageStudentRecords.ts:113`)와 병합 채택(`SyncFromCloud.ts:91,119`)은
둘 다 `TRACKED_GROUP_FIELDS`에서 **파생**된다. 레지스트리 한 줄만 고치면 양쪽이 자동 정합된다.
(엔티티 파일이 이 설계를 명시적으로 문서화해 뒀다 — `StudentRecord.ts:47-52`)

### 9-4. M6 종류별 체크리스트와의 관계

현재 검토 화면의 `신청서/보고서/증빙자료` 칩(`ReviewMode.tsx:449-471`)은 '제출 완료' 안의 **하위 진행도**가 된다.

- **'제출 대상 아님'이면 종류 칩은 무의미** → 숨겨야 한다
- `deriveDocumentSubmitted`("전 종류 제출 = 완료") 불변식에 `documentNotRequired` 우선순위를 얹어야 한다
- 지금 정책 게이트 때문에 검토 큐에서만 보이던 종류 칩이, 9안에서는 **'미제출' 상태 모든 기록**에서 보일 수 있다

### 9-5. 새로 생기는 부담 — 반복 노동

모든 출결에 상태가 생기면 **일괄 처리가 선택이 아니라 필수**가 된다.
"이 학생 이번 달 질병 지각 전부 대상 아님" 같은 조작이 없으면 클릭 노동이 폭증한다.

이미 있는 것: `bulkMarkDocumentSubmitted`(스토어), 배너 일괄 버튼, 검토 큐 체크박스 일괄.
필요한 것: **'대상 아님' 일괄** + 사유·상태별 필터 걸어 일괄.

주의 — "질병 지각은 전부 대상 아님으로" 같은 **규칙성 일괄은 사실상 정책 설정과 같은 일**이다.
9-2 iii처럼 정책을 초기값 제안으로 남겨 두면 이 순환이 자연스럽게 풀린다
(자주 쓰는 규칙은 정책에, 예외는 기록에).

### 9-6. 화면 예산 경고

목록·타임라인의 출결 행마다 배지가 **나이스 + 서류 2개**가 상시로 붙는다.
지금은 서류가 조건부라 대부분 1개다. 밀도가 실제로 올라간다.

메모리 규칙상 **디자인·UI·UX 단독 진행 금지**다. 배지 밀도·색·순환 인터랙션은
확정 전에 프론트엔드 디자인 협업이 필요하다(오너 승인 시).

### 9-7. 오너 결정이 필요한 것

   i은 오너 의도에 더 직설적이지만 M4 과다 카운트가 재발한다.

## 10. 오너 결정 1차 (2026-08-27) — **§11로 일부 대체됨**

### 10-1. 초기 상태 — §9-2 iii 채택 + '미인정' 공통 예외

정책 매트릭스를 **"정답"에서 "초기값 제안"으로 강등**한다(§9-2 iii 그대로).

**추가 확정 — 사유가 '미인정'이면 서류 제출이 필요 없다. 학교 공통.**
(오너 진술. 기재요령 원문 대조는 하지 않았다 — 규정 문서가 아니라 도메인 사실로 채택.)

이 규칙이 정책 매트릭스보다 **우선**한다.

| 사유 축        | 초기 상태                            | 정책 매트릭스에서           |
| -------------- | ------------------------------------ | --------------------------- |
| 인정(출석인정) | 정책 기본값에 따라 **'미제출'**      | 편집 가능                   |
| 질병           | 정책 설정에 따름 (기본: '대상 아님') | 편집 가능                   |
| 기타           | 정책 설정에 따름 (기본: '대상 아님') | 편집 가능                   |
| **미인정**     | **항상 '제출 대상 아님'**            | **행 자체를 노출하지 않음** |

구현 메모:

- `requiresDocument()`에 `axisOf(reason) === '미인정' → false` 를 **정책 조회보다 앞에** 둔다.
  `axisOf`는 이미 '미인정'을 '인정'보다 먼저 판정하므로(`attendanceDocumentPolicy.ts:47-53`) 순서 문제 없음.
- 설정 편집기(`RecordReminderSection.tsx:576-639`)의 `DOC_REASON_AXES` 렌더에서 '미인정' 행 제외.
- **기존 저장 정책에 '미인정'이 켜져 있어도 마이그레이션 불필요** — 읽을 때 무시하면 된다.
  (설정 whole-file LWW 동기화를 건드리지 않는 게 유리 — plan.md 리스크 표 참조)
- 안전판: 기록 단위 3상태는 그대로이므로, 미인정에 서류를 걷는 예외 상황이 생겨도
  선생님이 그 기록만 '미제출'로 뒤집을 수 있다. **공통 규칙이 막다른 길이 되지 않는다.**

### 10-2. 설정 화면 — 이름·설명 재작성 (확정)

"증빙서류 요구 설정" → **서류 기본값 설정**(가칭). 의미가 "무엇을 집계할지"에서

### 10-3. 모바일 — 이번엔 제외 (확정)

§5-1(모바일 전면 미지원)은 이번 작업 범위 밖. 별도 작업 단위로 미룬다.

### 10-4. 배지 밀도 — 상태별 표현 차등 (권고, 디자인 확인 전)

**근거: 같은 행에 이미 이 언어가 있다.** `DefaultRecordListView.tsx:134-149`의 후속조치 표시는
알약이 아니라 **맨 아이콘**이다(완료 `task_alt` 초록 / 미완료 `push_pin` 회색). 바로 옆 `record.method`(`:126-133`)도
맨 아이콘. **나이스·서류만 완료 여부와 무관하게 알약을 써서 튄다.**

| 상태           | 표현                                     |
| -------------- | ---------------------------------------- |
| 제출 완료      | 초록 **아이콘만**                        |
| 제출 대상 아님 | 흐린 회색 **아이콘만** (가장 조용)       |
| 미제출         | 주황 **알약 + "미제출"** (유일하게 외침) |

나이스 배지도 같은 규칙으로 통일(반영 완료 → 초록 아이콘, 미반영 → 빨강 알약).

**밀도 비교 — 지금보다 낮아진다:**

| 경우                        | 지금               | 바뀐 뒤  |
| --------------------------- | ------------------ | -------- |
| 나이스 완료 + 서류 완료     | 알약 2             | 아이콘 2 |
| 나이스 완료 + 서류 정책밖   | 알약 1             | 아이콘 2 |
| 나이스 미반영 + 서류 미제출 | 알약 1 (서류 숨음) | 알약 2   |

처리가 끝난 기록(정상 상태)은 조용해지고 **할 일이 남은 기록만 눈에 띈다** → 목록이 "남은 일" 화면이 된다.
아이콘은 항상 있으므로 "칸이 존재한다"는 발견성은 유지되고, 클릭 토글도 그대로다.

**기각한 안**

- **통합 칩 1개(`마무리 1/2`) + 팝오버** — 밀도는 최소지만 무엇이 남았는지 열어야 알고 클릭이 2회.
  매일 수십 건 처리하는 화면에 부적합.
- **완료 시 완전 숨김** — 가장 조용하나 **오조작 되돌리기가 불가능**해진다. 실수 복구 경로를 없애는 건 위험.

**미확정** — 배지 색·아이콘·순환 인터랙션의 최종 시각 확정은 프론트엔드 디자인 협업 대상이다
(메모리 규칙: 디자인·UI·UX 단독 진행 금지). 위 표는 **구조 권고**이며 시각 확정이 아니다.

### 10-5. 확정된 작업 범위

1. 도메인 — 3상태 파생 함수 + '미인정' 공통 예외 + `deriveDocumentSubmitted` 불변식 재정의

3. 배지 — `RecordCompletionBadge` 3상태화 + 상태별 알약/아이콘 차등
4. 목록·타임라인 — 정책 게이트 제거(상시 표시)
5. 집계(배너·검토 큐·통계·필터) — '미제출'만 카운트

7. 검토 화면 — '대상 아님'이면 종류별 칩 숨김

9. 사용자 가이드(`landing/src/content/docs.ts`) — 출결 서류 문단 재작성

### 11-3. §10-2 정정 — 설정 이름은 그대로 둔다

§10-2에서 "증빙서류 요구 설정 → 서류 기본값 설정"으로 바꾸기로 했는데, **이 근거가 사라졌다.**
정책이 "초기값 제안"으로 강등됐을 때만 성립하던 이름이다. 2상태에서는 정책이 다시
**진짜 요구 범위를 결정하는 게이트**이므로 **"증빙서류 요구 설정"이 정확한 이름이다. 유지한다.**

바꾸는 것은 **설명 문구**뿐 — 기본값이 인정+질병으로 넓어졌고 미인정 행이 사라진 걸 반영한다.
§3의 이름 통일(화면 표기를 "증빙서류"로)은 그대로 유효하다.

### 11-4. 남는 구멍과 대응 — 정책 밖의 침묵

2상태는 정책 게이트를 유지하므로, **정책 밖 출결에서 아무것도 안 보이는 문제(§1~§6)가 그대로 남는다.**
다만 범위가 크게 줄었다.

| 사유        | 기본 상태  | 침묵하나 | 정당한가                               |
| ----------- | ---------- | -------- | -------------------------------------- |
| 인정 · 질병 | 대상       | 아니오   | —                                      |
| 미인정      | 제외(공통) | 예       | **정당** — 규칙이 명확하니 안내 불필요 |
| 기타        | 기본 제외  | 예       | **아니오 — 안내 필요**                 |

→ **§7-2 B안(안내 문구 + 설정 딥링크)을 유지한다.** 정책 밖 출결의 수정 화면에 한 줄:
"지금 방침에선 이 출결의 증빙서류를 걷지 않아요 · **[방침 바꾸기]**" → `settings#record-reminder` 딥링크.
비용이 작고(기존 `ssampin:navigate` 메커니즘), 원래 피드백이 나온 지점을 정확히 막는다.

**입력 화면(§1 A)에는 체크박스를 넣지 않는다.** 2상태에서 새 기록은 자동으로 '미제출'로 시작하므로
입력 시점에 선생님이 할 일이 없다. 서류는 나중에 받으므로 조회·검토에서 체크하는 게 실제 흐름과 맞다.
팔레트가 이미 밀집해 있어 넣을 이유도 없다.

### 11-5. 반드시 대비할 것 — **기존 사용자의 미제출 건수가 갑자기 늘어난다**

정책 기본값에 '질병'이 추가되면, 설정을 한 번도 안 만진 사용자(`attendanceDocumentPolicy === undefined`)는
업데이트 즉시 **과거 질병 출결 전부가 '미제출'로 재계산된다.** 배너·검토 큐·통계가 함께 커진다.

이건 버그가 아니라 **의도된 결과**다(§11-1). 하지만 예고 없이 터지면 사고로 인식된다.

- 날짜 컷오프로 "앞으로 만드는 기록만" 적용하는 건 **불가능** — 정책은 기록에 저장되지 않고 조회할 때마다
  계산된다(`requiresDocument`). 과거 기록도 같이 재계산된다.
- 따라서 **데이터가 아니라 안내로 푼다.**

**대응(확정):** 업데이트 후 1회 닫을 수 있는 안내 배너 — `SampleRosterWarningBanner.tsx` 패턴 재사용
(settings에 `dismissedAt` 저장). 문구 요지: "이번 업데이트부터 **질병 출결도 증빙서류 대상**입니다.
학교 방침이 다르면 [설정]에서 끄실 수 있어요." + 설정 딥링크.
릴리즈 노트에도 같은 내용을 넣는다.

### 11-6. 배지 밀도 — §10-4 유지 (2상태로 축소)

§10-4의 상태별 차등은 그대로 유효하다. 3상태가 2상태로 줄어 더 단순해진다.

| 상태      | 표현                                                               |
| --------- | ------------------------------------------------------------------ |
| 제출 완료 | 초록 **아이콘만** (같은 행의 후속조치 완료 `task_alt`와 같은 언어) |
| 미제출    | 주황 **알약 + "미제출"**                                           |

나이스 배지도 같은 규칙(반영 완료 → 초록 아이콘, 미반영 → 빨강 알약).
근거·기각안·밀도 비교표는 §10-4 그대로. 시각 최종 확정은 여전히 디자인 협업 대상이다.

### 11-7. 최종 작업 범위 (9건 → 7건)

1. **도메인** — `requiresDocument`에 '미인정' 공통 제외를 정책 조회보다 앞에 추가
