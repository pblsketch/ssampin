### 같은 수정에서 확인할 연결 문제

- `Homeroom/Survey/SurveyStudentDetail.tsx`는 담임 저장소를 직접 받고 `s.number ?? idx + 1` 사용. 담임 실제 필드는 `studentNumber`. 응답 상태·시간·내보내기·PIN 안내까지 실제 번호로 맞춘다.
- `Homeroom/shared/StudentGrid.tsx`, `Homeroom/Records/SearchMode.tsx`, `Tools/Timer/PresentationMode.tsx`도 위치 기반 표시가 있다. 실제 호출과 재현을 확인해 동일 원인의 오류를 수정한다. 단순 입력 순서·발표 순서를 학번과 혼동해 일괄 치환하지 않는다.
- 상담의 `buildStudentNumberIndex`, `listUnbookedStudents`는 같은 결번 사례에서 정상이다. 회귀 대조로 유지한다. 신고자의 설치본/기존 링크가 정상임을 확인한 것은 아니다.

## 구현 원칙과 경계

- 배열 위치, 정렬 순서, 활성 학생 수를 학생 식별자로 사용하지 않는다.
- 담임 학생 고유 ID, 수업반 ID, 학생 소속 학년/반/번호의 의미를 현재 저장 구조에서 확인하고 공통 식별 규칙을 정한다. 새 전역 ID 개편으로 불필요하게 범위를 넓히지 않는다.
- 식별 정보가 누락된 구형 제출물과, 정보가 명시적으로 충돌하는 제출물을 구분한다. 번호만으로 모호하게 연결하지 않는다. 미확인 상태·교사 확인 경로 등 안전한 처리와 사용자 안내를 검증한다.
- 학생 번호 없음·중복·재사용, 혼합반 같은 번호, 이름만 식별하는 과제/동명이인에 대해 기존 호환성을 검토한다. 이름만으로 추측하지 않는다.
- 설문은 앱 변경만으로 끝나지 않는다. 기존 DB 정의/RPC/정책/학생 웹 코드까지 추적하고 필요한 스키마 변경·마이그레이션·구버전 호환·배포 순서를 로컬에서 준비한다. 기존 PIN 비공개 처리와 인증 보호를 약화하지 않는다.
- 과제는 생성 당시 명단을 로컬 및 서버에 보관한다. 새 생성 수정이 기존 과제까지 복구한다고 주장하지 않는다.
- **기존 과제·설문·이미 저장된 근거 복구는 별도 항목**으로 원래 ID/이력에 근거한 안전한 로컬 방안, 미확인 사례 처리, 롤백을 준비한다. 현재 명단 번호로 과거 데이터를 일괄 덮어쓰지 않는다. 근거 부족 시 자동 복구하지 않고 남은 범위를 명시한다.
- 실제 운영 데이터 변경·push·PR·배포는 별도 사용자 승인 전 실행하지 않는다. 승인 요청 전 로컬 코드·검증·적용/복구 절차를 구체적으로 준비한다. 브랜치/worktree/PR 자동 생성 금지.
- 병렬 구현 금지. 다른 세션의 변경을 되돌리지 않는다.

## 권장 단계와 완료 기준

1. **S0: 기준 확인·회귀 테스트** — 재현 5건을 실제 모듈/호출 경로를 검증하는 정식 테스트로 고정. 수정 전 실패 확인. 단계별 파일 소유/영향 범위 정리.
2. **S1: 과제 명단·식별·근거 후보** — A/B/E 및 모바일·알림·미제출 목록. 결번 보존과 다른 학생 자료 차단을 함께 확인.
3. **S2: 설문 전 구간** — D/C 및 담임 응답 연결. 생성·복제·재공유·학생 선택·PIN·응답 조회·CSV 확인. 서버 변경이 필요하면 로컬 준비와 운영 적용 상태를 구분.
4. **S3: 추가 표시 경로·기존 자료 호환** — 격자/검색/발표 번호 및 기존 링크/과제/PIN/제출자료의 호환·복구 검토. 미해결은 근거와 함께 명시.
5. **S4: 검증·사용자 가이드·기록** — 아래 게이트와 UI 사례 확인, 새 결정은 ADR, 상태판 및 월별 기록 업데이트. 최종 보고는 로컬 검증/설치본 검증/운영 적용을 구분.
