## 1. 한 줄 결론

오너 자료가 말하는 좋은 세특의 정의는 하나로 모인다 — **"활동을 나열하지 말고, 호기심(질문)으로
이어진 하나의 탐구 서사를 깊게 써라."** 그런데 쌤핀의 관찰 기록은 지금 **서로 연결되지 않은 낱장**이고,
AI는 그 낱장을 자루째 받는다. 즉 시스템 구조 자체가 **"활동 나열형"** 을 낳는다. 고쳐야 할 것은
프롬프트가 아니라 **기록이 이어지는 단위(탐구 흐름)** 를 앱에 만드는 일이다. 성취기준은 그 흐름의
**주제 키워드**를 대는 재료이고, STT는 흐름에 **낱장을 빨리 붙이는 입력 방법**이다.

하게 둔다.

## 4. 성취기준의 올바른 자리 — 문장이 아니라 키워드

### 4-1. 왜 원문을 AI에 보내면 안 되는가

실측에서 Solar Pro 3는 **입력에 있는 문장을 그대로 옮겨 적는** 경향이 확인됐다(금지 항목 C 사례,
2/2 → 보강 후에도 2/2). 성취기준 원문을 근거 옆에 실으면 같은 기전으로 **성취기준 복사형(K1)** 이
나온다. 1차 분석 방안 2-5의 "코드가 아니라 원문을 함께 싣는다"는 **철회**한다.

### 4-2. 대신 — 핵심 키워드만, 그것도 로컬에서

- 성취기준 원문(예: "일차함수의 개념을 이해하고, 그 그래프를 그릴 수 있다")에서 **명사 핵심어만**
  뽑는다 → `일차함수` · `그래프`. 서술어("이해하고", "그릴 수 있다")는 버린다 — 그 부분이 복사형의
  몸통이다.
- 추출은 **AI가 아니라 로컬 형태소 분석**으로 한다. `ssampin-record-check` 에서 띄어쓰기용으로
  이미 검증한 **Kiwi(kiwi-nlp, WASM, 44MB 구성, 15ms)** 를 그대로 쓴다. 결정론적이라 같은 성취기준은
  늘 같은 키워드가 나온다. 번들 시점에 미리 뽑아 두면 런타임 비용도 0이다.
- 키워드는 **칩**으로 보인다. 교사가 빼고 더할 수 있다("기울기", "y절편" 같은 교과서 어휘를 손으로 추가).
- 이 키워드가 하는 일 세 가지:
  1. **탐구 흐름의 주제 어휘** — 새 흐름을 열 때 이름 후보(§5).
  2. **낱장 → 흐름 자동 제안** — 새 관찰 본문에 흐름의 키워드가 들어 있으면 "'프레이밍 효과' 흐름에
     이어 붙일까요?" 를 띄운다(문자열 포함 검사, AI 불필요).
  3. **복사 검사(K1)** — 초안 본문과 연결된 성취기준 원문의 **어절 n-gram 겹침**을 재서 "성취기준
     문장을 옮겨 적은 것 같다" 를 경고한다. 원문은 이 검사에만 쓰고 AI에는 가지 않는다.

### 4-3. 주제(topic)의 "관찰 증거·평가 문항"은 쓰지 않는다

1차 §3-2에서 본 대로 기계 생성 틀 문장이다. 세특 재료로도, 관찰 힌트로도 쓰지 않는다. 자기평가
문항의 **씨앗**(Phase 3)으로만 남겨 두되 그것도 교사가 고쳐 쓰는 전제다.

## 5. 핵심 제안 — "탐구 흐름(Inquiry Thread)" 을 기록의 단위로 만든다

### 5-1. 무엇인가

학생 한 명의 **한 주제에 대한 기록 줄기**. 관찰 낱장·과제 제출·루브릭 평가·자기평가가 시간순으로
꿰어진다. 세특 초안은 **흐름 하나**를 입력으로 받는다.

```
[흐름] 2-3반 12번 · 경제 · "할인 문구와 선택" · 키워드: 합리적 선택, 기회비용, 프레이밍
  09-02 수업     기회비용·매몰비용 수업                                  (진도에서 자동)
  09-02 질문     "쿠폰이 있으면 왜 필요 없는 물건도 사게 되나요?"       (관찰·슬롯 질문)
  09-04 피드백   되물음 → 프레이밍 효과를 언급, 직접 확인해 보겠다고 함  (관찰·슬롯 피드백)
  09-11 시도     학급 30명 두 집단 간이 설문 설계                          (관찰·슬롯 시도)
  09-18 시행착오 순서 효과 발견 → 2차 조사                                (관찰·슬롯 시행착오)
  09-25 산출물   보고서 제출                                              (과제수합 제출 → 자동 후보)
  09-27 평가     루브릭 "자료 해석" 수준 상, 총평 "표본 한계를 먼저 밝힘" (루브릭 채점 → 자동 후보)
  09-27 융합     국어 설득 전략과 연결해 설명                             (관찰·슬롯 융합)
  ── 빈 고리 힌트: 호기심②(두 번째 질문)가 없어요. "광고 규제가 필요한가"는 질문으로 남길까요?
  ── 다음 탐구 메모: 광고 문구 규제 → 2학기 법과정치에서 이어 볼 것
  ── 역량 키워드(교사): 자료 해석력 · 경제 현상에 대한 과제 집착력
```

### 5-2. 데이터 — 새 엔티티 하나, 나머지는 선택 필드

- `InquiryThread { id, studentRef, classId, title, keywords[], standardCodes?, competencyKeywords?,
nextNotes?, status: open|closed, term, createdAt, updatedAt }` — `inquiry-threads.json`. 동기화·보관함
  등록 필수(근거 창고가 빠졌던 실수 재발 방지).
- `ObservationRecord.threadId?` · `RecordEvidence.threadId?` — 선택. **없어도 저장된다**(슬롯과 같은
  불가침). 흐름을 안 쓰는 교사는 지금과 똑같이 쓴다.
- 과제·루브릭·성적 근거는 `evidenceImport` 가 이미 근거 창고로 옮기므로 **근거 창고의 threadId 만
  붙이면** 흐름에 들어온다. 과제·루브릭 엔티티는 건드리지 않는다.
- 브릿지 `normalizeRecord` 화이트리스트와 계약 메타테스트(`entitySampleContract`)에 새 필드를 넣는다 —
  **안 넣으면 AI가 읽는 경로에서 조용히 사라진다**(D4 재발 방지).

### 5-3. 낱장을 흐름에 붙이는 방법 — 교사 부담을 늘리지 않는다

| 상황                           | 동작                                                                                                  |
| ------------------------------ | ----------------------------------------------------------------------------------------------------- |
| 새 관찰을 쓴다                 | 본문에 열린 흐름의 키워드가 있으면 "○○ 흐름에 이어 붙일까요?" 칩. 탭 한 번. 없으면 낱장 그대로        |
| 같은 학생 낱장이 3개 이상 쌓임 | "이 기록들을 한 흐름으로 묶을까요?" 제안(키워드 겹침 기준). 묶으면 흐름 이름 후보 = 성취기준 키워드   |
| 과제 제출이 들어옴             | 과제에 `standardCodes` 가 있고 그 학생에게 같은 코드의 열린 흐름이 있으면 **산출물 후보**로 자동 표시 |
| 루브릭 채점 저장               | 위와 같이 **평가 후보**로 표시. 총평·요소 메모가 흐름 노드가 된다(점수는 원래부터 안 들어간다)        |
| 학기말                         | 흐름 목록에서 **주 흐름 1개(+부 흐름)** 를 골라 [AI 초안]. 근거 자루 전체를 보내지 않는다             |

### 5-3-b. 흐름을 만드는 주된 자리는 **근거 창고**다 (오너 지적 2026-09-04)

오너: "초안을 쓰기 전에 재료를 모으는 단계에서 교사가 **주제별로 재료를 분류**하는 과정이 필요하지 않을까."

확인한 현재 상태 — 근거 창고(`RecordEvidenceView.tsx`)의 분류 축은 \*\*생기부 영역 탭(자율·진로·행특·세특…)

- 미분류 탭** 하나뿐이다. "주제"라는 축이 없다. 한 학생의 세특 탭에 근거 12건이 **한 줄로\*\* 늘어서고,
  그 12건이 몇 개의 이야기인지는 교사 머릿속에만 있다.

→ **흐름(§5-1)은 창고에서 묶어 만드는 것이 기본 경로**다. 입력 시점의 "이 흐름에 붙일까요?"(§5-3)는
보조 경로로 남긴다. 창고 화면에 주제 축을 더한다:

- 영역 탭 안에 **주제 열**: `미분류 | 주제 A | 주제 B | + 새 주제`. 근거를 체크해 "주제로 묶기" 또는 끌어다 놓기.
- 새 주제 이름 후보는 **수행평가 이름**(`AssessmentPlanItem.title` · `Rubric.title`)에서 먼저 뜬다 — 오너 결정
  (2026-09-04): "루브릭 요소보다는 수행평가 명". 그다음 과제 제목·성취기준 키워드. 루브릭 **요소** 이름은
  주제 이름이 아니라 **매칭용 키워드**로만 쓴다(§5-3-c 2).
- 같은 키워드가 든 미분류 근거는 "이것도 이 주제?" 로 제안한다(문자열 포함 검사, AI 없음).
- 주제 열마다 시간순 줄기와 **빈 고리 힌트**가 보이고, **[AI 초안] 버튼은 주제 단위**에 붙는다.
- 주제 = `InquiryThread`. 데이터 모델은 §5-2 그대로다. 창고에서 만들든 입력 때 만들든 같은 것이다.

⚠️ **ADR-072 결정 6 과의 관계를 분명히 해 둔다.** 그 결정은 "슬롯을 학기말에 창고에서 분류하는 배치 작업"
을 폐기했다. 슬롯은 기록 하나의 속성이라 쌓는 순간 탭 한 번이 맞다. **주제는 다르다** — 주제는 기록이
몇 개 쌓인 뒤에야 드러나므로 창고에서 묶는 것이 자연스럽다. 다만 배치가 커지지 않도록 **"미분류 N건"
을 관찰 알림·창고 배지로 조금씩 재촉**한다(누구를 부를지는 안 바꾼다). 결정 6 의 정신(큰 배치 작업을
만들지 않는다)은 그대로 지킨다.

### 5-3-c. 루브릭(채점기준표)과의 연결 — 되어 있는 것과 안 된 것

| 항목                                              | 상태                                                                                                             |
| ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| 루브릭 채점 → 근거 창고 끌어오기                  | **됨.** 요소 이름 · 수준 이름 · 성취 설명 · 요소 메모 · 총평(`rubricGradingToEvidence`). 배점·점수는 안 들어간다 |
| 수행평가 결과의 증빙 메모·학기 성취도(A~E) → 근거 | **됨**(`gradeToEvidence` · `semesterGradeToEvidence`)                                                            |
| 과제 제출 ↔ 루브릭 채점 연결 필드                 | **있음**(`PerformanceAssessmentResult.assignmentId` · `rubricGradingId`)                                         |
| 루브릭 ↔ 성취기준                                 | **없음.** `Rubric`·`RubricCriterion` 에 코드 칸이 없다                                                           |
| 평가계획서(HWP·PDF) 파싱 시 성취기준 코드         | **읽고 버린다**(`scoringRubricParser.ts` — 코드 접두사로 과목만 추정)                                            |
| 루브릭 요소 이름을 주제·키워드로 활용             | **없음**                                                                                                         |

추가하면 좋은 것 — 루브릭은 **교사가 이미 자기 말로 써 둔 "이 활동에서 보려는 것"** 이라 성취기준보다
더 좋은 키워드 원천이다.

1. `Rubric.standardCodes?`(선택) — 평가계획서에서 루브릭을 만들 때 **파서가 읽은 코드를 버리지 말고 싣는다.**
   손으로 만든 루브릭은 나중에 성취기준 칩으로 붙인다.
2. **주제 이름은 수행평가 이름**(`AssessmentPlanItem.title`·`Rubric.title`, 예: "논설문 쓰기", "탐구 보고서")
   에서 끌어온다 — 교사가 평가계획서에 이미 정해 둔 이름이라 학기 내내 같은 말로 부른다. 루브릭
   **요소 이름**("자료 해석", "주장의 명확성")은 주제 이름이 아니라 **매칭 키워드**다 — 관찰 본문에
   요소 이름이 들어 있으면 그 수행평가 주제로 제안한다.
3. 루브릭 채점이 저장되면 같은 학생의 **해당 주제에 "평가" 노드 후보**로 자동 표시된다(§5-3).
4. 초안을 쓸 때 **요소별 수준 이름·성취 설명이 교사의 평가적 기술 재료**가 된다 — "탁월함"이 아니라
   "자료의 측정 조건 차이를 스스로 지적함"(성취 설명) 쪽을 쓰도록 근거 문면에 이미 실려 있다.

### 5-4. 흐름이 주는 것

- **K2·K3·K4 해결의 실체** — 초안 입력이 "이 학생의 근거 12건" 이 아니라 "이 흐름의 8단계" 다.
  모델은 순서를 지어낼 필요가 없고, 활동 나열로 갈 재료 자체가 없다.
- **빈 고리 힌트**(K3·K11) — 흐름에 `질문` 노드가 하나뿐이거나 `시행착오` 가 없으면 화면에 그대로
  적는다. "호기심②가 없어요"가 곧 교사가 다음 수업에 **무엇을 물어볼지**가 된다. 관찰 알림도
  학생 단위가 아니라 **흐름 단위**로 "빈 고리" 를 말할 수 있다(누구를 부를지는 안 바꾼다 — ADR-072 결정 6).
- **다음 탐구 메모**(K12) — 흐름을 닫을 때 "남은 질문"을 적는다. 다음 학기 같은 학생의 새 흐름을
  열 때 지난 메모가 보인다. 학년도 전환·보관함과 함께 움직인다.
- **교사의 평가적 기술 키워드**(K4 끝) — 흐름에 `competencyKeywords` 를 적는다. **분야를 붙인
  형태**("경제 현상에 대한 자료 해석력")를 칩 입력 도우미가 유도한다. AI가 짓지 않고 교사가 적는다.
- **한 흐름 = 한 학생의 것** — K14("다른 학생에게 옮겨도 말이 되는가")가 구조적으로 어려워진다.

### 5-5. 하지 않는 것

- 흐름을 **AI가 자동 생성**하지 않는다(대필 금지 원칙의 연장). 제안은 키워드 포함 검사다.
- 흐름을 **필수**로 만들지 않는다. 낱장 기록은 그대로 낱장으로 산다.
- 담임 누가기록(행특)에는 흐름을 적용하지 않는다. 행특은 "탐구"가 아니라 "사람" 이다(프롬프트 4-2).
  담임에게 필요한 것은 슬롯 `변화` 와 시기 대비이며 이미 있다.

## 6. STT — 관찰을 말로 남긴다

### 6-1. 현재

앱(데스크톱·옆핀·모바일) 어디에도 음성 입력 코드가 없다(`SpeechRecognition`·`MediaRecorder`·whisper
등 0건). 모바일에는 관찰 입력 시트(`ObservationSheet.tsx`)가 있다.

### 6-2. 제약 — 이 PC 와 공식 문서로 확인한 것 (2026-09-04)

| 항목                                     | 확인 결과                                                                                                   |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| Windows 받아쓰기(`Win+H`) 한국어         | **지원**(MS 공식 문서 언어 표에 Korean 명시)                                                                |
| 인터넷                                   | **필수** — Azure 음성 서비스로 처리. 오프라인 지원 언급 없음                                                |
| 이 PC 의 오프라인 한국어 인식기          | **없음** — `Speech_OneCore\Engines\SR` 비어 있음, `Recognizers\Tokens` 0건, 온라인 음성 인식 동의 기록 없음 |
| "음성 입력 시작 도구" 설정               | **있음** — 켜 두면 글자 칸에 커서를 두는 순간 OS 가 작은 마이크 버튼을 띄운다. 자동 문장부호 옵션도 있음    |
| 브라우저 `SpeechRecognition`(Web Speech) | **Electron 에서는 동작하지 않는다**(구글 음성 서버 키 없음). 모바일 크롬·사파리는 한국어 동작               |
| 휴대폰 키보드 마이크                     | 모바일 관찰 시트(`ObservationSheet.tsx`)의 글자 칸에서 이미 동작                                            |
| 로컬 STT(sherpa-onnx 한국어)             | int8 약 126MB. 설치파일 207MB 에 얹기엔 크다. 인식률 미실측                                                 |
| 서버 STT(외부 API)                       | **배제** — 선생님 비용 0 원칙 위배 + 학생 이름이 담긴 음성의 외부 전송                                      |
| 앱이 직접 듣기(WinRT 음성 인식기)        | **제외(오너 결정 2026-09-04)** — 이 PC 에서 지원 언어 목록이 비어 나왔고, OS 받아쓰기로 충분                |

★핵심: 윈도우에서 한국어 음성 입력은 **어차피 OS 가 온라인으로 처리**한다. 앱이 엔진을 넣을 이유가
없고, 할 일은 **OS 받아쓰기를 쓰기 쉽게 만드는 것**뿐이다.

### 6-3. 제안 — OS 가 듣고, 앱은 켜 주고 정리한다

**윈도우**

1. **Win+H 대신 눌러 주기**: 관찰 칸(데스크톱·수업 직후 알림 팝업·옆핀 메모)에 마이크 버튼. 누르면
   앱이 그 칸에 커서를 두고 메인 프로세스가 짧은 PowerShell 로 `Win+H` 키 입력을 보낸다 → OS 받아쓰기
   패널이 그 칸 위에 뜨고 글자가 흘러 들어온다. Electron 자체는 OS 키를 못 보내므로 이 우회가 필요하다.
   ★첫 사용 때 OS 의 "온라인 음성 인식 켜기" 동의 화면이 한 번 뜬다 — **실기기 확인 항목**.
2. **첫 실행 안내 한 장**: "설정 → 음성 입력 시작 도구를 켜면 글자 칸을 클릭할 때마다 마이크가 저절로
   나타납니다." 이걸 켜 둔 교사에게는 **1 의 버튼조차 필요 없다** — OS 가 버튼을 그려 준다.
   코드 0줄, `/docs` 한 줄.

**모바일**

3. **관찰 시트 마이크 버튼 + Web Speech API**: 한 번 누르면 듣기 시작, 말하는 동안 글자가 실시간으로
   칸에 쌓이고, 다시 누르면 멈춘다. 키보드 마이크와 다른 점은 **연속 듣기**와 **앱이 결과를 받아
   정리할 수 있다**는 것. ★아이폰 홈 화면 설치(PWA 독립 실행) 상태에서의 동작은 **실기기 확인 항목**.
4. **시트를 열 때 글자 칸에 자동 커서**: 키보드 마이크까지 한 탭. 코드 한 줄.
5. **휴대폰을 PC 의 마이크로**: 관찰 기록은 이미 기기 간 동기화된다. 복도에서 휴대폰에 말하면 교무실
   PC 의 흐름·초안에 그대로 보인다. 새 기능이 아니라 **안내**다.

**공통 — 글자가 들어온 뒤(진짜 가치)**

6. **구조화 층**: 말로 쓴 글은 길고 여러 학생이 섞인다("3번은 …했고 12번은 …"). 이 글을 **쌤핀 AI 의
   `add_observation` 도구(ADR-074, 이미 있음)** 에 태운다 — 별칭 가림 → 학생·본문·슬롯으로 나눈
   **미리보기 카드** → [실행]. 새 도구가 아니라 **입력 경로 하나 추가**. 여러 학생이면 카드 여러 장.
   열린 흐름의 키워드가 있으면 "○○ 흐름에" 제안까지. ★모델은 관찰문을 **짓지 않는다** — 나누고
   옮길 뿐(ADR-074 결정 2).
7. **고지 한 줄**: "음성은 OS 제조사(마이크로소프트·구글·애플) 서버에서 글자로 바뀝니다." 학생 이름이
   말로 들어가므로 설정 화면에 쉬운 말로 적는다.

**하지 않는 것**: 로컬 STT 엔진 동봉·앱 자체 청취(WinRT)·외부 유료 STT.

### 6-4. STT 가 흐름과 만나는 자리

"**수업 직후**" 가 핵심이다. 관찰 알림은 이미 수업 종료 10분 안에 뜬다(옵저베이션 리마인더 D1).
그 팝업에 **[말로 남기기]** 가 있으면, 복도에서 30초 말한 것이 낱장 3개가 되고 흐름에 붙는다.
K5(질문·문답 최우선)는 **기억이 생생할 때** 만 잡힌다 — 학기말에는 못 쓴다.

## 7. 점검 축 확장 — 자료의 "나쁜 세특" 을 로컬 규칙으로 잡는다

`ssampin-record-check` 는 AI 맞춤법 검사를 실측으로 탈락시키고 **로컬 규칙 5축**으로 결론 냈다. 같은
정신으로 **서사 품질 축**을 더한다. 전부 결정론적이고 오프라인이다. 막지 않고 경고만 한다(ADR-072 결정 5-b).

| 검사                | 방법                                                                                                   | 기준  |
| ------------------- | ------------------------------------------------------------------------------------------------------ | ----- |
| 성취기준 복사       | 초안 ↔ 연결 성취기준 원문의 어절 n-gram 겹침(예: 4어절 이상 연속 일치)                                 | K1    |
| 공통 입력 문구      | **같은 교사·같은 반**의 다른 학생 초안과 문장 단위 중복(첫 문장 특히). 로컬 데이터라 가능              | K7    |
| 일반 평가 나열      | 사전 어휘("성실", "이해력이 뛰어남", "수업 태도가 바름" …)가 **장면 없이** 연속으로 나옴               | K8    |
| 활동 나열           | 산출물·활동 명사(보고서·실험·발표·토론·설문)가 N개 이상인데 접속 질문 표지("궁금", "의문", "질문")가 0 | K2·K3 |
| 관찰 불가 내면 표현 | 기존 `checkGrounding` 계열에 어휘 추가("이해함", "깨달음", "흥미를 느낌" → 행동 동사 제안)             | 3-2   |
| 변화 서사 근거      | "점차·꾸준히·갈수록" 이 있는데 흐름/근거에 시기 대비 노드(`변화` 슬롯 또는 두 학기 날짜)가 없음        | K9    |

이 검사들은 브릿지 `check_record_draft` 와 본체 초안 저장 관문 **양쪽**에 같은 함수를 미러한다
(`hasProhibitedRecordItem` 선례).

## 8. 그 밖의 아이디어 (작지만 현장 효과가 큰 것)

- **질문·되물음 쌍 기록**: 관찰 입력에서 슬롯 `질문` 을 고르면 "선생님은 뭐라고 되물었나요?" 한 줄이
  더 열린다(선택). 저장은 낱장 2개(질문·피드백)로, 흐름에서 쌍으로 보인다. K5 를 입력 단계에서 만든다.
- **후보 여럿 만들기 도우미(K11)**: 흐름의 키워드로 "이 주제를 심화·확대·융합·적용으로 넓히면?" 네
  칸 빈 양식을 띄운다. **채우는 건 교사·학생**이고 AI는 부르지 않는다. 오너 자료의 5단계 매뉴얼
  ②(내용 생성)의 종이 양식을 앱 안으로 옮기는 일이다.
- **교과 간 배분 보기**: 같은 교사가 여러 수업반을 맡을 때, 같은 학생의 흐름을 과목별로 나란히 보여
  "이 학생은 경제·수학에서 같은 소재를 다뤘다"를 알린다(강의 E-9). 교사 간 공유는 로컬 원칙상 없다.
- **우수 사례 구조 보기**: 초안 화면에 "구조 분해" 보기 — 초안 문장을 [총평][수업][호기심][탐구][심화]
  [평가]로 교사가 **직접 표시**해 보는 도구. 어느 칸이 비었는지 스스로 본다. 실명 없는 구조 예시 하나를
  앱에 둔다(오너 자료의 모범 사례는 원문 저작권·출처 문제로 **그대로 싣지 않는다** — 구조만).
- **자기평가서 → 흐름 질문(Phase 3 연결)**: 학생 답 중 "남은 질문" 항목은 교사가 고르면 흐름의
  `질문` 노드가 된다. 학생이 쓴 서사가 교사의 흐름과 맞물린다(K13).
- **하네스 확장(저장소 밖)**: F 사례 "성취기준 키워드만 주었을 때 원문을 복원해 쓰는가", G 사례
  "흐름 8단계를 순서대로 주었을 때 나열형으로 무너지는가 / 뒤섞어 주었을 때 순서를 지어내는가".
  §7 검사기가 이 사례를 자동 채점한다.

## 10. 확인하지 못한 것

- Win+H 첫 실행 시 OS 동의 화면과 `Win+H` 키 입력 우회(PowerShell)의 실기기 동작.
- 아이폰 홈 화면 설치(PWA) 상태에서 Web Speech API 동작 여부.
- Kiwi 명사 추출이 성취기준 원문에서 뽑는 키워드의 품질(띄어쓰기용으로만 실측됨).
- 흐름 화면의 실제 배치 — 디자인 협업 필수(단독 결정 금지).
- 오너 자료의 모범 사례 문장의 저작권·출처 조건(앱 내 예시로 쓰려면 별도 확인).
- 세특 기재요령 원문의 성취기준 서술 요건(1차와 동일하게 미확인).
