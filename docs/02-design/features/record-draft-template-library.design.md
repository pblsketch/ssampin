# 생기부 작성 방식 라이브러리 — 설계서

- 작성: 2026-09-09 KST · [계획서](../../01-plan/features/record-draft-template-library.plan.md) · [ADR-099](../../03-decisions/ADR-099.md)
- 바꾸는 기존 결정: ADR-094(교사 평가 맨 앞 = **고정** → **기본값**), ADR-085(형광펜 순서 = 글 순서 → **색은 고정, 순서는 구성이 정함**).

## 1. 층 나누기 — 무엇이 어디에 있어야 하는가

```
[1층] 서버 규정 RECORD_PROMPT_L1 (판본 3)   ← 못 끔. 사실성·시점·문체·기재 금지·점검
        │  "글의 구성·순서·시작 방식은 요청서의 「작성 구성」을 따른다"
        ▼
[2층] 요청서 = recordDraftPack.text          ← 학생 별칭 · 영역 · 주제 · 근거 · 성취기준 키워드
        ├─ 「작성 구성」 블록  ← 이번에 신설. 초점·시작·묶기·요소가 여기로만 나간다
        ├─ 「선생님 지시」    ← 추가 지시(마스킹 통과)
        ├─ 표식 지시          ← 역할 어휘 4종 고정, **순서는 위 구성을 따름**
        └─ 지어내기 금지 한 줄 ← 항상 맨 끝(최신성)
```

**원칙**: 선택으로 바뀌는 것은 전부 2층에만 있다. 1층에는 선택으로 바뀌는 문장이 하나도 없어야 한다.
1층에 순서가 남아 있으면 선택은 "모델이 어느 쪽을 따를지"의 도박이 된다.

### 2-2. 타입

```ts
// v2(2026-09-09 오너 검토 후) — 10종에서 7종으로 줄였다. §3-1 참조.
type RecordFocusId =
  | 'legacyInquiry' // 기존형 — 하나의 탐구 흐름 (기본값). 성취·개념 적용·질문 검증을 흡수
  | 'compareJudge' // 근거 비교·판단
  | 'feedbackRevise' // 피드백·수정
  | 'designCreate' // 설계·창작·문제 해결
  | 'collaborate' // 협업·기여
  | 'interestExplore' // 관심 탐색·선택
  | 'lifeRelation'; // 행동특성 및 종합의견 — 생활·관계 종합

// 없어진 값은 별칭 표로 기존형이 된다(저장된 설정 호환).
type RecordFocusIdLegacy = 'achievement' | 'conceptApply' | 'questionVerify';

type RecordOpening = 'evaluation' | 'performance' | 'question';
type RecordGrouping = 'single' | 'connected' | 'byAchievement';

interface RecordWritingStyle {
  focus: RecordFocusId;
  opening: RecordOpening;
  grouping: RecordGrouping;
  disabledModules?: readonly RecordModuleId[]; // 기본 구성에서 뺀 것
  extraModules?: readonly RecordModuleId[]; // 초점이 허락한 추가 요소만
  instruction?: string; // 추가 지시(자유 문장)
}
```

`DEFAULT_RECORD_WRITING_STYLE = { focus: 'legacyInquiry', opening: 'evaluation', grouping: 'connected' }`.

### 2-3. 요소(모듈)

요소는 문장 틀이 아니다. **무엇을 근거로 무엇을 쓸지** 정하는 단위이며 다음을 갖는다.

```ts
interface RecordModule {
  id: RecordModuleId;
  label: string; // 화면·지시문에 쓰는 한국어 이름
  role: NarrativeRole; // 형광펜 4색 중 하나 (evaluation|motive|process|result)
  purpose: string; // 지시문 본문 — 무엇을 쓰는 자리인가
  needs: string; // 필요한 근거
  forbid?: string; // 이 자리에서 하면 안 되는 추론
  optional?: boolean; // 근거 없으면 건너뛰어도 되는 요소
}
```

**형광펜 어휘는 늘리지 않는다.** 모듈은 많아도 색은 `평가·동기·과정·결과` 넷뿐이다 —
옛 초안·저장된 `roleMarks`·파서·범례가 그대로 산다(AC-08·AC-10). 바뀌는 것은 **순서**뿐이다.

### 2-4. 교사 판단 요소의 자리 = 시작 방식이 정한다

`teacherJudgement`(역할 `evaluation`)는 모든 초점의 공통 요소이며, 본문 목록에 넣지 않고
`opening` 이 자리를 정한다.

| 시작 방식          | 구성                                              | 첫 문장 어미             |
| ------------------ | ------------------------------------------------- | ------------------------ |
| `evaluation`(기본) | 교사 판단 → 본문 요소들                           | `~하는 학생임.` **강제** |
| `performance`      | 본문 요소들 → 교사 판단                           | 강제 없음                |
| `question`         | (동기 역할 요소를 맨 앞으로) → 나머지 → 교사 판단 | 강제 없음                |

`question` 은 그 초점에 **동기 역할 요소가 있을 때만** 의미가 있다. 없으면 경고를 띄우고
`performance` 처럼 동작한다(조용히 바꾸지 않고 화면에 적는다).

## 3. 초점별 기본 구성

`(역할)` 은 형광펜 색. `*` 는 근거 없으면 건너뛰는 선택 요소.

### 3-1. 왜 10종이 아니라 7종인가 (2026-09-09 오너 검토)

실제 모델로 같은 근거를 여러 초점에 돌려 본 결과, **「성취·수행」·「질문·검증」·「개념 적용」 셋이
기존형과 거의 같은 글을 냈다.** 오너 판단: "결과물이 비슷한 템플릿은 하나로 추려라. 기존형이 더 낫다."

- 셋을 **기존형에 합쳤다.** 그 셋이 갖고 있던 지침(개념은 이름보다 쓰인 방법 · 조사·실험·증명 구별 ·
  결론 강도 · 성취기준 문구 그대로 옮기지 않기 · 참여만으로 숙달 단정 금지)은 기존형의 세 요소로 옮겼다.
- 쓸모 있던 선택 요소는 기존형의 **「더 넣을 수 있는 요소」**로 살렸다: 사용한 개념 · 적용 범위·한계 · 한계·추가 검토.
- 없어진 세 값은 `RECORD_FOCUS_ALIASES` 로 기존형에 매핑한다. 저장된 설정·「내 작성 방식」이 조용히
  기본값으로 떨어지지 않는다.

| 초점           | 기본 구성(교사 판단 제외)                                                                     | 추가 가능                                                  |
| -------------- | --------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| 기존형         | 동기·질문(동기) → 탐구 과정(과정) → 결과·적용(결과)                                           | 수업 맥락*, 사용한 개념*, 적용 범위·한계*, 한계·추가 검토* |
| 근거 비교·판단 | 쟁점(동기) → 비교 기준(과정) → 사용한 근거(과정) → 타당성 판단(결과) → 자신의 결론(결과)      | 반론 검토*, 수업 맥락*                                     |
| 피드백·수정    | 첫 수행의 특징(과정) → 받은 의견·자기 점검(과정) → 학생이 고른 수정(과정) → 달라진 수행(결과) | 수업 맥락\*                                                |
| 설계·창작      | 목적·조건(동기) → 선택한 전략·표현(과정) → 제작·실행(과정) → 산출물의 특징(결과)              | 검토·개선*, 수업 맥락*                                     |
| 협업·기여      | 공동 과제(동기) → 개인의 행동(과정) → 의견 교환·조정·지원(과정) → 공동 작업에 대한 기여(결과) | 수업 맥락\*                                                |
| 관심 탐색      | 확인된 관심(동기) → 탐색 경험(과정) → 알게 된 조건·특성(결과) → 선택 또는 재고(결과)          | 다음 탐색*, 수업 맥락*                                     |
| 생활·관계 종합 | 반복 관찰된 특성(과정) → 대표 생활 장면(과정) → 자기관리·관계·책임(과정)                      | 공동 작업 기여*, 달라진 수행*                              |

각 요소의 `purpose`·`needs`·`forbid` 문장은 v2 조사 문서 §4~§5의 "AI 지시 / 필요 근거 / 생략" 을 옮긴 것이다.
예: T5 `revisedPerformance.forbid` = "교사가 고쳐 준 것을 학생이 스스로 해결한 것으로 바꾸지 않습니다."

## 4. 「작성 구성」 블록이 실제로 나가는 모양

기존형 + 교사 판단 시작 + 이어진 과정 = **오늘과 글자 하나까지 같은 요청서를 만든다**(블록 자체를 안 붙인다).
그래야 "고르지 않은 선생님"에게는 아무 변화가 없다(AC-08).

기존형이 아닐 때만 근거 자료와 표식 지시 사이에 이 블록이 들어간다.

```
작성 구성 - 아래 차례로 씁니다. 근거가 없는 항목은 통째로 건너뛰고, 없는 사실을 지어내 채우지 않습니다.
1. [평가] 교사 판단 - 이 학생을 어떤 사람으로 보았는지 한 문장으로 씁니다.
   · 필요한 근거: 뒤따르는 수행 전체
   · 하지 말 것: 근거 없는 칭찬을 쓰지 않습니다. 역량은 반드시 분야와 함께 씁니다.
   · 어미: 이 문단의 첫 문장은 '~하는 학생임.' 으로 맺습니다.
2. [과정] 첫 수행의 특징 - ...
...
근거를 묶는 방식: 서로 이어진 하나의 과정으로 씁니다. 다만 시간 순서만으로 인과관계를 만들지 않습니다.
```

이어서 표식 지시가 나가고, 마지막 줄은 지금과 같은 "근거만 보고 쓰세요…" 다(최신성 자리를 뺏지 않는다).

## 5. 표식 지시의 가변화

`NARRATIVE_MARK_INSTRUCTION`(고정 문자열)을 `narrativeMarkInstruction(options)` 함수로 바꾸고,
**옛 상수는 기본 옵션의 결과로 그대로 남긴다**(값·글자 동일). 옵션은 둘뿐이다.

```ts
narrativeMarkInstruction({ followComposition?: boolean; firstIsEvaluation?: boolean })
```

- `followComposition` 이면 "순서는 반드시 [평가] → [동기] …" 대신 **"순서는 위 「작성 구성」을 따릅니다."**
- `firstIsEvaluation === false` 면 첫 문장 어미 요구를 빼고, 마지막 문단이 교사 평가임을 적는다.

`buildNarrativeRemarkPack`([다시 표시])은 **순서를 요구하지 않는 변형**을 쓴다. 지금은 본문을 한 글자도
바꾸지 말라면서 동시에 순서를 강제해 자기모순이었고, 순서가 다른 초안에서는 모델이 순서를 고치려 들 수 있다.

## 6. 저장

새 JSON 파일을 만들지 않는다. 두 값 모두 **설정(`settings`)** 에 얹는다 — 학생 자료가 아니라
선생님 개인 취향이고, `miniApps` 가 같은 방식으로 이미 설정에 산다.

```ts
// Settings
recordWritingStyles?: Readonly<Record<string, RecordWritingStyle>>; // 키 = RecordArea. 영역마다 마지막 선택 기억
recordStylePresets?: readonly RecordStylePreset[];                  // 내 작성 방식(상한 30)
```

- 둘 다 **선택 필드** — 옛 설정 파일은 그대로 읽히고 기본값(기존형)이 적용된다(AC-08).
- 프리셋에는 **학생 원문·근거·초안 본문을 넣지 않는다.** 이름·구성·추가 지시뿐이다.
- 프리셋을 지워도 그 방식으로 만든 초안은 그대로 남는다. 재현 정보는 판(`RecordAiDraft`)에 남긴다(§7).

## 7. 판(RecordAiDraft)에 남기는 재현 정보

```ts
style?: {
  focus: RecordFocusId; opening: RecordOpening; grouping: RecordGrouping;
  moduleIds: readonly RecordModuleId[];   // 실제로 나간 구성(요소 조정 반영 후)
  catalogVersion: number;                 // 카탈로그가 바뀌어도 무엇으로 썼는지 남는다
  hadInstruction: boolean;                // 추가 지시가 있었는지만. **본문은 저장하지 않는다**
  presetName?: string;                    // 내 방식으로 만들었으면 그 이름(지워도 남는다)
}
```

추가 지시 본문을 저장하지 않는 이유: 판 파일은 Drive 로 동기화된다. 선생님이 지시문에 학생 이름을
적을 수 있는데, 보낼 때는 마스킹되지만 **저장은 마스킹을 거치지 않는다.** 있었는지만 남긴다.

## 8. 규정 판본 문지기 (되돌리기 설계)

`RECORD_STYLE_MIN_PROMPT_VERSION = 3`.

| 서버가 준 판본 | 고른 방식   | 동작                                                                                  |
| -------------- | ----------- | ------------------------------------------------------------------------------------- |
| 3 이상         | 무엇이든    | 그대로 적용                                                                           |
| 3 미만         | 기존형      | 그대로(오늘과 동일)                                                                   |
| 3 미만         | 기존형 아님 | **기존형으로 되돌려 실행**하고 화면에 이유를 적는다. 판에는 되돌린 뒤의 구성이 남는다 |

- 승인 전에는 운영이 판본 2를 돌려주므로 **새 구성은 아무에게도 나가지 않는다.** 화면은 보이되 실행이 기존형이다.
- 되돌리기: 시크릿을 판본 2 본문으로 되돌리고 함수를 판본 2로 재배포 → 모든 앱이 자동으로 기존형만 쓴다.
  앱 재설치·설정 삭제가 필요 없다.
- 캐시: 클라이언트는 1시간 TTL + 24시간 만료 유예를 쓴다. 판본 3 배포 후 최대 1시간(앱 재시작이면 즉시)
  동안 판본 2가 캐시에 남아 기존형으로 되돌려 실행된다 — **틀린 글이 나오는 게 아니라 옛 글이 나온다.**

## 9. 근거 부족·조합 충돌 검사 (앱이 실제로 판정할 수 있는 것만)

`checkStyleReadiness(style, evidences, area)` 가 경고 목록을 돌려준다. **막지 않고 알린다.**

| 경고                        | 조건                                                | 문구                                                       |
| --------------------------- | --------------------------------------------------- | ---------------------------------------------------------- |
| `few-evidence`              | 초점의 `minEvidence` 보다 근거가 적음(T3·T5 는 2건) | "근거가 N건뿐입니다. 「성취·수행」이 더 맞을 수 있습니다." |
| `no-before-after`           | T5 인데 날짜가 구별되는 근거가 2건 미만             | "전후가 확인되지 않습니다. 변화·향상은 쓰지 않습니다."     |
| `question-opening-unfit`    | 시작 방식이 질문인데 초점에 동기 역할 요소가 없음   | "이 초점에는 질문 자리가 없어 수행부터 씁니다."            |
| `connected-single-evidence` | 묶기가 이어진 과정인데 근거 1건                     | "근거가 하나라 이어 붙일 과정이 없습니다."                 |
| `area-focus-mismatch`       | 행특인데 수업 초점 / 세특인데 생활·관계 종합        | "이 영역에는 「…」이 더 맞습니다."                         |
| `prompt-version`            | 서버 규정이 판본 3 미만인데 기존형이 아님           | "지금은 기존 방식으로 만들어집니다(규정 판본 대기)."       |

경고는 **글을 만들기 전에** 보여 준다. 무엇도 자동으로 바꾸지 않는다(§8 판본 되돌림만 예외이며 그것도 적는다).

## 10. 화면

「AI 초안」 패널 위쪽, 실행 단추 **위**에 한 줄.

```
작성 방식  [ 기존형 ▾ ]   [자세히 ▾]
```

`[자세히 ▾]` 를 열면(기본 닫힘):

- **시작 방식** — 라디오 3개
- **묶는 방식** — 라디오 3개
- **넣을 요소** — 기본 구성 체크 목록 + "더 넣을 수 있는 요소"
- **추가 지시** — 여러 줄 입력(상한 500자). 아래에 "공통 규정·기재 금지·개인정보 보호는 이 칸으로 끌 수 없습니다."
- **적용될 설정** — 실제로 나갈 구성을 번호 목록으로 그린다(경고 포함)
- **내 작성 방식** — [이 설정 저장] · 저장 목록에서 [불러오기]·[복제]·[이름 바꾸기]·[삭제]

원칙: 처음 보이는 것은 한 줄뿐이다. 고르지 않으면 오늘과 같다.

## 11. 실행 계약

- **요청 시작 시 고정**: 학생·근거·본문에 더해 **작성 방식도 그 순간 값으로 잠근다.**
  큐가 도는 중 설정을 바꿔도 진행 중 요청은 안 바뀐다(AC-09).
- 분량 조절(줄이기·채우기)은 **구성 블록을 싣지 않는다.** 이미 쓴 글의 분량만 손대는 일이라
  구성을 다시 요구하면 모델이 글을 다시 짜 버린다. 표식 지시는 순서 없는 변형을 쓴다.
- 담임·교과 진입 모두 같은 패널이므로 같은 계약을 받는다.
- 쌤핀 AI(Solar)에는 초안 경로가 없다 — 바뀌는 것이 없다.

| 절             | 판본 2                                                                               | 판본 3                                                                  |

| 9 예시         | 예 2편 + "첫 문장이 평가" 해설                                                       | 예는 그대로 두되 **문체·시제·분량감만 참고, 순서는 요청서** 로 못 박음  |

빼도 구버전 앱의 결과는 바뀌지 않는다. 이 사실은 회귀 검사로 못 박는다.

실제 생성 20건을 오너가 읽고 지적한 4건을 반영했다. 근거는 전부 실제 생성 결과다.

### 14-1. 4번의 원인은 AI 가 아니었다 (정정)

1차 보고에서 "행특이 근거 3건 중 1건을 안 썼다"고 적었는데, **AI 가 빠뜨린 것이 아니라 앱이 보내지
않은 것이다.** 그 근거("체육대회 준비물이 부족하자 자기 것을 먼저 빌려주고…")에 **'대회'** 가 들어 있어
기재 금지 필터(`detectProhibitedTerms` → `대회·수상`)가 걸러 냈다. 요청서에 아예 실리지 않았다.

- ADR-072 의 의도된 동작이다("안 보내면 못 쓴다"). 화면은 "제외됨 1건(기재 금지 항목이 들어 있음)"으로 알린다.
- 다만 **'체육대회 준비물을 빌려준 장면'은 수상 기록이 아니다.** 이 필터의 과탐지는 이 작업의 범위 밖이며,
  손대려면 별도 결정이 필요하다(느슨하게 하면 진짜 수상 기록이 새어 나간다). **오너 판단 대상으로 남긴다.**
