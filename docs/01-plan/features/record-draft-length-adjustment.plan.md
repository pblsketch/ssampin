## 한 문단 요약

선생님이 구독 AI(클로드 코드 · 코덱스)로 생기부 초안을 받으면 결과가 영역 한도(예: 1,500바이트)를 넘거나 너무 짧게 나옵니다. 지금은 넘친 글은 **저장이 거부되고, 게다가 다른 칸을 누르는 순간 화면에서도 사라집니다**(아래에서 새로 찾은 결함). 이 계획은 오른쪽 AI 패널 안에 접었다 펴는 **[분량 조절]** 칸을 만들어, "이 글을 1,500바이트에 맞게 줄여 줘" 또는 "모아 둔 근거로 조금 더 채워 줘"를 부탁하고, **앱이 직접 바이트를 세어** 판정한 뒤, 새 판(버전)으로 남겨 원문과 나란히 비교하고, 선생님이 [이 글로 바꾸기]를 눌러야 실제 글이 바뀌게 합니다.

# A. RALPLAN-DR 요약

## A-1. 원칙 (이 기능이 지켜야 할 6가지)

1. **모델이 센 숫자를 믿지 않는다.** 바이트는 실제로 저장될 최종 본문으로 **앱이** 센다. 구체적으로 `neisByteLength(aiDraftText(판))` 이며, [뒤에 붙이기]라면 `appendedBytes(앞글, 새글)` 이다. AI가 "1,480바이트로 맞췄습니다"라고 말해도 그 문장은 화면에 쓰지 않는다.
2. **원문은 [이 글로 바꾸기] 전까지 한 글자도 바뀌지 않는다.** 조절 결과는 미리보기다. 예외는 딱 하나 — 선생님이 직접 [편집칸에 넣기]를 눌렀을 때이며, 그 자리에도 §E-2의 비교 게이트가 있다.
3. **가리는 일(이름 마스킹)은 조립 함수 안에서 한다.** "부르는 쪽이 이미 가렸을 것"이라는 주석 계약은 이 저장소에서 실제로 깨져 다른 학생 실명이 외부 CLI로 나갔다. 조절 대상 글도 **원문 그대로 넘겨받아 꾸러미 안에서** 가린다.
4. **규정 게이트를 우회하는 두 번째 생성 경로를 만들지 않는다.** 분량 조절은 본문을 **다시 쓰는** 요청이다. 초안 생성과 똑같이 서버에서 규정 지시문(L1)을 받고, **못 받으면 실행하지 않는다.**
5. **못 맞추면 정직하게 못 맞췄다고 말한다.** 문자열 끝을 강제로 자르지 않고, 근거 없이 채우지 않고, 무한 재시도하지 않는다. 자동 재조정은 **딱 1회**.
6. **한도는 확인된 것만 강제한다.** 초등처럼 공식 수치를 확인하지 못한 영역(`isAreaLimitVerified === false`)은 이 기능이 새로운 강제 한도로 승격시키지 않는다.

  - 학급 운영·수업 관리가 공통 `RecordDraftView`를 쓰므로 한 번 만들면 양쪽에 붙는다.
- 단점(한정적)
  - 패널이 세로로 길어진다 → 접힘 기본값과 섹션 순서를 디자인 단계에서 정한다.
  - 좌우 비교 폭이 좁다(1,500바이트 두 벌) → 좁을 때 세로로 떨어지는 반응형이 필요하다.
  - `RecordDraftAiPanel.tsx`가 이미 **789줄**이다 → 조절 섹션은 별도 파일로 뗀다.

### (b) 별도 모달 / 전체 화면 비교 편집기

- 장점: 원문·조절안을 넓게 좌우로 놓을 수 있다. 목표 입력·모드 선택을 크게 배치할 수 있다.
- 단점(한정적)
  - **유리 모드 함정을 정면으로 맞는다.** 사이드바 안에서 뜬 모달은 `backdrop-filter` 때문에 갇힌다 → `createPortal` 필수, 회귀 항목 추가, 실기기 확인 증가.
  - 판·비교·반영 흐름이 두 곳으로 갈라진다. 같은 개념이 두 문법으로 있으면 "어느 쪽이 진짜 내 글인가"가 흐려진다.
- **판정: 기각.** 비교 폭 문제는 (a)의 반응형으로 완화된다. 실사용에서 "비교가 좁아 못 쓰겠다"가 쌓이면 2차에서 재검토한다.

### (c) 사후 조절 없이, 첫 생성 요청에 목표 분량만 실어 보내기

- 장점: 변경이 가장 작다. 새 UI·새 판 종류·새 실패 상태가 없다.
- 단점(한정적)
  - **이미 있는 글을 못 고친다.** 선생님이 직접 쓴 1,780바이트 글은 손댈 방법이 없다. 이 과제가 시작된 자리가 거기다.
  - 못 맞췄을 때 할 수 있는 게 "처음부터 다시 생성"뿐이라 손본 부분이 날아간다.
- **판정: 단독 기각, 부분 채택.** 첫 생성에도 목표를 선택적으로 싣는다(오너 결정 8).

### (d) 앱이 코드로 잘라 맞추기 (문장 단위 절삭) — **무효화**

- 무효화 사유: 생기부는 문장 하나가 학생 평가의 근거다. 뒤 문장을 기계적으로 버리면 "교사 평가"가 통째로 사라지고 선생님이 눈치채지 못한 채 NEIS에 넣는다. 이 저장소에는 이미 **"끌 수 없는 필터가 데이터 소실처럼 보인"** 사고가 있다(근거 8건이 조용히 사라짐, 게이트 4종은 초록).
- **이 무효화는 기재 금지 항목 처리에도 그대로 적용된다** — 조절 대상 본문에서 금지 문장을 자동으로 지우는 것도 같은 종류의 조용한 삭제다(오너 결정 4).

## A-4. 사전 부검 (pre-mortem) — "6주 뒤 이 기능이 실패했다. 왜?"

### 시나리오 1 — 보충하기가 근거 없이 지어냈고, 그대로 NEIS에 들어갔다

- **무슨 일이 벌어졌나**: 620바이트 글에 [근거로 보충하기]를 눌렀는데 보낼 수 있는 근거가 1건뿐이었다. 모델은 빈칸을 채우려 "모둠 발표에서 리더 역할을 맡아"처럼 그럴듯하지만 근거에 없는 문장을 넣었다. 화면은 "1,463바이트 · 목표 달성"만 보여 줬고, 선생님은 길이가 맞으니 통과한 줄 알고 반영했다.
- **조기 경보 신호**
  - 늘어난 바이트가 **보낸 근거 총 길이보다 크다**(없는 재료로 채웠다는 뜻).
  - 근거 0~1건인데 목표를 "달성"으로 표시한 실행이 로그에 남는다.
  - QA에서 "AI가 안 한 활동을 썼다"는 신고.
- **예방책**
  - 보낼 수 있는 근거가 **0건이면 [근거로 보충하기] 버튼 자체를 비활성화**하고 이유를 쓴다.
  - 조절안 옆에 **항상** `근거 N건 사용 · 제외 M건`을 붙인다. 길이 숫자만 크게 보여 주지 않는다.
  - 지시문에 `채울 근거가 모자라면 목표보다 짧아도 됩니다`를 명시하고, 모델이 `[근거 부족]` 표식을 마지막 줄에 달게 한다(§C-1 지시문 전문). 그 표식이 오면 **재조정 재시도를 하지 않고** `근거가 부족해 목표보다 짧게 작성했어요.`로 멈춘다.
  - 목표 미달로 멈춘 결과에 성공색(초록)을 쓰지 않는다.
  - **품질 자동 판정을 하지 않는다.** "사실 보존이 검증됐다"는 표시를 절대 만들지 않는다.

### 시나리오 2 — 두 번 눌러도 목표를 못 맞춰서 아무도 안 쓴다

- **무슨 일이 벌어졌나**: 1차 1,610바이트, 재조정 후 1,552바이트. 여전히 초과라 [이 글로 바꾸기]가 비활성. 세 번째로 눌렀더니 1,340바이트로 너무 짧아졌다. 매번 30~60초를 기다린 끝에 손으로 지웠다.
- **조기 경보 신호**
  - 재조정 1회 후에도 목표 범위 밖인 실행이 **절반을 넘는다**(관측 로그).
  - 같은 칸에서 조절 시도가 3회 이상 반복된다.
- **예방책**
  - 목표를 **약속으로 말하지 않는다.** "정확히 1,500"이 아니라 "1,500바이트 안에서 가깝게".
  - **별칭 어림 보정**(§C-1)으로 1차 명중률을 올린다.
  - 재조정 후에도 안 맞으면 **[다시 시도]가 아니라 [목표 바꾸기]를 먼저** 제시한다.
  - **개인 목표만 넘고 실제 한도 이내면 반영을 막지 않는다.** `목표보다 52바이트 많음`만 표시한다.
  - **한도를 넘어도 결과를 버리지 않는다** — [편집칸에 넣기(저장 안 함)]로 선생님이 이어서 손볼 수 있게 한다(오너 결정 2).

### 시나리오 3 — 조절하는 사이 선생님이 쓰던 글이 날아갔다

- **무슨 일이 벌어졌나**: [분량 조절]을 누르고 기다리는 동안 초안 칸을 더 고쳤다. [이 글로 바꾸기]를 눌렀더니 조절 시작 시점의 옛 글 기준 결과가 방금 고친 내용을 통째로 덮었다. 또 다른 경로에서는 **[분량 조절] 버튼을 누르느라 편집 칸에서 초점이 빠지는 순간, 저장이 거부된 초과분 글자가 화면에서 사라졌다.**
- **조기 경보 신호**
  - "취소했는데 글이 짧아졌다", "방금 쓴 문장이 없어졌다"는 신고.
  - 편집 상태와 저장된 내용이 어긋난 상태에서 화면이 다시 그려지는 코드 경로가 새로 생긴다.
- **예방책**
  - 후자는 **이미 존재하는 결함**이다(§D-4 새 발견 3). **C0에서 먼저 고친다** — 내 손글씨가 저장된 글보다 최신이면 되돌리지 않는다.
  - 행의 현재 입력을 담는 등록부는 **읽기 전용**이다. 쓰는 자리는 [편집칸에 넣기] 딱 한 곳뿐이고, 그 자리에도 §E-2 비교 게이트를 통과시킨다.
  - 조절 시작 시점의 원문(`sourceText`)을 붙들어 두고, [이 글로 바꾸기] 순간 행의 최신 입력과 **다시 비교**한다.
  - 조절 반영에도 기존 **30초 [되돌리기]**를 붙인다.
  - 이 계약들을 회귀 항목 #68·#69로 못 박는다.

## C-0. C0 상세 — 기존 결함 3건 수리 (새 기능보다 먼저)

**(ㄱ) 반영 실패가 아무 반응 없이 삼켜진다**
`RecordDraftAiPanel.tsx`의 `applyVersion`(378행)에 `try/catch`가 없다. `onApply`가 `RecordDraftLimitError`를 던지면 그 뒤의 `markApplied`도 `continueQueue`도 실행되지 않는다. 즉 **한도를 넘긴 AI 초안은 [반영]을 눌러도 아무 일도 안 일어나고 아무 안내도 없다.**
→ `try/catch`로 감싸고, 실패하면 미리보기·원문을 그대로 둔 채 오류 문구를 띄운다. 큐가 있었다면 "여기서 멈췄다"를 명시한다.

**(ㄴ) 초점을 잃으면 저장 거부된 글이 화면에서 되돌아간다** — _이번에 새로 찾음_
`RecordDraftRow` 안의 되돌리기 효과:

```ts
useEffect(() => {
  if (!focused) setText(draft?.content ?? '');
}, [draft?.content, draft?.updatedAt, focused]);
```

`focused`가 의존 목록에 있으므로, 편집 칸에서 **초점이 빠지는 것만으로** 이 효과가 다시 돈다. 저장이 성공했으면 같은 글이라 티가 안 나지만, **한도 초과로 저장이 거부되면 `draft.content`는 옛 글 그대로**라 화면 글자가 옛 글로 되돌아간다. 붉은 오류 문구는 남고 글은 사라진다.
→ "내 손글씨가 저장된 것보다 최신이면 되돌리지 않는다"로 고친다. 마지막 편집 시각을 참조(렌더를 일으키지 않는 기억 상자)에 적어 두고, 그 시각이 `draft.updatedAt`보다 나중이면 되돌리기를 건너뛴다. AI 반영·동기화로 `updatedAt`이 갱신되는 경우에는 지금처럼 자동 입력이 된다(`upsert`가 `updatedAt`을 저장 시각으로 찍으므로 언제나 `updatedAt > lastEdit`이 된다 — 기존 자동 입력 경로는 깨지지 않는다).
★**[편집칸에 넣기] 배달도 이 도장을 찍어야 한다**(§C-2 (3)). 안 찍으면 이 수리를 완벽히 해도 배달한 글만 되돌아간다.

**(ㄷ) `useState`로 만든 중복 실행 잠금**
[다시 표시]가 `const [remarking, setRemarking] = useState(false)`(173행)로 막고 있다. 이 저장소에서 **상태 기반 잠금은 뚫린 전례**가 있다(상태 갱신이 비동기라 두 호출이 같은 옛 상태를 본다).
→ 참조(ref) 기반 잠금으로 바꾸고 테스트로 고정한다. 이 잠금은 S2에서 부모로 올라간다.

**신규 `src/domain/rules/recordLengthGoal.ts`** — 순수 함수만. 화면도 저장소도 모른다.
(단서: `judgeLength`가 안에서 부르는 `resolveAreaLimit`은 **미지의 (영역 × 학교급)에서 예외를 던진다** — 조용한 폴백을 금지한 기존 설계다. "순수 함수"라 적었지만 예외는 나갈 수 있다. 부르는 쪽은 화면에서 고른 영역·학교급만 넘기므로 실사용 위험은 낮다.)

- `defaultTargetBytes(area, level)` : 목표 기본값 = 그 영역의 한도.
- `clampTargetBytes(input, area, level)` : 확인된 한도(`isAreaLimitVerified === true`)에서는 목표를 한도 이하로 자른다. 넘겨 치면 화면이 `이 영역 한도는 1,500바이트예요.`로 되돌린다.
  - **왜 필요한가(Critic B6)**: 한도 1,500 영역에서 목표를 2,000으로 치면 1,950바이트 결과가 "맞음"으로 판정돼 [이 글로 바꾸기]가 켜지고, 저장은 거부된다. 이 계획이 잡겠다고 한 "미리보기는 통과, 저장은 거부"를 스스로 다른 경로로 만드는 셈이다.
- `goalFloor(targetBytes)` : 목표 하한 = `Math.ceil(targetBytes * 0.95)`. 1,500 → 1,425.
- `judgeLength({ bytes, targetBytes, area, level })` → `'over-limit' | 'over-goal' | 'under-goal' | 'ok'`
  - **인자를 `(area, level)`로 받는다.** `(limit, limitVerified)` 두 개를 따로 받으면 부르는 쪽에서 짝이 어긋날 수 있다. 한도와 확인 여부는 함수 안에서 `resolveAreaLimit` / `isAreaLimitVerified`로 함께 구한다.
  - **판정 순서를 못 박는다: `over-limit`을 가장 먼저 본다.** 단 `isAreaLimitVerified(area, level) === true`일 때만 `over-limit`이 나올 수 있다. 초등의 미확인 한도는 구조적으로 `over-limit`이 될 수 없다.
- `appendedBytes(base, addition)` : [뒤에 붙이기] 합산 길이. **코드와 글자 단위로 같게** 정의한다.

  ```ts
  // RecordDraftAiPanel 의 mergedText 계산과 정확히 같아야 한다:
  //   mode === 'append' && base.trim().length > 0 ? `${base.trim()} ${text}` : text
  export function appendedBytes(base: string, addition: string): number {
    const head = base.trim();
    if (head.length === 0) return neisByteLength(addition);
    return neisByteLength(head) + 1 + neisByteLength(addition); // 공백 한 칸 = 1B
  }
  ```

  - ★분석 §4-7은 "기존 글 + **빈 줄** + 새 글"이라 적었으나 **코드는 공백 한 칸**으로 잇는다(오너 결정 2026-09-06). 또한 앞글이 비어 있으면 공백도 없다 — 여기까지 맞춰야 "미리보기 통과, 저장 거부"가 안 생긴다.

- `aliasByteDelta(realText, maskedText)` : **어림 보정**용 차이값.

  ```ts
  // 예: 실명 '김지훈'(9B) → 별칭 '［이름1］'(13B) 이면 delta = 9 - 13 = -4
  export const aliasByteDelta = (real: string, masked: string): number =>
    neisByteLength(real) - neisByteLength(masked);

  // 모델은 별칭만 보고 쓴다. 답을 실명으로 되돌리면 그만큼 길이가 달라지므로,
  // 모델에게 주는 목표를 미리 반대로 밀어 준다.
  export const modelTargetBytes = (finalTargetBytes: number, delta: number): number =>
    finalTargetBytes - delta; // 위 예에서는 1500 - (-4) = 1504

  // ★하한도 같은 delta 로 보정한다. 상한만 보정하면 지시문의 두 숫자가 서로 다른 기준이 된다.
  export const modelFloorBytes = (finalTargetBytes: number, delta: number): number =>
    goalFloor(finalTargetBytes) - delta; // 1425 - (-4) = 1429
  ```

  - **부호를 단위 테스트로 못 박는다**: `aliasByteDelta('김지훈', '［이름1］') === -4`, `modelTargetBytes(1500, -4) === 1504`. 지금 문구만으로는 반대로 구현해도 통과하기 때문이다(Architect M6).
  - **이건 정확한 계산식이 아니라 어림 보정이다.** 모델의 답에 별칭이 원문과 다른 횟수로 등장하면 과·소보정이 난다. 그래서 인수 기준은 "정확히 맞는다"가 아니라 **"부호와 크기가 맞고, 1차 명중률이 보정 없이보다 높다"**로 둔다. 최종 판정은 언제나 앱이 센 실제 바이트다.

- **키는 행의 마운트 키와 글자 그대로 같게**: `` `${studentRef}:${activeArea}:${subject ?? ''}` ``
  - **왜(Architect M3 · Critic B2)**: 행은 이 3축 키로 마운트된다(`RecordDraftView.tsx`의 `visibleStudents.map` 안 `key`). 그런데 부모 `RecordDraftView`는 `activeArea`가 내부 상태라 **영역을 바꿔도 다시 만들어지지 않는다.** 키를 `studentRef` 하나로 두면, 자율 활동에 1,782바이트를 쓰고 → 진로 활동으로 이동 → 진로에서 [분량 조절]을 눌렀을 때 **자율 활동 본문이 CLI로 나가고 진로 칸에 반영된다.** "활성 학생만 거른 배열의 위치를 출석번호로 쓴" 사고와 같은 유형이다.
  - **언마운트 때 자기 항목을 지우지 않는다(Architect A-N6 · Critic 비차단 1 채택).** 3축 키를 쓰면 남의 영역 글이 섞이는 일이 구조적으로 불가능하므로 삭제는 정확성에 필요 없고, 크기도 (학생 수 × 영역 수)라 무시할 만하다. 반대로 지우면 **영역을 바꿨다 돌아왔을 때 저장이 거부된 초과 글이 화면에서도 등록부에서도 사라져 완전히 소실된다.** 남겨 두면 [분량 조절]이 그 글을 되찾아 준다.
- **항목이 없을 때의 값을 명시한다(Architect M4)**: 행은 글자를 칠 때만 기록하므로 **한 번도 안 친 학생은 항목이 없다.**

  ```ts
  const currentText = liveTextRef.current.get(key) ?? draft?.content ?? '';
  ```

  `?? ''`로 두면 빈 글을 조절하게 된다. "타이핑한 적 없는 학생도 저장된 초안을 조절할 수 있다"를 인수 기준에 넣는다.

- **부모는 이 값을 행에 되돌려 쓰지 않는다.** 쓰는 자리는 아래 (3) 딱 한 곳이다.

### (2) 한도 전달

패널에 없던 것 2개를 넘긴다: **`area: RecordArea`** 와 **`level: SchoolLevel`**.

- 확인 결과 현재 패널 props에는 `areaLabel: string`(한국어 라벨)만 있고 `area`도 `level`도 **없다.**
- **왜 한도(숫자)가 아니라 이 둘인가(Critic N-B3)**: §C-1에서 `judgeLength` · `clampTargetBytes` · `defaultTargetBytes`의 서명을 `(area, level)`로 정했다. 한도 숫자만 넘기면 **계획이 정의한 함수를 계획이 정의한 prop으로는 부를 수 없다.** 넘기는 것은 **단일 진실원천 하나**(영역·학교급)이고, 한도와 확인 여부는 도메인 함수가 거기서 구한다.
- 화면에 `영역 한도 1,500바이트`를 적으려면 `areaLimit: number`를 함께 넘겨도 된다 — 표시용이다. (옛 개정본의 "같은 숫자를 두 곳에서 계산하지 않는다"는 근거 문장은 **삭제한다.** `judgeLength`가 안에서 `resolveAreaLimit`을 다시 부르므로 어차피 두 번 계산된다.)

### (3) 편집칸에 넣기 — 유일한 쓰기 경로 (오너 결정 2)

한도를 넘긴 조절 결과에만 나오는 **[편집칸에 넣기(저장 안 함)]**. 부모가 행에 **한 번만 배달되는 상자**를 내려보낸다: `{ key, text, token }`. 행은 토큰이 바뀔 때만 그 글을 편집 칸에 넣고 배달 완료를 알린다.

- 편집 칸은 **이미 한도를 넘긴 글자를 담을 수 있다** — 거부하는 건 저장(`upsert`)이지 입력이 아니다. 그래서 이 버튼이 성립한다.
- 다만 C0의 (ㄴ)을 먼저 고쳐야 한다. 안 고치면 넣자마자 다음 초점 이동에서 되돌아간다.
- 이 자리에도 §E-2의 비교 게이트를 통과시킨다 — 조절 시작 이후 선생님이 글을 고쳤다면 바로 덮지 않는다.
- 화면 문구: `저장하려면 52바이트를 더 줄여야 해요.`
- ★**배달은 "선생님이 그 글을 방금 친 것"과 완전히 같게 취급한다.** 배달을 받은 행은 편집 칸에 글을 넣는 것과 **동시에** (ㄱ) 위 (1)의 등록부에 같은 글을 기록하고, (ㄴ) C0 (ㄴ)이 쓰는 **마지막 편집 시각 도장을 지금으로 찍는다.**
  - **왜 필요한가**: 배달은 `onChange`를 타지 않는데, 등록부 기록도 편집 시각 도장도 **둘 다 타이핑에 걸려 있다.** 이걸 빼먹으면 두 가지가 한꺼번에 무너진다.
    1. 등록부에 **조절 전 옛 글이 남는다.** 1,552바이트를 넣은 직후 다시 [분량 조절]을 누르면 등록부는 1,782바이트 옛 글을 돌려주고, §E-2 비교 게이트도 옛 값으로 비교해 오작동한다.
    2. **도장이 안 찍혀 되돌아간다.** 배달한 글은 다음 `draft.updatedAt` 변화(동기화·다른 칸 저장·AI 반영)에 옛 글로 되돌아간다. **C0 (ㄴ)을 완벽히 고쳐도 이 기능만 그대로 무너진다.**
  - 이 자리는 §A-1 원칙 2가 "유일한 예외"로 인정한 쓰기 경로다. 예외가 자기 안전장치를 비껴가면 예외가 아니라 구멍이다. §F-2에 두 행으로 고정한다.

### (4) 실행 잠금·토큰을 부모로 올리기 (Architect M5)

패널은 `key={studentRef:area:subject}`로 **통째로 새 인스턴스가 된다.** 잠금과 토큰을 패널 안에 두면:

- 옛 인스턴스의 토큰은 옛 클로저에 살아 있어 **비교가 항상 통과**하고,
- 새 인스턴스의 잠금은 초기값이라 **CLI 왕복 2건이 동시에 돈다.**

즉 §E-5가 이름 붙인 바로 그 상황을 못 막는다. → **(ㄱ)안 채택**: 잠금과 토큰을 부모 `RecordDraftView`의 기억 상자에 두고 패널에 넘긴다. 부모는 학생·영역을 바꿔도 다시 만들어지지 않으므로 잠금이 살아남는다.

**아직 고르지 않은 조절 후보 두 개도 같은 자리에 둔다.** 잠금·토큰과 같은 부모의 기억 상자에 `` `${studentRef}:${activeArea}:${subject ?? ''}` `` 3축 키로 보관한다.

- **왜(★1 — 두 리뷰어가 독립적으로 같은 곳을 지적)**: 결정 7("1차 결과는 디스크에 안 남기고 고른 하나만 저장")과 결정 11("결과는 언제나 요청한 학생 칸에 저장")은 후보를 **패널 안에** 두면 동시에 참일 수 없다. 고르기 전에 다른 학생을 누르면 패널이 통째로 새로 만들어져 두 후보가 **사라지고**(결정 11이 거짓), 그렇다고 둘 다 디스크에 저장하면 결정 7이 막으려던 판 상한 소모가 그대로 일어난다.
  부모는 다시 만들어지지 않으므로, 후보를 부모에 두면 **두 결정이 동시에 성립한다.** M5 때문에 부모에 기억 상자를 이미 만들기로 했으므로 추가 비용이 거의 없다.
- 화면을 떠났다 돌아오면 후보 두 탭이 **그대로** 보인다. 디스크에 가는 것은 선생님이 고른 하나뿐이다.

**잠금은 반드시 풀린다 — 해제 조건을 계약으로 못 박는다 (Architect A-N2).** `askOnce`의 약속은 짝이 맞는 `done`/`error` 이벤트나 `run()` 거절이 있을 때만 결착한다. 메인 프로세스가 조용히 죽거나 실행 번호가 어긋나면 **영원히 기다린다.** 지금까지는 패널이 다시 만들어지면서 잠금이 초기화돼 저절로 풀렸지만, **부모로 올리면 이 화면을 떠났다 돌아올 때까지 초안 생성·분량 조절·[다시 표시]가 전부 잠긴다.** 이 저장소에는 "stdin 을 안 닫아 codex 가 무한 대기한" 전례가 있다.

1. 실행 코드는 **반드시 `finally`에서 잠금을 푼다.** 약속이 결착하면 패널이 사라졌더라도 옛 클로저가 실행되므로 동작한다.
2. **시간 상한**을 둔다. 왕복 상한을 넘기면 잠금을 풀고 `응답이 오지 않아 멈췄어요. 다시 시도해 주세요.`를 띄운다.
3. §F-2에 "실행이 결착하지 않아도 일정 시간 뒤 잠금이 풀린다" 테스트를 넣는다.

`RecordDraftAiPanel.tsx`가 이미 789줄이므로 조절 섹션은 새 파일로 뗀다: `src/adapters/components/RecordDraft/RecordDraftLengthPanel.tsx`.

```
분량 조절                         대상: AI 초안 v2
현재 1,782바이트                   영역 한도 1,500바이트

목표 분량 [ 1,500 ] 바이트
[줄이기] [근거로 보충하기]
```

스타일 규칙(어기면 반려):

- 색은 `sp-*` 토큰만. 하드코딩 HEX 금지. **`sp-*` 토큰에 Tailwind 투명도 수식(`bg-sp-card/40`)은 무효**이므로 쓰지 않는다(규칙 자체가 생성되지 않아 배경은 투명, ring은 파란 기본색이 된다). 반투명이 필요하면 기존 패널처럼 Tailwind 기본 색(`bg-blue-500/15`, `ring-blue-500/30`)을 쓴다.
- 라운드는 Tailwind 기본 키(`rounded-lg`, `rounded-full`)만. `rounded-sp-*` 금지, 직각 금지.
- 모든 문구 한국어. em 대시(`—`) 금지, 쌍점(`:`) 사용.
- 글자 크기는 **`text-xs` 이상, 본문·미리보기는 `text-sm` 이상**. 임의 rem 값(`text-[0.6rem]` 등)을 쓰지 않는다 — `recordDraftFontScale.meta.test.ts`가 그것만 본다.
  - ★**`DRAFT_TEXT_METRICS`를 미리보기에 붙이지 않는다.** 그건 `'px-3 py-2 text-sm leading-relaxed whitespace-pre-wrap break-words border rounded-lg'`로, **편집 칸과 형광펜 레이어를 픽셀 단위로 겹치게 하는 정렬 묶음**이지 일반 타이포 규격이 아니다. 미리보기에 붙이면 원치 않는 테두리와 여백이 생긴다. (옛 개정본이 이를 "타이포 규격이고 메타 테스트가 지켜 준다"고 잘못 적었다.)
- **모달을 만들지 않는다.** 인라인 접이식이라 `createPortal`이 필요 없다. 설계 검토에서 모달로 바뀌면 `createPortal`이 **필수**다.
- ★**되묻는 자리도 모달이 아니다 (Architect A-N3).** 이 계획에는 선생님에게 되묻는 자리가 두 곳 있다 — (ㄱ) 기재 금지 항목 확인(오너 결정 4 · ADR 결정 8), (ㄴ) §E-2의 `[최신 글로 다시 조절] / [그래도 이 글로 바꾸기]`. **둘 다 섹션 안 2단계 인라인 확인**으로 만든다. `[조절안 만들기]`를 누르면 그 자리에 붉은 안내와 두 버튼이 나타나고, 고르면 진행한다.
  - **왜**: 확인 창을 사이드 패널 안 모달로 만들면 §A-3 (b)를 기각한 바로 그 이유(유리 모드의 `backdrop-filter`가 화면 고정 요소를 가둔다)를 **뒷문으로 들이게 된다.** 굳이 모달로 가야 한다면 `createPortal`이 필수이고 회귀 항목과 실기기 확인을 함께 늘려야 한다.
- **디자인/UI/UX 단독 진행 금지.** S0·S3a에서 프론트엔드 디자인 에이전트와 협업한다. 에이전트가 빈 반환을 하면 재개 1회까지, 그 뒤에는 **"승인 못 받음"을 명시**하고 진행 여부를 오너에게 묻는다.

### C-3-1. 조절안 판의 버튼 규칙 (Critic B3)

기존 판 목록 블록은 판 종류를 가리지 않고 `[바꾸기] [뒤에 붙이기] [버리기] [내 글과 비교]`를 조건 없이 그린다. 1,782 → 1,463 조절안에서 [뒤에 붙이기]를 누르면 `1,782 + 1 + 1,463 ≈ 3,246바이트`가 되어 저장이 거부된다. **의미 없는 버튼을 보여 준 것이 원인이다.**

→ `adjust`가 붙은 판에서는:

| 버튼                            | 조절안 판에서                                         |
| ------------------------------- | ----------------------------------------------------- |
| `[바꾸기]` / `[반영]`           | **[이 글로 바꾸기]**로 이름만 바꿔 유지               |
| `[뒤에 붙이기]`                 | **숨긴다** (합산이 거의 항상 한도를 넘는다)           |
| `[내 글과 비교]`                | **[원문과 비교]**로 대체 (왼쪽 = `adjust.sourceText`) |
| `[버리기]`                      | 유지                                                  |
| **[편집칸에 넣기(저장 안 함)]** | `over-limit`일 때만 표시                              |

### C-3-2. 미저장 입력이 있으면 [뒤에 붙이기]를 막는다 (오너 결정 6 · Architect A-N9)

[뒤에 붙이기]의 앞글은 **저장된** 글인데 분량 조절은 **화면의 현재 입력**을 쓴다. 이 어긋남 때문에, 미저장 입력이 있는 채 [뒤에 붙이기]를 누르면 그 입력이 조용히 사라진다. 통일은 이번 범위 밖이므로(§B-2) **막고 이유를 표시**한다: `저장되지 않은 글이 있어요. 먼저 저장하거나 분량을 줄여 주세요.`

- **"미저장"의 정의를 못 박는다**: 행의 `flush`가 쓰는 술어를 **통째로 그대로** 쓴다 — `text.trim().length > 0 && text !== (draft?.content ?? '')`. ★앞 조건을 빼면 **칸을 완전히 비운 상태가 영구 미저장으로 판정돼 [뒤에 붙이기]가 계속 막힌다**(빈 칸은 저장할 것이 없으므로 `flush`가 성공으로 본다). 저장 상태 표시(`saveState`)로 판정해도 틀린다(저장이 끝난 뒤에도 `idle`이 된다).
- 이 판정은 행 안에서만 가능하므로, 부모가 **등록부의 현재 입력과 저장값을 비교해** 패널에 `hasUnsavedInput: boolean`으로 내려 준다.
- **이 절충이 죽은 버튼을 새로 만들지는 않는다**: 자동저장이 700밀리초라 미저장 창이 열려 있는 경우는 사실상 **저장이 거부된 초과 글일 때뿐**이고, 그때는 붙이기 합산이 어차피 한도를 넘어 거부된다.
- 담당 단계: **S3b**. §F-2에 테스트 한 행.

## C-4. S4 상세 — 안전 배선

- **중복 실행 잠금**: 부모의 기억 상자에 둔 잠금 하나로 초안 생성 · 분량 조절 · 형광펜 [다시 표시] 셋을 함께 막는다(C0 (ㄷ)에서 참조 방식으로 바꾼 것을 여기서 부모로 올린다). **`finally`에서 반드시 풀고, 시간 상한을 둔다**(§C-2 (4)).
- **늦게 도착한 결과**: 실행 시작 때 부모의 기억 상자에 토큰(번호 하나)을 적고, 결과가 왔을 때 그 값이 그대로인지 본다. 다르면 **미리보기 초점만** 버린다.
- **후보와 결과의 자리**: 아직 고르지 않은 조절 후보는 부모의 기억 상자에 3축 키로 남고, **선생님이 고른** 결과 판만 요청한 학생 칸에 저장된다(§C-2 (4) · ADR 결정 7·11).
- **반영 실패 표시**: C0 (ㄱ)에서 만든 `try/catch`를 조절 반영에도 그대로 쓴다.

# E. 연결부 8건 — 각각의 구체적 해결책

분석 §5는 8개 항목이다(옛 개정본이 "7건"으로 잘못 셌다).

### E-1. 미저장 글 전달

- **문제**: 행의 현재 입력과 저장된 `draft.content`는 다르다. 한도를 넘긴 입력은 저장이 거부되므로 디스크에 없고, **C0 (ㄴ)을 고치기 전에는 초점이 빠지는 순간 화면에서도 사라진다.**
- **해결**: C0 (ㄴ) 수리 + §C-2의 3축 키 등록부. 항목이 없으면 `draft?.content ?? ''`로 떨어진다.
- **회귀 #68**: "조절은 저장된 글이 아니라 행의 현재 입력을 쓴다" — **통합 테스트 존재·생존 검사** 형태(§F-3).

### E-2. 편집 도중 결과 도착

- 실행 시작 시 `sourceText`를 붙들어 둔다. **[이 글로 바꾸기]와 [편집칸에 넣기] 둘 다** 누르는 순간 등록부에서 행의 최신 입력을 읽어 `sourceText`와 비교한다.
  - 같으면 진행. 다르면 덮지 않고 `그 사이에 글을 고치셨어요.` + `[최신 글로 다시 조절] / [그래도 이 글로 바꾸기]`. 자동으로 고르지 않는다. **이 두 갈래도 모달이 아니라 섹션 안 인라인으로 띄운다**(§C-3).
  - ★[편집칸에 넣기]로 배달한 글은 등록부에도 함께 기록되므로(§C-2 (3)), 넣은 직후 다시 조절해도 이 비교가 **넣은 글 기준으로** 돈다.
- **회귀 #69**: "반영 전에 최신 입력과 `sourceText`를 비교한다".

### E-3. 원문 비교

- 기존 [내 글과 비교]는 저장된 내 글 ↔ AI 판을 본다. v2를 줄인 v3은 **v2와** 비교해야 한다.
- 조절안 판에는 [원문과 비교]를 둔다(왼쪽 = `adjust.sourceText`, 오른쪽 = 조절안 본문). 조절안 판에서 [내 글과 비교]는 **숨긴다**(§C-3-1).
- 좁은 폭에서는 위아래로 떨어지는 반응형.

### E-4. 반영 실패

- C0 (ㄱ)에서 만든 `try/catch`를 조절 반영에도 쓴다. 실패하면 미리보기·원문 유지, 오류 문구 표시, `markApplied` 미호출, 큐 미진행.

### E-5. 실행 상태 (중복 실행 · 잘못된 대상)

- 잠금·토큰을 **부모로 올린다**(§C-2 (4)). 패널이 다시 만들어져도 잠금이 살아남는다. 대신 **`finally` 해제 + 시간 상한**이 반드시 함께 간다 — 안 그러면 응답이 영영 안 올 때 그 화면의 AI 기능이 통째로 잠긴다.
- **아직 고르지 않은 조절 후보 두 개**는 부모의 기억 상자에 3축 키로 남는다. 화면을 떠났다 돌아와도 그대로 있다.
- **선생님이 고른** 결과 판은 언제나 요청한 학생 칸에 저장된다. 버리는 것은 미리보기 초점뿐이다.
- "남은 학생 모두" 일괄 생성은 현재 학생의 조절이 끝날 때까지 대기한다. **반대 방향도 의도한 것이다** — 일괄 생성이 도는 동안(수 분이 걸릴 수 있다)에는 분량 조절도 막힌다. 한 화면에서 CLI 왕복 두 건이 동시에 도는 것을 허용하지 않는 편이 결과가 뒤섞이는 것보다 낫다.
- 조절 중인 학생도 `onActiveChange`에 실어 필터가 걸려 있어도 행이 사라지지 않게 한다.

### E-6. 영역 한도

- 부모가 **`area`와 `level`**을 넘긴다(§C-2 (2)). 한도와 확인 여부는 도메인 함수가 이 둘에서 구한다 — 그래야 `judgeLength(…, area, level)`을 부를 수 있고 한도와 확인 여부의 짝이 어긋날 방법이 없다. 화면 표시용 `areaLimit`을 함께 넘기는 것은 무방하다.
- 목표 입력은 확인된 한도에서 `clampTargetBytes`로 잘린다.
- `isAreaLimitVerified(area, level) === false`(초등)면 `한도 수치는 확인 중이에요.`를 함께 쓰고 **반영을 절대 막지 않는다**. `judgeLength`가 구조적으로 `over-limit`을 못 내놓는다.

### E-7. 기록 상태 · 되돌리기

- 조절안 반영은 기존 [반영]과 **똑같은 경로**(`onApply` → `upsertDraft`)를 탄다. 따라서 교사 검토 필요 상태·금지 항목 경고·서사 품질 점검이 자동으로 다시 돈다. 새 경로를 만들지 않는다.
- 30초 [되돌리기]를 조절 반영에도 붙인다(형광펜 표식도 함께).
- 조절안 판에도 `markApplied`를 찍어 판 탭에 `✓`가 뜨게 한다.

### E-8. 데이터 · 주제 범위 (분석 §5의 8번째 항목 "데이터" + 분석 §3의 주제 고정 + Critic B7)

- `RecordAiDraft`에 선택 필드 `adjust` 하나만 추가한다(§D-1). 내 글의 영구 이력 보존은 이번 범위 밖.
- **주제(`threadId`) 범위 고정**: 분석 §3은 "조절을 시작한 AI 판의 `threadId`를 기준으로 근거 범위를 고정한다"고 요구했는데 옛 개정본에는 `threadTitle?`만 있고 **누가 정하는지가 없었다.**
  - 패널의 기존 근거 선별은 **현재 칩 상태**를 본다. 그대로 두면 주제 B로 쓴 v2를 보충할 때 칩이 주제 A면 **주제 A 근거가 섞인다.**
  - → `mode === 'expand'`의 근거 범위는 **조절 대상 판의 `threadId`**로 고정한다. 직접 쓴 글이면 현재 영역 전체 근거를 쓰고 화면에 `주제: 전체 근거`라고 적는다. **현재 칩 선택은 조절에 영향을 주지 않는다.**

- 화면: 실패는 반드시 **한국어 문장**으로 뜬다. 조용한 실패를 만들지 않는다.
- 콘솔: `[RecordLengthAdjust]` 태그로 **수치만** — `mode`, `finalTargetBytes`, `modelFloorBytes`, `modelTargetBytes`, `sourceBytes`, `attempt1Bytes`, `attempt2Bytes`, `pickedAttempt`, `evidenceCount`, **`evidenceChars`**, `verdict`, `insufficientEvidence`. **본문·이름은 절대 남기지 않는다.**
  - `evidenceChars`(보낸 근거의 총 글자 수)가 없으면 §A-4 시나리오 1의 조기 경보 하나("늘어난 바이트가 보낸 근거 총 길이보다 크다")를 **잴 수 없다.** 신호를 적어 놓고 재는 수치를 안 남기면 경보가 아니다.
- 이 수치가 있어야 A-4 시나리오 2의 조기 경보("재조정 후에도 목표 밖이 절반 이상")를 실사용에서 볼 수 있다.

# I. ADR 초안 — ADR-086

> 파일: `docs/03-decisions/ADR-086.md` (HEAD `880a82c4`에서 마지막 번호 ADR-085 재확인) · `DECISIONS.md` 맨 아래 한 줄

**제목**: ADR-086 · 생기부 분량 조절은 "앱이 세고, 한 번만 다시 묻고, 반영 전까지 원문을 안 건드린다"

**Decision (결정)**

1. 분량 조절은 **오른쪽 AI 패널 안 접이식 섹션**으로 만든다. 별도 모달·전체 화면을 만들지 않는다.
2. 바이트는 **앱이** 최종 저장 본문으로 센다 — `neisByteLength(aiDraftText(판))`, [뒤에 붙이기]는 `appendedBytes(앞글, 새글)`. 모델이 말한 숫자는 화면에 쓰지 않는다.
3. 목표 범위를 벗어나면 **자동 재조정은 딱 1회**. 그 뒤에는 실제 수치와 이유를 표시하고 멈춘다. 문자열을 잘라 맞추지 않는다.
4. 조절 대상 본문의 마스킹은 **조립 함수(`buildLengthAdjustPack`) 안에서** 한다. 별칭 보정도 그 안에서 하고 `modelTargetBytes`·`finalTargetBytes`를 함께 돌려준다.
5. **분량 조절도 규정 지시문(L1)을 받고, 못 받으면 실행하지 않는다.** 초안 생성과 같은 게이트다.
6. 결과는 **새 판**으로 남기고, `[이 글로 바꾸기]` 전까지 선생님의 글은 바뀌지 않는다. 반영 뒤 30초 [되돌리기]를 붙인다.
7. **자동 재조정의 1차 결과는 디스크에 남기지 않는다.** 선택 전까지 후보 두 개를 **부모 화면의 기억 상자에 3축 키로** 두고(패널이 아니다 — 패널은 학생을 바꾸면 통째로 새로 만들어진다), **고른 하나만** 저장한다. 판에는 실제 왕복 횟수(`attempts`)와 고른 쪽(`pickedAttempt`)을 적는다. (ADR-085의 "만든 것마다 전부 남긴다"에서 벗어나는 지점 — 교사 관점에서 재조정은 한 번의 요청이고, 판 상한 20개를 두 배로 갉아먹지 않기 위해서다. 화면에는 둘 다 보이고 화면을 떠났다 돌아와도 그대로이므로 "보여 준다"는 취지는 지킨다.)
8. **기재 금지 항목이 든 본문은 문장을 지우지 않고 그대로 보내되, 보내기 전에 확인을 띄운다.** 자동 삭제는 §A-3 (d)에서 무효화한 조용한 삭제의 재현이다.
9. 반영 차단은 **확인된 한도**에서만 한다. 개인 목표만 넘고 한도 이내면 수치만 표시한다. **한도를 넘어도 결과를 버리지 않는다** — [편집칸에 넣기(저장 안 함)]로 이어서 손볼 수 있게 한다.
10. `mode:'expand'`의 근거 범위는 **조절 대상 판의 `threadId`**로 고정한다. 현재 칩 선택은 조절에 영향을 주지 않는다.
11. 실행 잠금과 요청 토큰, 그리고 **아직 고르지 않은 조절 후보**는 **부모 화면(`RecordDraftView`)**이 든다. **선생님이 고른** 결과 판은 언제나 요청한 학생 칸에 저장된다(초점이 다른 학생으로 옮겨 갔더라도). 잠금은 `finally`에서 반드시 풀리고 **시간 상한**을 갖는다 — 부모로 올린 잠금이 안 풀리면 그 화면의 AI 기능이 통째로 잠긴다.

**Drivers (결정 동인)**

- 개인정보: 이번 기능부터 **편집 중인 초안 본문**이 외부 CLI로 나가고, 그 본문은 기재 금지 필터를 거친 적이 없다.
- 데이터 보호: 한도를 넘긴 글은 저장이 거부될 뿐 아니라 초점을 잃으면 화면에서도 사라진다(수리 대상).
- 기존 결함 위에 새 기능을 얹지 않는다: 좁은 영역에서만 이미 3건을 찾았다.

**Alternatives considered (고려한 대안)**

- **별도 모달/전체 화면 비교 편집기**: 비교 폭은 넓지만 유리 모드의 `backdrop-filter` 함정을 정면으로 맞고 흐름이 두 곳으로 갈라진다. **기각.**
- **사후 조절 없이 첫 생성에 목표만 싣기**: 이미 있는 글을 못 고친다. **부분 채택**(첫 생성에도 목표를 싣되 사후 조절을 함께 만든다).
- **앱이 코드로 문장을 잘라 맞추기**: 교사 평가가 조용히 사라진다. **무효화.** 같은 이유로 기재 금지 문장의 자동 삭제도 **무효화.**
- **모델이 보고한 바이트 수를 신뢰**: 프롬프트로 규정을 못 막는다는 실측이 있다. **무효화.**
- **잠금·토큰을 패널 안에 두기**: 패널이 학생·영역마다 다시 만들어져 잠금이 초기화되고 옛 토큰 비교가 항상 통과한다. **무효화**(부모로 올린다).
- **한도 초과 결과를 완전히 사용 불가로 두기**: CLI 왕복 1~2분이 통째로 버려지고, 선생님은 손으로 다시 쓴다. **기각**(편집칸에 넣기로 대체).

**Why chosen (왜 이걸 골랐나)**

기존 패널에는 판 · 미리보기 · 비교 · 반영 · 되돌리기가 이미 다 있다. 분량 조절은 그 문법에 **한 종류의 판을 더하는 일**이지 새 화면을 만드는 일이 아니다. 새 화면을 만들면 개인정보 경로와 실패 처리 경로가 하나 더 생기고, 이 프로젝트에서 사고는 늘 "경로가 둘로 갈라진 자리"에서 났다.

**Consequences (결과)**

- `RecordAiDraft`에 선택 필드 `adjust`가 생긴다. 옛 파일에는 없으므로 **부재를 빈 값으로 덮지 않는 계약**이 하나 늘어난다. `RecordAiDraftAddInput`과 `add`의 객체 생성부 **양쪽**에 넣어야 한다.
- **한도를 넘어 `record-drafts.json`에는 저장이 거부된 본문이, `record-ai-drafts.json`에는 `adjust.sourceText`로 남고 동기화된다.** 사실상 한도 강제를 우회해 보관하는 셈이다. 의도된 절충이며, 판 상한(20)과 학년도 전환 초기화가 자연 만료를 준다.
- 판 저장 용량이 조절안마다 원문 스냅숏만큼 늘어난다(칸당 최대 약 60KB).
- `RecordDraftView`가 행의 현재 입력을 읽는 3축 키 등록부를 갖는다. 쓰는 자리는 [편집칸에 넣기] 한 곳뿐이고 회귀 항목 2건이 지킨다.
- `useState` 기반 중복 실행 잠금이 참조 기반으로 바뀌고 부모로 올라간다(기존 [다시 표시] 포함).
- 초안 행이 "내 손글씨가 더 최신이면 되돌리지 않는다"는 규칙을 갖는다.
- 브릿지 바이트 계약과 동기화·보관함 등록은 **바뀌지 않는다.**

**Follow-ups (후속)**

1. 학급 전체 일괄 분량 조절.
2. 학기 간 잔여 바이트 계산(2026학년도 공통과목 1·2학기 합산) — 과목 매핑 선행.
3. 실제 NEIS 입력창과 줄바꿈·특수문자 바이트 대조(브릿지 계약과 함께).
4. 판 상한 20 → 12 하향 검토.
5. 내 글 영구 이력 보존 — ADR-085와 별도 결정.
6. [뒤에 붙이기]의 앞글 기준을 "화면의 현재 입력"으로 통일할지 재검토.

# J. 롤백 계획

## J-1. 되돌리기 단위

**커밋 5개**로 나눈다. 각 커밋은 **경로를 지정해서** 만든다: `git commit -m "..." -- <path> <path>`.

| 커밋   | 내용                                                      | 단독 되돌리기                                                                                                  |
| ------ | --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| **C0** | 기존 결함 3건 수리 + 그 테스트                            | 가능하지만 **되돌리지 말 것** — 새 기능과 무관하게 지금도 있는 결함을 고친 것이다. 되돌리면 옛 결함이 돌아온다 |
| C1     | S1 도메인 + 단위 테스트                                   | 가능. 화면이 안 쓰면 동작 변화 없음                                                                            |
| C2     | S2 배선(등록부 · 한도 · 잠금 올리기 · 편집칸에 넣기 배달) | C3를 먼저 되돌린 뒤에 가능                                                                                     |
| C3     | S3a·S3b UI                                                | 가능. 되돌리면 버튼만 남으므로 C2와 함께                                                                       |
| C4     | S4 안전 배선 + S5a 테스트·이음매·회귀 + S5b 문서·ADR      | 가능                                                                                                           |

## J-2. 되돌릴 때 확인할 것

1. **데이터는 되돌릴 필요가 없다.** `adjust`는 선택 필드라 코드를 되돌려도 이미 저장된 판은 그대로 읽힌다. 되돌린 뒤에는 그냥 AI 판으로 보인다 — 손상이 아니다.
2. **위에서부터 되돌린다**(C4 → C3 → C2 → C1). C1만 되돌리고 C3을 남기면 빌드가 깨진다. **C0은 마지막까지 남긴다.**
3. 되돌린 뒤 검증 게이트 4종을 다시 돌린다. 특히 `npm run regression-check`에서 **#68·#69가 함께 빠졌는지** 확인한다(코드는 지웠는데 검사만 남으면 빨간불이 된다). `ownAiEgress.test.ts`에 추가한 `describe`도 함께 뺀다.
4. `/docs` 가이드도 함께 되돌린다. 기능이 없는데 가이드가 남으면 선생님이 없는 버튼을 찾는다.
5. 되돌리기 커밋도 **경로 지정**으로 만든다.

## J-3. 긴급 무력화 (되돌리기보다 빠른 길)

- 조절 진입점은 실험실 스위치(`ownAiEnabled`, "내 AI로 실행")에 매여 있다. 이 스위치를 끄면 AI 초안 자체가 사라지므로 조절도 함께 사라진다.
- 조절만 끄고 싶다면, S3a에서 조절 섹션 노출 조건을 **한 곳의 상수**로 모아 둔다. 그 상수 하나를 `false`로 바꾸는 한 줄 커밋이 긴급 무력화 경로가 된다.
