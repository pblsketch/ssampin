## 한 문단 요약

선생님이 구독 AI(클로드 코드 · 코덱스)로 생기부 초안을 받으면, 결과가 영역 한도(예: 1,500바이트)를 넘거나 반대로 너무 짧게 나옵니다. 지금은 넘친 글은 **저장 자체가 거부**되고, 짧은 글은 아무 안내가 없습니다. 이 계획은 오른쪽 AI 패널 안에 접었다 펴는 **[분량 조절]** 칸을 하나 만들어, "이 글을 1,500바이트에 맞게 줄여 줘" 또는 "모아 둔 근거로 조금 더 채워 줘"를 한 번에 부탁하고, **앱이 직접 바이트를 세어** 맞았는지 판정한 뒤, 새 판(버전)으로 남겨 원문과 나란히 비교하고 선생님이 [이 글로 바꾸기]를 눌러야 실제 글이 바뀌게 합니다.

# A. RALPLAN-DR 요약

## A-1. 원칙 (이 기능이 지켜야 할 5가지)

1. **모델이 센 숫자를 믿지 않는다.** 바이트는 실제로 저장·복사될 최종 본문으로 **앱이** 센다. AI가 "1,480바이트로 맞췄습니다"라고 말해도 그 문장은 화면에 쓰지 않는다.
   - 근거: 이 저장소에서 "프롬프트로는 규정을 못 막는다"가 실측으로 확인됐다(금지 항목을 전부 열거해도 모델이 그대로 옮겨 적음, 2/2 실패 → `useRecordDraftsStore.ts` 주석).
2. **원문은 [이 글로 바꾸기] 전까지 한 글자도 바뀌지 않는다.** 조절 결과는 미리보기다. 실패해도, 취소해도, 화면을 닫아도 선생님이 쓰던 글은 그대로다.
3. **가리는 일(이름 마스킹)은 조립 함수 안에서 한다.** "부르는 쪽이 이미 가렸을 것"이라는 주석 계약은 이 저장소에서 실제로 깨져 다른 학생 실명이 외부 CLI로 나간 적이 있다. 조절 대상 글도 **원문 그대로 넘겨받아 꾸러미 안에서** 가린다.
4. **못 맞추면 정직하게 못 맞췄다고 말한다.** 문자열 끝을 강제로 자르지 않고, 근거 없이 채우지 않고, 무한 재시도하지 않는다. 자동 재조정은 **딱 1회**.
5. **한도는 확인된 것만 강제한다.** 초등처럼 공식 수치를 확인하지 못한 영역(`isAreaLimitVerified === false`)은 이 기능이 새로운 강제 한도로 승격시키지 않는다. 목표는 제안하되 반영을 막지 않는다.

## A-2. 결정 동인 Top 3

| 순위 | 동인                                 | 왜 이게 1순위인가                                                                                                                                                                                                                                                               |
| ---- | ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | **개인정보**                         | 지금까지는 "근거 자료"만 외부 AI로 나갔다. 분량 조절은 **선생님이 지금 쓰고 있는 초안 본문**을 내보낸다. 초안에는 근거보다 더 다듬어진 학생 서술이 들어 있고, 다른 학생 이름이 섞여 있을 수 있다. 마스킹 경로를 새로 만들지 않고 기존 조립 함수 안에 넣는 것이 최우선 제약이다. |
| 2    | **선생님이 쓴 글을 잃지 않는 것**    | 한도를 넘긴 글은 지금 **저장이 거부된다**(`useRecordDraftsStore.upsert` → `RecordDraftLimitError`). 즉 "조절해야 할 그 글"은 디스크에 없다. 저장소에서 다시 읽어 오는 구현은 조절해야 할 글을 잃는다. 화면의 현재 입력을 직접 넘기는 길을 먼저 내야 한다.                       |
| 3    | **최소 범위 · 미커밋 변경과의 공존** | 지금 작업 트리에 v3 화면·근거 보드 변경이 **커밋되지 않은 채** 여러 파일에 걸쳐 있다(`RecordDraftView.tsx`, `recordDraftPack.ts`, `useRecordDraftsStore.ts` 등). 새 화면 뼈대나 새 저장 구조를 만들지 않고 기존 판(`RecordAiDraft`) 위에 얹어야 충돌·되돌리기 비용이 작다.      |

## A-3. 실행 가능한 선택지

### (a) AI 패널 안 접이식 [분량 조절] 섹션 — **권장**

지금 있는 오른쪽 「AI 초안」 패널 안에, 판 미리보기 아래에 접었다 펴는 칸을 하나 더 만든다.

- 장점
  - 새 창·새 화면이 없다. 유리 모드에서 사이드바 안 모달이 갇히는 문제(`createPortal` 필수 규칙)를 아예 피한다.
  - 판(버전) 탭 · 미리보기 · [내 글과 비교] · [반영] 이 이미 그 자리에 있어 조절안도 같은 문법으로 다룰 수 있다.
  - 학급 운영·수업 관리가 공통 `RecordDraftView`를 쓰므로 한 번 만들면 양쪽에 붙는다.
- 단점(한정적)
  - 패널이 세로로 길어진다. 판 탭·비교·조절이 한 화면에 쌓이면 스크롤이 늘어난다 → 접힘 기본값과 섹션 순서를 디자인 단계에서 정해야 한다.
  - 좌우 비교 폭이 좁다. 1,500바이트 두 벌을 나란히 놓기에 패널 폭이 빠듯하다 → 비교는 "원문 / 조절안" 2열을 세로 스택으로 떨어뜨리는 반응형이 필요하다.
  - `RecordDraftAiPanel.tsx`가 이미 778줄이다. 여기에 250줄을 더하면 한 파일이 1,000줄을 넘는다 → 조절 섹션을 별도 컴포넌트 파일로 떼어 낸다(같은 폴더).

### (b) 별도 모달 / 전체 화면 비교 편집기

- 장점
  - 원문·조절안을 넓게 좌우로 놓을 수 있어 긴 글 비교가 편하다.
  - 목표 입력·모드 선택·재시도를 한 화면에 크게 배치할 수 있다.
- 단점(한정적)
  - **유리 모드 함정을 정면으로 맞는다.** 사이드바 안에서 뜬 모달은 `backdrop-filter` 때문에 화면에 갇힌다 → `createPortal` 필수, 회귀 검사 대상 추가, 실기기 확인 항목 증가.
  - 판(버전)·비교·반영 흐름이 패널과 모달 두 곳으로 갈라진다. 같은 개념이 두 문법으로 존재하면 "어느 쪽이 진짜 내 글인가"가 흐려진다.
  - 화면 하나를 새로 만드는 만큼 디자인 에이전트 협업·실기기 QA 범위가 눈에 띄게 커진다.
- **판정: 첫 버전에서 채택하지 않는다.** 비교 폭 문제는 (a)의 반응형으로 충분히 완화되고, 유리 모드 리스크를 지불할 만큼의 이득이 없다. 실사용에서 "비교가 좁아 못 쓰겠다"는 신고가 쌓이면 2차에서 재검토한다.

### (c) 사후 조절 없이, 첫 생성 요청에 목표 분량만 실어 보내기

- 장점
  - 변경이 가장 작다. `DraftPackInput`에 목표 필드 하나 추가하고 프롬프트 한 줄이면 끝난다.
  - 새 UI·새 판 종류·새 실패 상태가 생기지 않는다.
- 단점(한정적)
  - **이미 있는 글을 못 고친다.** 선생님이 직접 쓴 1,780바이트 글, 혹은 예전에 반영해 둔 글은 손댈 방법이 없다. 이 과제가 시작된 자리가 바로 거기다.
  - 목표를 넣어도 모델이 맞추지 못했을 때 할 수 있는 게 "처음부터 다시 생성"뿐이다. 다시 생성하면 내용이 통째로 바뀌어 선생님이 손본 부분이 날아간다.
- **판정: 단독 안으로는 채택하지 않는다.** 다만 **(a)와 같이 넣는다** — 첫 생성에도 목표 바이트를 선택적으로 실어 보내면 조절을 눌러야 하는 횟수 자체가 줄어든다(분석 §5 마지막 문단). 비용이 거의 없다.

### (d) 앱이 코드로 잘라 맞추기 (문장 단위 절삭) — **무효화**

- 무효화 사유: 생기부는 문장 하나가 학생 평가의 근거다. 뒤 문장을 기계적으로 버리면 "교사 평가"가 통째로 사라지고, 선생님이 그걸 눈치채지 못한 채 NEIS에 넣는다. 이 저장소에는 이미 **"끌 수 없는 필터가 데이터 소실처럼 보인다"**는 실제 사고가 있다(근거 8건이 조용히 사라짐, 게이트 4종은 전부 초록). 조용히 문장을 버리는 기능은 같은 사고를 훨씬 위험한 자리에서 반복한다.
- 예외적으로도 쓰지 않는다: 분석 §4-5의 "문자열 끝을 강제로 자르지 않는다"를 코드 주석이 아니라 **테스트로** 고정한다.

## A-4. 사전 부검 (pre-mortem) — "6주 뒤 이 기능이 실패했다. 왜?"

### 시나리오 1 — 보충하기가 근거 없이 지어냈고, 그대로 NEIS에 들어갔다

- **무슨 일이 벌어졌나**: 620바이트 글에 [근거로 보충하기]를 눌렀는데 보낼 수 있는 근거가 1건뿐이었다. 모델은 빈칸을 채우려 "모둠 발표에서 리더 역할을 맡아"처럼 그럴듯하지만 근거에 없는 문장을 넣었다. 화면은 "1,463바이트 · 목표 달성"만 보여 줬고, 선생님은 길이가 맞으니 통과한 줄 알고 반영했다.
- **조기 경보 신호**
  - 보충하기 결과의 늘어난 바이트가 **보낸 근거 총 길이보다 크다**(없는 재료로 채웠다는 뜻).
  - 근거 건수 0~1건인데 목표를 "달성"으로 표시한 실행이 로그에 남는다.
  - QA에서 "AI가 안 한 활동을 썼다"는 신고.
- **예방책**
  - 보낼 수 있는 근거가 **0건이면 [근거로 보충하기] 버튼 자체를 비활성화**하고 이유를 쓴다(`보충할 근거가 없어요. 먼저 근거 보드에서 기록을 넣어 주세요.`).
  - 조절안 옆에 **항상** `근거 N건 사용 · 제외 M건`을 붙인다. 길이 숫자만 크게 보여 주지 않는다.
  - 목표 미달로 멈춘 결과에도 성공색(초록)을 쓰지 않는다. 문구는 `근거가 부족해 목표보다 짧게 작성했어요.`로 고정한다.
  - **품질 자동 판정을 하지 않는다.** "사실 보존이 검증됐다"는 표시를 절대 만들지 않는다(분석 §3). 화면은 "확인은 선생님이 합니다"를 유지한다.

### 시나리오 2 — 두 번 눌러도 목표를 못 맞춰서 아무도 안 쓴다

- **무슨 일이 벌어졌나**: 1차 결과가 1,610바이트, 자동 재조정 후 1,552바이트. 여전히 초과라 [이 글로 바꾸기]가 비활성. 선생님은 세 번째로 [조절안 만들기]를 눌렀고 이번엔 1,340바이트로 너무 짧아졌다. 매번 30~60초를 기다린 끝에 결국 손으로 지웠다.
- **조기 경보 신호**
  - 재조정 1회 후에도 목표 범위 밖인 실행이 **절반을 넘는다**(관측 로그의 수치 요약).
  - 같은 칸에서 조절 판이 3개 이상 쌓인 실행이 반복된다.
  - "차라리 손으로 지우는 게 빠르다"는 피드백.
- **예방책**
  - 목표를 **약속으로 말하지 않는다.** 화면 문구는 "정확히 1,500"이 아니라 "1,500바이트 안에서 가깝게"다. 내부 목표 범위 95~100%(1,500이면 1,425~1,500)는 판정에만 쓰고 규정상 최소 분량처럼 표시하지 않는다.
  - **별칭 보정**을 넣는다: 모델은 실명이 아니라 `［이름1］` 같은 별칭을 보고 쓴다. 별칭과 실명의 바이트 차이만큼 모델에게 주는 목표를 미리 보정하면 1차 명중률이 올라간다(§C-1에 계산식).
  - 재조정 후에도 안 맞으면 **[다시 시도]가 아니라 [목표 바꾸기]를 먼저 제시한다.** 실패를 반복시키지 않고 선생님의 결정을 묻는다.
  - **개인 목표만 넘고 실제 영역 한도 이내면 반영을 막지 않는다.** `목표보다 52바이트 많음`만 표시하고 선택은 선생님에게 넘긴다(분석 §4-7).

### 시나리오 3 — 조절하는 사이 선생님이 쓰던 글이 날아갔다

- **무슨 일이 벌어졌나**: [분량 조절]을 누르고 결과를 기다리는 동안 선생님이 초안 칸을 더 고쳤다. 결과가 도착해 [이 글로 바꾸기]를 눌렀더니, 조절이 시작될 때의 옛 글을 기준으로 만든 결과가 방금 고친 내용을 통째로 덮었다. 또 다른 경로에서는 [분량 조절] 버튼이 화면을 다시 그리면서 편집 칸이 **저장된 옛 글**로 되돌아가, 저장에 실패해 남아 있던 초과분 글자가 사라졌다.
- **조기 경보 신호**
  - QA에서 "취소했는데 글이 짧아졌다", "방금 쓴 문장이 없어졌다"는 신고.
  - `RecordDraftRow`의 편집 상태(`text`)와 저장된 `draft.content`가 어긋난 상태에서 리렌더가 도는 코드 경로가 새로 생긴다.
- **예방책**
  - 행의 현재 입력은 **읽기만** 한다. 부모는 값을 되돌려 쓰지 않는다(§E-1의 등록부 방식 — 렌더를 유발하지 않는 참조로만 읽는다).
  - 조절 시작 시점의 원문(`sourceText`)을 붙들어 두고, [이 글로 바꾸기] 순간에 **행의 최신 입력과 다시 비교**한다. 다르면 덮지 않고 `그 사이에 글을 고치셨어요. 최신 글로 다시 조절할까요?`를 띄운다.
  - 조절 반영에도 기존 **30초 [되돌리기]**를 붙인다.
  - 이 두 가지를 회귀 검사(REGRESSION #68, #69)로 못 박아 다음 사람이 무심코 되돌리지 못하게 한다.

## C-1. S1 상세 — 계산과 요청문 (도메인, 외부 의존성 없음)

**신규 `src/domain/rules/recordLengthGoal.ts`** — 순수 함수만. 화면도 저장소도 모른다.

- `defaultTargetBytes(limit)` : 목표 기본값 = 영역 한도.
- `goalFloor(targetBytes)` : 목표 하한 = `Math.ceil(targetBytes * 0.95)`. 1,500 → 1,425.
- `judgeLength({ bytes, targetBytes, limit, limitVerified })` → `'ok' | 'under-goal' | 'over-goal' | 'over-limit'`
  - `over-limit`은 **`limitVerified === true`일 때만** 나온다. 초등의 미확인 한도는 절대 `over-limit`이 되지 않는다(원칙 5).
- `appendedBytes(base, addition)` : [뒤에 붙이기] 합산 길이. **기존 글 + 공백 한 칸 + 새 글**로 센다.
  - ★분석 §4-7은 "기존 글 + 빈 줄 + 새 글"이라고 적었으나 **코드는 공백 하나로 잇는다**(`applyVersion` 의 `` `${base.trim()} ${text}` ``, `aiDraftText`의 `join(' ')`, 오너 결정 2026-09-06). 실제 저장값과 어긋나지 않도록 **공백 한 칸**이 맞다. → §정정 목록 참조.
- `aliasByteDelta(realText, maskedText)` : 실명본과 별칭본의 바이트 차이. 모델에게 줄 목표를 `targetBytes - delta`로 보정하는 데 쓴다. (모델은 별칭만 보는데 최종 저장은 실명으로 되돌린 글이라 길이가 달라진다 — 분석 §4 마지막 문단의 실제 원인.)

**수정 `src/domain/services/recordDraftPack.ts`** — `buildLengthAdjustPack(input)` 추가.

- 왜 이 파일인가: **가리는 자리를 한 곳에 둔다**는 이 프로젝트의 원칙(주석 계약 사고의 재발 방지). 새 파일에 마스킹을 또 만들면 두 곳이 갈라진다.
- 입력은 **실명 그대로** 받는다: `{ studentName, roster, areaLabel, threadTitle?, mode: 'shrink' | 'expand', sourceText, currentBytes, targetBytes, evidences, teacherPrompt? }`
- 함수 안에서 `createMaskSession()` 한 세션으로 **학생 이름 · 조절 대상 본문 · 근거 · 주제 · 선생님 지시**를 함께 가린다. 같은 사람은 같은 별칭을 받는다.
- 근거는 `mode === 'expand'`일 때만 싣는다. 제외 규칙(선생님 제외 / 빈 것 / 기재 금지 / 분량 초과)은 기존 `buildRecordDraftPack`과 **완전히 같은 순서**로 재사용한다.
- 반환형은 기존 `DraftPack`과 같다(`text`, `studentAlias`, `mappings`, `includedCount`, `exclusions`).
- 문단 표식 지시(`NARRATIVE_MARK_INSTRUCTION`)를 그대로 붙인다 — 그래야 조절안을 반영해도 형광펜이 살아 있다.
- 화면 문구·모델에게 가는 문구에 **em 대시(`—`) 금지**(메타 테스트 `recordDraftNoEmDash.meta.test.ts`). 새로 만드는 도메인 파일은 그 테스트의 `EXTRA_FILES` 목록에 **추가한다**.

**수정 `src/domain/entities/RecordAiDraft.ts`** — 선택 필드 하나 추가. §D 참조.

## C-2. S2 상세 — 행의 현재 입력을 부모가 읽는 길

`RecordDraftView.tsx` 안에 **되돌아 쓰지 않는 읽기 전용 등록부**를 만든다.

- 부모가 `useRef<Map<string, string>>` 하나를 들고, `RecordDraftRow`에 넘긴다.
- 행은 `onChange`마다 그 지도에 `studentRef → 현재 입력`을 **기록만** 한다. 참조에 쓰는 것이라 **화면이 다시 그려지지 않는다**(키 입력마다 전체 목록이 리렌더되는 사고를 피한다).
- 부모는 필요할 때(=[분량 조절]을 눌렀을 때, [이 글로 바꾸기]를 눌렀을 때)만 읽는다.
- **부모는 이 값을 행에 되돌려 쓰지 않는다.** 되돌려 쓰는 순간 시나리오 3의 사고가 난다.

같은 단계에서 패널에 없던 것 2개를 넘긴다(분석 §5 "영역 한도"):

- `areaLimit: number` (= `resolveAreaLimit(activeArea, level)`)
- `areaLimitVerified: boolean` (= `isAreaLimitVerified(activeArea, level)`)
- 확인 결과 **현재 패널 props에는 `level`도 한도도 전혀 없다.** 패널이 스스로 계산하게 두지 말고 부모의 판정을 그대로 넘긴다(같은 숫자를 두 곳에서 계산하지 않는다).

행에는 바이트 카운터 옆에 `[분량 조절]` 버튼을 붙인다. 누르면 `onOpenLengthAdjust(studentRef, 현재입력)`으로 부모에게 **행의 현재 입력을 직접** 넘기고, 오른쪽 패널의 「AI 초안」 탭을 열며 조절 섹션을 펼친다.

# D. 데이터 · 계약 변경

## D-1. `RecordAiDraft`에 선택 필드 하나

```ts
/** 이 판이 "분량 조절"로 만들어졌으면 그 내역. 부재 = 조절이 아니라 새로 쓴 판(병합에서 덮지 말 것). */
readonly adjust?: {
  readonly kind: 'shrink' | 'expand';
  /** 선생님이 고른 목표 바이트. */
  readonly targetBytes: number;
  /** 조절 대상이 된 판의 id. 대상이 "직접 쓴 글"이었으면 없다. */
  readonly sourceVersionId?: string;
  /** 조절 직전 원문 스냅숏. [원문과 비교]가 이걸 쓴다. */
  readonly sourceText: string;
  /** 앱이 최종 본문으로 실제로 센 바이트. 모델이 말한 숫자가 아니다. */
  readonly resultBytes: number;
  /** 1 = 한 번에 나옴, 2 = 자동 재조정 1회를 거침. */
  readonly attempts: 1 | 2;
};
```

**왜 `sourceText`를 판 안에 넣나**: 판 상한이 20개이고 `enforceAiDraftCap`이 **미반영 판부터** 지우기 때문에, `sourceVersionId`가 가리키던 원문 판이 먼저 지워질 수 있다. 그러면 [원문과 비교]가 빈 화면이 된다. 스냅숏을 함께 넣어 그 경우에도 비교가 산다.
→ ★분석 §5는 "기존 판 상한 20개 정책을 따른다"까지만 적었다. **끊어진 참조 문제는 분석에 없던 것**이므로 여기서 보완한다(§정정 5).

**저장 용량**: 1,500바이트 본문 × 2벌 × 20판 ≈ 한 칸당 60KB. 학생 30명 × 영역 6개면 최대 수십 MB이지만 실제로는 판 20개를 다 채우는 칸이 드물다. 허용 범위로 본다. 초과가 관측되면 상한을 20 → 12로 낮추는 것을 후속으로 둔다.

**개인정보 수위**: `sourceText`는 이미 실명이 복원된 초안 본문이며, `RecordAiDraft`는 `RecordDraft`와 같은 폴더·같은 백업·같은 보관함·같은 동기화 수위다(ADR-085). 새로 노출되는 경로가 없다.

## D-2. 브릿지 바이트 계약 영향 — **없음**

# E. 연결부 7건 — 각각의 구체적 해결책 (분석 §5)

### E-1. 미저장 글 전달

- **문제**: 행의 `text`(현재 입력)와 저장된 `draft.content`는 다르다. 한도를 넘긴 입력은 저장이 거부되므로 **디스크에 없다.** 저장소에서 다시 읽는 구현은 조절해야 할 그 글을 잃는다.
- **해결**: `RecordDraftView`가 `useRef<Map<string,string>>` 등록부를 들고, 행이 `onChange`마다 기록한다(참조 쓰기 → 리렌더 없음). [분량 조절]을 누르면 그 지도에서 현재 입력을 읽어 조절 대상으로 넘긴다.
- **함께 점검**: 행의 `onBlur`(`flush`)는 `text.trim().length > 0 && text !== draft.content`일 때 저장을 시도하고, 실패하면 `saveError`만 띄우고 `text`는 유지한다 → 값은 안 날아간다. 다만 `useEffect`가 `focused === false`일 때 `draft.content`로 되돌리므로, **부모가 어떤 이유로든 `draft`를 갱신하면 초과분 입력이 저장된 옛 글로 되돌아간다.** 조절 흐름이 `draft`를 건드리지 않도록 하고(반영 전까지 저장 없음), 이 성질을 테스트로 고정한다.
- **회귀 검사 REGRESSION #68**: "분량 조절은 저장된 `draft.content`가 아니라 행의 현재 입력을 쓴다" — 조절 진입점이 등록부를 읽는 코드 형태를 grep으로 못 박는다.

### E-2. 편집 도중 결과 도착

- **해결**: 실행 시작 시 `sourceText`(그 순간의 원문)를 판에 저장한다. [이 글로 바꾸기] 순간 등록부에서 **행의 최신 입력**을 다시 읽어 `sourceText`와 비교한다.
  - 같으면 그대로 반영.
  - 다르면 덮지 않고 `그 사이에 글을 고치셨어요.` + `[최신 글로 다시 조절] / [그래도 이 글로 바꾸기]` 두 갈래를 준다. 자동으로 고르지 않는다.
- **회귀 검사 REGRESSION #69**: "조절 반영 전에 최신 입력과 `sourceText`를 비교한다".

### E-3. 원문 비교

- **문제**: 기존 [내 글과 비교]는 `target.existingText`(저장된 내 글) ↔ AI 판을 비교한다. v2를 줄인 v3은 **v2와** 비교해야 한다.
- **해결**: 조절안 판에는 [원문과 비교] 버튼을 따로 둔다. 왼쪽 = `adjust.sourceText`(스냅숏), 오른쪽 = 조절안 본문. 기존 [내 글과 비교]는 그대로 둔다(둘은 묻는 게 다르다: "AI가 내 글과 얼마나 다른가" vs "이 조절이 무엇을 덜어냈나").
- 좁은 폭에서는 2열이 아니라 위아래로 떨어지는 반응형(디자인 단계에서 확정).

### E-4. 반영 실패

- **해결**: `applyVersion`(과 조절안 반영)을 `try/catch`로 감싼다. 실패하면
  - 미리보기와 원문을 **그대로 유지**하고,
  - `RecordDraftLimitError`면 그 메시지를, 그 외면 `저장하지 못했습니다.`를 붉은 칸에 띄우고,
  - `markApplied`를 부르지 않고 큐도 넘기지 않으며,
  - 큐 실행 중이었다면 "여기서 멈췄다"를 명시한다.
- 이건 **지금도 조용히 실패하는 경로**를 고치는 것이다(§D-4 정정 2).

### E-5. 실행 상태 (중복 실행 · 잘못된 대상)

- `busyRef`(참조) 하나로 초안 생성 · 분량 조절 · [다시 표시]를 함께 잠근다. 기존 `remarking`(`useState`)도 참조 방식으로 바꾼다.
- `runToken` + 실행 시작 시점의 (학생·영역·과목)을 붙들어, 결과 도착 시 다르면 **버린다.**
- 패널은 이미 `key={studentRef:area:subject}`로 학생이 바뀌면 새로 만들어진다. 그래도 진행 중이던 약속(promise)은 살아 있으므로 위 토큰 검사가 필요하다.
- "남은 학생 모두" 일괄 생성은 현재 학생의 조절이 끝날 때까지 대기한다(조절 중에는 큐를 진행시키지 않는다).
- 조절 중인 학생도 `onActiveChange`에 실어 **필터가 걸려 있어도 행이 사라지지 않게** 한다(기존 UltraQA P1 대응 재사용).

### E-6. 영역 한도

- 부모가 계산한 `areaLimit` · `areaLimitVerified`를 패널에 넘긴다(§C-2). 패널이 스스로 계산하지 않는다.
- `areaLimitVerified === false`(초등)면
  - 목표 기본값은 그대로 제시하되 `한도 수치는 확인 중이에요.`를 함께 쓰고,
  - **반영을 절대 막지 않는다.** `over-limit` 판정이 아예 나오지 않는다(`judgeLength`가 보장).
- 이것은 저장소의 `levelKnown` 가드와 같은 정신이다(잘못 거부하는 쪽이 더 나쁘다).

### E-7. 기록 상태 · 되돌리기

- 조절안을 반영하면 기존 [반영]과 **똑같은 경로**(`onApply` → `upsertDraft`)를 탄다. 따라서 교사 검토 필요 상태(`requiresTeacherReview`)·금지 항목 경고·서사 품질 점검이 자동으로 다시 돈다. 새 경로를 만들지 않는다.
- 30초 [되돌리기]를 조절 반영에도 붙인다(기존 `armUndo` 재사용, 형광펜 표식도 함께 되돌린다).
- 조절안 판에도 `markApplied`를 찍어 판 탭에 `✓`가 뜨게 한다.

## F-4. e2e (실기기 · 실제 AI 왕복) — **자동 테스트로 대체 불가**

이 저장소에는 **게이트 4종이 전부 초록인 채 존재한 결함**이 반복해서 나왔다. 아래는 사람이 직접 해야 한다.

1. 실제 연결된 **클로드 코드**로 1,782바이트 합성 글 줄이기 1회 — 결과 바이트, 핵심 활동·교사 평가 보존 여부를 눈으로 대조.
2. 실제 연결된 **코덱스**로 같은 것 1회 — 두 공급자 간 결과 차이 확인.
3. 620바이트 글에 근거 6건으로 보충하기 — 근거에 없는 문장이 들어왔는지 한 줄씩 대조.
4. 근거 0건 상태에서 보충하기 시도 — 버튼이 비활성인지, 안내 문구가 뜨는지.
5. 조절 실행 중 다른 학생으로 이동했다가 돌아오기 — 결과가 남의 칸에 붙지 않는지.
6. 유리 모드에서 조절 섹션 실렌더 — 배경이 사라지지 않는지(`data-sp-floating` 계약), 접힘/펼침이 갇히지 않는지.
7. 학급 운영과 수업 관리 두 곳에서 같은 절차 반복.
8. 편집 후 `git diff --numstat`으로 **CRLF 뒤집힘 없음** 확인(편집 도구가 src를 CRLF로 뒤집은 전례).

## F-5. 관측 (실패가 눈에 보이게)

- 화면: 실패는 반드시 **한국어 문장**으로 뜬다. 조용한 실패를 만들지 않는다.
- 콘솔: `[RecordLengthAdjust]` 태그로 **수치만** 남긴다 — `mode`, `targetBytes`, `attempt1Bytes`, `attempt2Bytes`, `evidenceCount`, `verdict`. **본문·이름은 절대 로그에 남기지 않는다.**
- 이 수치가 있어야 A-4 시나리오 2의 조기 경보("재조정 후에도 목표 밖이 절반 이상")를 실사용에서 볼 수 있다.

# I. ADR 초안 — ADR-086

> 파일: `docs/03-decisions/ADR-086.md` (마지막 번호 ADR-085 확인함) · `DECISIONS.md` 맨 아래 한 줄 추가

**제목**: ADR-086 · 생기부 분량 조절은 "앱이 세고, 한 번만 다시 묻고, 반영 전까지 원문을 안 건드린다"

**Decision (결정)**

1. 분량 조절은 **오른쪽 AI 패널 안 접이식 섹션**으로 만든다. 별도 모달·전체 화면·설정 페이지를 만들지 않는다.
2. 바이트는 **앱이** 최종 저장·복사될 본문으로 센다. 모델이 말한 숫자는 화면에 쓰지 않는다.
3. 목표 범위를 벗어나면 **자동 재조정은 딱 1회**. 그 뒤에는 실제 수치와 이유를 표시하고 멈춘다. 문자열을 잘라 맞추지 않는다.
4. 조절 대상 본문의 마스킹은 **조립 함수(`buildLengthAdjustPack`) 안에서** 한다. 부르는 쪽을 믿지 않는다.
5. 결과는 **새 판**으로 남기고, `[이 글로 바꾸기]`를 누르기 전까지 선생님의 글은 바뀌지 않는다. 반영 뒤 30초 [되돌리기]를 붙인다.
6. 반영 차단은 **확인된 한도**에서만 한다. 개인 목표만 넘고 실제 한도 이내면 수치만 표시하고 선생님이 고른다.
7. **자동 재조정의 1차 중간 결과는 판으로 남기지 않는다.** 판에는 `attempts` 수만 기록한다. (ADR-085의 "만든 것마다 전부 남긴다"에서 벗어나는 지점 — 교사 관점에서 재조정은 한 번의 요청이고, 판 상한 20개를 두 배로 갉아먹지 않기 위해서다.)

**Drivers (결정 동인)**

- 개인정보: 이번 기능부터 **편집 중인 초안 본문**이 외부 CLI로 나간다.
- 데이터 보호: 한도를 넘긴 글은 저장이 거부되므로, 조절 대상은 디스크가 아니라 화면에만 있다.
- 최소 범위: 미커밋 v3/근거 보드 변경 위에서 순차 작업해야 한다.

**Alternatives considered (고려한 대안)**

- **별도 모달/전체 화면 비교 편집기**: 비교 폭은 넓지만 유리 모드의 `backdrop-filter` 함정(`createPortal` 필수)을 정면으로 맞고, 판·비교·반영 흐름이 두 곳으로 갈라진다. 채택하지 않음.
- **사후 조절 없이 첫 생성에 목표만 싣기**: 변경은 가장 작지만 이미 있는 글을 못 고친다. **부분 채택** — 첫 생성에도 목표를 선택적으로 싣되, 사후 조절을 함께 만든다.
- **앱이 코드로 문장을 잘라 맞추기**: 교사 평가가 조용히 사라진다. 이 저장소에는 "끌 수 없는 필터가 데이터 소실처럼 보인" 사고가 이미 있다. **무효화.**
- **모델이 보고한 바이트 수를 신뢰**: 프롬프트로 규정을 못 막는다는 실측이 이미 있다. **무효화.**

**Why chosen (왜 이걸 골랐나)**

기존 패널에는 판(버전) · 미리보기 · 비교 · 반영 · 되돌리기가 이미 다 있다. 분량 조절은 그 문법에 **한 종류의 판을 더하는 일**이지 새 화면을 만드는 일이 아니다. 새 화면을 만들면 개인정보 경로와 실패 처리 경로가 하나 더 생기고, 이 프로젝트에서 사고는 늘 "경로가 둘로 갈라진 자리"에서 났다.

**Consequences (결과)**

- `RecordAiDraft`에 선택 필드 `adjust`가 생긴다. 옛 파일에는 없으므로 **부재를 빈 값으로 덮지 않는 계약**이 하나 더 늘어난다.
- 판 저장 용량이 조절안마다 원문 스냅숏만큼 늘어난다(칸당 최대 약 60KB).
- `RecordDraftView`가 행의 현재 입력을 읽는 등록부를 갖는다. **읽기 전용**이라는 계약을 회귀 검사 2건으로 지킨다.
- `useState` 기반 중복 실행 잠금이 `ref` 기반으로 바뀐다(기존 [다시 표시] 포함).
- 브릿지 바이트 계약(`neisByteLength`)과 동기화·보관함 등록은 **바뀌지 않는다.**

**Follow-ups (후속)**

1. 학급 전체 일괄 분량 조절.
2. 학기 간 잔여 바이트 계산(2026학년도 공통과목 1·2학기 합산) — 과목 매핑 선행.
3. 실제 NEIS 입력창과 줄바꿈·특수문자 바이트 대조(브릿지 계약과 함께).
4. 판 상한 20 → 12 하향 검토(용량·상한 압박 관측 후).
5. 내 글(직접 쓴 초안) 영구 이력 보존 — ADR-085와 별도 결정.

# J. 롤백 계획

## J-1. 되돌리기 단위

이 작업은 **커밋 4개**로 나눈다. 각 커밋은 단독으로 되돌릴 수 있다.

| 커밋 | 내용                                                    | 단독 되돌리기 가능?                                                                                                      |
| ---- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| C1   | S1 도메인(계산 · 조절 꾸러미 · 선택 필드) + 단위 테스트 | 가능. 화면이 안 쓰면 죽은 코드일 뿐 동작 변화 없음                                                                       |
| C2   | S2 배선(등록부 · 한도 전달 · 행 버튼)                   | 가능. 단, C3를 먼저 되돌려야 함                                                                                          |
| C3   | S3 패널 UI                                              | 가능. 되돌리면 버튼만 남으므로 C2와 함께 되돌린다                                                                        |
| C4   | S4 안전 배선 + S5 테스트 · 회귀 · 문서 · ADR            | 부분 되돌리기 주의 — 안전 배선(`try/catch`, `ref` 잠금)은 **기존 결함도 함께 고치는 것**이라 되돌리면 옛 결함이 돌아온다 |

**커밋은 반드시 경로를 지정한다**: `git commit -m "..." -- <path> <path>` (다중 세션에서 git 인덱스는 공유 상태이며, 실제로 남의 파일 8개가 딸려 나간 적이 있다).

## J-2. 되돌릴 때 확인할 것

1. **데이터는 되돌릴 필요가 없다.** `adjust` 필드는 선택 필드이므로, 코드를 되돌려도 이미 저장된 판은 그대로 읽힌다(모르는 필드는 무시된다). 다만 되돌린 뒤에는 `adjust`가 붙은 판이 "그냥 AI 판"으로 보인다 — 데이터 손상이 아니다.
2. **부분 되돌리기 금지 조합**: C1만 되돌리고 C3을 남기면 빌드가 깨진다. 항상 위에서부터(C4 → C3 → C2 → C1) 되돌린다.
3. 되돌린 뒤 검증 게이트 4종을 다시 돌린다. 특히 `npm run regression-check`에서 **#68·#69가 함께 빠졌는지** 확인한다(코드는 지웠는데 검사만 남으면 게이트가 빨간불이 된다).
4. `/docs` 가이드도 함께 되돌린다. 기능이 없는데 가이드가 남으면 선생님이 없는 버튼을 찾는다.

## J-3. 긴급 무력화 (되돌리기보다 빠른 길)

실기기에서 심각한 문제가 나면, 코드를 되돌리기 전에 **버튼 노출만 끄는 것**으로 먼저 막을 수 있다.

- 조절 진입점 2곳은 이미 실험실 스위치(`ownAiEnabled`, "내 AI로 실행")에 매여 있다. 이 스위치를 끄면 AI 초안 자체가 사라지므로 조절도 함께 사라진다.
- 조절만 끄고 싶다면, S3에서 조절 섹션 노출 조건을 **한 곳의 상수**로 모아 둔다(설계 시 반영). 그 상수 하나를 `false`로 바꾸는 한 줄 커밋이 긴급 무력화 경로가 된다.
