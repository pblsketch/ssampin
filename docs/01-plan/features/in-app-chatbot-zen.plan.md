## 0. 용어 미리 풀기 (비개발자 오너용)

| 용어                            | 쉬운 뜻                                                                                                                                     |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| **AI 브릿지**                   | 지금 쌤핀에 있는 기능. 선생님 PC에 개발자용 프로그램(Claude Code 등)을 깔고 로그인해야 쓸 수 있어서, 사실상 개발자만 쓴다.                  |
| **도구(tool) 호출**             | AI가 스스로 "이건 출결을 봐야 답할 수 있네" 하고 앱에 데이터를 요청하는 것. 챗봇이 챗봇답게 동작하려면 이게 반드시 돼야 한다.               |
| **함수 호출(function calling)** | 위 '도구 호출'의 기술 용어. AI 모델이 지원해야만 가능하다.                                                                                  |
| **중계 서버 (Edge Function)**   | 앱이 AI에 직접 말을 걸지 않고, 우리가 운영하는 작은 서버가 대신 전달해 주는 구조. 이미 쌤핀에 20개가 돌고 있다.                             |
| **API 키**                      | AI를 쓸 수 있는 비밀 열쇠. 앱 안에 넣으면 누구나 꺼내 갈 수 있어서 반드시 서버에만 둔다.                                                    |
| **레이트 리밋(rate limit)**     | "1분에 몇 번까지"처럼 사용 횟수에 거는 상한.                                                                                                |
| **집계(aggregate)**             | 개별 내용이 아니라 숫자만. "결석 3명"은 집계, "김지훈 결석"은 개별.                                                                         |
| **가명(假名)**                  | 이름을 '학생A'로 바꾼 것. 원래 이름과 이어 붙일 수 있으므로 **여전히 개인정보다.**                                                          |
| **재식별(再識別)**              | 이름을 지웠는데도 남은 단서를 조합해 누구인지 알아내는 것.                                                                                  |
| **egress(이그레스)**            | "밖으로 나가는 것". 여기서는 앱에서 외부 AI로 실제 전송되는 데이터를 뜻한다.                                                                |
| **옵트인(opt-in)**              | 기본값은 꺼져 있고, 선생님이 직접 켜야만 동작하는 방식.                                                                                     |
| **딥링크**                      | 챗봇이 답 대신 "이 화면 열어 드릴게요" 하고 앱 안 특정 화면으로 바로 데려가는 것. 외부 전송이 0이다.                                        |
| **스트리밍**                    | AI 답이 한 글자씩 흘러나오게 보여 주는 것. 다 만들어질 때까지 기다리지 않아도 된다.                                                         |
| **명령 팔레트**                 | `Ctrl+K`를 누르면 뜨는 한 줄 검색창. 기능을 찾거나 화면을 이동한다. **쌤핀에 이미 있다**(`src/adapters/components/common/CommandPalette/`). |
| **도킹(docking) 패널**          | 화면을 **덮지 않고** 옆에 붙어서 본문을 밀어내는 패널. 덮는 것(모달·플로팅)과 결정적으로 다르다 — 뒤에 있던 내용이 계속 보인다.             |

## 1. 개요

### 1.1 무엇을 만드는가

지금 쌤핀에서 AI를 쓰려면 **AI 브릿지**(별도 저장소 `ssampin-ai-bridge`, 도구 53개)를 거쳐야 하고, 선생님이 개발자용 프로그램을 직접 설치·로그인해야 한다. 실제로는 개발자만 쓴다.

이걸 **"설정에서 스위치 하나 켜면, 앱 안에서 바로 대화"** 로 바꾼다.

- 모델 공급처: **OpenCode Zen** (`https://opencode.ai/zen/v1`), 무료 모델 `deepseek-v4-flash-free`
- 키는 앱에 넣지 않고 **Supabase 중계 함수**에만 둔다
- 선생님은 설치도 로그인도 결제도 하지 않는다

### 1.2 전제 — 이미 검증된 사실 (재론하지 않는다)

| 사실                                                                                                                                       | 이 계획에 미치는 영향                                                                                                                                                                                                                                     |
| ------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **쌤핀은 교사 업무용 도구이지, 학생이 쓰는 교육용 SW가 아니다**                                                                            | 학생 대상 AI 규제(학생 데이터의 AI 학습 이용, 아동 보호 요건)의 직접 적용 대상이 아니다. 다만 **교사가 다루는 데이터가 학생 정보**이므로 개인정보 보호 요건은 그대로다. 이 구분을 사용자 안내 문구에도 반영한다 — "학생이 AI와 대화하는 기능이 아닙니다". |
| **Zen의 모든 모델은 미국에서 호스팅된다**(공식 문서). 딥시크는 open-weight 모델이라 미국 인프라에서 추론되며 데이터가 중국으로 가지 않는다 | 국외이전 관할 = **미국**. 쌤핀 개인정보처리방침에 이미 미국 사업자 4곳(Supabase·Vercel·Google LLC·업스테이지 인프라)이 §28의8 근거로 표에 있으므로 **행 하나 추가 수준**이다. 새 법적 구조를 만들 필요가 없다.                                            |
| **Google Gemini 무료 티어는 대안이 못 된다** (Flash 계열 하루 500~1,500건)                                                                 | 키 하나로 전체 사용자를 중계하는 구조에서 무의미. **다시 제안하지 않는다.**                                                                                                                                                                               |
| **API 키를 앱에 심으면 안 된다** (Electron asar는 압축만 풀면 코드가 보이고, 암호화해도 복호화 키가 동봉된다)                              | **Supabase Edge Function 중계 필수.** 렌더러에서 Zen 직접 호출 금지.                                                                                                                                                                                      |

### 1.3 유일하게 남은 제약 — 이것이 설계의 축이다

무료 모델 약관: **"During its free period, collected data may be used to improve the model"** (무료 기간 중 수집 데이터가 모델 개선에 쓰일 수 있음).

이 조항은 **호스팅 위치와 무관하게 남는다.** 미국에서 처리되든 어디서 처리되든, 우리가 보낸 것이 모델 학습에 쓰일 수 있다는 뜻이다.

→ 따라서 **개인정보가 나가지 않는 범위**로 한정한다. 이 경계가 이 계획의 핵심이며, **도구 등급제**(§4)로 구현한다.

이 방향은 이미 검증된 전례가 있다. AI 브릿지의 `get_weekly_summary`가 정확히 1등급 설계다 — "집계 수치 + 카테고리명만, 자유서술·실명 미반환"이고, egress 테스트로 강제돼 있다. **새 발명이 아니라, 이미 통과한 설계를 챗봇 전체에 확장하는 것이다.**

### 1.4 이 계획의 서명 문장

> **이름은 화면에 남고, 숫자만 밖으로 나간다.**

선생님이 "지훈이 요즘 어때?"라고 물으면, 앱은 로컬에서 '지훈 = 학생 3번'을 알아내고, **모델에게는 "담당 학생 1명의 이번 달 집계"라는 익명 질문 + 숫자만** 보낸다. 화면에는 "지훈이는…"으로 표시된다. 이름은 앱을 떠나지 않는다.

## 2. 범위

### 2.1 하는 것

1. **업무 보조 전용 UI** — `Ctrl+K` 명령 팔레트(이미 있음)를 진입점으로, 우측 도킹 패널을 본체로. 기존 고객지원 챗봇과 **완전히 별개** (§5)
2. **도구 등급제** — 1등급 도구만 챗봇에 등록. 2·3등급은 구조적으로 등록 불가 (§4)
3. 도구 결과 화이트리스트 재구성 + 전송 직전 PII 차단 관문 (§4.4)
4. **자유 입력창 3층 방어** — 제안 칩으로 자유 입력 축소 + 3등급 표현 차단 (§5.7)
5. Supabase 중계 함수 `ssampin-assist` 신설 (21번째 함수)
6. 옵트인 설정(기본 꺼짐) + 최초 1회 안내 + 로컬 대화 이력/전송 로그
7. 무료 티어 한도 대비 설계 (설치별 상한, 429 UX, 유료 전환 지점 1파일)
8. 개인정보처리방침 개정 + `/docs` 사용자 가이드 갱신 (같은 작업 단위)

## 3. RALPLAN-DR 요약

### 3.1 원칙 (Principles) — 5개

1. **P1. 이름은 앱을 떠나지 않는다.** 가명 치환이 아니라 **삭제**다. 되돌리는 단계를 만들지 않으므로 오복원 사고가 원리적으로 불가능하다. 적용 지점은 세 곳 — 선생님이 입력창에 친 문장, 도구 실행 결과, 시스템 프롬프트.
2. **P2. 숫자는 모델이 다시 쓰지 않는다.** 도구 결과는 앱이 직접 그린 카드로 보여 주고, 모델은 그 위에 한 줄 해설만 붙인다. 모델의 숫자 환각이 화면에 들어올 통로가 없다. (교육부 지침의 "교사가 원본" 책임 소재와 직결)
3. **P3. 등급은 코드가 강제한다, 사람이 기억하지 않는다.** 도구 정의에 등급 필드가 **필수**이고, 허용 등급 목록은 상수 하나이며, 레지스트리를 순회하는 계약 테스트가 새 도구를 자동으로 검사한다.
4. **P4. 비용도 열쇠도 사용자에게 넘기지 않는다.** 무료 모델 + 서버 보관 키. 선생님은 결제도 설치도 하지 않는다.
5. **P5. AI가 죽어도 답의 절반은 남는다.** 도구 실행은 로컬에서 끝나므로, 모델이 429·장애여도 **숫자 카드는 그대로 보여 준다.** "요약 문장은 지금 만들 수 없지만 숫자는 이렇습니다."

### 3.2 의사결정 동인 (Decision Drivers) — 상위 3개

1. **D1 — 무료 모델 약관("수집 데이터가 모델 개선에 쓰일 수 있음")이 선택지를 결정한다.** 이 한 문장이 도구 등급제 전체의 존재 이유다. 호스팅 위치·국외이전은 이미 해결됐고(§1.2), 남은 건 이것뿐이다.
2. **D2 — 도구 호출 가능 여부가 제품의 성립 조건이다.** Zen 공식 문서에 함수 호출 언급이 **전혀 없다.** 안 되면 "챗봇"이 아니라 다른 물건을 만들어야 한다. Phase 0의 1순위.
3. **D3 — 키 하나로 전체 사용자를 중계한다.** 무료 티어 한도가 비공개이고, Zen 약관에 중계를 금지하는 조항도 허용하는 조항도 없다. 한도 소진과 키 정지가 단일 장애점이다.

### 3.3 선택지 (Options)

#### 옵션 A — 모델이 도구를 고르는 정통 챗봇 (권고)

모델에게 1등급 도구 목록을 주고, 모델이 스스로 필요한 도구를 골라 호출하게 한다. 앱은 도구를 실행하고 결과를 정화해 돌려준다.

- **장점:** 진짜 챗봇. 선생님이 어떻게 물어도 대응 / 새 도구를 등록하면 자동으로 활용됨 / 브릿지 사용 경험과 이어짐
- **단점:** **Zen이 함수 호출을 지원하는지 미검증**(D2) / 도구 선택이 틀리면 엉뚱한 답 / 멀티턴에서 도구 목록 유지 여부 불명 / 한국어 질의에서의 선택 정확도 불명

#### 옵션 B — 앱이 도구를 고르고 모델은 문장만 (안전망 / 축소안)

앱이 질문을 키워드·패턴으로 몇 가지 유형에 분류하고, 앱이 데이터를 조회한 뒤, 모델에게는 **"이 숫자들을 한 문단으로 설명해 줘"** 만 시킨다. 함수 호출 기능이 필요 없다.

- **장점:** **Zen이 함수 호출을 지원하지 않아도 성립한다** / 무엇이 나가는지 100% 예측 가능(도구 선택이 모델 손에 없음) / egress 검증이 훨씬 쉬움 / 토큰 사용량이 적어 무료 한도에 유리
- **단점:** 유형 밖 질문에 "무슨 말인지 모르겠어요" / 유형 목록을 사람이 계속 늘려야 함 / 대화라기보다 "말로 하는 검색"에 가까움

#### 옵션 C — 하이브리드 (A 우선, 실패 시 B로 자동 강등)

모델에게 도구를 주되, 도구 선택이 실패하거나(스키마 붕괴·미지원 응답) 429가 나면 앱이 로컬 라우터로 넘어간다.

- **장점:** A의 상한 + B의 하한 / Phase 0 결과가 회색이어도 출시 가능 / 유료 전환 시 A 비중을 늘리기만 하면 됨
- **단점:** 두 경로를 다 만들어야 해 구현 물량이 가장 큼 / "왜 이번엔 잘 알아듣고 저번엔 못 알아듣나"를 사용자가 겪음 → 강등 사실을 UI에 표시해야 함

#### 옵션 D — 옆핀(SidePin) 안에 채팅 칸 신설 (기각, 무효화 근거)

- **무효화 근거:** ①옆핀은 포인터가 나가면 **400ms 뒤 접힌다**(`SIDE_PIN_COLLAPSE_DELAY_MS`). 챗봇은 답을 기다리며 다른 화면을 보는 것이 정상 사용인데 그때 패널이 사라진다. `isEditorBusy`로 붙잡을 수 있지만 "입력 중"과 "기다리는 중"은 다른 상태라 상태 축이 하나 더 늘어난다. ②옆핀은 **별도 BrowserWindow**라 스트리밍·도구 호출 상태를 IPC로 미러링해야 한다. ③폭이 좁아 대화·도구 칩·등급 안내를 담기 어렵다. ④최근 3라운드 QA에서 드러난 함정(호버로 여는 UI에 드래그를 얹으면 서로 잡아먹음, 움직이는 창 위 드래그는 `window` 전역으로 받아야 함)이 채팅 입력·스크롤과 다시 충돌한다. **검토 대상에서 제외하고, 진입점만 남긴다.**

#### 옵션 E — 무료 모델을 포기하고 유료 모델로 2등급까지 개방 (기각)

- **무효화 근거:** 오너 확정 제약 "사용자 비용 0원". 우리가 비용을 부담하면 사용자 수에 비례해 원가가 늘어 지속 불가. **단, §8.4에 전환 지점을 미리 설계해 둔다** — 나중에 판단이 바뀔 수 있는 유일한 축이기 때문이다.

### 3.4 권고

**옵션 C(하이브리드)를 권고하되, Phase 0 결과에 따라 A 또는 B 단독으로 축소한다.**

- Phase 0에서 도구 호출이 **잘 되면** → A 단독 (B 경로를 만들지 않는다. 죽은 코드 방지)
- **회색이면** → C
- **안 되면** → B 단독. 이 경우 제품 이름을 "챗봇"이라 부르지 않고 "말로 묻는 요약"으로 포지셔닝을 바꾼다

**이 판단은 Phase 0 종료 시 오너가 내린다.** 지금 C로 확정하면 도구 호출이 잘 될 경우 쓰지 않을 코드를 만들게 된다.

#### 쓰기 도구 — 읽기와 분리해 다룬다

**핵심 구분: 읽기 도구는 *결과*가 나가고, 쓰기 도구는 *인자*가 나간다.**

`add_observation("3학년 2반 김지훈, 오늘 발표에서 …")` 를 모델이 호출하려면 그 문자열 전체를 모델이 만들어야 하고, 그 말은 **저장할 자유서술 원문이 요청 본문에 실려 밖으로 나간다**는 뜻이다. 읽기 도구의 등급제로는 이걸 막을 수 없다.

| ---------------------------- | -------------------- | --------------------------------------------------------------------- |
| `add_observation`            | **전면 제외**        | `open_observation_form(classId, studentId)` — 화면을 열어 준다 (§4.3) |
| `update_*` 계열              | **전면 제외**        | 동일                                                                  |
| `delete_homeroom_attendance` | **전면 제외 (영구)** | 삭제는 복구 불가. AI 경로로 열지 않는다                               |
| `polish_sentence`            | **유일한 예외**      | 이름 삭제 후 문장 1개만. 자매 계획 안전장치 4종 필수                  |

### 4.3 '화면 열기' 도구 — 거절을 기능으로 바꾸는 장치

쓰기와 2등급 조회를 대체하는 3번째 종류의 도구다. **로컬에서만 실행되며 외부 전송이 0이다.**

| 도구                                        | 동작                                                                              |
| ------------------------------------------- | --------------------------------------------------------------------------------- |
| `open_screen(target)`                       | 앱 안 특정 화면으로 이동 (출결 입력, 학생 관리, 기록 조회, 진도 등)               |
| `open_observation_form(classId, studentId)` | 관찰 기록 입력 폼을 해당 학생으로 열어 준다. **초안은 비워 둔다**(생성 금지 원칙) |
| `open_bridge_guide()`                       | AI 브릿지 설정 화면 + 설명                                                        |

모델에게는 `open_*` 도구의 **인자로 자유서술을 받지 않는다**(id와 열거형만). 타입 수준에서 강제한다.

### 4.4 egress를 코드로 강제하는 방법 — 4중 그물

사람이 등급을 기억하는 설계는 6개월 뒤에 무너진다. 네 겹으로 강제한다.

**① 등급 필드는 필수, 허용 목록은 상수 하나**

```
// src/domain/entities/AssistTool.ts (개념)
export type AssistToolGrade = 1 | 2 | 3;
export interface AssistToolDef {
  readonly id: AssistToolId;
  readonly grade: AssistToolGrade;   // optional 아님 — 빠뜨리면 컴파일 실패
  readonly outbound: 'result' | 'args' | 'none';  // 무엇이 나가는가
}
/** 지금 무료 모델에 허용된 등급. 유료 전환 시 여기만 [1, 2] 로 바꾼다. */
export const ALLOWED_GRADES = [1] as const;
```

**② 도구 결과는 걸러내지 않고 새로 짓는다 (화이트리스트 재구성)**

기존 객체에서 위험 필드를 `delete` 하는 방식은, 나중에 원본 엔티티에 필드가 추가되면 **조용히 새어 나간다.** 대신 허용 필드만으로 **새 객체를 만든다.**

```
// src/domain/services/sanitizeToolResult.ts (개념)
type ModelSafe<T> = T & { readonly __modelSafe: unique symbol };
// 중계 함수로 보내는 타입이 ModelSafe<> 만 받으므로,
// 재구성 함수를 통과하지 않은 객체는 타입 시스템이 거부한다.
```

**③ 전송 직전 최종 관문 — 경고가 아니라 차단**

`assertNoPii(payload, roster)`:

- 명단 이름 검사: `src/domain/privacy/keywordMask.ts`의 `detectKeywords` 재사용. ⚠️ **`applyMask`는 기본적으로 명단 학생 이름을 가리지 않는다**(패턴 + 설정된 `keywordGroups`만 본다) → 학급 명단을 `keywordGroups`로 **주입**해야 동작한다. 이 사실을 코드 주석에 명시한다.
- 패턴 검사: `src/domain/privacy/maskRules.ts`의 `detectPatterns` 재사용 (phone·rrn·email·birth·address)
- 하나라도 걸리면 **전송 차단 + 사용자에게 사유 표시.** 경고 후 진행 금지.

**④ 레지스트리 순회 계약 테스트 — 새 도구가 자동으로 검사된다**

```
// 개념
for (const tool of ASSIST_TOOL_REGISTRY) {
  expect(ALLOWED_GRADES).toContain(tool.grade);          // 등급 위반
  if (tool.outbound === 'args') expect(tool.argsSchema).toHaveNoFreeText();  // 자유서술 인자 금지
  const result = await runWithFixture(tool);              // 픽스처 데이터로 실행
  expect(assertNoPii(result, FIXTURE_ROSTER)).toBe(true); // 명단 이름·PII 0건
  expect(result).not.toHaveDeepKey(FREE_TEXT_FIELDS);     // content/notes/memo/reason 등
}
```

**픽스처에는 함정을 심는다** — 학생 이름을 일부러 관찰 기록 본문·할 일 제목·출결 사유에 넣어 두고, 그게 새어 나오면 테스트가 빨간불이 되게 한다. (기존 교훈: "그물은 버그를 되살려 빨간불이 나는지 실증할 것")

**추가 grep 계약 테스트**

- `ASSIST_TOOL_REGISTRY`에 `grade: 2` 또는 `grade: 3` 인 항목이 없다
- `학생A`, `[이름]` 등 가명 치환 토큰이 assist 경로 코드에 없다 (복원 로직 부재의 증거)
- `restore(` 가 assist 경로에서 호출되지 않는다

## 5. UI/UX 설계

### 5.0 출발점 — 이건 기존 챗봇과 다른 물건이다

앱에는 이미 챗봇이 하나 있다(`src/adapters/components/HelpChat/`, 우하단 플로팅 버튼). **그것을 참고하지 않는다.** 목적이 다르기 때문이다.

|             | 기존 챗봇 (고객지원)                    | 이번 기능 (업무 보조)                           |
| ----------- | --------------------------------------- | ----------------------------------------------- |
| **성격**    | **목적지** — 막혔을 때 찾아간다         | **동반자** — 하던 일 옆에 있다                  |
| 무엇을 묻나 | "이 기능 어디 있어요?", "이거 버그예요" | "오늘 결석 몇 명?", "이번 주 마감 뭐 남았지?"   |
| 언제 쓰나   | 드물게. 문제가 생겼을 때                | 자주. 업무 중간중간                             |
| 답의 형태   | 설명 문단 + 개발자 전달                 | **숫자 + 화면 이동**                            |
| 화면 맥락   | 필요 없다                               | **가장 큰 가치다** — 지금 보는 학급·날짜를 안다 |
| 대화 길이   | 여러 턴 (문제 해결까지)                 | 대개 한두 턴 (묻고 → 보고 → 화면으로)           |
| 데이터      | 공개 문서                               | **선생님의 학급 데이터**                        |
| 모델·약관   | 업스테이지 Solar (유료 계약)            | 무료 모델 (**학습에 쓰일 수 있음**)             |

**성격이 다르면 형태도 달라야 한다.** 목적지는 "찾아가서 머무는 곳"이라 플로팅 패널이 맞지만, 동반자는 **"곁에 있다가 비켜 주는 것"** 이라 다른 형태가 필요하다. 아래는 기존 챗봇을 근거로 삼지 않고, 업무 보조의 성질에서 요구사항을 먼저 뽑아 형태를 도출한 결과다.

### 5.1 요구사항 도출 → 형태 결정

#### 5.1.1 업무 보조의 성질에서 나오는 요구사항 7개

#### 5.1.2 확인된 코드 사실 — 명령 팔레트가 **이미 있다**

`src/adapters/components/common/CommandPalette/` 에 완성된 명령 팔레트가 있고 `src/App.tsx:1297`에 마운트돼 있다.

- `Ctrl+K` / `Cmd+K` 토글. **입력창·textarea에 포커스가 있어도 작동**한다 (`useCommandPalette.ts:20`)
- 검색 + 그룹(`최근`·`빠른 추가`·`담임 업무`·`학교 정보`·`페이지`·`설정`) + 키보드 내비게이션(↑↓/Enter/Esc)
- **한글 초성 검색** 지원 (`toChosungString`, `isChosungQuery`)
- 최근 사용 기록 (`useCommandRecentStore`)
- 매치가 없으면 **"일치하는 명령을 찾을 수 없습니다"** 로 끝난다 (`CommandPalette.tsx:31`)

> **오너 리서치의 "명령 팔레트" 수요는 이미 충족돼 있다.** 이 기능이 그 수요를 "흡수"하는 게 아니라, **팔레트가 지금 답하지 못하는 자리를 채운다.** 그 자리가 정확히 위의 "일치하는 명령을 찾을 수 없습니다"이다 — **자연어 질문은 정확히 여기로 떨어진다.** 이보다 자연스러운 이음새는 없다.

또 하나: `src/App.tsx:1241`의 레이아웃이 `[Sidebar] [main]` 가로 배치다. `main` 옆에 형제 요소를 넣으면 **본문이 밀리고 덮이지 않는다.** 도킹 패널이 구조적으로 쉽다.

#### 5.1.3 4안 비교

| 안                                                    | R-1 덮지 않음     | R-2 빠른 호출 | R-3 화면 이동                | R-4 읽는 시간       | R-5 입력 개입   | R-6 구분                      | 판정                                 |
| ----------------------------------------------------- | ----------------- | ------------- | ---------------------------- | ------------------- | --------------- | ----------------------------- | ------------------------------------ |
| **A. 명령 팔레트 확장** (`Ctrl+K` → 자연어 질문 인식) | ✗ 오버레이가 덮음 | **◎ 최상**    | **◎ 팔레트의 본업**          | ✗ 실행 후 닫힘      | △ 한 줄뿐       | ◎ 새 버튼 0                   | **진입점으로 채택, 본체로는 부적합** |

| **D. 옆핀(SidePin) 채팅 칸**                          | ○                 | ○             | ✗                            | **✗ 400ms 뒤 접힘** | ✗               | ○                             | **기각**                             |

**D(옆핀) 기각 근거 — 유효하므로 유지:**
①포인터가 나가면 **400ms 뒤 접힌다**(`SIDE_PIN_COLLAPSE_DELAY_MS`, `src/domain/services/resolveSidePinTransition.ts`). 챗봇은 답을 기다리며 다른 화면을 보는 것이 정상 사용인데 그때 사라진다. ②**별도 BrowserWindow**라 스트리밍·도구 호출 상태를 IPC로 미러링해야 한다. ③폭이 좁아 숫자 카드·도구 칩·등급 안내를 담기 어렵다. ④최근 3라운드 QA에서 드러난 함정(호버로 여는 UI에 드래그를 얹으면 서로 잡아먹음, 움직이는 창 위 드래그는 `window` 전역으로 받아야 함)이 채팅 입력·스크롤과 다시 충돌한다.

**C(전용 플로팅) 기각 근거:** 우하단 원형 버튼이 2개가 된다. 오너가 "기존 것을 참고하지 말라"고 한 이유가 바로 **형태가 같으면 성격이 다른 것을 구분할 수 없기 때문**인데, C는 정확히 그 실수를 반복한다.

#### 5.1.4 결정 — **A(진입점) + B(본체)**

> **`Ctrl+K`로 부르고, 답은 오른쪽 도킹 패널에서 읽는다.**

이 조합만이 R-1~R-7을 모두 만족한다. A 단독은 읽을 자리가 없고(R-4), B 단독은 호출이 느리다(R-2). 둘을 이으면 서로의 약점이 사라진다.

**동작:**

```
1. 선생님이 3-2반 출결 화면을 보다가 Ctrl+K
2. 팔레트에 "오늘 결석" 입력
   → 매칭되는 명령이 있으면 기존대로 실행 (변화 없음)
   → 매칭이 없고 질문처럼 보이면 맨 위에 한 줄:
        💬 "오늘 결석" 업무 도우미에게 묻기          ↵
3. Enter → 팔레트가 닫히고 → 우측 도킹 패널이 열리며 그 질문으로 시작
4. 본문(3-2반 출결)은 왼쪽에 그대로 보인다. 좁아질 뿐 가려지지 않는다
5. 답변의 [출결 화면 열기] 버튼 → 왼쪽 본문이 바뀐다. 패널은 그대로
6. Esc 또는 토글 → 패널이 닫히고 본문이 원래 폭으로
```

**5번이 이 설계의 값이다.** 답과 결과를 **동시에** 본다. 덮는 형태에서는 불가능하다.

**팔레트 변경 범위 — 최소:**

- `commandRegistry.ts`에 "AI에게 묻기" 항목을 동적으로 추가한다. 조건: **매칭 결과가 0건이고, 질문처럼 보이는 입력**(길이 ≥ 4, 초성 검색이 아님)
- 매칭이 있으면 **아무것도 바뀌지 않는다.** 기존 사용자의 근육 기억을 건드리지 않는 것이 최우선
- 옵트인이 꺼져 있으면 이 항목이 아예 나타나지 않는다

#### 5.1.5 두 기능을 어떻게 구분해 보이게 하는가 — 통합이 아니라 **구분**으로 푼다

**핵심: 새 기능에는 플로팅 버튼을 만들지 않는다.** 그래서 "버튼 2개" 문제가 발생할 여지 자체가 없다.

|                 | 기존 챗봇 (그대로 둔다)              | 새 기능                                     |
| --------------- | ------------------------------------ | ------------------------------------------- |
| **명칭**        | "AI 도우미" (현행 유지)              | **"업무 도우미"**                           |
| **위치**        | 우하단 **떠 있는 원형 버튼**         | **사이드바 하단의 고정 항목** + `Ctrl+K`    |
| **아이콘**      | 말풍선 `chat_bubble` (현행)          | **`assistant`** — 말풍선 계열을 쓰지 않는다 |
| **형태**        | 화면 위에 **떠서 덮는** 패널         | 본문을 **밀어내는** 도킹 패널               |
| **나타나는 곳** | 화면 오른쪽 아래 구석                | 화면 오른쪽 **전체 높이**                   |
| **한 줄 설명**  | "쌤핀 사용법이 궁금하거나 건의할 때" | "내 업무 데이터를 물어볼 때"                |

위치·형태·높이가 전부 달라 **첫눈에 다른 물건으로 읽힌다.** 명칭과 아이콘까지 겹치지 않으므로 혼동 여지가 없다.

**⚠️ 기존 챗봇은 코드·문구·동작 어느 것도 건드리지 않는다.** `HelpChatPanel.tsx`·`useHelpChat.ts`는 이 작업의 수정 대상이 아니다(git diff 계약 테스트로 강제, §10.2).

### 5.2 등급 경계를 사용자가 어떻게 체감하는가 — 핵심 UX 과제

**거절을 만들지 말고, 답을 바꾼다.** "못 해요"가 잦으면 제품이 바보처럼 보인다.

**시나리오: 선생님이 "지훈이 요즘 어때?" 라고 묻는다.**

나쁜 응답 (하지 않는다):

> "죄송해요, 개인정보 보호를 위해 개별 학생 정보는 알려 드릴 수 없어요. AI 브릿지를 사용해 주세요."

채택하는 3단 응답:

```
┌─ [앱 데이터] ────────────────────────────┐
│  지훈 (3-2, 8월)                          │
│  결석 2 · 지각 1 · 관찰 기록 3건          │
│  기록 분류: 수업태도 2 · 교우관계 1       │
└───────────────────────────────────────────┘
   ↑ 앱이 직접 그린 카드. 모델이 만든 숫자가 아니다 (P2)

[AI 요약] 8월에는 결석이 2회 있었고 관찰 기록은 수업태도 쪽이
많네요. 기록 내용까지는 여기서 볼 수 없어요.

  [ 기록 3건 열어보기 ]  [ 출결 화면 열기 ]
     ↑ 앱 안 화면으로 이동. 외부 전송 0

  ⌄ 더 깊이 분석하려면 (AI 브릿지)     ← 접혀 있음. 마지막 수단
```

**설계 원리 3가지:**

1. **답할 수 있는 부분은 답한다.** 집계 숫자는 1등급이므로 그냥 준다. 완전 거절이 아니다.
2. **나머지는 "화면"으로 넘긴다.** 앱이 원래 잘하는 일이고 외부 전송이 0이다. 등급 경계가 금지가 아니라 **자연스러운 분업**으로 읽힌다.
3. **브릿지 안내는 접어 둔다.** 매번 "브릿지 쓰세요"가 뜨면 "이 챗봇은 반쪽짜리"라는 인상이 굳는다.

**이름 처리 — 선생님이 이름을 직접 타이핑한 경우**

이것이 가장 중요한 지점이다. 선생님이 입력창에 "지훈"이라고 치면 그 이름은 **이미 전송 대상 문자열 안에 들어와 있다.**

처리 흐름:

```
입력: "지훈이 요즘 어때?"
  ↓ 로컬 명단 대조 (앱 밖으로 나가지 않음)
  '지훈' = 3-2반 12번 학생 → studentId 해석
  ↓ 이름 삭제 (치환 아님)
모델에게 나가는 것: "담당 학생 1명의 이번 달 상태를 요약해 줘"
                  + 도구 결과 { absent: 2, late: 1, records: 3, byCategory: [...] }
화면에 남는 것: "지훈이는…"  ← 앱이 로컬에서 이름을 다시 붙인다
```

이름을 되붙이는 것은 **화면 렌더링 단계**이지 모델 응답 복원이 아니다. 모델은 이름을 받은 적이 없으므로 되돌릴 것도 없다 — **오복원 사고가 원리적으로 불가능하다.**

**나갈 문장을 상시 보여 준다 (자매 계획 안전장치 ②의 챗봇판)**

자매 계획은 전송 전 모달로 확인을 받는다. 챗봇에서 매 턴 모달을 띄우면 못 쓴다. 대체:

- 입력창 아래에 **한 줄 상시 표시**: `실제로 나갈 문장: "담당 학생 1명의 이번 달 상태를 요약해 줘"`
- 이름이 감지돼 지워졌으면 그 사실을 알린다: `이름 1개를 지우고 보냅니다`
- 모달은 `polish_sentence` 도구에서만 유지한다(자매 계획 그대로)

> ⚠️ **이 한 줄만으로는 부족하다.** 이름은 지워진 것이 눈에 보이지만, "아버지 실직" 같은 3등급 서술은 **그대로 남아 아무 변화가 없어 보인다** → 선생님은 "괜찮구나"로 읽는다. **침묵이 승인으로 오독된다.** 이 구멍의 대응은 §5.7에서 정면으로 다룬다.

**상시 안내 한 줄** (입력창 하단 고정): `숫자·요약은 여기서, 이름·기록 원문은 나가지 않아요.` 첫 2등급 질문이 나온 시점에 1회만 자세한 설명을 편다.

### 5.3 도구 호출 가시화

답변 위에 **접힌 칩 줄**을 둔다.

```
🔍 읽음: 출결 요약 (3-2반, 8월)   🔍 읽음: 기록 통계 (3건)   ⌄
```

- 1등급 도구는 **사전 확인 없이 실행**하되 **사후 표시는 필수**다. "무엇을 읽었는지 모르게" 두지 않는다.
- 칩을 누르면 **실제로 모델에게 나간 값**을 사람이 읽을 형태로 그대로 펼친다. 요약이 아니라 원본이다.
- 사전 확인이 필요한 도구는 색이 다르다: `polish_sentence`(전송 모달), `open_*`(화면 이동 확인).
- 실패한 도구도 표시한다: `⚠ 실패: 진도 요약 (데이터 없음)`.
- 색은 `sp-*` 토큰만. 하드코딩 HEX 금지.

### 5.4 어디까지가 AI인가 — 출처 배지

교육부 지침의 "교사가 원본"이라는 책임 소재와 직결되는 부분이다.

| 배지          | 뜻                                             | 표시                    |
| ------------- | ---------------------------------------------- | ----------------------- |
| `[앱 데이터]` | 앱이 직접 그린 카드. 모델이 만든 문장이 아니다 | 카드 테두리 + 좌측 배지 |
| `[AI 요약]`   | 모델이 생성한 문장                             | 말풍선 좌측 배지        |
| `[AI 다듬음]` | 선생님 문장을 모델이 윤문한 것                 | 결과 상단               |

**P2 원칙의 구현:** 도구가 돌려준 숫자는 **모델을 거치지 않고** 앱이 직접 카드로 그린다. 모델은 그 위에 한 줄 해설만 붙인다. 그래서 모델이 "결석 5회"라고 환각해도 카드에는 "결석 2"가 찍혀 있고, 둘이 다르면 눈에 띈다. (추가 방어: 모델 답변에 도구 결과와 다른 숫자가 있으면 감지해 경고 — 2차 검토 항목)

기록에 삽입할 때: 복사 시점에는 "AI가 다듬은 문장입니다" 꼬리표가 붙고, 실제 저장 시에는 꼬리표를 떼되 **로컬 로그에 "이 문장은 AI를 거쳤다"는 사실을 남긴다.**

### 5.5 대화 이력 — 저장 위치·삭제·동기화

| 항목        | 결정                                                            | 근거                                                                                                                                                                                    |
| ----------- | --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

### 5.6 스트리밍 응답 · 실패 UX

**스트리밍 흐름 (Zen이 SSE를 지원하는 경우):**

```
사용자 입력
  → [비스트리밍] 도구 판단 턴      ← 도구 인자는 완결돼야 파싱 가능
  → [로컬] 도구 실행
  → [즉시 렌더] 숫자 카드           ← 여기서 이미 화면에 답의 절반이 나온다
  → [스트리밍] 최종 해설 문장
```

숫자 카드가 먼저 뜨므로, 모델 응답이 느려도 선생님은 이미 답을 보고 있다.

**Zen의 SSE 지원이 Phase 0에서 미확인이면:** 1차는 비스트리밍 + "생각 중" 표시로 출시하고 스트리밍은 후속. 숫자 카드 선행 렌더가 있으므로 체감 손실이 작다.

**실패 UX — 대화가 통째로 날아가지 않을 것**

| 상황                | 동작                                                                                                         |
| ------------------- | ------------------------------------------------------------------------------------------------------------ |
| 입력창 내용         | **어떤 실패에서도 사라지지 않는다.** 전송 실패 시 입력창에 그대로 복원                                       |
| 대화 이력           | 실패한 턴도 자리를 지킨다. 오류 카드 + `[다시 시도]` 버튼                                                    |
| 429 (한도 초과)     | "오늘 질문 한도를 다 썼어요. 내일 다시 열려요." + **숫자 카드는 그대로 표시**(도구는 이미 로컬에서 실행됐다) |
| 모델 장애·타임아웃  | "요약 문장은 지금 만들 수 없지만 숫자는 이렇습니다" + 카드 (P5)                                              |
| 네트워크 끊김       | 동일. 앱의 다른 기능은 정상                                                                                  |
| 도구 실행 실패      | 해당 칩만 `⚠ 실패`로 표시하고 나머지는 진행                                                                  |
| 옵션 C에서 A→B 강등 | "간단한 방식으로 답했어요"를 조용히 표시. 침묵하면 품질 편차의 원인을 사용자가 모른다                        |

**남은 횟수 표시:** 429를 _맞기 전에_ 알게 한다. 입력창 옆 `오늘 남은 질문 32회`.

### 5.7 자유 입력창 — 이 계획의 가장 큰 구멍

#### 5.7.1 문제 — 등급제로는 막을 수 없다

§4의 도구 등급제는 **도구가 돌려주는 결과**를 통제한다. 그러나 선생님이 입력창에 직접 치는 문장은 통제하지 못한다.

> "지훈이가 어제 **아버지 실직** 얘기를 꺼냈는데 어떻게 대응하면 좋을까?"

이름 '지훈'은 §5.2 설계대로 지워진다. 그러나 **"아버지 실직"은 그대로 나간다.** 이건 3등급(가정환경)이고, 무료 모델은 이걸 학습에 쓸 수 있다.

**정직하게 적는다: 이 경로를 완전히 막는 것은 불가능하다.** 3등급 표현은 무한히 다양하고, 우회 표현("집이 좀 어려운 애가 있는데", "요즘 아빠가 안 계셔서")은 어떤 규칙으로도 다 잡히지 않는다. 아래는 "막았다"가 아니라 **"위험을 어디까지 줄이고, 남는 것은 무엇인가"** 의 설계다.

#### 5.7.2 1층 — 구조적 축소: 자유 입력의 **필요성 자체**를 줄인다

가장 강력한 방어는 탐지가 아니라 **애초에 자유 타이핑을 하지 않게 만드는 것**이다.

- **제안 칩 상시 배치.** 패널을 열면 지금 화면 맥락에 맞는 칩이 먼저 보인다:
  `[오늘 출결 요약]` `[이번 주 마감]` `[3-2반 기록 통계]` `[이번 달 진도]`
  → 클릭 = 자유 입력 0. 문장을 지어낼 이유가 없다
- 팔레트에서 들어오는 질문은 대개 짧은 조회다("오늘 결석", "3반 진도"). 긴 서술은 드물다
- **관측 지표:** 제안 칩 대 자유 타이핑의 비율을 로컬 통계로 남긴다(§10.4). 자유 타이핑 비율이 높으면 칩 설계가 실패한 것이고, 그게 곧 위험 신호다

#### 5.7.3 2층 — 탐지와 **단계적 개입** (경고가 아니라 차단)

자매 계획의 `reidentificationRisk`(안전장치 ③)를 **재사용하되, 정책이 다르다.**

| 감지 대상                                                                                 | 자매 계획(생기부 윤문)           | **이 계획(챗봇 입력)**           |
| ----------------------------------------------------------------------------------------- | -------------------------------- | -------------------------------- |
| 3등급 명시 키워드 — 실직·이혼·수급·한부모·조손·병명·진단·수술·입원·상담·자해·학대·가출 등 | 경고 (선생님이 판단해 강행 가능) | **전송 차단.** 강행 옵션 없음    |
| 패턴 — 전화·주민번호·이메일·주소                                                          | 경고                             | **차단** (§4.4 관문이 이미 수행) |
| 명단 이름                                                                                 | 삭제                             | 삭제 (§5.2)                      |
| 재식별 저신뢰 — 학교명·직위·수상                                                          | 경고                             | 경고 + 강조. 강행 가능           |

**왜 자매 계획은 경고인데 여기는 차단인가 — 성격이 다르기 때문이다.**

|                | 생기부 윤문                                            | 챗봇 입력                                  |
| -------------- | ------------------------------------------------------ | ------------------------------------------ |
| 입력의 성질    | 선생님이 **이미 다듬어 쓴 문장.** 내용을 통제하고 있다 | **즉흥적으로 친 질문.** 판단할 여유가 없다 |
| 전송 전 확인   | 모달로 멈춰 세운다                                     | 흐름상 멈출 수 없다                        |
| 되돌릴 수 있나 | 둘 다 불가 — 모델 학습에 들어가면 회수할 수 없다       | 동일                                       |

**경고는 무시된다. 차단은 무시할 수 없다.** 되돌릴 수 없는 피해에는 차단을 쓴다.

**차단 시 화면 — 벌주지 않고 길을 준다:**

```
┌────────────────────────────────────────────┐
│ ⛔ 이 내용은 AI에 보내지 않아요             │
│                                            │
│ 가정 형편·건강·상담 내용은 무료 AI에       │
│ 보내면 학습에 쓰일 수 있어서 막았어요.     │
│ 선생님 잘못이 아니에요.                    │
│                                            │
│  [ 상담 기록에 남기기 ]  [ 이 부분만 지우기 ]│
└────────────────────────────────────────────┘
```

- **감지된 부분을 화면에 표시**한다(어디가 걸렸는지 모르면 고칠 수 없다)
- `[이 부분만 지우기]` — 해당 구절만 지우고 나머지 질문은 살린다. 질문을 통째로 날리지 않는다
- `[상담 기록에 남기기]` — 앱 안 상담 기능으로 유도. **AI가 못 하는 일을 앱이 대신 받는다**
- 입력 내용은 **절대 사라지지 않는다.** 차단이지 삭제가 아니다

#### 5.7.4 3층 — 침묵이 승인으로 읽히지 않게

§5.2의 "실제로 나갈 문장" 한 줄은 **이름에는 작동하지만 3등급 서술에는 작동하지 않는다.** 이름은 지워진 게 보이는데 "아버지 실직"은 그대로라 아무 일도 없어 보이기 때문이다.

보완:

- 3등급 감지 시 그 줄이 **차단 상태로 시각적으로 바뀐다** — 보내기 버튼 비활성 + 걸린 구절 강조. "아무 일 없음"처럼 보이지 않게 한다
- 최초 안내(§5.8)에 **구체 예시**를 넣는다: "가정 형편·건강·상담 내용은 물어볼 수 없어요(자동으로 막힙니다)". 추상적인 "개인정보 주의"는 행동을 바꾸지 못한다
- 차단이 발생한 **횟수만** 로컬에 기록한다(**내용은 저장하지 않는다**). 자주 걸리면 UX가 잘못 유도하고 있다는 신호다

#### 5.7.5 그래도 남는 위험 — 막을 수 없다고 적는다

| 남는 위험                                                            | 왜 못 막나                                                | 완화                                                                              |
| -------------------------------------------------------------------- | --------------------------------------------------------- | --------------------------------------------------------------------------------- |
| **우회·완곡 표현** ("집이 좀 어려운 애", "요즘 힘든 일이 있는 학생") | 키워드·정규식의 원리적 한계. 의미 판단은 로컬에서 못 한다 | 1층(제안 칩)이 유일한 실질 방어. 가이드에 "짐작하게 하는 표현도 피해 주세요" 명시 |
| **맥락 없는 단어 조합** ("걔 요즘 상황 때문에")                      | 동일                                                      | 동일                                                                              |
| 선생님이 의도적으로 우회                                             | 통제 불가                                                 | 옵트인 안내에서 이유를 설명해 **협조를 구한다.** 감시가 아니라 동의               |

**근본 해결책은 하나뿐이다 — 유료 전환.** 모델이 "학습에 쓰지 않는다"를 계약으로 보장하면 이 경로의 심각도가 근본적으로 낮아진다(§8.4). **이 위험이 §8.4 유료 전환의 가장 큰 동기다.** 무료 모델을 쓰는 한 이 위험은 0이 되지 않으며, 그 사실을 사용자 가이드에 적는다.

> 상호 참조: 사전 부검 **시나리오 4**(§11), 리스크 **R6**(§12, 심각도 **치명**), 유료 전환 동기(§8.4)

### 5.8 옵트인 — 기본 꺼짐 + 최초 1회 안내

**설정 위치:** 기존 `ai-bridge` 탭(내부 제목 "AI 연결") 안에 **카드 1개 추가.**

⚠️ **탭 id·라벨은 건드리지 않는다.** 딥링크·`/docs`·챗봇 KB가 탭 id를 참조하고 있다. `SettingsSidebar.tsx`의 `{ id: 'ai-bridge', … }` 항목을 그대로 두고, `AiBridgeTab.tsx` 안에 `<InAppAssistCard />` 를 한 줄 추가한다.

**최초 1회 안내 (켤 때 1번):**

| 항목                  | 내용                                                                                                                                                                                              |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **나가는 것**         | 선생님이 친 질문 문장(이름 삭제 후), 집계 숫자, 카테고리 이름, 학급 이름                                                                                                                          |

| **물어볼 수 없는 것** | **가정 형편·건강·상담 내용은 질문 자체가 자동으로 막힙니다.** 예: "○○이 아버지 실직 얘기를 꺼냈는데…" → 차단. 선생님을 못 믿어서가 아니라, 무료 AI는 보낸 내용을 학습에 쓸 수 있어서입니다 (§5.7) |
| **어디로**            | 미국에 있는 AI 서버(OpenCode Zen). 쌤핀 중계 서버를 거치며, 본문은 저장하지 않습니다                                                                                                              |
| **꼭 알아야 할 것**   | 지금 쓰는 모델은 **무료 모델이라, 보낸 내용이 모델 개선에 쓰일 수 있습니다.** 그래서 개인정보가 나가지 않는 범위로만 만들었습니다                                                                 |
| **아닌 것**           | 학생이 AI와 대화하는 기능이 아닙니다. 선생님 업무용입니다                                                                                                                                         |
| **끄기**              | 언제든 이 화면에서 끌 수 있고, 끄면 아무것도 나가지 않습니다                                                                                                                                      |

문구는 새로 쓰지 말고 **기존 `FAQ.tsx`의 검증된 문장을 가져다 쓴다**(과거 교훈: 개인정보 문구를 새로 쓰다 사실과 어긋난 사례가 있다).

**꺼져 있을 때:**

- 사이드바의 "업무 도우미" 항목이 **보이지 않는다**
- `Ctrl+K` 팔레트에 "AI에게 묻기" 항목이 **나타나지 않는다** (팔레트의 기존 동작은 100% 그대로)
- 어떤 경로로도 `ssampin-assist` 요청이 나가지 않는다
- 기존 고객지원 챗봇은 **아무 영향 없이** 그대로 동작한다

## 7. 단계별 계획

### Phase 0 — 세 가지 실측 (유일한 착수 관문)

**본 구현 전에 반드시 재고.** 셋 중 하나라도 결과가 나쁘면 이 계획의 형태가 바뀐다.

#### 실측 ① 도구 호출(function calling) 성공률 — **1순위**

**왜 1순위인가:** Zen 공식 문서에 함수 호출 관련 언급이 **전혀 없다.** 안 되면 "챗봇"이라는 제품 자체가 성립하지 않는다.

**측정:**

| 항목                    | 방법                                                             | 통과 기준                 |
| ----------------------- | ---------------------------------------------------------------- | ------------------------- |
| `tools` 파라미터 수용   | OpenAI 호환 `chat/completions`에 `tools` 넣고 400/무시 여부 확인 | 오류 없이 수용            |
| 스키마 준수             | 도구 5종 × 질의 20건. 인자 JSON이 스키마와 맞는가                | ≥ 90%                     |
| 한국어 도구 선택 정확도 | 한국어 질의 20건에서 올바른 도구를 골랐는가                      | ≥ 80%                     |
| 멀티턴 유지             | 3턴 이상 대화에서 도구 목록·이전 결과를 유지하는가               | 3턴 유지                  |
| 병렬/연속 호출          | 한 답에 도구 2개가 필요한 질문                                   | 성공 여부 기록(필수 아님) |
| 스트리밍(SSE) 지원      | `stream: true` 응답 형태                                         | 지원 여부 기록            |

**실패 시 분기:**

| 결과                                           | 분기                                                                                                                                                                                                                  |
| ---------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **통과**                                       | **옵션 A 단독으로 진행.** `routeAssistLocally.ts`를 만들지 않는다(죽은 코드 방지)                                                                                                                                     |
| **부분** (단일 도구는 되나 멀티턴/스키마 불안) | **옵션 C.** 도구를 1턴 1개로 제한하고, 실패 시 로컬 라우터로 강등. 강등 사실을 UI에 표시(§5.6)                                                                                                                        |
| **실패** (`tools` 미지원 또는 스키마 붕괴)     | **옵션 B 단독으로 축소.** 앱이 질문을 유형 분류 → 앱이 데이터 조회 → 모델은 **숫자 카드에 한 줄 해설만.** 이건 함수 호출 없이도 성립한다. **제품 포지셔닝을 "챗봇"에서 "말로 묻는 요약"으로 바꾼다 — 오너 판단 지점** |
| 그 외                                          | Zen의 다른 무료 모델을 같은 절차로 재측정. **Gemini 무료 티어는 재검토하지 않는다**(§1.2)                                                                                                                             |

#### 실측 ② 무료 티어 rate limit

**왜 필요한가:** 문서 미공개인데 **키 하나로 전체 사용자를 중계한다.** 한도가 최대 단일 리스크다(D3).

**측정:** 분당 한도 / 일일 한도 / 429 발생 패턴(헤더에 `Retry-After`가 오는가) / 동시 요청 허용치 / 429 이후 회복 시간.

**실패 시 분기:**

| 결과                             | 분기                                                                                                             |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| **여유** (분당 ≥ 20, 일 ≥ 5,000) | 계획대로. 설치별 상한을 보수적으로 시작해 관측 후 완화                                                           |
| **빠듯**                         | 설치별 일일 상한을 낮춘다 + 도구 결과 캐시(같은 질문 재요청 방지) + 비스트리밍 + 히스토리 축약 강화              |
| **심각** (분당 한 자리)          | **전면 재검토.** ①§8.4 유료 전환을 앞당겨 오너 판단 ②또는 기능 보류 ③또는 옵션 B로 축소(토큰 사용량이 훨씬 적다) |

#### 실측 ③ 한국어 품질

**측정:** 실제 관찰 메모 성격의 문장 10건(실제 학생 데이터가 아니라 지어낸 유사 문장) 기준.

## 8. 무료 티어 한도 소진 대비 설계

### 8.1 서버 상한 (중계 함수)

| 규칙                  | 초안 값      | 근거                                         |
| --------------------- | ------------ | -------------------------------------------- |
| IP 기준 분당          | 6회          | 기존 `checkRateLimit` 재사용. 실측 ② 후 확정 |
| 설치 식별자 기준 일일 | 40회         | 챗봇은 윤문보다 턴 수가 많다. 실측 ② 후 확정 |
| 전역(키 전체) 일일    | 실측 ②의 80% | **키가 정지되기 전에 우리가 먼저 막는다**    |

**설치 식별자:** 기존에 쓰는 값이 있는지 먼저 확인한다(§14 미해결 질문). 없으면 로컬 생성 UUID를 쓰되 **서버에는 해시만** 보낸다.

### 8.2 앱 측 예산 — "한 번에 한 문장"의 챗봇 번역

자매 계획의 안전장치 ④("한 번에 한 문장 / 배치 금지")는 챗봇에서 **성립하지 않는다.** 대화는 본질적으로 누적이기 때문이다. 다음으로 대체한다.

| 대체 장치                     | 내용                                                                                           | 막는 것                                                                   |
| ----------------------------- | ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| **대화당 학생 1명 상한**      | 한 대화에서 서로 다른 학생을 2명 이상 다루면 "새 대화를 시작해 주세요"로 끊는다                | **한 세션에 학급 프로필이 쌓이는 것.** 이것이 배치 금지의 정확한 번역이다 |
| **히스토리 미재전송**         | 모델에 보내는 이력은 최근 K턴 + **도구 결과는 최신 것만.** 과거 도구 결과를 다시 보내지 않는다 | 누적                                                                      |
| **명단 통째 반환 불가**       | `list_students` 상당 도구가 **존재하지 않는다**(구조적)                                        | 프로필                                                                    |
| **대화당 도구 호출 N회 상한** | 초안 10회                                                                                      | 폭주                                                                      |
| **남은 횟수 표시**            | 429를 맞기 전에 알린다                                                                         | UX                                                                        |

### 8.3 429가 나도 절반은 남는다

도구 실행은 **로컬에서 끝난다.** 모델이 429여도 숫자 카드는 그대로 나온다(P5, §5.6). 이것이 무료 티어 리스크의 가장 강력한 완화책이다 — **한도가 소진돼도 기능이 0이 되지 않는다.**

### 8.4 유료 전환 시 갈아끼울 지점

| 지점            | 파일                                   | 방법                                                                        |
| --------------- | -------------------------------------- | --------------------------------------------------------------------------- |
| 모델·엔드포인트 | `supabase/functions/_shared/zenLlm.ts` | 환경변수 `ZEN_MODEL` 값 교체. 코드 수정 0 (기존 `UPSTAGE_MODEL` 패턴)       |
| **등급 정책**   | `src/domain/entities/AssistTool.ts`    | `ALLOWED_GRADES = [1]` → `[1, 2]`. **상수 한 줄**                           |
| 등급 정책 검증  | 계약 테스트                            | 위 상수를 읽으므로, 바꾸는 즉시 어떤 도구가 새로 열리는지 테스트가 드러낸다 |
| 상한            | 환경변수                               | 값만                                                                        |

**중요:** 등급 정책은 **모델이 아니라 계약에 달려 있다.** "유료 모델이니 안전하다"가 아니라, **"학습에 쓰지 않는다"가 계약으로 보장되는가**가 기준이다. 유료 전환 시 그 계약 문구를 직접 확인하고 문서에 인용한 뒤에만 `[1, 2]`로 바꾼다.

**1차에는 2등급 도구를 하나도 만들지 않는다.** 미래를 위해 미리 만들면 죽은 코드가 되고, 죽은 코드는 언젠가 실수로 켜진다.

**전환의 가장 큰 동기는 도구가 아니라 §5.7이다.** 도구 등급제는 코드로 완벽하게 강제할 수 있지만, **선생님이 입력창에 직접 치는 문장은 원리적으로 완전히 막을 수 없다**(우회·완곡 표현). 무료 모델을 쓰는 한 이 위험은 0이 되지 않는다. **"학습에 쓰지 않는다"가 계약으로 보장되는 순간, 이 경로의 심각도가 근본적으로 낮아진다.** 유료 전환을 검토할 때 비용 대비 편익의 계산에 이 항목을 반드시 넣는다 — 도구를 몇 개 더 여는 것보다 이쪽이 훨씬 크다.

### 10.4 관측성 (Observability)

**서버 — 본문 없이 숫자만:**

- 요청 수 / 성공·실패 / 실패 사유 분류(429, 타임아웃, 상류 4xx/5xx, 스키마 거부)
- 응답 시간 p50·p95
- 레이트 리밋 히트율 (IP별 / 설치별 / 전역)
- **도구 호출 성공률** — 옵션 C에서 A→B 강등이 얼마나 자주 일어나는가. Phase 0 실측이 운영에서도 유지되는지 보는 유일한 창
- **요청·응답 본문은 절대 기록하지 않는다.** 디버깅을 위해서도 예외를 두지 않는다

**앱 — 로컬 로그:**

- 전송 시각 / **실제로 나간 문자열** / 호출된 도구와 결과 / 받은 답 / 성공·실패
- 선생님이 열람·삭제 가능. 서버로 올라가지 않음

**앱 — §5.7 위험 지표 (횟수만, 내용 미저장):**

- **제안 칩 대 자유 타이핑 비율** — 자유 타이핑이 많으면 1층 방어(칩 설계)가 실패한 것이고, 그것이 곧 누출 위험 신호다
- **3등급 차단 발생 횟수** — 자주 걸리면 UX가 잘못 유도하고 있다는 뜻. **차단된 문장 내용은 절대 저장하지 않는다**(저장하는 순간 우리가 그 위험을 만든다)
- 이 지표는 로컬에만 남고 서버로 가지 않는다. 오너가 설정 화면에서 확인한다

**운영 알림:**

- 전역 일일 한도 80% 도달
- Zen이 401/403 반환 (키 정지 신호) — **즉시 오너에게 닿는 경로 확보**
- 실패율 임계치 초과

## 11. 사전 부검 (Pre-mortem) — deliberate 필수

> "6개월 뒤 이 기능이 대형 사고로 끝났다. 무엇이 원인이었나?"

### 시나리오 1 — "챗봇 대화 몇 개를 이어 붙였더니 학급 명부가 나왔다"

**어떻게 벌어졌나:** 한 선생님이 편해서 하루 종일 챗봇을 썼다. 대화당 학생 1명 상한은 있었지만, 새 대화를 시작하면 초기화되므로 30번 새로 시작해 30명을 차례로 물었다. 각 답은 익명 집계였지만, 같은 API 키·같은 시간대·같은 학급 이름·연속된 번호가 맞물려 **외부에는 한 학급의 프로필이 축적**됐다. 무료 모델이라 그 데이터는 학습에 쓰였다.

**징후:** 한 설치에서 짧은 시간에 새 대화가 반복 생성됨 / 같은 학급 이름이 연속 등장 / 대화당 상한만 있고 **일일 학생 수 상한이 없음**

**예방:**

- 대화당 상한에 더해 **설치별 일일 "서로 다른 학생 수" 상한**을 둔다 (초안 5명). 로컬 판정이라 서버가 학생 식별자를 알 필요가 없다
- 학급 이름도 도구 결과에서 **일반화**한다 — `"3-2반"` 대신 `"담당 학급"`. 학급 이름은 개인정보가 아니지만 **연결 고리**가 된다
- 히스토리 미재전송 + 도구 결과 최신 것만 (§8.2)
- 상한에 걸리면 차단이 아니라 **설명**한다: "오늘은 학생별 요약을 많이 보셨어요. 나머지는 화면에서 보시는 게 더 정확해요."

### 시나리오 2 — "도구 하나가 조용히 등급을 넘었다"

**어떻게 벌어졌나:** 6개월 뒤 누군가 "카드에 이름이 안 나와서 불편하다"며 `get_attendance_summary` 반환에 `studentName`을 추가했다. 화면 표시용이었다. 그런데 **도구 결과는 화면에도 쓰이고 모델에도 간다** — 두 경로가 같은 객체를 쓰고 있었다. 코드 리뷰에서 "화면용 필드"로 설명됐고 통과했다. 몇 달 뒤 로그 조사에서 실명이 계속 나가고 있었음이 드러났다.

**징후:** 도구 반환 타입에 사람 이름·본문 필드가 추가되는 커밋 / "화면에 필요해서"라는 리뷰 코멘트 / 계약 테스트 픽스처가 함께 수정되는 커밋(그물을 통과시키려 그물을 고친 것)

**예방:**

- **도구 결과 타입을 화면용과 모델용 둘로 나눈다.** 모델용은 `ModelSafe<T>` 브랜드 타입이고, 화이트리스트 재구성 함수를 통과해야만 만들어진다. 화면용에 필드를 추가해도 모델용에는 나타나지 않는다 — **타입이 물리적으로 막는다**
- 레지스트리 순회 계약 테스트가 새 도구·새 필드를 자동으로 검사 (§4.4 ④)
- **함정 픽스처를 고치는 커밋은 반드시 리뷰**임을 테스트 파일 주석에 명시. "가드를 고쳐서 통과시키지 말 것"은 이 저장소의 기존 규칙이다
- 등급 위반 시 경고가 아니라 **차단**. 경고는 무시되지만 차단은 무시할 수 없다

### 시나리오 3 — "어느 날 아침 전국의 선생님이 동시에 오류를 봤다"

**어떻게 벌어졌나:** 선생님 수가 늘면서 우리 키 하나로 하루 수만 건이 나갔다. OpenCode Zen이 "키 하나로 다수 사용자에게 중계"를 재판매(resale)로 보고 키를 정지시켰다. 또는 `deepseek-v4-flash-free`의 무료 기간이 끝났다. 사전 문의는 "나중에 하자"로 미뤄져 있었고, 회신도 없는 상태였다.

**징후:** 사용량 급증 / Zen에서 401·403 / 무료 기간 종료 공지 / `help@anoma.ly` 문의가 Phase 2 이후로 밀리는 논의

**예방:**

- **`help@anoma.ly`에 Phase 0에서 문의를 발송한다** (Phase 2가 아니라 0). Zen 약관에 중계를 금지하는 조항도 허용하는 조항도 **없으므로**, 서면 확인이 유일한 근거가 된다. 회신이 없어도 문의 기록 자체가 선의의 증거다
- 전역 일일 한도를 실측의 80%에 걸어 **키가 정지되기 전에 우리가 먼저 막는다**
- **P5가 이 시나리오의 안전망이다.** 모델이 완전히 끊겨도 도구 실행은 로컬이므로 숫자 카드는 계속 나온다. 선생님이 보는 것은 "AI 요약은 지금 사용할 수 없습니다" 한 줄뿐이다
- 사용자 가이드에 **"무료 모델에 의존하는 부가 기능이며 중단될 수 있다"**를 처음부터 적는다. 나중에 적으면 변명이 된다
- 전환 지점을 1파일 + 상수 1개로 좁혀 둔다 (§8.4)

### 시나리오 4 — "등급제를 다 만들었는데, 정작 선생님이 직접 쳐서 내보냈다" (§5.7 상호 참조)

**어떻게 벌어졌나:** 도구 등급제·4중 그물은 완벽하게 작동했다. 도구에서 나간 건 숫자뿐이었다. 그런데 한 선생님이 어려운 상담 상황에 부딪혀 챗봇에 이렇게 물었다 — _"우리 반에 아버지가 실직하고 어머니가 아프신 학생이 있는데 어떻게 대해야 할까요?"_ 이름은 없었으니 이름 삭제도 작동하지 않았고, 등급제는 도구 결과만 보므로 아무것도 걸리지 않았다. 그 문장은 그대로 무료 모델로 갔고 학습에 쓰였다.

**왜 놓쳤나:** 계획이 **"AI가 우리 데이터를 가져가는 것"** 만 위험으로 봤다. 실제 위험의 절반은 **"선생님이 AI에게 주는 것"** 이었다. 게다가 이런 질문은 **선의에서 나온다** — 학생을 도우려는 마음이 가장 민감한 정보를 밖으로 내보낸다. 막을 동기가 사용자에게 없다.

**징후:** 자유 타이핑 비율이 높음 / 3등급 차단이 자주 발생 / "차단이 너무 빡빡하다, 경고로 바꾸자"는 논의 / 제안 칩을 늘리자는 요구가 없음

**예방:**

- **1층이 가장 중요하다** — 제안 칩으로 자유 타이핑의 필요성 자체를 줄인다 (§5.7.2). 탐지는 2차 수단이다
- 3등급은 **경고가 아니라 차단.** 자매 계획이 경고인 것과 정책이 다른 이유를 §5.7.3에 명시해 뒀다. **"경고로 완화하자"는 변경은 이 문서를 근거로 거부한다**
- 차단 화면이 **선생님을 벌주지 않는다.** "선생님 잘못이 아니에요" + 앱 안 상담 기능으로 유도 (§5.7.3). 벌주는 UI는 우회를 유발한다
- **막을 수 없는 부분이 있음을 문서와 가이드에 적는다** (§5.7.5). 완벽을 약속하면 그 약속이 다음 사고의 원인이 된다
- 자유 타이핑 비율·차단 횟수를 지표로 본다 (§10.4). **내용은 저장하지 않는다**
- **이 시나리오가 §8.4 유료 전환의 가장 큰 동기다.** 학습 미사용이 계약으로 보장되면 이 경로의 심각도가 근본적으로 낮아진다

> deliberate 요구는 3개 시나리오이나, 오너 지적으로 이 4번째를 추가했다. **§5.7의 구멍이 이 계획에서 가장 정직하게 다뤄야 할 부분이다.**

## 13. ADR — 인앱 AI 챗봇 (OpenCode Zen) 도입

> ADR 번호는 `DECISIONS.md` 최신이 ADR-051이므로 **ADR-052 이후**로 부여한다 (자매 계획과 번호 충돌 주의).

### Decision (결정)

교사가 앱 안에서 바로 대화할 수 있는 AI 챗봇을 도입한다. 모델은 **OpenCode Zen의 무료 모델 `deepseek-v4-flash-free`**, 키는 **Supabase 중계 함수 `ssampin-assist`** 에만 둔다.

무료 모델 약관("수집 데이터가 모델 개선에 쓰일 수 있음") 때문에, 챗봇이 쓸 수 있는 도구를 **1등급(집계형·교사 본인·익명 문장)으로만 한정**하고, 이를 도구 레지스트리의 필수 등급 필드 + 화이트리스트 재구성 + 전송 직전 차단 관문 + 계약 테스트의 **4중 그물로 코드가 강제**한다. 2등급(개별 학생 기록)은 챗봇이 집계로 답하고 앱 화면·AI 브릿지로 안내하며, 3등급(상담·건강·가정)은 도구 자체를 만들지 않는다. **쓰기 도구는 전면 제외**하고 '화면 열기' 도구로 대체한다.

UI는 기존 고객지원 챗봇과 **완전히 별개의 물건**으로 만든다 — 성격이 "목적지"와 "동반자"로 다르기 때문이다. **`Ctrl+K` 명령 팔레트(이미 구현돼 있음)를 진입점으로, 우측 도킹 패널을 본체로** 삼는다. 도킹은 본문을 밀어낼 뿐 덮지 않으므로 화면 맥락이 유지된다. **새 플로팅 버튼도 새 전역 단축키도 만들지 않는다.**

또한 **자유 입력창이 등급제로 막을 수 없는 최대 누출 경로**임을 인정하고, 3층 방어(제안 칩으로 자유 입력 필요성 축소 → 3등급 표현 **차단** → 침묵이 승인으로 읽히지 않게)를 둔다. **완전 차단이 불가능하다는 사실을 문서와 사용자 가이드에 명시한다.**

기본값은 꺼짐이다.

### Drivers (동인)

1. **무료 모델 약관이 선택지를 결정한다** — 개인정보가 나가지 않는 범위로 한정하는 것 외에 다른 길이 없다
2. **도구 호출 가능 여부가 제품의 성립 조건이다** — Zen 문서에 언급이 전무해 Phase 0 실측이 착수 관문
3. **키 하나로 전체 사용자를 중계한다** — 한도 소진과 키 정지가 단일 장애점

### Alternatives considered (검토한 대안)

| B. 앱이 도구를 고르고 모델은 문장만     | **유효.** 함수 호출 없이도 성립. Phase 0 실패 시 축소 대안                                                                                                     |

### Why chosen (선택 이유)

교사가 AI를 쓰려면 개발자 도구를 설치해야 하는 지금 상태는 사실상 기능 미제공이다. 이를 해소하는 유일한 무료 경로가 Zen이고, Zen의 무료 약관을 수용 가능하게 만드는 것은 **"개인정보가 나가지 않는다"는 성질 하나뿐**이다.

그런데 그 성질은 사람이 기억해서 지켜지지 않는다. 6개월 뒤 "화면에 이름이 필요해서" 한 줄이 추가되는 것으로 무너진다(부검 2). 그래서 **등급을 타입과 테스트로 강제하는 것**이 이 결정의 실질이며, 챗봇 기능 자체보다 이 그물이 더 중요하다.

또한 도구 실행이 로컬에서 끝나는 구조 덕분에, 모델이 429·장애·키 정지로 완전히 끊겨도 **숫자 카드는 계속 나온다.** 무료 티어 의존이라는 가장 큰 리스크(R2·R3)가 기능을 0으로 만들지 않는다.

**형태를 `Ctrl+K` + 도킹으로 정한 이유**는 업무 보조의 성질에서 나온다. 이 기능의 가장 큰 가치는 "지금 보고 있는 화면을 안다"는 것인데, **덮는 형태는 바로 그 가치를 가린다.** 도킹은 밀어낼 뿐 덮지 않아 답과 본문을 동시에 볼 수 있다. 다만 도킹은 호출이 느리므로, 이미 완성돼 있는 `Ctrl+K` 팔레트를 진입점으로 이어 붙였다. 팔레트가 지금 답하지 못하고 "일치하는 명령을 찾을 수 없습니다"로 끝나는 자리가 **자연어 질문이 떨어지는 바로 그 자리**라서, 이보다 자연스러운 이음새가 없다.

**§5.7을 정면으로 다룬 이유**는, 등급제가 완벽해도 그 옆에 뚫린 구멍이 있으면 전체가 무의미해지기 때문이다. 그리고 이 구멍은 **선의에서 열린다** — 학생을 도우려는 질문이 가장 민감한 정보를 내보낸다. 사용자에게 막을 동기가 없으므로 제품이 대신 막아야 하고, 그마저 완전하지 않다는 사실을 숨기지 않는 것이 유일하게 정직한 선택이다.

### Consequences (결과)

**얻는 것**

- 선생님이 설치·로그인·결제 없이 앱 안에서 AI를 쓴다
- 학생 이름·학번·기록 본문·상담·건강 정보가 물리적으로 전송되지 않는다
- 등급 위반이 컴파일 또는 테스트에서 드러난다 — 사람의 기억에 의존하지 않는다
- 모델이 끊겨도 숫자는 나온다
- AI 브릿지가 2등급 이상의 정식 경로로 명확히 자리 잡는다
- **답과 결과를 동시에 본다** — 도킹이 본문을 덮지 않으므로, 답변의 버튼을 눌러 왼쪽 화면이 바뀌는 것을 그대로 지켜볼 수 있다
- **새 진입점을 거의 만들지 않았다** — `Ctrl+K`는 이미 있고, 새 플로팅 버튼도 새 전역 단축키도 없다. 학습 비용과 회귀 위험이 함께 낮다

**감수하는 것**

- **챗봇이 개별 학생 기록을 답하지 못한다.** 이것은 버그가 아니라 설계이며, 사용자 안내에 명시해야 한다
- 21번째 Edge Function과 API 키 관리 부담
- **무료 모델 의존** — 무료 기간 종료·키 정지 시 요약 문장이 중단될 수 있다
- 개인정보처리방침 국외이전 표에 행 추가 필요 (미국)
- 도구를 추가할 때마다 등급 판정과 픽스처 갱신이라는 고정 비용이 붙는다
- **앱에 챗봇이 2개가 된다.** 통합하지 않기로 했으므로, 두 기능이 첫눈에 구분되도록 위치·형태·아이콘·명칭을 계속 관리해야 한다
- **`App.tsx` 레이아웃과 명령 팔레트라는, 이미 잘 쓰이는 두 자산을 건드린다.** 변경은 최소지만 회귀 위험이 0은 아니다 (R11·R12)
- 도킹이 본문을 좁힌다 — 좁은 화면에서는 맥락 유지를 포기하고 오버레이로 전환한다
- **자유 입력창의 누출 위험을 완전히 없앨 수 없다.** 우회·완곡 표현은 못 잡는다. 이 사실을 사용자 가이드에 적어야 하며, 이것이 유료 전환의 가장 큰 동기가 된다

## 15. 성공 기준

1. Phase 0 실측 3종이 완료되고 오너 판정이 문서에 기록되었다
2. 도구 등급 배정표대로 **1등급 도구만** 레지스트리에 존재한다
3. 함정 픽스처로 전 도구를 실행해 **명단 이름·PII가 0건**이고, 일부러 새게 만들면 테스트가 **빨간불이 된다**
4. 등급 위반·PII 잔존 시 **전송이 차단**된다 (경고가 아니라 차단)
5. 옵트인 꺼짐 상태에서 `ssampin-assist` 요청이 **0건**이다
6. API 키가 앱 빌드 산출물 어디에도 없다
7. 2등급 질문에서 **완전 거절이 아니라** 집계 답변 + 화면 안내가 나온다
8. **3등급 표현을 입력하면 전송이 차단되고, 강행 경로가 UI에도 코드에도 없다** (§5.7)
9. 모델이 실패해도 **숫자 카드와 입력 내용이 사라지지 않는다**
10. **기존 고객지원 챗봇(`HelpChat/`, `ssampin-chat`)이 코드·동작 모두 무회귀**다
11. **명령 팔레트의 기존 동작이 100% 그대로**이고, 매칭이 있는 질의에서는 아무 변화가 없다
12. 도킹 패널이 열려도 **본문이 가려지지 않는다**(밀릴 뿐)
13. **새 플로팅 버튼도 새 전역 단축키도 추가되지 않았다**
14. 4단 게이트 + `deno check` + 랜딩 게이트가 전부 통과했다
15. 개인정보처리방침·`/docs`가 같은 릴리즈에서 갱신되었고, **"완전히 막을 수는 없다"는 한계가 가이드에 적혀 있다**
