## 1. 목표

새 학년도·새 학기가 되면 교사가 가르치는 학생·과목·담임 반이 바뀐다. 지금 쌤핀에는 **학년도 개념이 아예 없어서**, 2년차 사용 시 작년 기록과 올해 기록이 같은 파일에서 뒤섞인다(조사 §2). 목표는 셋이다.

1. **기존 기록을 지우지 않고 보관한다** — 언제든 다시 열람 가능.
2. **새 학년도·새 학기를 깨끗한 상태에서 시작한다.**
3. **삭제와 보관을 언어·동선·색으로 강하게 분리한다** — "보관"은 절대 데이터를 잃지 않는다는 약속.

쉬운 말로: **작년 서류를 버리지 않고 캐비닛에 넣어두고, 책상 위는 올해 것만 놓는 기능**이다.

### 1.1 왜 지금인가 — 회의론자 반론에 대한 정면 응답

**반론(Critic)**: "P1이 정말 개학 전에 필요한가? P1은 진짜 고장(학생 식별키 `학년-반-번호` 충돌)을 하나도 고치지 않는다. S1.2b 결함조차 `archived` 필드가 생겨야 성립하는, **P1이 스스로 만든 문제를 P1이 고치는** 구조다. 남는 가치는 목록 정리 UX뿐이다."

**이 반론은 상당 부분 옳다.** 그래서 v2는 두 가지로 응답한다.

**(1) 반론을 인정하고 계획을 줄였다.** v1의 P1(스토리 8개, 필터 13곳)을 **P1 골격으로 대체**했다(§5.1). 남은 것은 "보관 토글 + 목록 분리 + 새로 기록할 대상을 고르는 표면에서 숨기기"뿐이다.

**(2) 미루면 무엇을 잃는가 — 세 가지, 전부 P1 없이는 대안이 없다.**

- **개학 후 몇 주간 매일 겪는 마찰.** 고교학점제 고등학교는 학기마다 선택과목 수업반이 통째로 재편성된다. 1학기 반 8개와 2학기 반 8개가 **한 목록에 16개로 섞인 채 한 학기를 보낸다.** 출결·진도·기록 입력마다 고를 목록이 두 배다. UX 개선이 아니라 매일 반복되는 오입력 위험이다.
- **현상 유지가 능동적으로 파괴적이다.** 보관이 없으면 교사가 쓸 수 있는 유일한 정리 수단은 **삭제**다. 그런데 `deleteClass`는 출결을 **그룹 단위로 지운다**(`useTeachingClassStore.ts:368-380`, 함정 ㉔) — 형제 반의 출결까지 날아간다. **"기다린다"는 안전한 선택이 아니라, 교사에게 데이터를 파괴하는 버튼만 남겨두는 선택이다.**
- **P2를 위한 시간을 사는 일이다.** P2(전면 전환)는 2027년 2월 마감이고 파괴적이다. P1이 `archived` 개념·도메인 규칙·보관 UI 언어를 먼저 실사용에 올려두면, P2는 "이미 익숙한 개념의 확장"이 된다. P1을 건너뛰면 P2에서 개념 도입과 파괴적 전환을 동시에 처음 선보이게 된다.

**정직하게 남는 약점**: P1은 학생 식별키 충돌을 고치지 않는다. 그건 P2의 스냅샷이 해결한다(작년 데이터가 물리적으로 분리되어 키가 충돌할 상대가 없어진다). **이 계획은 P1을 "2년차 고장의 해결"로 홍보하지 않는다.**

## 3. 개념 모델 — 2단 시간 축

```
학년도  2026학년도  ├─ 2026-1 (1학기) ─┬─ 2026-2 (2학기) ─┤
담임 축: 명렬·담임 출결·누가기록·좌석·생기부 초안   → 수명 = 학년도
교과 축: 수업반·진도·관찰기록·루브릭·성적분석       → 수명 = 학기 (고교학점제 재편성)
```

- **학기 라벨은 `'2026-1'` 형식.** 내부 선례 `useAiBridgeConsentStore.ts:43-49` `academicTerm()`. 경계: 3~8월=1학기, 9~12월=2학기, **1~2월=직전 학년도 2학기**.
- **전환 장치 둘**: (A) 수업반 단위 보관 = **P1** / (B) 학년도 마무리 마법사 = **P2**.
- **epoch(전환 세대) 스탬프의 저장 위치는 별도 결정**(ADR-034, APPROVED 방향 · P2 착수 시 선결 검증 4건) — 레코드 단위. `archivedTerm`은 이 결정에 의존하지 않는다(TeachingClass는 그 자체가 레코드).

    - **드래그 재정렬과 충돌하지 않게** 한다 — 체크박스 영역과 드래그 핸들 영역을 분리하고, 선택 모드에서는 드래그를 비활성화한다.
  - **② 보관 섹션 그룹화 표시 (v4 오너 결정 2)**
    - 보관된 반을 평평한 목록이 아니라 **`archivedTerm` → `groupId`(교실) 2단으로 묶어** 보여준다.
      예: `2026학년도 1학기` › `3학년 2반` › [통합과학, 통합사회] / `3학년 5반` › [통합과학]
    - `groupId`가 없는 단독 반은 학기 그룹 아래 **"기타"**로 모은다.
    - `archivedTerm`이 없는 레거시 항목(P1 이전에 어떤 경로로든 생긴 경우)은 **"학기 미상"** 그룹으로 — 숨기지 않는다.
    - 이 그룹화가 P3 보관함 뷰어(S3.1)의 학년도→학기 그룹핑과 **같은 개념**이므로, 가능하면 표시 로직을 공용 부품으로 뽑아 P3에서 재사용한다.
  - **③ 확인 다이얼로그 — 개별 보관 기준으로 교체 (v4)**
    - 단건: `"○○(과목)을 보관할까요? 출결·진도·기록은 그대로 남고 언제든 다시 볼 수 있어요."`
    - **같은 `groupId` 형제가 활성으로 남는 경우 한 줄 추가**: `"같은 반의 다른 과목 N개는 계속 활성 상태로 남습니다."` — v3의 "함께 보관됩니다"와 **정반대 안내**이므로 문구를 반드시 바꾼다.
    - 일괄: `"선택한 N개 수업반을 보관할까요? 기록은 그대로 남아요."` + 대상 목록 표시.
    - **사전 동기화 안내를 여기로 일원화** (v4 — 배너가 사라졌으므로): `"다른 기기(폰·다른 PC)를 먼저 동기화한 뒤 정리해 주세요."` ADR-033의 위험 창을 좁히는 안내가 **이제 이 다이얼로그에만 있다.**
    - "정말요?" 금지. **성공 후 토스트 + 되돌리기(Undo).**
  - 보관된 반 선택 시 상단 **읽기 전용 배지**("보관됨 · 2026학년도 1학기").
- **⚠️ 읽기 전용은 저장 버튼 비활성만으로 부족하다**: 출결은 `createAttendanceSaveSequencer`(`attendanceAutosave.ts`) **자동저장**이다. AC-2가 탭 열람을 요구하므로 시퀀서는 반드시 마운트된다. 버튼만 끄면 **자동저장이 그대로 돈다.**
- **완료 기준(AC)**
  1. 보관 → 활성 목록에서 사라지고 보관 섹션에 나타난다. 보관 해제 → **활성 목록 맨 아래**(S1.2 order 규칙).
  2. 보관된 반의 출결·진도·관찰 **탭을 열면 데이터가 그대로 보인다**(읽기 전용). 조회가 막히면 실패.
  3. **입력 컨트롤 전체가 비활성**(저장 버튼뿐 아니라 셀·팔레트·텍스트 입력 포함).
  4. **자동저장 시퀀서가 생성되지 않는다**(보관된 반일 때).
  5. **강제로 저장 함수를 호출해도 파일이 변하지 않는다**(단위 테스트 — 방어 3겹).
  6. **다중 선택 → "선택한 N개 보관" → N개가 모두 보관 섹션으로 이동**하고, 저장·업로드는 각 1회다(S1.2 AC-9와 짝).
  7. **선택 모드에서 드래그 재정렬이 비활성**이고, 선택 해제 후 정상 복귀한다.
  8. **보관 섹션이 `archivedTerm` → `groupId` 2단으로 묶여 표시**된다. `groupId` 없는 반은 "기타", `archivedTerm` 없는 반은 "학기 미상"에 들어가며 **어느 것도 목록에서 사라지지 않는다.**
  9. **형제가 활성으로 남는 단건 보관 시 확인 문구에 "다른 과목 N개는 계속 활성" 안내가 나온다**(N은 실제 활성 형제 수).
  10. UI 규칙: `sp-*` 토큰만, 투명도 수식 금지, `rounded-sp-*` 금지, raw `text-white` 금지. `npm run check-hex-hardcoding` 통과. 라이트/다크 실렌더.
- **의존**: S1.2 · **frontend-design 에이전트 협업 필수**

## 7. 결정 사항 — ADR

> `DECISIONS.md` 최신 ADR은 028. 아래를 ADR-029~036으로 등재한다(등재 시 번호순 정렬).

### ADR-029: 학기(term)를 최소 시간 단위로 삼고 라벨은 `'YYYY-S'`로 통일한다 — **APPROVED**

- **Decision**: 시간 축 최소 단위는 **학기**. 라벨 `'2026-1'`, 계산 정본 `src/domain/rules/academicCalendar.ts`. 경계: 3~8월=1학기, 9~12월=2학기, **1~2월=직전 학년도 2학기**.
- **Drivers**: ① 고교학점제는 선택과목 수업반이 학기 단위로 재편성 ② `useAiBridgeConsentStore.ts:43-49`에 같은 형식·경계가 이미 구현(선례 승격이 신규 발명보다 안전) ③ 학년도 입도는 학기 요구를 담지 못한다.
- **Alternatives**: (a) 학년도 입도 — 단순하나 1년 만에 재설계. (b) 날짜(ISO) 기반 — 정밀하나 "같은 학기인가" 판정에 매번 규칙 계산, 학사 경계가 아닌 임의 시각으로 갈린다.
- **Why chosen**: 학기 입도는 학년도 입도를 **포함한다**(학년도 = 두 학기 묶음). 반대는 성립하지 않고 비용 차이는 거의 없다.
- **Consequences**: 담임 축은 학기를 관통해야 하므로 전환 장치가 둘로 갈린다. 학사 규범상 불가피.
- **Follow-ups**: `GradeAnalysis`의 `semester: '1'|'2'`(연도 없음) term 축 수선 → **P2로 이연.** 안전 근거: **`grade-analysis`는 `SYNC_REGISTRY` 미등재 = 동기화 위험 0**이므로 기기 간 충돌이 발생할 수 없다. 로컬 단일 기기 내 충돌만 남고, 그건 P2 스냅샷이 물리 분리로 해결한다.
- **⚠️ epoch 저장 위치 조항은 이 ADR에서 분리했다** → ADR-034.

### ADR-034: epoch(전환 세대) 스탬프는 **레코드 단위**에 둔다 — **APPROVED (방향) · P2 착수 시 선결 검증 4건**

> ADR-029에서 **분리**했다. 라벨 형식(029)은 승인됐지만 **저장 위치는 별개 결정**이며, **P1은 이 결정에 의존하지 않는다.**
> **v3에서 PENDING → APPROVED(방향)으로 전환**했다(r2 NEW-8). v2의 "PENDING"은 확정 조건이 falsifiable하지 않아 본문이 확정 서술인데 상태만 유보인 모순이 있었다. **방향은 승인하고, 착수 전 통과해야 할 검증을 반증 가능한 형태로 못박는다.**

**P2 착수 전 선결 검증 4건 (하나라도 실패하면 대안 (a)~(c) 재검토)**

| #   | 검증                                     | 통과 기준                                                                                                                                                                                                    | 실패 시                                                                           |
| --- | ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------- |
| ①   | **`build*` 경유 불변식 실측**            | 병합 3도메인의 저장 경로가 **100% `build*` 3함수를 경유**한다(봉투 메타테스트로 고정, S2.2). 우회 경로가 1개라도 있으면 그 경로의 레코드에는 term이 안 붙는다                                                | 우회를 먼저 봉합하거나, 봉합 비용이 크면 (a) 봉투 보존 수정과 재비교              |
| ②   | **`date` 파생 결정 가능성**              | 3도메인 모두 `date`가 존재하고 학기를 결정할 수 있다 — **이미 확인됨**(`Attendance.ts:34`, `Observation.ts:6`, `StudentRecord.ts:68`). `date` 부재 레코드의 비율을 실측해 "term 미부착" 폴백이 소수인지 확인 | 부재 비율이 높으면 폴백이 사실상 기본이 되어 가드가 무력 — 재설계                 |

| ④   | **레코드 증가분 실측**                   | 실사용 규모 데이터에서 term 필드 추가로 인한 **파일 크기·동기화 페이로드 증가가 수용 범위**(레코드당 ~14바이트 × 건수). 출결은 학생 수 × 교시 × 날짜로 곱해지므로 실측 필요                                  | 증가가 크면 term을 레코드가 아닌 **레코드 그룹(날짜·반)** 단위로 올리는 절충 검토 |

- **Decision(방향)**: 병합 3도메인(`attendance`/`observations`/`student-records`)의 **레코드에 `term?: string`을 붙인다.** 저장 chokepoint 3(`build*`) + merge 필터 3 = **6 편집.**
- **Drivers**: ① **파일 루트는 자기 코드가 벗긴다** — 봉투 재조립 9지점이 화이트리스트 재조립이고 이는 의도된 방어 불변식이다(`ManageObservations.ts:16-18`) ② 부활 위험은 병합 3도메인에만 존재 — 통파일 도메인은 epoch가 막을 것이 없다 ③ 레코드 필드는 구버전에서 **증명 가능하게 생존**(merge 전부 `map.set(r.id, r)`, 스토어 전부 스프레드).
- **Alternatives**: (a) 봉투 9지점 보존 수정 — 편집 9, 구버전 생존 0%, 실패가 조용함. 필요조건이나 불충분. (b) 사이드카 파일 — **더 나쁨**: 사이드카 자체가 통파일 LWW·무순서 도착에 노출. (c) 최소 버전 강제 — **탐지기로만 병행 채택**(`SyncToCloud.ts:218/225` `version:1` 데드 코드 → 구버전 감지 → 마법사 차단).
- **Why chosen**: (d)만이 **실패가 가시적**이고 구버전 생존 ~100%이며, "반쯤 전환된 상태"라는 오류 케이스를 **소멸시킨다**(레코드가 자기 학기를 스스로 말하므로 섞여 있어도 정상).
- **Consequences**
  - **term 파생은 반드시 `date`(사건 발생일)다. `createdAt` 사용 금지** (r2 NEW-2). 3도메인 모두 두 축을 따로 갖고 있고(`Attendance.ts:34` / `Observation.ts:6,9` / `StudentRecord.ts:68,69`), **8/10 수업을 9/2에 기록하면 `date`→`2026-1`, `createdAt`→`2026-2`로 갈린다.** 하필 가드가 작동하는 유일한 시점(학기 경계)에 답이 갈리므로 규칙을 못박지 않으면 3도메인이 서로 다르게 구현된다. 교사가 방학 중 밀린 기록을 몰아 쓰는 것은 정상 업무이고, 그 기록은 **지난 학기 것이어야 한다.**
  - `date` 부재·파싱 불가 시 **term을 붙이지 않는다**(추측 금지 → 현행 병합 폴백).
  - merge 3종에 필터가 붙어 병합 로직이 약간 복잡해진다.
  - 레코드마다 필드가 늘어 파일 크기·동기화 페이로드가 증가한다(선결 검증 ④로 실측).
- **Follow-ups**: **P2 착수 시 선결 검증 4건 수행 후 확정.** **v1이 든 기각 근거 "300+ 호출처"는 ADR-030(전 엔티티 `schoolYear`)에서 잘못 이전된 숫자이며, 레코드 스탬프에는 적용되지 않는다.**

### ADR-030: 아카이브는 엔티티 필드가 아니라 **파일 스냅샷**으로 만든다 — **APPROVED**

- **Decision**: 전환 시 대상 파일(약 17키 + 바이너리)을 `{userData}/data/archives/{term}/`으로 통째 복사 + 매니페스트. **전 엔티티에 `schoolYear`를 추가하지 않는다.**
- **Drivers**: ① **전 엔티티 필드안은 30+ 엔티티·300+ 호출처** — 회귀 표면이 코드베이스 전체. _(이 숫자는 **이 대안에만** 적용된다. 특정 3도메인 레코드 스탬프(ADR-034)에는 해당하지 않는다.)_ ② 스냅샷은 `backupManager.ts` 패턴 재사용으로 **라이브 코드 수정 ≈0** ③ "원형 그대로 열람"이 구조적으로 보장.
- **Alternatives**: (a) 전 엔티티 `schoolYear` — 모든 조회에 필터가 붙고 하나만 빠뜨려도 작년·올해가 섞인다. **검증 불가능한 표면. 기각.** (b) SQLite 도입 — 오프라인 로컬 JSON 정체성과 백업/동기화 인프라를 전부 재구축. **기각.**
- **Why chosen**: "보관된 것은 불변"이라는 강한 계약을 준다. 불변이면 병합도 충돌도 없고 뷰어는 순수 읽기만 하면 된다. 위험이 전환 1회로 국소화된다.
- **Consequences**: 오래된 아카이브를 최신 뷰어가 읽을 때 필드 부재 처리 필요(관대 파싱). 디스크 누적 → 용량 표시·삭제 경로 필요.
- **Follow-ups**: 매니페스트에 앱 버전 기록 → 버전별 관대 파싱.

### ADR-031: 보관함 뷰어 MVP는 5개 도메인으로 한정한다 — **APPROVED**

- **Decision**: 뷰어 v1 = 명렬 · 누가기록 · 관찰(첨부) · 출결 통계 · 진도. 좌석·설문·과제·루브릭·성적분석은 **아카이브에는 저장하되 뷰어는 후속.**
- **Drivers**: ① 교사가 실제로 다시 찾는 것은 기록과 출결 통계 ② 뷰어는 도메인마다 별도 컴포넌트라 범위가 곧 일정 ③ 데이터가 이미 아카이브에 있으므로 뷰어 추가는 비파괴적.
- **Alternatives**: (a) 전 도메인 뷰어 — P3가 P2보다 커진다. (b) 뷰어 없이 내보내기만 — PowerSchool이 이 길로 가서 "PDF로 따로 저장하라"는 불신을 낳았다(조사 §5-7). **기각.**
- **Why chosen**: 저장 범위와 열람 범위를 분리하면 열람은 나중에 늘려도 손해가 없다. 반대는 되돌릴 수 없다.
- **Consequences**: 뷰어에 없는 도메인은 **존재를 알려야 한다**(S3.2 AC-5).
- **Follow-ups**: P4에서 좌석·루브릭·성적분석 뷰어.

### ADR-032: 마법사 v1은 "전부 보관" 고정, 삭제는 보관함에서만 2단계 — **APPROVED**

- **Decision**: 마법사에 **"파기" 옵션 없음.** 영구 삭제는 보관함에서 학년도 단위 2단계 게이트(확인 문구 입력 + 내보내기 제안). 상담(Supabase)은 범위 밖.
- **Drivers**: ① 업계 표준이 "아카이브를 거쳐야만 삭제"(Google Classroom, Trello) ② 마법사에 삭제 분기를 넣으면 **가장 위험한 조작이 가장 흔한 동선 안에** 들어간다 ③ 개인정보 규범(교육부 훈령 476호)은 **파기 경로가 존재하면** 충족된다 — 그 경로가 마법사 안일 필요는 없다.
- **Alternatives**: (a) 마법사 ②단계 도메인별 보관/파기 선택 — 규범 친화적이나 연 1회 낯선 마법사에서 되돌릴 수 없는 선택을 요구한다. **v1 기각, v2 재검토.** (b) 파기 경로 미제공 — 규범 대응 불가. **기각.**
- **Why chosen**: 되돌릴 수 없는 것은 항상 별도 화면·별도 동사·추가 마찰 뒤에 둔다.
- **Consequences**: 디스크 누적 → 학년도별 용량 표시 필요(§12-A ⑤).
- **Follow-ups**: 상담 보관·파기는 별도 트랙.

### ADR-033: `teaching-classes` 동기화는 현행 통파일 LWW를 유지한다 (미결 3 = NO) — **APPROVED**

- **Decision**: P1에서 `teaching-classes`에 **레코드 단위 병합을 도입하지 않는다.** 대신 **보관/복원 성공 후 동기화 업로드 트리거를 S1.2의 요구사항으로 둔다**(완화책이 아니라 이 결정의 성립 조건이다).
- **Drivers**: ① **승자 판정의 출처가 Drive `modifiedTime`이다**(`SyncToCloud.ts:138-143`) — 로컬 파일 쓰기는 매니페스트를 건드리지 않으므로 "낡은 기기가 앱을 열기만 해도 승자"는 **성립하지 않는다** ② `SyncToCloud.ts:123-132` **DEFER**가 리모트 변경 시 업로드를 유예하고 `useDriveSyncStore.ts:133-139`가 pull-merge-push한다 ③ 남는 실제 위험 창은 **"보관 ~ 다음 업로드 사이의 업로드 경쟁"뿐**이다. **⚠️ 이 창은 고정 5분이 아니다** — `src/App.tsx:955-958`에서 주기는 `autoSyncIntervalMin` **사용자 설정**이고, `!enabled`이면 **주기 동기화 자체가 돌지 않아 창이 무한**해진다. 그래서 ③은 **S1.2의 업로드 트리거가 있어야만 성립한다**(동기화를 꺼둔 사용자는 기기가 하나이므로 애초에 경쟁이 없다).
- **Alternatives**: (a) P1에 레코드 병합 도입 — 안전하지만 D-14 일정에 물리적으로 불가능하고 위험 규모가 그만한 투자를 정당화하지 않는다. (b) **조건부 결정(실측 후 판단)** — v1이 택했던 안. **기각**: 2주 미접속 기기 시드는 D-11에 만들 수 없고, 프로젝트에 2기기 Drive 왕복 실측 이력이 없다(ADR-027). **미결을 임계 경로에 남기는 것 자체가 최대 일정 리스크**였다.
- **Why chosen**: 위험이 과대평가였음이 코드로 확인됐고, 종결이 일정을 살린다.
- **Consequences**: ① 업로드 트리거 이전의 짧은 창에서 두 기기가 동시에 수업반을 편집하면 한쪽이 진다 — **기존 동작이며 P1이 새로 만든 위험이 아니다.** ② **S1.2 업로드 트리거가 빠지면 이 ADR의 근거가 무너진다** — 그 경우 미결 3(레코드 병합)을 다시 열어야 한다. ③ **(v4)** 배너가 삭제되면서 **"다른 기기를 먼저 동기화하세요" 사전 안내의 유일한 지점이 S1.3 보관 확인 다이얼로그가 되었다** — 거기서 빠지면 안내가 0이 된다.
- **Follow-ups**: §8.4 실측을 **"보관 직후 B 선업로드 경쟁"** 테스트로 교체(2주 시드 테스트는 거짓 안심이므로 폐기).

### ADR-037: 시즌 배너를 만들지 않는다 — **APPROVED (오너 결정, v4)**

> **오너 지시 수정(owner-directed amendment)**. 합의(v3 APPROVE) 이후 오너의 제품 판단으로 추가된 결정이며, 기술 검토의 결과가 아니다.

- **Decision**: 2학기 시즌 배너(구 S1.5)를 **만들지 않는다.** 새 학년도 배너(2/15~3/15)도 P1~P3에서 만들지 않고 **P2 마법사 설계 시 재검토**한다. 기능 발견성은 **상설 UI + 릴리즈 노트 + `/docs`**가 담당한다.
- **Drivers**: ① **오너 판단** — _"학교마다 개학일이 너무 달라 배너는 불필요. 기능 노출만 잘 되면 됨."_ 실제로 한국 중·고교 2학기 개학은 8월 초부터 9월 초까지 분포하며, 단일 날짜 구간으로 "지금이 정리할 때"라고 말하면 **절반에게는 틀린 시점**이다. ② 배너는 **연 1~2회만 유효한데 판정 로직·dismiss 상태·설정 필드를 상시 보유**한다 — 유지 비용 대비 수명이 짧다. ③ 발견성의 실질은 **교사가 수업 관리 화면에 들어왔을 때 거기 있는 것**이고, 그건 kebab 메뉴와 보관 섹션이 이미 한다.
- **Alternatives**: (a) 배너 유지 + 노출 창을 넓게(8/1~9/15) — v3 안. 개학이 이른 학교에는 늦고 늦은 학교에는 이르다. **오너 기각.** (b) 개학일을 사용자에게 입력받아 개인화 — 온보딩에 질문이 하나 늘고, 그 값을 틀리게 넣으면 배너가 영영 안 뜬다. 배너 하나를 위해 설정 항목을 만드는 것은 비용이 역전된다. **기각.**
- **Why chosen**: 배너는 "때를 알려주는" 장치인데 **때가 학교마다 다르면 장치의 전제가 무너진다.** 반면 상설 진입점은 사용자가 이미 그 맥락에 들어왔을 때 작동하므로 개학일과 무관하다.
- **Consequences**: ① `academicCalendar`에 **시즌 판정 함수가 없다**(소비처 0). ② `Settings`에 `seasonBannerDismissedTerm`을 **만들지 않는다.** ③ **P1이 `src/App.tsx`를 건드리지 않는다** — 다중 세션 충돌 위험 감소. ④ 계획 전체에서 **날짜 의존이 사라져** §5.1 축소 게이트가 상대 기준(착수 후 5일차)으로 바뀌었다. ⑤ **사전 동기화 안내가 S1.3 다이얼로그 하나에만 남는다**(ADR-033 Consequences ③).
- **Follow-ups**: P2(S2.3)에서 마법사 시즌 안내가 필요하면 **날짜 구간부터 다시 설계**한다 — 이 ADR의 근거(개학일 분산)가 새 학년도 배너에도 동일하게 적용된다.

### ADR-036: 아카이브 파일의 Drive 동기화는 P4로 미룬다 — **APPROVED**

> v2에서 ADR-033의 각주로 강등돼 있던 결정을 **독립 ADR로 승격**했다(r2 NEW-7). **P2 출시 조건 1(S2.1b)의 근거가 이 결정이므로** 각주로 둘 수 없다.

- **Decision**: 아카이브 파일(`data/archives/{term}/`)은 **P1~P3 기간 로컬 전용**이다. Drive 동기화는 **P4(S4.1)**에서 도입한다. 그동안의 기기 간 이동 수단은 **수동 백업 파일**이다.
- **Drivers**: ① 아카이브는 **용량이 크고 불변**이라 라이브 데이터와 동기화 설계가 다르다 — 대용량 업로드·부분 실패·용량 초과 처리가 P2에 통째로 얹히면 파괴적 단계의 위험이 배가된다 ② 아카이브는 불변이라 **병합이 필요 없다** — 즉 P4로 미뤄도 설계가 더 어려워지지 않는다(오히려 라이브와 분리해 단순하게 만들 수 있다) ③ 수업반 보관 플래그(P1)는 일반 데이터라 **이미 자동 동기화**되므로, 사용자가 체감하는 기기 간 일관성은 P1 시점에 확보된다.
- **Alternatives**: (a) P2에 Drive 동기화 포함 — 새 PC에서 즉시 열람 가능하지만 파괴적 릴리즈의 표면을 크게 늘린다. **기각.** (b) 아카이브를 아예 동기화하지 않음(영구 로컬) — PC 교체가 곧 이력 소실이라 장기적으로 성립하지 않는다. **기각.**
- **Consequences**: **⚠️ 이 결정이 S2.1b를 P2 출시 조건으로 만든다.** 아카이브가 로컬 전용인데 **수동 백업조차 아카이브를 담지 못하면**(§6.1-⑯) 이동 수단이 0이 되고, PC 교체 시 몇 년치가 조용히 사라진다. 두 결정은 짝이다 — **ADR-036을 유지하려면 S2.1b가 반드시 완료돼야 하고, S2.1b가 불가능하다면 ADR-036을 뒤집어 Drive 동기화를 P2로 당겨야 한다.**
  또한 보관함 화면과 `/docs`에 **"이 PC에 보관된 학년도"**라는 제약을 명시해야 한다.
- **Follow-ups**: S4.1에서 Drive 동기화 도입. 아카이브는 불변이므로 **파일 단위 업/다운로드로 충분하고 병합 로직이 필요 없다.**

### ADR-035: `archived` 3필드는 `notMirrored`로 등재한다 (미결 4 종결) — **APPROVED**

- **Decision**: `ENTITY_FIELD_CONTRACT.teachingClass`에 `archived`/`archivedAt`/`archivedTerm`을 **`notMirrored`**로 등록한다.
- **Drivers**: ① `mirrored`면 **별도 레포 `ssampin-ai-bridge`**의 벤더링 계약과 `mirrorRoundtrip.test.ts`를 함께 고쳐야 한다 — 개학 D-14에 크로스 레포 의존을 얹는다 ② **v1이 우려한 "AI가 보관된 반에 쓸 수 있다"는 이제 무의미하다** — S1.4(F)가 `applyLiveSyncWrite.ts:702` 쓰기 가드에서 직접 거부하므로 브릿지가 `archived`를 알 필요가 없다.
- **Alternatives**: (a) `mirrored` — 쓰기 차단은 이미 본체가 한다. 크로스 레포 비용만 남는다. **기각.**
- **Consequences**: 브릿지 응답에 보관 여부가 안 실린다. 필요해지면 P4에서 승격 가능(비파괴적).

### 8.3 레벨 2 — 통합 테스트

1. **보관 후 저장 무결성**: `archiveClass` → 해당 항목 외 무변경, `attendance.json`/`curriculum-progress.json` **바이트 무변경**.
2. **`reorderClasses` 보존**: 보관 반 존재 상태 재정렬 → 배열 길이 유지 (⑩).
3. **그룹 격리** (신규): 형제 1개 보관 → 활성 형제의 명렬·좌석·학생 상태 수정 → **보관된 반 바이트 동일** (㉒).
4. **S1.2b 통합** (신규): 같은 이름 (보관, 활성) 쌍 → 진도 캘린더·위젯·알림 4경로가 전부 활성 반에 결합.
5. **동기화 회귀 0**: 기존 병합 테스트 전건 무변경 통과.
6. **term 스탬프 파일 생존**: 저장 → 재로드 → **파일 내용 단언**(merge 단위 테스트만으로 만족되지 않게).
7. **전환 fail-closed**: `archive:create` 실패 주입 → 라이브 mtime·해시 무변경.
8. **safety backup 선행**: 생성 실패 → 전환 미시작.
9. **아카이브 무결성**: 전환 후 해시 == 전환 전 해시.
10. **뷰어 읽기 전용**: 열람 전후 라이브 mtime 무변경.
11. **자동저장 봉쇄** (신규): 보관된 반에서 저장 함수를 강제 호출해도 파일 무변경 (S1.3 AC-5).

### 8.4 레벨 3 — E2E(실렌더) 체크리스트

> **환경**: 브라우저 개발 모드는 명렬이 영속되지 않는다. `npm run electron:dev:fresh`(`--user-data-dir=.dev-data`)로 **격리된 영속 프로필**을 쓴다.

> **vite 서버 2개 동시 실행 금지**(deadlock).

**P1**

- [ ] 같은 이름 (보관, 활성) 쌍에서 진도 위젯·진도 캘린더·관찰 알림이 **활성 반**에 결합 (S1.2b — 최우선)

- [ ] 수업반 3개 → 1개 보관 → 보관 섹션에 나타남 / 보관 해제 → **활성 목록 맨 아래**
- [ ] 보관된 반의 출결·진도·관찰 탭에 **데이터가 보이고 입력이 전부 비활성**

- [ ] 활성 반만 드래그 재정렬 → 재시작 후 **보관된 반이 그대로**
- [ ] `ToolRandom`·`ToolGrouping`에 **보관 전 저장한 선택이 계속 해석된다**(빈 명렬 아님)

- [ ] AI 브릿지로 보관된 반에 진도 생성 시도 → **사용자 언어 오류로 거부**, 조회는 정상
- [ ] **다중 선택 → "선택한 N개 보관"** → N개 모두 이동, 저장·업로드 각 1회(로그 확인)

- [ ] **형제 1개만 보관 시 확인 문구에 "다른 과목 N개는 계속 활성"**이 나온다
- [ ] 모바일 수업반 목록·진도 기록 모달에 보관된 반이 안 보이고, 기존 상세는 열린다
- [ ] 집계·이력 화면(출결 통계)에서 보관된 반의 과거 기록이 **계속 집계된다**
- [ ] **경쟁 업로드 테스트(㉑ 실측, 2주 시드 대체)**: A에서 보관 → **A의 업로드 트리거가 끝나기 전에 B에서 먼저 업로드** → 결과 기록. **동기화를 꺼둔 상태에서 보관해도 오류가 나지 않는지도 함께 확인**(S1.2 AC-8). DEFER·pull-merge-push가 기대대로 도는지 로그로 확인
- [ ] 라이트/다크 실렌더

**P2**

- [ ] 마법사 3단계 이탈 → 재진입 3단계, 데이터 변경 0
- [ ] 실행 → safety backup 경로 표시
- [ ] 전환 후 빈 상태에 "보관함 열기"
- [ ] "전환 취소" → 완전 복귀
- [ ] 관찰 첨부가 보관함에서 열린다
- [ ] 전환 안 한 다른 기기와 동기화 → **옛 데이터가 되살아나지 않는다**
- [ ] 구버전 기기 접속 상태 → 마법사가 차단되고 사유 표시

## 9. 사전 부검 (Pre-mortem) — 3 시나리오

### 시나리오 A — "출시 후 데이터가 사라졌다는 신고가 왔다"

**경로(가능성 순)**

1. **`reorderClasses` 유실(⑩).** 보관 섹션이 활성 반 id만 넘기고 현 구현이 배열을 통째 재구성하며 미매칭을 버린다 → 목록 순서를 한 번 바꾸는 순간 **보관해둔 수업반이 영구 소실.** 보관 기능의 신뢰가 첫날에 무너진다.
2. **그룹 형제 덮어쓰기(㉒).** 보관된 반의 과거 명렬이 활성 형제 편집으로 조용히 변조. 뒤늦게 "작년 명렬이 이상하다"로 발견된다.
3. **읽기 전용 미봉쇄.** 보관된 반 출결 탭을 열어보기만 했는데 자동저장 시퀀서가 돌아 **보관된 학기 출결이 오늘 날짜로 갱신**된다.
4. **S1.0 미커밋 수정 폐기.** P1 착수 시 워킹트리를 정리하다가 ADR-027 계열 **미출시 데이터 무결성 수정 8개 경로를 날린다** — 이미 고쳐둔 유실 버그가 되살아난다.
5. **P2 복사 실패를 못 잡음(⑪).** `data:write`가 실패를 삼켜 복사 실패를 성공으로 알고 라이브를 리셋.
6. **PC 교체 시 아카이브 증발(⑯).** 백업에 아카이브가 애초에 없다. 경고도 없다.
7. **루트 epoch가 벗겨짐(㉖).** _(v1 설계였다면)_ 평범한 저장 1회에 epoch가 날아가고 "부재 = 현행 병합" 규칙이 조용한 부활을 부른다.

**예방**

- (1) → **S1.2를 P1의 첫 코드 변경으로.** UI보다 먼저 고치고 회귀 테스트를 먼저 쓴다. 유즈케이스 경유로 락도 회복.
- (2) → `shouldPropagateToSibling` 술어 + 그룹 격리 테스트(§8.3-3).
- (3) → 읽기 전용 3중 방어(입력 비활성 + 시퀀서 미생성 + 강제 호출 무저장).
- (4) → **S1.0을 스토리로 명문화**: 폐기 금지 · 명시 path 커밋 · v2.2.14 선출시 포함.
- (5) → `archive:*` `{ok, error}` + 성공 타입에서만 다음 단계 호출 가능한 시그니처.
- (6) → **S2.1b를 P2 출시 조건으로.**
- (7) → **레코드 스탬프 채택**(ADR-034) + 봉투 메타테스트.
- (전방위) → safety backup 선행 + 경로 표시. **Drive 웹 "버전 관리" 리비전(30일)** 복구 절차 준비(2026-07-13 유실 신고에서 실제로 통한 경로). **startup 스냅샷**(`{userData}/data/backups/startup/`, 14일)이 `student-records`·`observations`를 이미 보관 중임을 복구 안내에 포함.

**탐지**: P1 출시 후 2주간 "수업반이 사라졌다"류 피드백 별도 라벨. 1건이라도 오면 롤백 판단.

## 12.2 엣지 케이스 (우선순위)

1. 같은 이름의 교체 반 → `findMatchingClass`가 보관된 반을 고름 (S1.2b)
2. 그룹 소유자 보관 + 형제 활성 → 과거 명렬 변조 (S1.2)
3. 보관된 반 탭 열람만으로 자동저장이 돎 (S1.3)
4. 저장된 도구 선택(`"tc:<id>"`)이 보관 후 빈 명렬로 해석 (S1.4-A)
5. 모든 반이 보관됨 → 빈 화면이 죽은 화면이 되면 안 됨
6. 리셋이 5바이트 미만 파일을 씀 → 조용히 되살아남 (㉓)
7. 마법사 중단 → 반쯤 리셋된 상태 감지·이어하기
8. 모바일에 아카이브 폴더 없음 → 격리가 곧 삭제 (12-B 13)
9. 그룹 출결 소유자 반을 보관함에서 삭제 → 형제가 출결 상실 (㉔)
10. `conflictPolicy: 'ask'` 사용자에게 보관 직후 충돌 다이얼로그가 뜰 수 있음(기본은 `'latest'`) — 문구 확인 필요
