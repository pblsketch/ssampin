- 작성일: 2026-08-24
- 관련 결정: [ADR-072](../../../DECISIONS.md) · 실측: [`docs/03-analysis/record-draft-solar-quality.analysis.md`](../../03-analysis/record-draft-solar-quality.analysis.md)

> ⚠️ **이 저장소는 PUBLIC 이다.** 생기부 프롬프트 원문·측정 하네스를 이 계획서나 저장소 안에

## 1. 배경 / 문제

생기부 초안을 쓸 수 있는 경로는 지금 **AI 브릿지(MCP)뿐**이다. 외부 AI 앱 설치 + MCP 설정 +
고위험 토글이 필요해 대부분의 교사에게는 사실상 닫혀 있다. 쌤핀 AI(인앱)는 `ALLOWED_GRADES=[1]`
과 생기부 도구 **의도적 미등록**(`assistToolRegistry.ts:26`)으로 막혀 있다.

오너의 요구는 두 겹이다.

1. **근거 3종이 유기적으로 결합**해야 한다 — 교사 관찰 / 학생 과제물과 교사 평가 /
   **학생 자기평가서**. 확인 결과 세 번째가 통째로 없다(엔티티 검색 0건).
2. **평소에 꾸준히 누적**되어야 한다. 학기말 몰아쓰기를 위한 도구가 아니다.

그리고 실측이 세 번째 문제를 드러냈다 — **프롬프트로는 규정을 못 지킨다.**

- 기재 금지 항목(수상·어학 점수·학원명·모의고사 등급·부모 직업)을 시스템 프롬프트에 전부
  열거하고 사용자 턴 끝에 재강조해도 **2/2 → 보강 후에도 2/2 실패.** 세특 본문에 그대로
  옮겨 적는다. NEIS 에 들어가면 감사 대상 문장이다.
- 교사 커스텀 지시 두 줄("반드시 채워라")이 안전 규칙을 이겨 **한도의 4배(7,156B)** 를
  창작으로 채웠다.
- 반면 근거만 두꺼우면 문장력은 쓸 만하다(0.8~1.7초). **병목은 모델이 아니라 근거의 구조와 위생이다.**

## 2. 목표

1. 근거 3종을 **같은 언어(슬롯 축)** 로 정렬해 근거 창고(`RecordEvidence`)에 모은다.
2. 슬롯은 **쌓는 순간**에 붙는다. 학기말 정리 작업을 만들지 않는다.
3. 기재 금지 항목이 **AI 에 도달하지 않게** 한다(출력 검사가 아니라 입력 차단).
4. 생기부 초안을 **쌤핀 AI(인앱)** 로도 쓸 수 있게 한다.
5. 프롬프트는 **2층**(쌤핀 기본 + 교사 커스텀)이고, 기본 프롬프트는 저장소 밖에 둔다.

## 3. 원칙

- **P1 막는 자리는 입력이다.** 프롬프트·출력 검사에 안전을 의존하지 않는다(실측 근거).
- **P2 교사 부담을 늘리지 않는다.** 늘어나는 동작은 칩 한 번 탭까지다. 기록이 안 쌓이면
  이 계획 전체가 무의미하다.
- **P3 기존 구조를 재사용한다.** 새 엔티티·새 계약을 최소화한다 — 태그 축·학생 웹앱·
  브릿지 고위험 어휘 사전·`resolveAreaLimit` 이 이미 있다.
- **P4 오탐이 기능을 죽이지 않게 한다.** 자동 판정은 교사가 켜고 끌 수 있어야 한다
  (`screenAssistInput.ts` 의 교훈 — 차단은 안 쓰이는 안전장치를 만든다).
- **P5 법정기록 보수성.** `requiresTeacherReview` 정신 불변. 자동 확정 경로를 만들지 않는다.

## 4. 범위

### Phase 0 — 시스템 프롬프트를 저장소 밖으로 (독립·소)

**왜 먼저인가**: 지금 이미 노출돼 있다. 생기부와 무관하게 챗봇·쌤핀 AI 프롬프트가
공개 저장소에서 읽힌다. 그리고 Phase 4 의 2층 구조가 이 자리를 전제로 한다.

- `supabase/functions/_shared/assistRequest.ts` 의 `buildAssistSystemPrompt` 본문을
  서버 환경변수 또는 DB 로 옮기고, 코드에는 **불러오는 부분만** 남긴다.
- `chatLlm.ts` 쪽 챗봇 프롬프트도 같은 처리를 검토한다(범위 확인 필요).
- 저장소 비공개 전환은 하지 않는다(과거 `repo-privatization` 취소 이력).

**수용 기준**: AC0-1 저장소 어디에도 프롬프트 본문이 없다. AC0-2 프롬프트 미설정 시
함수가 조용히 빈 프롬프트로 돌지 않고 명시적으로 실패한다.

### Phase 1 — 금지 항목을 AI 에 안 보낸다 (독립, 브릿지도 즉시 이득)

- 근거 창고(`RecordEvidence`)에 **`excludedFromAi`(선택 필드)** 를 더한다.
- 근거가 창고에 들어올 때(직접 입력·끌어오기 모두) 금지 항목을 자동 탐지해 표시한다.
  사전은 브릿지 `packages/core/src/grounding.ts` 의 고위험 어휘를 본체로 미러한다
  (브릿지를 import 하지 않는다 — `RecordDraft.ts` 미러 방식 선례).
- **교사가 켜고 끌 수 있다**(P4). 화면에는 "AI 에 보내지 않음" 배지로 보인다.
- 브릿지 `get_record_evidence` 와 (Phase 4 의) 인앱 경로 **양쪽에서 제외**한다.
- **바이트 한도를 코드에서 자른다** — 저장 시 `resolveAreaLimit` 초과분 거부(기존 함수).
- **곁들여 고칠 것**: `record-evidence.json` 이 동기화 대상 34개에 없다
  (`src/usecases/sync/syncRegistry.ts`). 보관함에는 있다(`archiveScope.ts:35`). 창고가
  이 계획의 무게중심이 되므로 **지금 넣는다.**
  ⚠️ 동기화 레지스트리는 다른 세션이 만지는 중일 수 있다 — 착수 전 `git status` 확인.

**수용 기준**: AC1-1 수상·어학·학원명·모의고사·부모 직업이 포함된 근거가 자동으로 제외
표시된다. AC1-2 제외된 근거는 `get_record_evidence` 응답에 없다. AC1-3 교사가 제외를
해제하면 다시 나간다. AC1-4 한도 초과 초안은 저장 시 거부된다. AC1-5 근거 자료가
기기 간에 동기화된다.

### Phase 2 — 관찰 슬롯 (쌓는 순간에 붙는다)

**설계서: [observation-slots.design.md](../../02-design/features/observation-slots.design.md)** — 화면·어휘·연동 상세.

**★초기 판단 정정**: 이 계획서 v1.0 은 "태그 어휘 확장 — 새 필드·저장 구조 변경 없음"이라고
적었다. **교과 관찰만 놓고 보면 맞지만, 담임 누가기록까지 포함하면서 성립하지 않는다.**
`StudentRecord.tags` 는 이미 "세부 분류"로 쓰이고 있어(`InlineRecordEditor.tsx:40-41`) 슬롯을
섞으면 한 배열에 두 의미가 뒤섞인다. 또 태그로 가면 통계 표 열이 14개가 되어 넘친다.
→ **두 엔티티에 선택 필드 `slots?` 를 새로 둔다**(`category?`·`term?` 선례와 같은 additive optional).

**범위(오너 확정 2026-08-25)**

- **슬롯 어휘 두 벌** — 교과(세특): 질문 / 시도 / 시행착오 / 산출물 / 주고받음 / 연결 ·
  담임(행특): 학습 태도 / 인성·관계 / 학급 역할 / 변화 / 아쉬운 점 / 진로.
  ★`변화` 는 "변화 서사를 써도 되는가"의 근거 표식이기도 하다(실측 D 사례를 데이터로 받침).
- **입력은 데스크톱 + 모바일 둘 다.** 한쪽만 고치면 모바일 기록에 슬롯이 안 붙어
  "꾸준히 누적"이 반쪽이 된다.
- **화면 배치는 (나)안** — 본문 아래 "어떤 장면인가요?" 행. **클릭 1번, 접지 않는다.**
- **알림은 문구만** 슬롯 인지형으로. **누구를 부를지는 안 바꾼다** — 어제 기록한 학생을
  슬롯이 비었다고 다시 부르면 알림을 끄게 된다.
- **통계는 별도 구역 신설.** 기존 태그 표의 열 수는 그대로 둔다. **검색 필터는 이번 범위 밖.**
- **근거 창고**에 슬롯을 실어 보낸다(`RecordEvidence.slots?` + `evidenceImport`).
- **브릿지** `get_observations` 가 슬롯을 탈식별해 노출한다.

⚠️ **화면 배치는 실렌더 확인 후 조정한다**(단독 확정 금지). 디자인 에이전트가 2회 연속
빈 응답이라 프로젝트 디자인 문서(`design-system.md`·`.impeccable.md`)를 근거로 후보 3안을
만들어 오너가 (나)를 골랐다. 실제 화면을 보고 다시 볼 것.

⚠️ **동기화에서 구 데이터의 슬롯 부재를 빈 배열로 덮지 말 것**(부재 ≠ 빈 배열).

**수용 기준**: 설계서 §8 의 AC-1~AC-10 을 따른다.

### Phase 3 — 학생 자기평가서 (세 번째 근거)

- 기존 학생용 웹앱(`student.html` → `src/student/`)과 과제의 `shareUrl`/`shortUrl` 방식을
  재사용한다. 참여 링크·본인 확인·PIN·제출 폼이 이미 있다.
- 문항 양식은 **슬롯 축과 같은 언어**로 만든다 — 어떤 의문이 있었나 / 무엇을 시도했나 /
  무엇이 잘 안 됐나 / 무엇이 남았나.
- 제출분은 `RecordEvidence` 에 `sourceType: 'selfAssessment'` 로 자동 적재한다
  (`EvidenceSourceType` 에 값 추가 — `RecordEvidence.ts:19-25`).
- Phase 1 의 금지 항목 검사를 **똑같이 통과시킨다**(학생이 수상·학원을 적을 수 있다).

**수용 기준**: AC3-1 교사가 링크를 열고 학생이 제출하면 그 학생 창고에 꽂힌다.
AC3-2 슬롯이 붙어 들어온다. AC3-3 금지 항목이 자동 제외 표시된다.

### Phase 4 — 쌤핀 AI 로 생기부 초안 쓰기

- **2층 프롬프트**: 1층=쌤핀 기본(Phase 0 의 서버 보관분), 2층=교사 커스텀.
- 서버 요청 계약에 커스텀 프롬프트용 키를 연다 — `assistRequest.ts` 의
  `ALLOWED_REQUEST_KEYS` 는 5개 고정이고 **모르는 키는 400** 이라 조용히 안 통한다.
- **교사 커스텀은 자유 입력 + 저장 시점 차단**(ADR-072 결정 4). 차단 대상은 실측에서
  실제로 사고를 낸 두 종류다 — **분량 강제**("반드시 채워라"), **근거 무시**("근거 없어도 써라").
  여기에 **학생 실명 유입 차단**을 더한다(앱의 이름 자동 삭제 장치 재사용).
- **근거 인용 지시는 사용자 턴 끝에 배치한다** — 실측에서 이 배치가 얇은 근거 창작을
  0/2 → 2/2 로 바꿨다. 시스템 프롬프트에만 적으면 묻힌다.
- 생기부 도구를 등급제 안에서 연다.

⚠️ **이는 ADR-061 결정 7("영구 경계")을 뒤집는다.**
`assistToolRegistry.contract.test.ts` · `assistServerRequest.test.ts` 두 계약 테스트가
빨간불이 된다. **끄지 말고**, 무엇이 새로 열리는지 드러낸 뒤 갱신한다(그게 이 테스트의 목적).
**ADR-061 결정 7을 대체하는 별도 ADR 을 그때 남긴다.**

⚠️ 무료 티어는 보낸 내용이 학습에 활용되고 옵트아웃이 없다(업스테이지 약관 제22조).
**이 사실을 쉬운 한국어로 교사에게 고지**하는 것은 유지한다.

**수용 기준**: AC4-1 인앱에서 영역별 초안이 생성돼 `RecordDraft` 로 저장된다.
AC4-2 모든 초안이 `requiresTeacherReview=true` 다. AC4-3 커스텀 칸에 분량 강제·근거 무시
지시를 넣으면 저장이 거부된다. AC4-4 커스텀 칸의 학생 실명이 저장 전에 제거된다.
AC4-5 실측 5사례 재실행에서 C·E 가 통과로 바뀐다.

## 5. 릴리즈 전략 — 통째로 미루지 않는다

**이것은 한 덩어리 기능이 아니다.** 단계별 위험도가 달라서 같은 배에 태우면 안 되는 것이
섞여 있다. Phase 0·1 을 Phase 4 때문에 붙잡아 두면 손해만 난다 — 그동안 프롬프트는 계속
공개돼 있고, 브릿지를 쓰는 교사는 계속 규정 위반 문장을 받는다.

| 단계            | 위험 | 다음 릴리즈 | 근거                                                              |
| --------------- | ---- | ----------- | ----------------------------------------------------------------- |
| 0 프롬프트 이전 | 없음 | ✅          | 사용자에게 보이는 변화 0. 지금 노출을 줄이는 일                   |
| 1 입력 차단     | 낮음 | ✅          | AI 에 **덜** 보내는 변경. 브릿지 사용자가 즉시 안전해짐           |
| 2 슬롯          | 중   | △           | 계약 변경 없음. 입력 화면이 바뀌어 디자인 협업 + 실기기 확인 필요 |
| 3 자기평가서    | 중상 | ❌          | 미성년자에게서 데이터를 새로 걷는다 — 방침·동의 문구 검토         |
| 4 쌤핀 AI 개방  | 높음 | ❌          | 개인정보 경계 해제. 검토 부담이 실질적으로 여기 몰려 있다         |

### 브랜치를 만들지 않는다

프로젝트 규칙대로 **main 단일 워킹트리**에서 순차 진행한다(여러 세션이 도는 환경에서
장기 브랜치는 충돌을 만든다). 대신 **실험실 기능 탭**(ADR-070)을 쓴다 — 코드는 main 에
들어가되 기본 꺼짐이고, 켜야만 진입점이 보인다. v2.4.4 에서 쌤핀 AI·온라인 교무실·
쿨메신저를 정확히 이 상황 때문에 그렇게 내보냈다.

### Phase 4 는 이중 잠금

실험실 토글 하나로는 부족하다. **기존 `allowRecordWrite` 패턴을 그대로 재사용한다** —
브릿지의 생기부 쓰기가 이미 "별도 고위험 토글 + 처음 켤 때 인라인 고지 확인"이다
(`Settings/aiBridge/AiBridgeCard.tsx:328-334`).

→ **실험실에서 켬 + 생기부 AI 를 따로 켬 + 고지 확인**의 3단이어야 동작한다.
무료 티어라 보낸 내용이 학습에 활용된다는 사실을 그 자리에서 쉬운 한국어로 알린다.

### "검토"의 실체 — 막연히 미루지 않기 위해

Phase 4 착수 전 확인할 것은 셋뿐이다.

1. **개인정보 처리방침** — 학생 서술이 업스테이지로 나간다. **재위탁 대상**에 미국
   사업자가 있는지 방침 표를 직접 열어 확인한다(법인 소재지로 판단하지 않는다).
2. **ADR-061 뒤집기** — 계약 테스트 2곳 갱신 + 대체 ADR. 기계적이라 오래 걸리지 않는다.
3. **실측 재확인** — 하네스를 다시 돌려 C·E 가 통과로 바뀌는지 본다.
   **이것을 릴리즈 게이트로 삼는다** — "검토했다"가 말이 아니라 숫자가 된다.

Phase 3 의 검토는 종류가 다르다 — 학생에게서 걷는 것이라 **에듀집(학운위) 필수기준**과
겹치는지 확인이 필요하다.

### 순서

- **다음 릴리즈**: Phase 0 + 1
- **그다음 릴리즈**: Phase 2 (디자인 협업 후)
- **실험실 뒤에서**: Phase 3 → 4. 위 3종 검토가 끝나면 실험실에서 정식 기능으로 승격

## 6. 검증

각 Phase 마다 프로젝트 게이트 4종을 통과한다.

```
npx tsc --noEmit        # 0 에러
npm run lint            # 통과
npm run test            # 통과
npm run regression-check # 통과
```

추가로 **Phase 4 종료 시 실측 하네스를 재실행**해 C·E 사례가 통과로 바뀌는지 확인한다
(하네스는 저장소 밖. 절차는 분석 문서 §6).

## 7. 이 계획에 넣지 않은 것

- **과제물 본문 텍스트** — 드라이브에만 있고 앱으로 안 들어온다. 기존 한계 그대로 둔다.
- **성취기준 데이터** — 진도에 `unit`·`lesson` 만 있다. 프롬프트가 요구하지만 별도 트랙.
- **`RecordDraft` 의 학년도·학기 칸 부재** — 학년이 바뀌면 덮어쓴다. 별도 트랙
  (학년도 전환 작업과 함께 보는 것이 맞다).
- **AI 브릿지 경로 제거** — 유지한다. Phase 4 는 대체가 아니라 추가다.
