## 3. 설계 원칙

> **클라우드는 "그게 누구인지" 몰라도 되게 한다.**

1. **열쇠를 서버에 두지 않는다.** `admin_key` 원본은 교사 PC와 공유 링크(URL 조각 `#`)에만.
   서버엔 대조용 해시만 둔다. URL 조각은 브라우저가 서버로 보내지 않는다 —
   상담 예약이 이미 쓰는 방식(`BookingPageContent.tsx:66`)이고, 설계는 옳았는데 열쇠를 같이 둬서 무력했다.
2. **이름은 링크 키로 암호화**해서 저장한다. 화면에 이름을 보여줘야 하는 곳(서명 명단 고르기)은
   링크를 가진 사람만 풀 수 있으면 충분하다.
3. **식별은 결정적 해시로.** 암호문은 매번 달라져 중복검사·`UNIQUE` 에 못 쓴다.
   `member_ref = HMAC(링크키, 정규화된 이름+학번)` 형태로 만들면 서버는 원본을 모른 채 같은 사람인지 판단한다.
   _(sigv2 엔 이미 `member_ref` 컬럼이 있다 — 현재 값이 무엇인지 확인 후 재사용 검토.)_
4. **공개 읽기 정책 금지.** `USING (TRUE)` 와 버킷 전체 공개는 쓰지 않는다.
   공개가 필요한 조회는 **RPC(SECURITY DEFINER)로 반환 열을 고정**한다.

### 감수하는 대가 (사용자 확인 완료)

- 교사가 링크를 잃으면 그 자료는 **아무도 못 연다.** 완화책: 쌤핀 앱이 링크 키를 로컬에 보관하고
  학년도 마무리 시 함께 보관·경고한다.
- 서버가 이름을 모르므로 정렬·검색 일부를 클라이언트로 옮겨야 한다.
- 기존 데이터(186·256·129행 등) 이관 작업이 따로 필요하다.

## 4. 단계

### P0 — 노출 차단 (즉시, 코드 변경 최소)

목표: **D1·D2·D3 를 먼저 닫는다.** 설계를 기다리지 않는다.

#### ✅ P0-1 완료 (2026-08-14, `f41969a5`, 마이그레이션 044)

`USING (TRUE)` 정책을 건드리는 대신 **컬럼 단위 GRANT** 로 민감 열만 가렸다.
RLS 는 행 단위라 열을 못 가리지만 GRANT 는 가린다 — 훨씬 작은 변경으로 D2 를 닫았다.

- [x] `consultation_schedules.admin_key` · `surveys.admin_key` · `surveys.pin_hashes`
      익명 SELECT 권한 회수 (테이블 권한 회수 후 민감 컬럼 제외하고 재부여,
      컬럼 목록은 `information_schema` 에서 도출해 향후 컬럼 추가에도 자동 대응)
- [x] `verify_survey_pin` RPC 신설 — pin_hashes 를 통째로 내려보내던 것을 서버 비교로 전환
- [x] 죽은 코드 `ConsultationSupabaseClient.getSchedule()` 삭제 (select 에 admin_key 포함돼 있었음)

**적용 후 실측**: `admin_key`·`pin_hashes` 요청 → HTTP 401 / 학부모·학생 화면이 쓰는 열 → HTTP 200 /
`verify_survey_pin` → 정상 / 배포 번들에 RPC 포함 확인 / `/check`·`/booking` 200.

#### 남은 P0

#### ✅ P0-2 완료 (2026-08-14, `a80de578`, 마이그레이션 045)

- [x] `sigv2-signatures` 버킷 익명 목록 조회 차단 (D3) — 정책 `sigv2_signatures_public_read` 삭제

035 의 주석은 이 정책을 "객체 직접 GET 허용, 버킷 LIST 차단"이라고 설명했지만
**실제로는 정반대였다.** `storage.objects` 에 SELECT 를 여는 것이 곧 LIST 를 여는 것이고,
직접 GET 은 이 정책과 무관하다(버킷이 `public = TRUE` 라 공개 경로는 RLS 를 안 탄다).

**만료되는 signed URL 로 바꾸지 않은 이유**: 서명 이미지는 교사의 Google Sheets 에
`=IMAGE(url)` 수식으로 들어간다. 구글 서버가 인증 없이 URL 을 가져가므로 signed URL 로
바꾸면 이미 배포된 시트가 깨진다. 이 단계의 정답은 "공개 GET 유지 + LIST 차단".

**적용 전후 실측(같은 객체 경로)**: 변경 전 LIST 가능·GET 200 → 변경 후 **LIST 차단·GET 200**.

한계: 공개 GET 은 여전히 URL 을 아는 사람은 볼 수 있다(obscurity). 근본 해결은 P2.
`signature-previews` 버킷에 같은 결함이 남아 있으나 객체 0건이라 제외했다.

#### ⚠️ P0-3 — 같은 날 처리 불가. 데스크톱 앱 배포가 선행되어야 한다

- [ ] `consultation_bookings`(256행) · `survey_responses`(129행) 전 행 익명 열람 차단 (D1)

**막힌 이유 (2026-08-14 확인)**: 이 두 테이블을 읽는 주체가 학생·학부모 화면만이 아니다.
**교사 데스크톱 앱이 같은 anon 키로 직접 읽는다.**

| 테이블                  | 데스크톱(교사)                                               | 랜딩(학생·학부모)  | 모바일 |
| ----------------------- | ------------------------------------------------------------ | ------------------ | ------ |
| `consultation_bookings` | 목록·단건·삭제 (`ConsultationSupabaseClient.ts:241,302,319`) | 중복 예약 확인     | 미사용 |
| `survey_responses`      | 목록·중복확인·삽입 (`SurveySupabaseClient.ts:160,191,220`)   | 중복확인·응답 제출 | 미사용 |

랜딩은 push 하면 즉시 배포되지만 **데스크톱은 설치형이라 선생님이 업데이트해야 반영된다.**
지금 테이블 SELECT 를 회수하면 **아직 업데이트하지 않은 모든 교사의 상담 예약 상세·
설문 응답 현황 화면이 즉시 깨진다.** P0-1·P0-2 처럼 당일 처리할 수 없는 이유다.

**필요한 순서 (3단계, 배포 주기에 걸침)**

1. RPC 신설 — 순수 추가라 무해
   - 익명용: `has_consultation_booking(schedule_id, student_number) → boolean`,
     `has_survey_response(survey_id, student_number) → boolean`
   - 교사용: `admin_key` 를 인자로 받아 해당 일정/설문 것만 반환하는 조회·삭제 RPC
2. 랜딩 + 데스크톱을 RPC 경유로 전환 → **데스크톱 릴리즈 포함해 배포**
3. 충분히 업데이트된 뒤 테이블 SELECT 권한 회수 (되돌리기 쉬운 마지막 단계)

**그때까지 남는 노출**: `consultation_bookings` 는 P0-1 로 `admin_key` 가 막혀 암호문을
풀 수 없으므로 학번·시간 메타데이터 수준. **`survey_responses` 의 응답 내용은 평문이라
이쪽이 더 급하다** — 설문 기능만 먼저 1~3단계를 밟는 것도 방법이다.

- [ ] 회귀 확인: 교사 현황 화면(상담 예약 상세·설문 응답 현황)을 실제로 열어볼 것
      — P0-1 은 익명 조회만 검증했고 교사 앱 실화면은 아직 확인하지 않았다

**위험**: 정책을 조이면 학부모·학생 화면이 조용히 깨질 수 있다. 반드시 실화면 확인 후 배포.
