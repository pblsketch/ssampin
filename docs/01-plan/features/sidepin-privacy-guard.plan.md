### 5.3 ⚠️ 알고 받아들이는 결함 — 듀얼 모니터

이 API는 **세션 전체 상태**다. → **프로젝터에서 PPT를 띄우면 노트북 옆핀도 함께 사라진다.**
이 저장소는 v2.4.6(ADR-075)에서 모니터별 옆핀 배치를 이미 출시했으므로 이 조합은 실재한다.

**설계가 받아들이는 알려진 결함**이다. ADR에 그대로 적는다.

**판정선(숫자로 못박는다)** — S1-1 관측에서:

> 듀얼 모니터 환경에서 **PPT 1회 발표당 노트북 옆핀이 가려진 시간이 5분을 넘으면** 후속에서 B(모니터별)로 좁힌다.
> 5분 이하면 §5.2의 A 채택을 유지한다.

(v2는 "심하면 좁힌다"라고만 써서 **어떤 결과가 나와도 그냥 진행**하게 돼 있었다.)

### 5.4 S1-1 — 감지 관측 (아무 동작도 안 바꾼다)

- 새 파일 `electron/platform/win32Presentation.ts`
- 한 번에 **세 가지**를 찍는다(값이 바뀔 때만):
  1. `SHQueryUserNotificationState` — 후보 A
  2. `GetForegroundWindow`+`GetWindowRect`+그 창의 모니터 — 후보 B가 정말 과잉 반응하는지
  3. `screen.getAllDisplays().length` + 옆핀이 올라간 모니터 — §5.3 판정선 측정
- **한 번의 실기기 세션으로 §5.2 선택과 §5.3 심각도를 동시에 확정한다.**

⚠️ **실패 처리는 이 저장소 관례와 다르다.** `win32Desktop.ts:447` 과
`win32SendKeys.ts:14-17`("조용한 실패 금지")은 **예외를 던진다.** 이 모듈은 `null`(모름)을 돌려준다.
**이유를 파일 머리말에 적는다**: 저 둘은 "사용자가 시킨 일"이지만 이건 **배경에서 도는 관측**이라
실패할 때마다 알려도 할 수 있는 일이 없다. 모르면 **숨기지 않는 쪽**(현상 유지)이 맞다.

**영구 실패 처리(v2에 없던 것)**: koffi 로드나 DLL 조회가 **연속 3회** 실패하면 **폴링을 영구 중단**하고
한 번만 로그를 남긴다. 3초마다 영원히 재시도하면 비Windows·구형 환경에서 로그가 폭주한다.

**절전 중에는 폴링을 멈춘다** — `powerMonitor` `suspend` 에서 타이머를 끄고 `resume` 에서 켠다.
안 그러면 3초 타이머가 절전 복귀를 유발하거나 배터리를 먹는다.

### 5.5 S1-2 — 보호 등급 신설 (`soft-protect`) + **dispose 억제**

지금 `force-protect` 는 **최대 반응**이다(`:890-911`, 확인함): `editorActivity: 'idle'` 로 밀고(`:902`)
`hide-all` 로 **패널을 파괴하고 손잡이까지 숨긴다.** 잠금·절전은 선생님이 확실히 자리에 없으니 맞다.
전체화면은 **추측으로 판단**하므로 여기 물리면 오탐 1회가 쓰던 메모를 날린다(P5).

#### 🚨 실기기에서 잡힌 설계 오류 — `collapse-panel` 을 쓰면 안 된다 (2026-09-01)

**v4까지 이 표는 `collapse-panel` 을 쓰라고 했다. 틀렸다.**
오너가 PPT 슬라이드쇼로 확인한 결과 **손잡이가 화면에 그대로 남았다.**

원인: `collapse-panel` 은 이름과 달리 **손잡이를 보이게 하는 명령**이다
(`sidePinWindow.ts:216-224` — `await rail.showInactive()` 후 `panel.hide()`).
그것이 원래 용도이기 때문이다(패널을 접어 손잡이로 되돌리는 것).
v4는 "손잡이가 남는다(D2)"를 **장점으로** 적었지만, 1단계의 목적은
**"전체화면일 때 옆핀을 숨기기"** 다. 손잡이가 남으면 목적 자체가 달성되지 않는다.

D2(되돌아올 수 있는가)를 자동 보호에 잘못 적용한 것이 근본 원인이다.
**자동으로 걸린 보호는 자동으로 풀린다** — 발표가 끝나면 `protect-released` 가
`ensure-rail` 을 보내 손잡이를 되돌린다(`sidePinWindow.ts:128-140`, 계약 테스트로 확인).
D2가 진짜로 필요한 곳은 **사람이 직접 누르는** S1-4(지금 가리기)이고, 거기서는
`close-requested` 가 손잡이를 남기므로 이미 만족한다.

**세 명령의 자리**:

| 명령                     | 손잡이     | 패널     | 쓰던 글       |
| ------------------------ | ---------- | -------- | ------------- |
| `collapse-panel`         | **보인다** | 숨김     | 살아 있다     |
| `hide-all`               | 숨김       | **파괴** | **날아간다**  |
| **`conceal-all`** (신설) | **숨김**   | 숨김     | **살아 있다** |

가운데가 비어 있어서 새로 만들었다. `CLEAR_PANEL` 도 보내지 않는다 — 창이 이미
화면에서 사라졌고 내용은 화면 쪽이 `locked` 로 스스로 비우므로, 여기서 비우면
발표가 끝났을 때 되살릴 것이 없다.

★ **교훈**: 명령 이름을 믿지 말고 **그 명령이 창에 실제로 무슨 일을 하는지 읽을 것.**
P4가 "처음과 끝을 모두 읽는다"였는데, 이번엔 `onHostResult`(끝)는 읽고
**호스트 구현(실제 동작)은 안 읽었다.** 도메인 테스트로는 절대 안 잡힌다 —
창을 다루는 건 `electron/sidePinWindow.ts` 층이기 때문이다.
재발 방지 테스트를 `sidePinWindow.contract.test.ts` 에 넣었다.

#### (나) 🚨 dispose 억제 — v2가 놓쳐 계획을 무너뜨린 자리

`collapse-panel` 이 **끝난 뒤** `onHostResult` 가 이렇게 한다(`:718-741`, 확인함):

```
const canReopen = isSidePinResponsive(state) && ...     // 보호 중이면 false
const transition = canReopen
  ? scheduleOf('reveal', ...)
  : scheduleOf('dispose-panel', revision, ctx.nowMs, SIDE_PIN_DISPOSE_DELAY_MS);   // ← 10초
```

`isSidePinResponsive` 는 `protectedReason !== null` 이면 false 다(`SidePinRuntimeState.ts:196-198`).
`soft-protect` 는 `protectedReason` 을 **설정하는 것이 핵심**이므로 dispose 가 예약된다.

#### ⚠️ 정정 — 위험한 자리는 "예약"이 아니라 "해제 직후"다 (v3 재확인)

예약 자체는 실제로 터지지 않는다. `onTimerFired`(`:488-491`)가 이렇게 막는다:

```
// 꺼졌거나 보호 중이면 예약만 조용히 버린다. 창은 절대 건드리지 않는다.
if (!isSidePinResponsive(state)) {
  return { next: bump(state, { pendingTransition: null }), commands: [] };
}
```

즉 **보호 중에는 10초 타이머가 터져도 폐기된다.** 패널은 안 파괴된다.

**진짜 위험은 순서다.** `protect-released`(`:913-928`)는 `protectedReason` 을 null 로 되돌리지만
**`pendingTransition` 은 건드리지 않는다**(`pendingHostOperations` 의 `hide-all` 만 지운다).
→ PPT를 끄고 **10초 안에** 예약이 터지면, 그때는 `isSidePinResponsive` 가 이미 true 라
**dispose 가 그대로 실행되어 패널이 파괴된다.** 쓰던 글이 그 순간 날아간다.

**고치는 법 (셋 다 한다)**:

1. `onHostResult` 의 `collapse-panel` 에서 **보호 이유가 soft 등급이면 dispose를 예약하지 않는다.**
   (예약을 애초에 안 만드는 쪽이 가장 단순하다)
2. **`protect-released` 가 예약된 `dispose-panel` 을 지우고 `cancel-schedule` 을 보낸다.**
   ← **이것이 실제 결함을 막는 항목이다.** 1번만으로는 다른 경로로 걸린 예약이 남을 수 있다.
3. **안전망 불변식**: `dispose-panel` 이 완료되면 `editorActivity` 를 **무조건 `'idle'` 로** 되돌린다.
   패널이 없는데 "쓰는 중"이 남는 고아 상태를 구조적으로 없앤다(경로가 무엇이든).

★ 따라서 v2의 **"화면 쪽 수정 0줄"은 유지되지만 "`onHostResult` 는 안 바뀐다"는 삭제한다.**

### 5.6 S1-2 (나) — soft/force 우선순위 (트래커 수정)

★ v2는 "`sidePinProtection.ts` 는 한 줄도 안 바뀐다"고 했다. **틀렸다.**

```ts
release(reason) {                                    // :41-50 (확인함)
  if (!reasons.delete(reason)) return { kind: 'none' };
  const [remaining] = reasons;                       // ← Set 삽입 순서로 아무거나
  if (remaining !== undefined) return { kind: 'protect', reason: remaining };
```

**구체적 실패**: PPT 발표 중(`fullscreen` 먼저) → 절전(`suspend`·`lock` 추가) → 깨어남 →
**이 파일 머리말이 경고한 대로 `resume` 이 `unlock-screen` 보다 먼저 온다** →
`release('suspend')` → 남은 이유 = 삽입 순서 첫 번째 = `'fullscreen'` → **soft-protect** →
`collapse-panel` → `rail.showInactive()` → **아직 잠금 화면인데 손잡이가 뜬다.**

(노출되는 건 손잡이 그림뿐이다 — 패널은 이미 파괴됐고 `isSidePinResponsive` 가 false라 안 열린다.
그래도 이 파일은 **정확히 이 사고를 막으려고** 쓰인 파일이다.)

**고치는 법**: 이유에 **등급**을 붙인다.

- `force`: `lock` · `suspend`
- `soft`: `fullscreen`
- `protect()`·`release()` **둘 다** 남은 이유의 **최고 등급**을 돌려준다.
- 즉 **soft와 force가 함께 걸려 있으면 언제나 force가 이긴다.**

⚠️ **트래커가 다루는 이유는 이 3종뿐이다**(확인함). `SidePinPowerReason` 은 지금
`'lock' | 'suspend'` 두 개다(`sidePinProtection.ts:13`). 나머지 둘은 트래커를 안 거친다 —
`adapter-unhealthy` 는 전이 함수가 직접 설정하고(`resolveSidePinTransition.ts:647`, `:670`),
`virtual-desktop-hidden` 은 **아직 어디에도 배선돼 있지 않다.** 등급 표에 넣지 않는다.

### 5.8 S1-4 — 기존 [닫기] 단추 고치기 (**새로 만들지 않는다**)

또한 다시 펼쳤을 때 **위젯 목록으로 돌아가 있어야 한다.** 열어 둔 채 접히면 다시 스칠 때 그대로 뜬다.

### 6.8 PIN 오버레이를 어디에 그릴 것인가

- ⚠️ **Esc 충돌 — 방향 정정(v2가 반대로 적었다)**: `SidePinWidgetZone.tsx:163-170` 이 **이미
  `e.stopPropagation()` 을 부르고**, React 18은 루트 컨테이너에 붙으므로 그 전파 차단이
  `PinOverlay` 의 `window` 리스너(`:99-101`)까지 도달을 막는다.

  → 오버레이가 떠 있는 동안에는 뒤쪽 Esc 처리를 **끈다.** 테스트로 못박는다.
- ⚠️ `PinOverlay` 의 `window` 키다운은 **숫자·Backspace도 전역으로 삼킨다**(`:94-101`).

## 8. 사전 부검 (Pre-mortem)

### 시나리오 1 — "옆핀이 자꾸 사라져서 껐어요"

감지가 오탐한다. 또는 **프로젝터 PPT가 노트북 옆핀까지 지운다**(§5.3, 세션 단위 API).

`soft-protect` 라 손잡이가 남아 되돌릴 수 있다 · **끄는 스위치가 같은 단계(S1-3)에 있다** ·
**§5.3의 5분 판정선**을 넘으면 후속에서 모니터별로 좁힌다.

### 시나리오 2 — "PIN을 하루에 열 번씩 쳐요"

§6.2를 제대로 안 하면 **확정적으로 일어난다**(§6.1).

**막는 법**: §6.2가 이 시나리오의 방어선이다 — **S2-1은 통짜로 나간다**(§4 ★).
S2-2 실기기 확인에서 **하루 실제 재잠금 횟수를 로그로 센다.**
**판정선: 하루 8회를 넘으면** "짧은 보호(60초 미만)는 재잠금 제외" 규칙을 넣는다.
(v2는 "잦으면"이라고만 써서 기준이 없었다.)

### 시나리오 3 — "교무실 위젯 숫자가 틀려요"

`unreadCount` 는 **모듈 단위**를 부서로 합친 값이다. 게시판이 여럿이면 어긋난다.
@호출 배지는 **확인 기록 경로(S3-2)가 빠지면 켜진 채 안 꺼진다.**

**막는 법**: 멤버십으로 좁힌 뒤 넘긴다(기존 함수 주석의 경고). 실기기 확인은 "숫자가 뜬다"가 아니라
**"실제 글 수와 맞는다"** — 글 3개 쓰고 3이 뜨는지, 하나 읽고 2가 되는지,
**@호출을 걸고 배지가 뜨는지, 그 글을 열면 줄어드는지.**
(이메일 정규화 위험은 §7.1 재확인으로 **제거됐다** — 삽입 쪽이 이미 정규화한다.)

## 10. ADR-078 (초안)

**결정**

1. 전체화면 감지는 `SHQueryUserNotificationState`(koffi, 3초 폴링, 2회 연속 + 30초 최소 유지,
   연속 3회 실패 시 영구 중단, 절전 중 정지).
2. 전체화면은 **새 `soft-protect` 등급**으로 반응한다 — 손잡이까지 감추되(`conceal-all`) 쓰던 편집을 안 지우고,
   **10초 dispose를 예약하지 않는다.** `lock`·`suspend` 는 기존 파괴적 동작 유지.
3. 보호 이유에 **등급**을 둔다. soft 와 force 가 섞이면 **언제나 force 가 이긴다.**
4. **옆핀의 PIN 해제 상태는 옆핀 상태 기계(전이 함수)가 들고, main 이 그것을 창들에 밀어준다.**
   (main 이 따로 들고 있는 것이 아니다 — 상태는 `dispatch` 로만 바뀐다.)
   파일 저장·창 간 해제 전파는 보안상 기각한다.
5. 재잠금은 **보호 해제 시점**(+12시간 안전 상한). 시간 기반 자동 잠금은 안 쓴다.
6. 창 간에는 **잠그는 방향만** 전파한다. **옆핀→본 앱은 제외**한다.
7. "즉시 가리기"는 **기존 [닫기] 단추를 고쳐** 만든다. 새 단추도 새 상태도 안 만든다.
8. 교무실 위젯 기본 표시는 **숫자만(A)**. 제목(C)은 옵트인이며 `ProtectedFeatureKey.staffroom` 으로 잠긴다.
9. @호출 배지는 **글 단위 확인 표시**(`staffroom_mention_reads`)를 쓴다. 부서·모듈 단위 커서는
   못 본 호출까지 0으로 만든다.
10. **끄는 스위치는 그 기능과 같은 단계에 출시한다**(전체화면 감지 끄기 → 1단계).

**동인** — D1 방해 빈도 · D2 되돌아올 수 있는가 · D3 검증 가능성

**검토한 대안**

- 감지: 포그라운드 창 크기 재기(±WinEvent 훅) → 최대화를 전체화면으로 오인. Electron 이벤트 → 남의 창을 못 본다.
- 잠금 기준: 5분 → 온종일 자물쇠. hover 펼침 → 하루 수십 번.
- 해제 상태 위치: 파일 저장 → **재시작 후에도 풀린 채**로 남고 창을 건너 퍼진다.
  dispose만 막기 → **5분 시계가 남아** 절반만 해결. `broadcastToAllWindows` 로 해제 전파 → 노출된 창이 저절로 열린다.
- 즉시 가리기: 새 '가림막' 상태 → 이미 있는 단추와 중복 + 되돌리기 부담.
- @호출: 모듈/부서 읽음 커서 재활용 → 게시판을 한 번 열면 못 본 호출까지 0이 된다.

**왜 이것인가** — 옆핀은 "늘 보이는 창"이다. 대시보드용 장치를 그대로 옮기면 선생님이 꺼 버려
보호가 0이 된다. 그리고 **정책보다 창의 수명이 먼저다** — 해제 상태가 어디 사는지, 패널이 언제
파괴되는지를 정하지 않으면 어떤 정책도 관측되는 동작을 바꾸지 못한다(v1·v2가 각각 여기서 넘어졌다).

**결과**

- (+) 대시보드에서 잠긴 4종이 옆핀에서도 실제로 잠긴다.
- (+) 오탐해도 쓰던 글이 안 날아간다(패널 창을 파괴하지 않는다). 발표가 끝나면 손잡이가 자동으로 돌아온다.
- (+) 교무실 위젯을 붙일 수 있게 된다.
- (−) **1단계는 "창 모드 앱을 프로젝터에 띄운 경우"를 막지 못한다**(§5.1). 릴리즈 노트에 그대로 쓴다.
- (−) **듀얼 모니터에서 프로젝터 PPT가 노트북 옆핀까지 가린다**(§5.3). 알고 받아들이는 결함.
- (−) 폴링이라 최대 6초 지연. 슬라이드쇼 첫 6초는 옆핀이 보일 수 있다.
- (−) **옆핀 메모 칸은 이번 범위에서 PIN으로 잠기지 않는다** — 설정에서 "메모"에 자물쇠를 걸어도
  **옆핀 메모는 그대로 읽힌다.** `SidePinApp.tsx:304` 의 `locked` 는 보호(잠금·절전·전체화면)일 뿐
  PIN이 아니다. §3의 문제 진술이 메모에 대해서는 그대로 남는다.
  **릴리즈 노트에 "위젯"이라고 명시하고 "옆핀을 잠갔다"라고 쓰지 않는다.** 후속 1순위(§11).
- (−) 본 앱과 옆핀에서 PIN을 각각 쳐야 하는 경우가 생긴다.
- (−) `ProtectedFeatureKey` 확장은 6개 파일·리터럴 5곳의 `tsc` 훑기를 부른다.
- (−) main 이 "PIN이 맞았다"를 렌더러 말만 듣고 믿는다. 위협 모델이 "화면을 보는 사람"이라 받아들인다.
- (−) **macOS 옆핀은 전체화면에 대해 여전히 무보호다**("퇴행 없음"이 아니라 **미보호**).
  `'fullscreen'` 이유값이 macOS에서는 **도달 불가 상태**가 된다 — 테스트는 Windows 경로만 단언한다.

## 13. 하지 말 것

- **S2-1을 쪼개서 내보내기** — 해제 상태·가드·접힘 방지 셋 중 하나라도 빠지면
  **각각이 결함을 살린 채 통과한다**(§4 ★).
- **`soft-protect` 를 만들면서 `protect-released` 의 예약 취소를 빼기** — 보호가 풀린 **직후 10초**에
  타이머가 터져 패널이 파괴된다. 쓰던 글이 그때 날아간다(§5.5(나) ②).

- **칸별 활동 지도를 창 파괴 때 안 비우기** — `panel.destroy()` 는 React 정리를 안 거치므로

- **보호 이유 등급 없이 `soft-protect` 를 배선하기** — 잠금 화면 위에 손잡이가 뜬다(C-6).

- `sidePin.eligible` 을 false 로 내려 문제 회피 (이미 쓰이는 기능 회수 금지)
