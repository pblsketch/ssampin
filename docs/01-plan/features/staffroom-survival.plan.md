## 0. 한 문단 요약 (비개발자용)

온라인 교무실은 부서 자료를 **읽는 길까지 "관리자 선생님 한 분의 구글 계정"을 지난다.**
그분이 전출하거나 구글 연결이 끊기면 그 부서 자료실이 **전원에게** 안 열리고, 부서를 지울 방법조차 없다.
그런데 **지금 이 기능을 쓰는 부서가 몇 개인지 아무도 모른다.** 그래서 먼저 숫자를 만들고,
그 숫자를 보고 나머지 순서를 정한다. 숫자를 만들 때 **다른 학교 선생님들의 부서 이름·이메일·글 제목은
오너 화면에 절대 올리지 않는다.** 같이 15줄짜리 결함 하나를 고친다 — **한 번 받아 본 자료는
관리자가 떠나도 계속 열리게.** 지금 가이드가 이미 그렇게 약속했는데 코드가 안 지키고 있다.

## 4. ★ P1 실측 게이트

**질문** — A 계정으로 올라간 부서 파일을, B 계정의 쌤핀 토큰으로 읽을 수 있는가?
(A 가 `grantReader` 로 권한을 준 뒤에도?)

**확보한 증거 — 두 갈래가 같은 답을 가리킨다**

- **(가) 구글 문서** — `drive.file` 은 "앱이 만든 파일 + 사용자가 피커로 직접 고른 파일"에만 닿고,
  **(앱, 사용자, 파일) 세 쌍마다 따로** 걸린다. **공유(ACL)받는 것과 앱 토큰이 API 로 읽는 것은 다르다.**
- **(나) 저장소 안의 이미 측정된 사실 — 더 강하다.** `staffroomDrive.ts:390` 주석:
  _"★ 서버가 바이트를 나르는 유일한 자리다. `drive.file` 권한 탓에 **멤버가 직접 못 읽어서** 어쩔 수 없다."_
  그리고 `download` 는 `grantReader` **뒤에도** 바이트가 아니라 브라우저 링크를 준다(F-2).
  **`grantReader` 만으로 앱 토큰 API 읽기가 열렸다면 이 설계일 이유가 없다.**

**판정: 안 될 가능성이 매우 높다(높은 확신).**
**그러나 두 계정으로 실제 왕복을 돌린 실측은 아직 못 했습니다** — 구글 계정 2개와 배포된 서버가
필요하고 **이 세션에서 제가 할 수 없습니다. 오너 도움이 필요합니다.**
(나)는 _멤버_ 실측이고 *공동 관리자*로의 추론이 한 걸음 들어 있다. 아래가 그 걸음을 없앤다.

**게이트 (P1 착수 세션 맨 앞, 30분)**

```
G-1 부서 생성(관리자 A) + 파일 1개 업로드
G-2 B 를 멤버로 초대, B 토큰을 검증용 별도 행에 임시 저장(운영 데이터 불변)
G-3 B 토큰 → GET /drive/v3/files/{id}?alt=media                    기대 404
G-4 A 토큰으로 grantReader(id, B) 뒤 G-3 재시도                     기대 404  ← 핵심
G-5 B 토큰 → files.list(q="'{folderId}' in parents")               기대 빈 목록
```

- **G-4 = 200** → 판정이 틀렸다. **P1 승격**(이미 쌓인 자료까지 살아난다).
- **G-4 = 404** → 판정대로. P1 의 값은 "앞으로 올라올 자료"로 줄고 §5 를 따른다.

★ **이 게이트 없이 P1 을 구현 착수하지 않는다.**

## 5. 순서

### 5.1 초안의 근거 하나가 무너졌다

초안은 **"P3 이 탈출구다"** 를 근거로 순서를 골랐다. **틀렸다.**

> **P3 은 관리자 토큰이 살아 있어야만 작동한다.** 그런데 이 프로젝트가 걱정하는 실패는
> **"관리자가 떠났다 / 토큰이 끊겼다"** 이다.
> **P3 이 구제하는 집합과 걱정하는 집합은 서로소다.** P3 은 탈출구가 아니라
> **"아직 멀쩡한 부서를 위한 백업"** 이다 — 필요해지기 전에만 살 수 있는 보험.

살아남는 근거: **P1 은 이미 난 사고를 못 고친다.** 약하게 살아남는 근거: P3 이 P2 의 부품을 미리 검증한다.

### 5.2 선택 — **P0 이 순서를 고르게 한다**

```
이번 세션:  P0 (계측 + download 결함수리)
   ↓ P0 숫자를 보고 분기 — 미리 정해 둔다
부서 총수 = 0          → ★ 아무것도 더 짓지 않는다 (정본 §10.4 를 이번에는 지킨다)
끊김 ≥ 1               → P2 최우선 (이미 사고 중 — 복구가 먼저)
끊김 = 0, 부서 ≥ 1     → 폴더 1:N 스키마(독립 단위) → P2 → P3 → P1(축소)
G-4 가 200             → P1 승격
```

**"폴더 1:N"을 독립 단위로 뺀 이유** — `staffroom_departments.drive_folder_id` 는 컬럼 **하나**인데
**P1(B 드라이브 새 폴더)과 P2-③(이전 중 A·B 동시 존재)이 둘 다** 여러 폴더를 필요로 한다.
**양쪽의 임계 경로**이므로 가장 위험한 작업(파일 이동)과 같은 세션에 묶지 않는다.

#### (나) ★ 건강 4상태 — 초안의 새 표를 버렸다

초안은 새 표를 만들고 `adminAccessToken` 에서 성공·실패를 모두 기록하려 했다. **세 이유로 버린다:**
① **"정상"의 답은 이미 DB 에 있고 소급된다**(F-4) ② **"미연결"은 계측이 아니라 파생이다**
③ **뜨거운 길에 성공 쓰기를 넣으면 안 된다**(P-6 — `adminAccessToken` 빠른 경로는 지금 쓰기 0회).

**★ 네 상태는 배타적이어야 한다 — 우선순위를 `CASE` 하나로 못박는다.**
그냥 나열하면 겹친다: `updated_at` 3일 전 + `last_broken_at` 1일 전이면 **정상이면서 동시에 끊김**이고,
`updated_at` 30일 전 + `last_broken_at` 20일 전이면 **조용함이면서 끊김**이다.
그러면 **네 칸의 합 ≠ `departments_total`** 이 되어, 오너가 유일한 의사결정 숫자의 **분모를 잘못 잡는다.**

```sql
CASE
  WHEN t.department_id IS NULL                          THEN 'unlinked'  -- 연결한 적 없음
  WHEN t.last_broken_at > t.updated_at                  THEN 'broken'    -- 마지막 시도가 실패
  WHEN t.updated_at >= now() - interval '14 days'       THEN 'ok'        -- 최근 14일 안에 통했다
  ELSE                                                       'quiet'     -- 토큰은 있는데 14일 무신호
END
```

**우선순위: 미연결 > 끊김 > 정상 > 조용함.** 부서마다 상태를 하나만 정하고 그 결과를 센다.

| 상태                  | 뜻                                              | 뜨거운 길 비용           |
| --------------------- | ----------------------------------------------- | ------------------------ |
| **미연결** `unlinked` | 구글을 연결한 적이 없다 (`LEFT JOIN … IS NULL`) | **0** (소급, 정확)       |
| **끊김** `broken`     | 마지막 실패가 마지막 성공보다 나중              | **실패할 때만** 1회 쓰기 |
| **정상** `ok`         | `updated_at` 이 최근 14일 이내                  | **0** (소급)             |
| **조용함** `quiet`    | 토큰은 있는데 14일 이상 무신호                  | **0** (소급)             |

- **★ 14일인 이유** — `updated_at` 은 **토큰 갱신 시에만** 오르고(`staffroomDrive.ts:157-166`,
  빠른 경로 `:121-124` 는 쓰기 0회) 액세스 토큰 수명이 1시간이다. 즉 **N 은 "연결 건강"이 아니라
  "최근 사용"의 창이다.** 14일은 **방학·연휴 2주를 견디는 값**이다. 7일이면 방학마다 전부 "조용함"이 된다.
- **"조용함"을 따로 둔 이유(걸쇠 방지)** — `last_broken_at > updated_at` 만 쓰면 걸리면 안 풀린다.
  끊긴 뒤 아무도 시도하지 않은 부서가 영원히 "끊김"으로 남아 긴급도를 부풀린다.
- **"미연결" vs "조용함"** — 전자는 _"부서를 만들어 놓고 설정 전에 포기했다"_(제품 신호),
  후자는 _"토큰은 있는데 자료실을 안 쓴다"_(사용 신호). 조치가 다르다.
- **★ 전역 플래그를 만들지 않는다 (H-4).** 암호화 키 부재는 `staffroomEncryptionKey()` 가
  **Deno 환경변수**를 읽는데 집계 함수는 **SQL** 이라 그 값을 볼 수 없다.
  → **`kind === 'missing'` 이면 아무것도 기록하지 않고 `console.warn` 만 남긴다.**
  키 오설정은 **Edge Function 로그로 진단**하고, 그 사실을 (카)의 한계로 적는다.
- **★ `'broken'` 쪽에도 같은 전역 오염이 하나 있다** — `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`
  부재(`staffroomDrive.ts:126-128`)는 `'broken'` 으로 오는데 **그건 부서별 사고가 아니라 전역 환경 사고**다.
  한 번의 오설정이 **전 부서를 "끊김"으로 물들여 §5.2 의 분기를 P2 로 잘못 튀게 한다.**
  → 이것도 **기록하지 않고 `console.warn` 만** 남긴다(구별 가능하다 — 갱신을 시도하기 *전*에 던진다).
  (새 표를 만들면 049 의 `_service_all`·REVOKE 관례와 `staffroomIsolation.meta.test.ts` 의
  `TABLES` 배열을 **함께** 고쳐야 한다 — 안 만드는 편이 훨씬 싸다.)

**스키마 — 새 표를 만들지 않는다.**

P1 에서 PK 가 `(department_id, admin_email)` 로 바뀌면 건강도 관리자별로 갈라지는데 **그게 맞는 모양**이다.

#### (다) 어디서·어떻게 기록하는가 — `list` 의 이미 있는 catch (F-5)

`staffroom-library` 의 `list`(`index.ts:224-236`)는 **이미** `driveStatus` 3상태를 계산하고
`AdminTokenError` 를 잡는다. **거기서 기록한다.**

- **뜻이 정확해진다** — "토큰 발급이 됐나"가 아니라 **"멤버가 자료실을 열 수 있었나"**.
  `driveQuota` 실패(**드라이브 용량 초과** — 정본 §10.6 이 경고한 그것 · 폴더 휴지통)까지 잡힌다.
- **★ kind 2 와 4 를 가르되, `driveConnected` 를 쓰면 안 된다.** `error.kind` 는 `'missing'|'broken'`
  **둘뿐**이라(`staffroomDrive.ts:59`) 그것만 보면 **kind 4 가 전부 2 로 기록되어 F-5 의 이득이 증발한다.**
  그런데 **기존 `driveConnected` 도 못 쓴다** — `catch` **첫 줄(`index.ts:233`)에서 `false` 로 되돌리고**
  `driveStatus` 도 `:234` 에서 `error.kind` 로 덮인다. 기록 코드가 놓일 자리에서는 **이미 지워져 있다.**
  → **`catch` 가 재대입하지 않는 새 지역 변수를 `:227` 옆에 세운다**:
  ```ts
  let tokenIssued = false;          // try 밖에 선언, catch 에서 건드리지 않는다
  try {
    const token = await adminAccessToken(db, departmentId);
    tokenIssued = true;             // :227 옆
    driveConnected = true; driveStatus = 'connected';
    const quota = await driveQuota(token);   // 여기서 실패하면 tokenIssued 는 true 로 남는다
  } catch (error) { … }
  ```
  **`tokenIssued === false` → `2`(갱신 실패) · `true` → `4`(드라이브 거부 = 용량 초과·폴더 휴지통).**
- **★ 실패 기록 UPDATE 는 `last_broken_at`·`broken_kind` 두 칸만 쓴다. `updated_at` 을 절대 포함하지 않는다 (H-10).**
  이 저장소의 기존 두 곳이 전부 `updated_at` 을 함께 넣기 때문에(`staffroomDrive.ts:164`·
  `save-admin-token:108`) **습관으로 넣기 쉽다. 넣으면 `updated_at ≥ last_broken_at` 이 되어
  "끊김"이 구조적으로 영원히 0 이고, 게이트 4종은 전부 초록이다.**
  (확인: `staffroom_admin_tokens` 에 `BEFORE UPDATE` 트리거는 **없다** — 넣지만 않으면 안전하다.)
- **★ 실패 기록에도 스로틀을 걸되, `.lt()` 만 쓰면 안 된다.** 끊긴 부서를 여러 멤버가 반복해서
  열면 쓰기가 몰리므로 스로틀은 필요하다. 그런데 `ADD COLUMN last_broken_at` 으로 **기존 모든 행의
  초기값이 NULL** 이고, SQL 에서 **`NULL < cutoff` 는 UNKNOWN → 행이 안 맞는다.**
  `.lt()` 만 쓰면 **첫 고장이 영영 기록되지 않아 `health_broken` 이 구조적으로 영원히 0** 이고,
  §9.4 의 확인은 실패하며 **게이트 4종은 전부 초록이다.** (H-10 과 같은 함정이 스로틀을 통해 되돌아온다.)
  → **`.or('last_broken_at.is.null,last_broken_at.lt.' + cutoff)`** 로 **왕복 1회**.
- **기록은 `await` 한다** — fire-and-forget 하면 응답과 함께 Deno isolate 가 내려가며 **간헐적으로 유실**된다.
- **기록 실패는 `try/catch` 로 삼킨다** — 계측이 자료실을 죽이지 않는다(P-6).

#### (라) 계측이 살아 있는지 — 무엇이 되고 무엇이 안 되는가 (B-2)

**★ 솔직하게: 대시보드만 보고 "끊김 0"이 진짜 0 인지, 계측이 죽은 건지 구별할 수 없다.**
성공 경로는 아무것도 쓰지 않기 때문이다(그게 옳다 — P-6). 두 경우 다 0 이다.

→ **화면에는 `마지막 기록 시각`(= `max(last_broken_at)`)만 진단용으로 둔다.**
"관측 기록 건수"라는 별도 지표는 **두지 않는다** — 끊김 건수와 같은 것을 세므로 착시를 만든다.
→ **계측이 살아 있는지는 §9.4 의 "토큰을 일부러 망가뜨려 보는" 확인으로만 판정한다.**

#### (마) 집계 함수 — 반환 컬럼 전체와, 빠지면 조용히 깨지는 두 줄

**★ 반환 컬럼 목록 (H-1) — 이건 구현 세부가 아니라 개인정보 방어선의 본체다.**
**허용 목록이 곧 계약이고, 테스트가 이것과 정확히 일치함을 단언한다.**

```sql
CREATE OR REPLACE FUNCTION staffroom_health_v1()
RETURNS TABLE (
  generated_at        timestamptz,   -- 이 숫자의 기준 시각 (탭 머리에 표시)
  departments_total   bigint,        -- 분모
  dept_members_0      bigint,        -- ★ 멤버 0명 부서 (없으면 히스토그램 합 ≠ 분모)
  dept_members_1      bigint,        -- 멤버 수 분포
  dept_members_2_5    bigint,
  dept_members_6_10   bigint,
  dept_members_11_30  bigint,
  dept_members_31_up  bigint,
  posts_total         bigint,
  comments_total      bigint,
  files_total         bigint,
  files_bytes         bigint,        -- NULL 가능 (0행일 때)
  last_activity_date  date,          -- NULL 가능 (활동 0건일 때)
  depts_no_activity   bigint,
  health_ok           bigint,        -- 정상
  health_broken       bigint,        -- 끊김
  health_quiet        bigint,        -- 조용함
  health_unlinked     bigint,        -- 미연결
  last_broken_at      timestamptz    -- NULL 가능 · 진단용 (라)
)
LANGUAGE sql
STABLE                               -- ★★ 필수
SECURITY DEFINER                     -- ★ 교무실 도메인 선례 3/3 (F-3, H-5)
SET search_path = public, pg_temp    -- ★ 선례 3/3 이 pg_temp 를 포함한다 (050:257·051:243·052:257)
AS $$
WITH mem AS (SELECT department_id, count(*) AS c FROM staffroom_members GROUP BY department_id),
     tok AS (SELECT d.id, t.department_id AS tid, t.updated_at, t.last_broken_at
               FROM staffroom_departments d
               LEFT JOIN staffroom_admin_tokens t ON t.department_id = d.id),
     act AS (SELECT department_id, max(at) AS last_at FROM (
               SELECT department_id, created_at  AS at FROM staffroom_posts
               UNION ALL SELECT department_id, created_at  FROM staffroom_comments
               UNION ALL SELECT department_id, uploaded_at FROM staffroom_files) x
             GROUP BY department_id)
SELECT now(),
       (SELECT count(*)::bigint FROM staffroom_departments),
       ...                                   -- 전부 스칼라 서브쿼리
       (SELECT COALESCE(sum(size),0)::bigint FROM staffroom_files),
       ...
$$;                                  -- ★ 바깥 SELECT 에 FROM 이 없다 → 구조적으로 항상 1행

REVOKE EXECUTE ON FUNCTION staffroom_health_v1() FROM PUBLIC, anon, authenticated;
GRANT  EXECUTE ON FUNCTION staffroom_health_v1() TO service_role;

NOTIFY pgrst, 'reload schema';       -- ★★ 필수 (061:921) — F-7: 교무실 관례엔 없다
```

- **★ 개인정보 계약은 두 겹이다.**
  ① **타입** — `uuid`·`text`·`jsonb` 컬럼이 하나도 없음(grep 으로 정확히 증명된다).
  ② **카디널리티** — **바깥 `SELECT` 에 `FROM` 이 없다(스칼라 서브쿼리만).** 이게 "항상 1행"을
  **구조로** 보장한다. 히스토그램의 `GROUP BY` 는 **CTE 안에 갇혀 밖으로 안 샌다.**
  → ②가 없으면 `RETURNS TABLE(members_count bigint, files_total bigint, last_activity_date date,
health_state smallint)` 같은 **부서당 한 행**이 타입 검사를 **통과하면서** 되살아난다.
  오너는 자기 학교 부서를 아니까 용량+마지막 활동일 조합만으로 특정 부서를 짚을 수 있다.
- **★ 정의를 지금 못박는다 (구현자가 즉석에서 정하지 않게)**
  - `last_activity_date` = `staffroom_posts.created_at` · `staffroom_comments.created_at` ·
    **`staffroom_files.uploaded_at`**(★ `files` 에는 `created_at` 이 없다) 셋의 최댓값
  - `depts_no_activity` = 위 셋 어디에도 행이 없는 부서 수
  - `dept_members_0` 를 **반드시 둔다** — 구간이 1부터 시작하면 **멤버 0명 부서가 어느 구간에도
    안 들어가** 히스토그램 합 ≠ `departments_total` 이 된다
  - **`files_bytes` 는 `staffroom_storage_usage`(`051:236-266`)와 다른 숫자다** — 그쪽은
    `files.size + preview_size + file_versions.size` 를 더한다. 이쪽은 **`files.size` 만**.
    **같은 말("자료 용량")로 두 답이 생기므로**, 오너가 교사 화면과 대조하면 어긋난다는 걸 적어 둔다
- **★★ 왜 `STABLE` 과 `NOTIFY` 가 치명적인가** — `fetchRpc` 는 **GET** 으로 부르고
  (`_lib/supabase.ts` — `method` 없음), **PostgREST 는 `VOLATILE` 함수의 GET 을 405 로 거부한다.**
  `LANGUAGE sql` 은 표기가 없으면 **기본이 VOLATILE**. `NOTIFY` 가 없으면 스키마 캐시가 새 RPC 를
  모르는 동안 404. 그리고 **`fetchRpc` 는 실패를 `return []` 로 삼킨다.**
  → **오류가 아니라 "데이터 없음"처럼 보인다. 게이트 4종이 초록인 채 탭이 빈 화면으로 나가는
  가장 유력한 경로다.**
- **★ DEFINER 를 고른 이유 (H-5)** — 061 데이터 RPC 16종은 INVOKER 지만 **교무실 도메인 3/3 은
  DEFINER 다**(`050:256`·`051:242`·`052:256`). 게다가 **동시에 대기 중인 옆핀 계획도 DEFINER**(`:379`).
  같은 도메인·같은 주에 정반대 관례를 넣지 않는다. 기능적으로는 둘 다 돌지만
  **INVOKER 에는 "대시보드 키가 언젠가 service_role 이 아닌 것으로 바뀌면 RLS 가 조용히 0행을
  돌려주고 탭이 빈 화면"** 이라는 §7 시나리오 1 과 같은 실패 경로가 붙는다. **근거를 ADR-079 에 적는다.**
- **★ 구현 첫 10분에 확정할 다섯 가지 (추측 금지 — 여기 답을 적어 둔다)**
  1. `dept_members_0` = `departments_total − (SELECT count(*) FROM mem)` ·
     `depts_no_activity` = `departments_total − (SELECT count(*) FROM act)`
     (`mem`·`act` CTE 에는 **해당 행이 있는 부서만** 들어오므로 빼기로 구한다)
  2. 4상태 `CASE` 는 **상태 CTE(`st`)를 하나 더 두어 한 번만** 쓰고, 바깥에서는 그 결과를 센다
  3. **`files_bytes` 는 `COALESCE(...,0)` 을 쓰므로 NULL 이 아니다** →
     NULL 가능 칸은 **`last_activity_date`·`last_broken_at` 둘뿐**(§9.1 목록도 2개로)
  4. 전역 `GOOGLE_CLIENT_ID`/`SECRET` 오설정은 **에러 객체로 `:128` 과 `:151` 이 구별되지 않는다**
     → **기록 직전에 `Deno.env.get()` 으로 직접 확인**하고, 없으면 `console.warn` 만
  5. **본문 컬럼 참조에 전부 별칭을 붙인다** — `last_broken_at` 은 **출력 파라미터 이름과 겹쳐**
     한정 없이 쓰면 `ambiguous` 로 **마이그레이션이 거절된다**
- **인증 확인함** — 대시보드는 `SUPABASE_SERVICE_ROLE_KEY` 로 붙는다(`_lib/supabase.ts:38-39, 84-85`).
  `ADMIN_API_KEY` 가 아니다. 페이지 접근 통제는 별개(`landing/middleware.ts:12-17` 쿠키 검사).
- **신선도** — `analytics_rollup_status` 를 쓰지 않는다(그건 롤업 갱신 시각). 함수가 `generated_at` 을 준다.

#### (차) ADR-079 (A-1 에 따라 번호 확정)

**결정** — 교무실 계측은 **집계 함수 단계에서 부서를 식별할 수 있는 칸을 만들지 않는다.**
숫자·날짜만 내보내고 이름·이메일·제목은 **SQL 에서 선택조차 하지 않는다.**
**드라이버** ① 오너 대시보드는 남의 학교 부서 내용을 볼 자리가 아니다 ② 화면에서 가리는 방식은
네트워크 응답에 남아 실질 방어가 아니다 ③ 필요한 건 분포지 명단이 아니다.
**대안** (a) 부서별 표 + 화면에서 가리기 → 응답 본문에 남아 탈락 (b) 이름 해시 → 부서 단위 추적 가능해 탈락.
**결과** 개별 부서를 못 본다. 나중에 필요해지면 SQL·meta 테스트·회귀검사 셋을 함께 고쳐야 한다(**의도된 마찰**).
**★ 분리선** — _"대시보드는 부서를 절대 보지 않는다. 운영상 꼭 필요할 때는 일부러 불편하게 만든
**일회성 운영 스크립트**로만 본다."_ (없으면 "그런 능력이 어디에도 없다"로 잘못 읽힌다.)
**★ 함께 적을 것** — ① **DEFINER 를 고른 이유**(교무실 3/3 선례 + 옆핀 계획과 관례 일치, 061 과 다른 근거)
② **개인정보처리방침을 P0 에서 개정하지 않는 이유**(건강 타임스탬프는 관리자 본인 연결에 대한 운영
메타데이터이고 교사·학생 개인정보가 새로 수집되지 않는다). 안 적으면 다음 세션이 다시 논쟁한다.

#### (카) P0 이 **말해줄 수 없는 것** (오너용 5줄)

1. **어느 학교·어느 부서인지 모른다** (의도적)
2. **"정상"으로 나와도 실제로 파일이 열리는지는 모른다** — 재는 건 "자료실 목록을 열 수 있었나"다
3. **아무도 안 연 부서는 "조용함"으로만 보인다** — 끊겼는지 안 썼는지 구별되지 않는다
4. **★ 서버 설정(`STAFFROOM_ENCRYPTION_KEY`)이 잘못된 날은 지표가 "정상"이라고 말한다** —
   키 부재는 `kind='missing'` 으로 오는데(`staffroomDrive.ts:107`) 그건 "토큰 행 없음"(`:116`)과
   **같은 message·같은 kind** 라 원리적으로 못 가른다. 그 날 교사 화면에는 전원 오류가 뜬다.
   **진단은 Edge Function 로그로** 한다(H-4).
5. **끊김 → 정상 회복은 즉시 반영되지 않는다** — `updated_at` 은 **토큰 갱신 때만** 오르므로
   고쳐도 최대 ~1시간 + 실사용이 있어야 지표가 풀린다.

### P0 안의 결함수리 — `download` 단락 (Phase 아님 · 마이그레이션 없음 · 약 15줄)

**정본 §3.4-(나)가 이미 약속했고, `/docs` 가 이미 사용자에게 말하고 있는데 코드가 안 지킨다:**

`download` 는 `adminAccessToken`(`index.ts:516`)을 grants 조회(`:519`)**보다 먼저** 부른다.
그래서 **이미 드라이브 권한을 받아 둔 멤버조차** 토큰이 끊기는 순간 **409** 로 막힌다(`:709-711`).
폴백 URL `https://drive.google.com/file/d/{id}/view`(`:539`)는 **DB 값만으로 조립되어 API 가 필요 없는데도** 그렇다.

**수리 (행복 경로는 그대로, 회복력만 더한다):**

1. grants 조회를 `adminAccessToken` **앞으로** 옮긴다.
2. 권한 행이 **있으면** 토큰·`fileMeta` 를 `try/catch` 로 감싸고 `AdminTokenError` 면
   **결정적 폴백 URL**(`https://drive.google.com/file/d/{drive_file_id}/view`)을 즉시 돌려준다.
3. 권한 행이 **없으면** 지금과 똑같이 동작한다(권한을 새로 줘야 하므로 토큰이 꼭 필요하다).

**★ 3-1. "새 판" 결함 — 이건 한 줄이 아니다. 안 하거나, 제대로 하거나 둘 중 하나다.**

새 판을 올리면 `staffroom_files.drive_file_id` 가 **그 자리에서 D1→D2 로 갈아끼워진다**(`:374-378`).
그런데 grants 조회는 `file_id + member_email` 로만 한다(`:519-524`) → **v1 을 받아 본 멤버는
grants 행이 있으므로 D2 권한을 영영 못 받는다.** (이건 결함수리 이전부터 있던 결함이다.)

**그런데 조회에 `.eq('drive_file_id', …)` 만 더하면 더 나빠진다 — 스키마와 부딪힌다:**

```

              ★ drive_file_id 는 키에 없다
index.ts:528  await db.from('staffroom_file_grants').insert({...})   ★ error 를 아무도 안 본다
```

필터가 붙은 조회는 새 판을 못 찾는다 → `grantReader(D2)` 로 **드라이브 권한은 실제로 나간다** →
그 뒤 `insert` 가 **유일 인덱스에 걸려 23505 로 실패** → **조용히 넘어간다.** 결과:

1. **grants 행이 D1·`permission_id_1` 인 채로 남는다.** `staffroom-members` 의 회수 경로

   영원히 안 걷힌다.** 정본 §10.6 이 걱정한 구멍을 **넓힌다.**
2. 내려받기마다 `grantReader` 재호출(구글 쿼터).
3. **실기기 확인이 이걸 못 본다** — "새 판도 열린다"는 통과한다(권한은 실제로 나갔으니까).
   **실패는 DB 에만 있다.**

**→ 제대로 하려면 함께 해야 한다:**

- 조회에 `.eq('drive_file_id', target.drive_file_id)` 추가
