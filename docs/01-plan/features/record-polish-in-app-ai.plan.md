## 1. 개요

교사가 학생 관찰 기록을 **입력하는 그 자리에서**, 방금 급하게 쓴 거친 문장 한 줄을 생활기록부 서술형 문체(`~함`, `~보임`)로 다듬어 주는 기능이다.

**핵심은 "쌤핀이 생기부를 써 주는 것이 아니다"라는 점이다.** 내용은 100% 선생님이 쓴 것이고, AI는 말투만 손본다. 교육부 지침이 서술형 항목에 대해 "윤문 등을 위한 보조 수단"까지만 AI 사용을 허용하고 최종 책임은 교사에게 둔다고 명시하고 있는데, 이 용법이 정확히 그 허용 범위 안이다.

### 1.1 왜 이 기능만 살아남았나

원래 계획서 2건은 기능 14개와 "여러 AI 모델 중 상황에 맞는 걸 자동으로 고르는" 라우팅 구조를 담고 있었다. 타당성 검토 결과:

- 누가기록으로 생기부 문단을 자동 생성하는 기능 → **오너 원칙 위반**(쌤핀이 생기부를 대신 쓰면 안 된다)
- 멀티모델 자동 라우팅 → **쓸 수 있는 무료 모델이 1종뿐이라 고를 대상이 없다**
- `nemotron-3-ultra-free`, `nemotron-3.5-lightning-free` → NVIDIA 약관에 "Trial use only — do not submit personal or confidential data"가 있어 **상용 제품에 못 쓴다**
- `hy3-free` → 장애 / `big-pickle` → 한시적 무료라 지속 불가
- 멀티모달·비전, 1M 토큰 분석, 30명 일괄 생성 → 범위 밖
- BYOK(선생님이 본인 API 키를 넣는 방식) → **오너 원칙 "사용자에게 비용이 들면 안 된다"에 위배**

남은 것이 이 윤문 하나다.

### 1.2 이 기능이 성립하는 단 하나의 근거

**생기부 서술형 문장에는 주어가 없다.**

생기부는 학생별 칸에 쓰는 글이라 "김철수는 ~했다"가 아니라 "~에 적극 참여함", "~하는 모습을 보임"처럼 쓴다. 즉 **AI에게 이름을 보낼 이유가 애초에 없다.**

그래서 기존 계획서에 있던 "김철수 → 학생A로 바꿔 보내고, 답이 오면 다시 김철수로 되돌리기"라는 2단계 방식을 **버린다.** 대신 **이름을 아예 지우고 보내는 1단계 방식**으로 간다. 되돌리는 단계가 없으니 "엉뚱한 학생 이름으로 복원되는 사고"가 원리적으로 발생할 수 없다.

이름·학교·반·번호가 나가지 않으면 받는 쪽(opencode Zen → DeepSeek) 입장에서 누구인지 특정할 수 없다. 그래서 무료 모델 약관의 "personal data 제출 금지" 조항에 걸리지 않는다. **이 전제가 무료 모델을 쓸 수 있는 유일한 근거이므로, 이 전제를 깨는 설계 변경은 전부 무효다.**

## 3. RALPLAN-DR 요약

### 3.1 원칙 (Principles) — 4개

1. **P1. 이름은 앱을 떠나지 않는다.** 치환이 아니라 삭제. 되돌리는 단계를 만들지 않는다.
2. **P2. 선생님이 눈으로 보고 누른 것만 나간다.** 실제 전송될 문자열을 그대로 보여주고 명시적 확인을 받는다. 자동 전송·백그라운드 전송 금지.
3. **P3. 쌤핀은 쓰지 않는다, 다듬을 뿐이다.** 입력이 비어 있으면 아무것도 못 한다. 생성 기능으로 확장되는 요청은 이 계획 밖이다.
4. **P4. 비용도 열쇠도 사용자에게 넘기지 않는다.** 무료 모델 + 서버 보관 키. 선생님은 결제도 설정도 하지 않는다.
5. **P5. AI가 죽어도 쌤핀은 멀쩡하다.** 윤문은 부가 기능이다. 실패하면 조용히 원문을 남기고 기록 저장은 정상 동작한다.

### 3.2 의사결정 동인 (Decision Drivers) — 상위 3개

1. **D1 — 법적/약관 리스크 최소화.** 개인정보가 나가는 순간 이 기능은 성립 불가. 무료 모델 약관("무료 기간 중 수집 데이터가 모델 개선에 쓰일 수 있음")을 수용 가능하게 만드는 것은 오직 "익명 교육 문장"이라는 성질뿐이다.
2. **D2 — 사용자 비용 0원.** 유료 모델·BYOK가 전부 탈락한 이유. 선택지의 폭을 극단적으로 좁힌 가장 강한 제약이다.
3. **D3 — 기존 신뢰 서사와의 충돌 관리.** 랜딩·방침에 "오프라인 100%", "자체 서버 없음", "외부 서버를 거치지 않아요"가 적혀 있다. 이 기능은 외부 전송이 발생하므로 문서 갱신이 **같은 작업 단위 안에** 없으면 기능 자체가 리스크가 된다.

### 3.3 선택지 (Options) — 4개 검토, 2개 유효

#### 옵션 A — 이름 삭제 + Supabase 중계 (채택 후보)

앱이 학급 명단을 알고 있으므로 문장 안의 학생 이름을 정확히 지운 뒤, 우리 서버를 거쳐 무료 모델에 보낸다.

- 장점: 이름이 물리적으로 나가지 않는다 / 복원 사고가 원리적으로 불가능 / 키가 앱에 없다 / 사용자 비용 0 / 사용량 상한을 서버에서 건다
- 단점: 서버 운영 부담이 생긴다("자체 서버 없음" 문구 수정 필요) / Zen이 "키 하나로 다수 중계"를 문제 삼을 여지 / 문장 문체 품질이 미검증

#### 옵션 B — 완전 로컬 규칙 기반 윤문 (AI 없음)

정규식·어미 변환 규칙으로 "~했다 → ~함"을 앱 안에서 바꾼다. 외부 전송 0.

- 장점: 개인정보 리스크 완전 0 / 오프라인 / 비용 0 / 랜딩·방침 수정 불필요 / 장애 없음
- 단점: 어미만 바꿀 뿐 **표현을 다듬지 못한다.** "애가 발표 잘함ㅋㅋ" 같은 거친 메모를 생기부 문체로 만들지 못한다. 선생님이 체감하는 가치가 낮다

#### 옵션 C — 로컬 규칙 선처리 + AI 후처리 (하이브리드, 채택 권장)

**옵션 A와 B를 합친다.** 먼저 로컬 규칙으로 어미와 명백한 구어체를 처리하고, 그 결과를 미리보기에 보여준다. 선생님이 "AI로 더 다듬기"를 누를 때만 옵션 A 경로를 탄다.

- 장점: A의 가치 + B의 안전망 / **AI가 죽거나 429(과다 요청)여도 로컬 결과가 남아 기능이 완전히 죽지 않는다**(P5 충족) / 미리보기 화면이 "로컬 결과 → AI 결과" 두 단계라 확인 UX가 자연스럽다 / 외부 전송 빈도 자체가 줄어 Zen 차단 리스크 완화
- 단점: 구현 물량이 A보다 큼(로컬 규칙 세트 추가) / 두 결과가 섞여 "어디까지가 AI인가"를 로그에 명확히 남겨야 함

#### 옵션 D — BYOK (기각, 무효화 근거 명시)

선생님이 본인 API 키를 넣는다.

- **무효화 근거:** 오너 확정 제약 2번("사용자에게 비용이 발생하면 안 된다")에 정면 위배. 또한 교사 대상 제품에서 API 키 발급을 요구하는 것은 사실상 기능 미제공과 같다. 검토 대상에서 제외한다.

### 3.4 권고

**옵션 C(하이브리드)를 권고한다.** 옵션 A는 AI 장애 시 기능이 통째로 사라지는데, 무료 티어의 rate limit이 비공개라 429가 얼마나 자주 날지 예측할 수 없다. 옵션 B를 안전망으로 깔아두면 최악의 경우에도 "어미 정리는 된다"가 보장된다.

단, **Phase 0 실측 결과 AI 품질이 로컬 규칙 대비 유의미하게 낫지 않으면 옵션 B 단독으로 축소한다**(외부 전송 자체를 없애는 것이 최선이므로). 이 판단은 Phase 0 종료 시 오너가 내린다.

## 4. 안전장치 4종 — 구현 방식과 인수 조건

### 4.1 안전장치 ① 이름 제거 (치환이 아니라 삭제)

**무엇을:** 전송 문자열에서 학생 이름을 완전히 지운다. 앱은 학급 명단을 이미 갖고 있으므로(담임=`useStudentStore`, 수업반=`useClassRosterStore`) 추측이 아니라 정확한 목록 대조로 지운다.

**어떻게:**

- 대상 명단 = 해당 학급 전원의 이름 (해당 학생 1명이 아니다 — 문장 안에 다른 학생 이름이 섞여 있을 수 있다)
- 호칭 변형 처리: 성+이름(`김지훈`), 이름만(`지훈`), 조사 결합(`지훈이가`, `지훈이는`, `지훈이를`, `지훈아`, `지훈은`, `지훈도`), 접미 `~이`
- 지운 자리는 빈 문자열로 두고 이중 공백을 정리한다. `학생A` 같은 대체 토큰을 **넣지 않는다**(복원 단계를 만들지 않기 위함)
- 이름이 짧아 오탐 위험이 있는 경우(예: 이름이 "미"처럼 1글자거나 일반명사와 겹치는 경우)는 **긴 이름 우선 매칭**으로 처리하고, 결과는 어차피 미리보기에서 선생님이 확인한다

**인수 조건:**

- [ ] `redactStudentNames(content, roster)` 순수 함수가 `src/domain/rules/` 에 존재하고 외부 import가 0개다
- [ ] 단위 테스트: 성+이름 / 이름만 / 조사 6종 결합 / 동명이인 / 문장 내 다른 학생 이름 / 이름 미포함 문장 — 각 케이스에서 명단의 어떤 이름도 결과 문자열에 남지 않는다
- [ ] **계약 테스트**: 전송 직전 문자열에 대해 "명단 이름 포함 여부"를 재검사하고, 하나라도 남아 있으면 **전송을 차단하고 오류를 띄운다**(경고가 아니라 차단)
- [ ] `학생A`, `[이름]` 등 대체 토큰 문자열이 코드 전체에서 검색되지 않는다 (복원 로직 부재의 증거)

### 4.2 안전장치 ② 전송 전 미리보기 + 명시 확인

**무엇을:** 실제로 나갈 문장을 **그대로** 보여주고, 선생님이 확인 버튼을 눌러야만 전송한다.

**어떻게:**

- 모달에 3개 영역: ①선생님이 쓴 원문 ②**실제 전송될 문장**(이름 삭제 완료본, 편집 가능) ③경고 목록(안전장치 ③ 결과)
- ②는 읽기 전용이 아니라 **편집 가능**하다. 경고를 보고 선생님이 직접 지울 수 있어야 한다
- 확인 버튼 문구는 "이 문장을 외부 AI에 보냅니다" — 완곡어법을 쓰지 않는다
- 취소 시 아무것도 전송되지 않고 원문 그대로 남는다

**인수 조건:**

- [ ] 모달의 ② 영역에 표시되는 문자열과 실제 네트워크 요청 본문이 **바이트 단위로 동일**하다 (테스트로 검증)
- [ ] 확인 버튼을 누르기 전에는 네트워크 요청이 0건이다 (테스트로 검증)
- [ ] ② 영역을 편집하면 편집 결과가 전송된다
- [ ] 취소·ESC·바깥 클릭 어느 경로로 닫아도 요청이 나가지 않는다

### 4.3 안전장치 ③ 희귀 식별 표현 경고

**무엇을:** 이름을 지워도 "전교 회장이자 축구부 주장", 학교명, 병명, 전화번호 같은 단서가 남으면 누구인지 알아낼 수 있다(재식별). 로컬 규칙으로 감지해 경고한다.

**어떻게 — 기존 자산 재사용:**

쌤핀에는 이미 `src/domain/privacy/`에 개인정보 패턴 탐지기가 있다(`maskRules.ts`의 `detectPatterns` — 전화번호·주민등록번호·이메일·생년월일·주소, `keywordMask.ts`의 `detectKeywords`, 테스트 파일 포함). **새로 만들지 말고 이것을 가져다 쓴다.** 단, 같은 폴더의 `maskEngine.ts`에 있는 `applyMask`/`restore`(별칭 치환 후 복원) 2단 방식은 **쓰지 않는다** — 우리 설계는 복원 단계가 없어야 하기 때문이다.

여기에 생기부 전용 규칙을 새로 추가한다(`src/domain/rules/reidentificationRisk.ts`):

| 위험 종류                       | 예시                                    | 신뢰도    |
| ------------------------------- | --------------------------------------- | --------- |
| 학교명                          | `○○고등학교`, `○○중`                    | high      |
| 직위·유일 역할                  | `전교 회장`, `학생회장`, `주장`, `대표` | high      |
| 건강·의료 정보                  | 병명, `진단`, `수술`, `입원`, `치료`    | high      |
| 가족·경제 상황                  | `한부모`, `기초생활수급`, `조손`        | high      |
| 수상·대회 고유명                | `제○회 ○○대회 금상`                     | low       |
| 연락처·주민번호·이메일·생년월일 | (기존 `detectPatterns` 그대로)          | high      |
| 희귀 조합                       | high 항목이 **2개 이상** 동시 등장      | 별도 경고 |

**교육부 기재 금지 항목**(교외 수상실적, 공인어학성적, 논문, 자격증 등)도 같은 엔진에서 경고한다. 이건 개인정보와 별개로 **생기부 자체에 못 쓰는 내용**이라, AI 전송 여부와 무관하게 선생님에게 유용한 경고다.

**인수 조건:**

- [ ] 경고는 **차단이 아니라 경고**다(안전장치 ①만 차단). 선생님이 판단해 지우거나 그대로 보낼 수 있다
- [ ] high 신뢰도 항목이 하나라도 있으면 확인 버튼에 2차 확인(문구 변경 또는 체크박스)이 붙는다
- [ ] 규칙은 전부 `src/domain/`의 순수 함수이며 단위 테스트가 있다 (오탐/미탐 케이스 각각 포함)
- [ ] 기존 `detectPatterns`를 재사용했음이 코드에서 확인된다 (중복 정규식 신규 작성 금지)
- [ ] `maskEngine.ts`의 `restore`를 이 기능 경로에서 호출하지 않는다

### 4.4 안전장치 ④ 한 번에 한 문장 — 일괄 전송 금지

**무엇을:** 개별 문장은 익명이지만, 한 학급 30명분을 한 세션에 연달아 보내면 "이 반은 이런 구성"이라는 프로필이 만들어진다. 성격이 완전히 달라진다.

**어떻게:**

- **중계 함수 API가 배열을 받지 않는다.** 요청 스키마상 `text: string` 하나만 받고, 배열이 오면 400으로 거절한다. 구조적으로 배치가 불가능하게 만든다
- 클라이언트에도 "선택한 문장 전부 다듬기" 같은 UI를 만들지 않는다
- 서버 레이트 리밋: 기존 `_shared/rateLimit.ts`의 `checkRateLimit` 재사용. 분당 상한 + 일일 상한을 함께 건다(구체 수치는 Phase 2에서 확정, 초안: IP 기준 분당 6회 / 설치 식별자 기준 일 60회)
- 짧은 시간에 연속 호출이 감지되면 앱이 부드럽게 안내한다("잠시 후 다시 시도해 주세요")

**인수 조건:**

- [ ] 중계 함수에 배열 입력을 보내면 400을 반환한다 (테스트)
- [ ] 코드베이스 전체에 `polishBatch`, `polishAll` 같은 배치 함수가 존재하지 않는다 (grep 계약 테스트)
- [ ] 레이트 리밋 초과 시 429가 반환되고, 앱은 원문을 잃지 않고 안내만 띄운다
- [ ] `ssampin_rate_limits` 테이블에 새 `endpoint` 값(`polish`)으로 기록된다 (새 마이그레이션 불필요 — 기존 테이블 재사용)

### 4.5 추가 안전장치 — 옵트인 + 전송 로그

- **옵트인:** 설정에 "기록 문장 다듬기(외부 AI 사용)" 항목을 두고 **기본값 꺼짐**. 처음 켤 때 무엇이 어디로 나가는지 설명하는 안내를 1회 보여주고 동의를 받는다. 설정 탭 id·라벨은 기존 것을 건드리지 않고 항목만 추가한다(딥링크·`/docs`·챗봇 KB가 탭 id를 참조하고 있음)
- **전송 로그:** 로컬에만 저장. 언제·어떤 문장을 보냈고 무엇을 받았는지 남긴다. 선생님이 열람·삭제할 수 있다. **서버에는 남기지 않는다.** 문제 발생 시 "무엇이 나갔는지"를 증명하는 유일한 수단이므로 필수다

**인수 조건:**

- [ ] 설정이 꺼져 있으면 버튼 자체가 보이지 않고, 어떤 경로로도 요청이 나가지 않는다
- [ ] 로그가 로컬 JSON에만 저장되며 동기화 대상에 포함되지 않는다(동기화 대상 파일에 동기화 부산물을 쓰지 않는다는 기존 원칙 유지 — 판단 필요 시 오너 확인)
- [ ] 로그 삭제 기능이 동작한다

- 참고 구현: `supabase/functions/ssampin-chat/index.ts` (Deno serve + 요청 타입 + 레이트 리밋 패턴)
- 재사용: `_shared/rateLimit.ts`의 `checkRateLimit`·`clientIpFrom`, `_shared/chatLlm.ts`의 `generateText`(LLM 실패 시 폴백 패턴)

- **pass-through**: 요청 본문·응답 본문을 DB에도 로그에도 남기지 않는다. 남기는 것은 "요청이 있었다"는 카운터뿐
- API 키는 Supabase 환경변수(secret)에만 존재. 앱 번들에 절대 넣지 않는다 (Electron asar는 압축만 풀면 코드가 보이고, 암호화해도 복호화 키가 같이 들어간다)

## 6. 단계별 계획

### Phase 0 — 문체 실측 스파이크 (착수 게이트)

**이 기능의 유일한 실질적 불확실성이다.** `deepseek-v4-flash-free`가 생기부 문체(`~함`, `~보임`)를 실제로 지킬 수 있는지 아무도 확인하지 않았다. 기존 계획서의 "한국어 문장력 최상"은 출처가 없는 문장이다.

**할 일:**

1. 실제 관찰 메모 성격의 문장 **10건**을 준비한다 (거친 구어체, 오탈자, 축약 포함. 실제 학생 데이터가 아니라 오너/개발자가 지어낸 유사 문장)
2. 프롬프트 초안 2~3종으로 각각 돌려 결과를 기록한다
3. 같은 10건을 **로컬 규칙(옵션 B)으로만** 처리한 결과도 나란히 만든다
4. 결과를 표로 정리해 오너가 직접 읽고 판단한다

**측정 항목:**

| 항목                                     | 목표                              |
| ---------------------------------------- | --------------------------------- |
| 문체 준수(`~함`/`~보임` 어미)            | 10건 중 9건 이상                  |
| 내용 왜곡·환각(없던 사실 추가)           | **0건** (1건이라도 나오면 재검토) |
| 존댓말·구어체 잔존                       | 10건 중 1건 이하                  |
| 이름·호칭 되살리기(없는 주어를 만들어냄) | **0건**                           |
| 응답 시간                                | 평균 5초 이하                     |
| 로컬 규칙 대비 체감 개선                 | 오너가 "확실히 낫다"고 판단       |

**게이트 판정:**

- **통과** → Phase 1 착수 (옵션 C)
- **부분 통과**(문체는 되는데 개선폭이 작음) → 옵션 B(로컬 전용)로 축소하고 외부 전송을 없앤다. 이 경우 Phase 2·5의 상당 부분이 불필요해진다
- **실패**(환각 발생) → 기능 보류

**인수 조건:**

- [ ] 10건 × 프롬프트 2종 이상의 원본 입출력이 `docs/03-analysis/`에 기록되어 있다

- [ ] 오너의 GO/축소/보류 판정이 문서에 기록되어 있다

## 9. 사전 부검 (Pre-mortem) — deliberate 필수

> "6개월 뒤 이 기능이 대형 사고로 끝났다. 무엇이 원인이었나?"를 미리 써 본다.

### 시나리오 1 — "이름이 나갔다"

**어떻게 벌어졌나:** 처음엔 이름 삭제가 완벽했다. 그런데 나중에 누군가 "다듬기 품질이 떨어진다, AI가 주어를 몰라서 그렇다"며 프롬프트에 학년·반·성별 같은 맥락을 조금 추가했다. 또는 "선생님이 이름을 직접 지웠는지 확인만 하고 삭제는 안 해도 되지 않나"라며 삭제 로직을 경고로 완화했다. 몇 달 뒤 로그 조사에서 실명이 외부로 나간 것이 드러났다.

**징후:** 프롬프트에 문장 외의 데이터가 추가되는 커밋 / 잔존 검사가 차단에서 경고로 바뀌는 변경 / "품질을 위해 맥락이 필요하다"는 논의

**예방:**

- 잔존 검사를 **차단**으로 못박고, 이를 검증하는 테스트를 회귀 테스트에 포함
- 전송 페이로드에 들어갈 수 있는 필드를 타입으로 제한(`text: string` 외 추가 불가)
- 이 문서 §1.2를 근거로 "맥락 추가 요청은 이 계획 밖"임을 명시
- 프롬프트 문자열 변경 시 리뷰 필수임을 코드 주석으로 표시

### 시나리오 2 — "약관 위반으로 차단됐다"

**어떻게 벌어졌나:** 선생님 수가 늘면서 우리 키 하나로 하루 수만 건이 나갔다. opencode Zen이 "키 하나로 다수 사용자에게 중계"를 재판매(resale)로 보고 키를 정지시켰다. 어느 날 아침 전국의 선생님이 동시에 오류를 봤다. 또는 무료 기간이 끝나 모델이 유료로 전환됐다.

**징후:** 사용량 급증 / Zen에서 401·403 / 무료 기간 종료 공지

**예방:**

- **`help@anoma.ly`에 사전 문의**해 중계 사용이 허용되는지 서면 확인 (Phase 2 착수 전)
- 서버 레이트 리밋을 처음부터 보수적으로 (분당·일별 이중)
- **옵션 C의 로컬 폴백이 이 시나리오의 안전망이다.** AI가 끊겨도 어미 정리는 계속 동작하고, 선생님은 "AI 다듬기는 현재 사용할 수 없습니다"만 본다
- 무료 모델 의존을 문서에 명시 — 언제든 중단될 수 있는 부가 기능임을 사용자 가이드에도 적는다

### 시나리오 3 — "쌤핀은 오프라인이라며?"

**어떻게 벌어졌나:** 기능은 잘 나갔는데 방침 개정이 "다음 릴리즈로" 미뤄졌다. 한 선생님이 랜딩의 "오프라인 100%", 방침의 "자체 서버를 운영하지 않음"을 캡처해 커뮤니티에 올렸다. 학교 정보 담당자가 문의를 넣었고, 쌤핀의 가장 큰 자산인 "우리 데이터는 내 컴퓨터에만 있다"는 신뢰가 흔들렸다.

**징후:** 문서 갱신이 별도 작업 단위로 분리되는 순간 / "일단 배포하고 문서는 나중에"라는 논의

**예방:**

- **Phase 4를 같은 릴리즈에 묶는다.** 방침·`/docs`·랜딩 수정 없이 이 기능은 출시하지 않는다 (릴리즈 게이트로 강제)
- 기본값을 끔으로 두어, 켜지 않은 선생님에게는 실제로 외부 전송이 0이다 — "오프라인" 서사가 기본값에서는 유지된다
- 최초 켤 때의 안내 문구를 방침과 같은 표현으로 맞춘다
- 개인정보 문구는 새로 쓰지 말고 기존 `FAQ.tsx`의 검증된 문장을 재사용한다

## 11. ADR — 생기부 윤문 인앱 AI 도입

### Decision (결정)

교사가 작성한 **문장 하나**를, **이름을 삭제한 뒤**, **자체 Supabase 중계 서버**를 거쳐 **무료 모델 `deepseek-v4-flash-free`** 로 보내 생기부 서술형 문체로 다듬는 기능을 도입한다. 기본값은 꺼짐이며, 로컬 규칙 윤문을 안전망으로 함께 둔다(옵션 C). 생기부 생성 기능은 도입하지 않는다.

### Drivers (동인)

1. 개인정보·약관 리스크 최소화 — 익명 문장이라는 성질만이 무료 모델 사용을 정당화한다
2. 사용자 비용 0원 — 유료 모델과 BYOK를 모두 배제한 제약
3. 기존 "오프라인·로컬 저장" 신뢰 서사와의 충돌 관리

### Alternatives considered (검토한 대안)

| 대안                                    | 판정                                                                                                           |
| --------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| A. 이름 삭제 + 중계 (AI 전용)           | 유효하나 AI 장애 시 기능이 통째로 사라짐                                                                       |
| B. 완전 로컬 규칙 윤문                  | 유효. 안전 최상이나 가치가 낮음. **Phase 0 결과에 따라 축소 대안으로 유지**                                    |
| **C. B + A 하이브리드**                 | **채택.** A의 가치 + B의 안전망                                                                                |
| D. BYOK                                 | **무효.** 오너 확정 제약 "사용자 비용 발생 금지"에 정면 위배                                                   |
| (참고) 별칭 치환 후 복원 2단 파이프라인 | **무효.** 복원 단계가 오복원 사고의 유일한 원인. 주어 없는 생기부 문장에는 애초에 이름이 필요 없어 삭제로 충분 |
| (참고) 멀티모델 자동 라우팅             | **무효.** 사용 가능한 무료 모델이 1종이라 라우터가 죽은 코드가 된다                                            |

### Why chosen (선택 이유)

무료 티어의 rate limit이 비공개라 429 빈도를 예측할 수 없고, Zen 약관에 중계 사용에 대한 조항이 없어 언제든 차단될 수 있다. 옵션 A 단독은 이 두 리스크에서 기능이 0이 되지만, 옵션 C는 로컬 결과가 남아 "어미 정리는 된다"가 보장된다. 또한 로컬 선처리로 외부 전송 빈도 자체가 줄어 R2 리스크도 완화된다.

### Consequences (결과)

**얻는 것**

- 선생님이 급하게 쓴 메모를 그 자리에서 생기부 문체로 다듬을 수 있다
- 교육부 지침이 명시 허용한 범위 안에서 동작한다
- 이름·학교·반·번호가 물리적으로 전송되지 않는다
- 복원 단계가 없어 오복원 사고가 원리적으로 불가능하다

**감수하는 것**

- **"자체 서버를 운영하지 않는다"가 더 이상 사실이 아니다.** 개인정보처리방침 개정이 필수다
- 21번째 Edge Function과 API 키 관리 부담이 생긴다
- 무료 모델 의존 — 무료 기간 종료·차단 시 기능이 중단될 수 있다(사용자 가이드에 명시)
- 이름 삭제는 명단 대조 기반이라 별명·오탈자는 못 잡는다. 완벽을 약속하지 않는다

- [ ] `help@anoma.ly` 문의 및 회신 기록 (R2)

## 12. 성공 기준

1. Phase 0에서 문체 준수 9/10 이상, 환각 0건이 실측으로 확인되었다
2. 안전장치 4종이 전부 구현되고 각각의 인수 조건을 테스트로 통과했다
3. 명단의 이름이 전송 문자열에 남으면 **전송이 차단**된다 (경고가 아니라 차단)
4. 옵트인 꺼짐 상태에서 네트워크 요청이 0건이다
5. API 키가 앱 빌드 산출물 어디에도 없다
6. 4단 게이트 + `deno check` + 랜딩 게이트가 전부 통과했다
7. 개인정보처리방침·`/docs`·랜딩 문구가 같은 릴리즈에서 갱신되었다
8. AI가 실패해도 선생님이 쓴 원문이 사라지지 않는다
