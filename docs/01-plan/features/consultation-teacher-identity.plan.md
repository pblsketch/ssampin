상태: **승인됨(2026-09-09, 오너) · 실행 대기** — 이 세션은 계획만 했고 코드·마이그레이션은 손대지 않았다. 실행은 다음 세션이 S1부터.
작성일: 2026-09-08 (검토 반영 3차, 2026-09-09)
관련 ADR: ADR-095(초안, 이 문서 맨 끝)
선행 작업: 마이그레이션 057~060(익명 접근 차단) 운영 적용 완료(2026-09-08)

> 이 문서는 **공개용 축약본**이다. 취약점 재현 조건, 대상 목록, 측정 원본은 비공개 작업 폴더에 있다.

## 0. 요약

지금 상담·설문에서 **선생님이 명단(예약자·응답자)을 볼 때 쓰는 신분증은 여덟 글자짜리 "관리 키"** 하나뿐이다.
그런데 이 관리 키는 학부모·학생에게 보내는 예약 링크에도 같이 실려 나간다. 그래서 **링크를 받은 사람이 같은 일정의 다른 예약을 읽을 수 있는 상태**다.

이 계획은 명단 조회의 신분증을 **"이 일정을 만든 선생님의 Google 계정 확인"** 으로 바꾼다.

- 일정·설문을 **만들 때** 서버가 Google 계정을 확인해 **소유자 이메일을 박는다.**
- 동시에 **옛 조회 경로도 고친다**: 소유자가 박힌 일정은 옛 관리 키 방식으로 열리지 않게 막는다. 이 조치가 있어야 "소유자가 정해진 뒤에는 그 계정으로만 열린다"가 참이 된다.
- **학부모·학생이 겪는 동작은 하나도 바뀌지 않는다.** 예약·변경·취소·설문 응답은 지금과 똑같아야 한다(최우선 제약).
- 아직 소유자가 없는 옛 일정은 **일정마다 미리 계산해 박아 둔 기한까지만** 옛 방식으로 열리고, 그 뒤로는 서버가 막는다.
- 오너 결정에 따라 **예약자 정보 암호화 방식 개선(일정마다 다른 난수 소금값)도 이번에 함께** 한다. 판 구분은 **암호문 자체에 붙는 접두사**로 한다.

용어를 처음 한 번씩 풀어 둔다.

- **관리 키(admin_key)**: 일정마다 하나씩 만들어지는 여덟 글자 문자열. 지금은 (가)예약자 정보를 암호로 잠그는 열쇠, (나)선생님임을 증명하는 신분증, (다)학부모 링크에 실려 나가는 값 — 세 가지를 혼자 다 겸한다. 세 역할이 한 값이라 문제가 생겼다.
- **RPC**: 서버(데이터베이스)에 미리 만들어 둔 함수를 앱이 이름으로 불러 쓰는 방식.
- **엣지 함수(Edge Function)**: 서버에서 도는 작은 프로그램. 앱이 보내는 값을 검사한 뒤 관리자 권한으로 데이터를 꺼내 준다. 쌤핀은 이미 "온라인 교무실"에서 같은 방식을 쓴다.
- **SECURITY DEFINER**: 부르는 사람 권한이 아니라 **만든 사람(관리자) 권한으로 도는 서버 함수.**
- **anon 권한**: 앱이 "내가 누구인지 밝히지 않고" 서버에 접근할 때 쓰는 공개 열쇠.
- **service_role 권한**: 서버 안쪽에서만 쓰는 관리자 열쇠. 앱에는 절대 넣지 않는다.
- **PUBLIC 실행 권한**: "누구에게나" 열어 둔 실행 허가. anon보다 더 넓다.
- **행 단위 접근 규칙(RLS) 정책**: 표의 행마다 누가 읽고 쓸 수 있는지 정하는 규칙. 권한(GRANT)과 **별개**라 둘 다 봐야 한다.
- **PostgREST 스키마 캐시**: 서버 앞단이 "표에 어떤 칸이 있는지"를 기억해 두는 목록. 칸을 새로 만들면 이 목록을 새로 고쳐야 조회가 된다.
- **정규화(normalize)**: 대소문자·앞뒤 공백 차이를 없애 같은 이메일로 취급하는 것.
- **sha256 대조**: 값을 그대로 보지 않고 **지문**을 뽑아 비교해 원하는 값이 제대로 들어갔는지 확인하는 방법.
- **소금값(salt)**: 같은 비밀번호라도 결과 암호가 달라지게 섞어 넣는 값. 지금은 모든 일정이 같은 값을 쓴다.
- **마이그레이션**: 데이터베이스 구조를 바꾸는 기록 파일. 067·070까지 이미 있으므로 이번엔 **071, 072**를 쓴다.
- **게이트 4종**: 완료 선언 전에 반드시 통과해야 하는 자동 검사(타입 검사, 코드 품질, 테스트, 회귀 검사).

규모: 마이그레이션 2건, 엣지 함수 2개, 앱 수정 10여 파일, 랜딩 2파일, 문서 갱신.
복잡도: **HIGH**(운영 데이터·구버전 앱 호환·학부모 흐름 무중단·암호화 판 전환이 동시에 걸림).

## 1. 배경

### 1.1 지금 구조

관리 키 하나가 세 가지 일을 겸한다.

| 역할                    | 어디서 쓰나                                                                        | 문제                                                            |
| ----------------------- | ---------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| 예약자 정보 잠그는 열쇠 | `src/domain/rules/cryptoUtils.ts`, 랜딩의 `bookingApi.ts` (같은 파생 로직이 두 벌) | 키를 아는 사람은 내용도 풀 수 있다. 소금값이 모든 일정에서 같다 |
| 선생님 신분증           | **교사용 조회 RPC 2종**(정본 이름은 §5·§6에)                                       | 키만 알면 누구든 통과한다                                       |
| 학부모 링크에 실려 나감 | 상담 스토어와 상세 화면의 링크 조립부                                              | 위 두 개와 같은 값이라 링크 수신자가 신분증을 갖게 된다         |

결과: **링크를 받은 학부모가 같은 일정의 다른 예약을 읽을 수 있고**, 돌려주는 값 안에 본인 확인용 토큰까지 들어 있어 무결성(내 것만 고칠 수 있어야 한다는 성질)도 지켜지지 않는다.

### 1.2 왜 지금까지 못 고쳤나

**상담 기능에 "이 일정은 누가 만들었는가"라는 정보가 아예 없다.** 상담 일정 표에도 설문 표에도 소유자 열이 없다. 그래서 관리 키 말고는 판단 근거가 없었다.

또 하나, **일정 정보를 고치는 경로에는 서버 쪽 신원 확인 단계가 없다.** 대상 메서드 목록은 비공개 작업 메모에 있고, 이번 작업에서 같은 문(엣지 함수) 안으로 모아 닫는다.

## 2. 원칙

1. **소유권은 서버가 검증한 신원으로만 생긴다.** 관리 키를 제시해 "이건 내 것"이라고 등록하는 창구(claim)는 만들지 않는다. 앱이 로컬 목록을 한꺼번에 제출하는 방식도 금지한다. — 이 원칙은 **쓰기(소유권 결속)에만** 적용된다. 유예 기한을 미리 계산해 박아 두는 것(§6 S1)은 소유권이 아니므로 위반이 아니고, 기한이 끝난 뒤 앱이 이미 받아 둔 로컬 사본을 여는 것도 예외다.
2. **학부모·학생이 겪는 동작은 하나도 바뀌지 않는다.** 코드 예외는 **랜딩 두 파일**뿐이다 — `bookingApi.ts`(암호 파생 함수, `ScheduleRow` 타입, 조회 컬럼 목록, 매핑)와 `BookingPageContent.tsx`(암호화 호출부). 화면 동작·응답 형태는 그대로다. 5장 목록이 계약서다.
3. **권한은 서버에서 막는다.** RLS 정책을 추가해 푸는 방식은 쓰지 않는다. 반드시 엣지 함수 또는 SECURITY DEFINER 함수로 막는다.
4. **전환은 시간으로 끊고, 비용은 실측 후 오너가 승인한다.** 대칭이다 — 구버전 차단 비용뿐 아니라 **"만들 때 Google 필수"로 생기는 비용도** 숫자와 임계치로 재고 승인 관문을 둔다.
5. **실패는 조용한 빈 화면이 아니라 이유로 말한다.**

## 3. 결정 동인

1. **학부모 흐름 무중단.** 예약이 하루라도 막히면 그날 상담이 통째로 어그러진다.
2. **Google 미연결 다수.** 유예 없는 전환은 불가능하다.
3. **되돌릴 수 있어야 한다.** 각 단계에 명시적 롤백 절차를 둔다.

## 4. 대안 검토

### 대안 A — 소유자 이메일 + 옛 RPC 잠금 + 엣지 함수 + 시한부 유예 (**권장**)

- 장점: 학부모가 겪는 동작이 그대로다. 옛 일정도 기한까지 살아 있어 현장 사고가 없다. 교무실 엣지 함수 8종이라는 검증된 선례가 있고 `verifyGoogleIdentity`를 재사용하므로 **새 Google 권한 요청이 필요 없다.** 신원 확인 없이 열려 있던 수정 경로도 같은 문에 모인다. 옛 RPC를 고치는 덕에 새 앱이 만든 일정은 배포 즉시 새 문으로만 열린다.
- 단점(정직하게):
  - **소유자가 없는 옛 일정은 072 적용 전까지 옛 관리 키 경로로 계속 열린다.**
  - **소유자가 박힌 일정을 같은 교사의 구버전 두 번째 기기에서 열면 거부된다**(§6 S1-2 참고). 상담 일정은 클라우드 동기화 대상이라 다기기 사용자에게 실제로 일어난다.
  - 만들 단계가 늘어난다(마이그레이션 2 + 엣지 함수 2 + 앱 10여 파일 + 랜딩 2파일).
  - 배포·시크릿을 따로 해야 살아난다는 함정이 있다.
  - Google 계정 확인 호출이 매번 일어난다(S2에서 완화).
- 판정: **채택.**

### 대안 B — 데이터베이스 함수 안에서 Google 토큰을 검증

- **Google 호출량 자체는 A안도 같다**(위치만 DB→엣지). 탈락 사유는 "외부 통신을 하니까"가 아니라 **"그 부담과 실패 처리를 작은 운영 DB에 얹을 수 없다"** 이다. 운영 DB는 2026-09-08에 한 시간 먹통 사고를 냈다. 캐시·재시도 같은 완화 수단도 DB 안에서는 만들기 어렵다.
- 판정: **탈락.**

### 대안 C — 열쇠를 둘로 쪼개기 (링크용 / 관리용)

- **이미 배포된 링크가 전부 깨진다**(원칙 2 위반). 소유자 개념이 없어 재발한다. → **탈락.**

### 대안 D — 유예 없이 즉시 전면 전환

- 서버에서 Google 연결 흔적이 확인되는 상담 사용 기기가 약 21%뿐이다(미연결이 다수라고 봐야 한다). → **탈락**(동인 2 정면 위반).

### 대안 E — 하지 않는다 → **탈락.**

### 대안 F — 전역 기한 없이 **일정별로만** 종료

- 장점: 9월에 끝난 일정은 10월에 이미 닫혀 노출 기간이 최소가 된다.
- 단점: 먼 미래 날짜를 가진 일정이 있으면 언제 끝나는지 확정되지 않는다. 날짜가 없는 설문에는 기준이 없다.
- 판정: **부분 채택 → 혼합안.** `min(2026-11-30, 그 일정의 마지막 상담일 + 30일)`. 날짜 없는 설문은 전역 기한만. **이 값을 071 시점에 계산해 칸에 박아 둔다**(매 조회 재계산 없음, §6 S1-2 참고).

### 대안 G — claim 계열(TOFU: 처음 접근한 Google 신원을 소유자로 고정)

- **학부모가 먼저 열면 학부모가 소유자로 박히고 진짜 교사는 영구 배제된다(선점).** → **탈락.**
- 다만 **운영자 수동 결속**은 예외로 허용한다 — 앱에 창구를 만들지 않고, 선생님이 요청하면 오너가 본인 확인 후 관리 경로로 소유자를 기입한다. **선행 조건으로 대상 교사의 앱 버전을 확인**한다(구버전 기기에서는 결속 직후 조회가 막히기 때문이다). ADR 후속에 절차를 남긴다.

### S1 — 마이그레이션 071

**하는 일**

1. **칸 추가.**
   - 상담 일정 표·설문 표: `owner_email`(비어 있어도 됨), `owner_set_at`.
   - 상담 일정 표만: `crypto_version smallint not null default 1`, `crypto_salt text null`. **설문은 응답을 암호화하지 않으므로(평문) 대상이 아니다.**
   - 상담 일정 표·설문 표: **`legacy_grace_until`** — 아래 2 참고.
   - 기존 행의 **소유자 값은 채우지 않는다.** 채우면 그게 claim이다.
2. **유예 만료일을 스냅샷으로 박는다.** 소유자가 없는 기존 행에 대해 `legacy_grace_until = min(2026-11-30, 그 일정의 마지막 상담일 + 30일)`을 **071 시점에 계산해 저장**한다. 날짜가 없는 설문은 전역 기한만 넣는다.
   - 이유: 시간대 표의 anon 수정 권한이 S6까지 남아 있어, 먼 미래 슬롯을 추가하면 매 조회 재계산 방식은 조기 종료가 무효화된다. 기한은 소유권이 아니므로 원칙 1 위반이 아니다. 재계산 비용도 사라진다.
3. **옛 조회 RPC 2종 수정** — `owner_email IS NOT NULL`이면 거부. 거부 문구는 기존 "관리 키가 일치하지 않습니다"와 **구분되는 새 문구**를 쓴다(오류 안내 분기가 그 문자열을 보기 때문이다).

   - **예외 두 가지를 정직하게 적는다**: (가) 상담 일정은 `src/usecases/sync/syncRegistry.ts`를 통해 **클라우드 동기화** 대상이므로, 신형 기기에서 만든 일정이 같은 교사의 **구버전 두 번째 기기**로 내려가면 그 기기의 조회는 거부된다. (나) 운영자 수동 결속 대상도 같은 상황이 된다. → 화면 사유 문구에 **"다른 기기에서 만든 일정이면 그 기기도 최신 버전으로 업데이트해 주세요"**를 넣는다.

4. **무비용 anon 권한 회수** — 앱이 전혀 쓰지 않는 것만: 설문 표의 수정·삭제, 상담 일정 표의 삭제, 여섯 개 표의 TRUNCATE/REFERENCES/TRIGGER.
5. **정책 DROP을 GRANT 회수와 반드시 짝으로.** 마이그레이션 010이 만든 `USING (TRUE)` 형태의 수정·삭제 정책이 남으면, 나중에 GRANT를 복구했을 때 **조용히 다시 열린다.** 060은 반대 함정(정책만 지우고 GRANT를 남기면 0행 200 응답)을 경고했다. 되돌리기 문구에 GRANT와 CREATE POLICY를 **함께** 적는다.
6. **PUBLIC 실행 권한 정리 5개**(§5 하단). anon 실행은 유지, PUBLIC만 걷는다.

**파일**: `supabase/migrations/071_consultation_owner_identity.sql`

**검증**

### S2 — 엣지 함수: `consultation-teacher`, `survey-teacher`

교무실 엣지 함수 8종과 **똑같은 호출 규격**: 본문에 `{ action, googleAccessToken, ... }`. 서버는 `googleIdentity.ts`의 `verifyGoogleIdentity`로 이메일을 확인하고 `normalizeEmail`로 정규화한 뒤 service_role로 데이터를 다룬다.

- **확인 한 줄**: `verifyGoogleIdentity`가 토큰을 발급받은 앱(aud)까지 검사하는지 코드로 확인한다. 안 하면 다른 앱의 Google 토큰도 통과하므로 이번에 추가한다.

**토큰은 서버에 저장하지 않는다.** 앱이 매 호출마다 토큰을 만들어 보낸다(데스크톱은 `AuthenticateGoogle.getValidAccessToken()`).

- **정정**: 이는 "토큰 갱신 함정을 아예 피한다"가 아니다. **저장하지 않는 대신 캘린더 인증 상태에 종속된다.** `getValidAccessToken`은 요청 권한(scope)이 바뀌거나 갱신이 거부되면 저장 토큰을 지우고 실패를 던진다. **캘린더 권한이 바뀌는 릴리즈 날 상담 명단도 함께 막힐 수 있다**(§11).

**판정 규칙 (조회 액션)**

| 순서 | 조건                                                                                                                       | 결과              |
| ---- | -------------------------------------------------------------------------------------------------------------------------- | ----------------- |
| 1    | Google 토큰 검증 성공 **AND** 소유자 이메일이 있고 검증 이메일과 일치                                                      | 허용              |
| 2    | **Google 토큰 검증 성공(이메일은 무엇이든)** AND 소유자 없음 AND **`legacy_grace_until` 이전(서버 시각)** AND 관리 키 일치 | 허용(레거시 유예) |
| 3    | 그 외                                                                                                                      | 거부              |

> 2번의 Google 토큰 검증이 핵심이다. **학부모 브라우저는 쌤핀 Google 토큰을 만들 수 없으므로**, 이 조건 하나로 링크만 가진 사람이 새 문으로도 못 들어온다.

**거부 사유 코드** 4종: `not_connected` · `different_account` · `legacy_closed` · `key_mismatch`.

전역 기한 상수는 함수 안 상수 또는 시크릿. 시크릿이면 **여러 줄 값이 첫 줄만 저장되는 함정**이 있으므로 CLI 대신 JSON API로 넣고 **sha256 대조**로 확인한다. 판정 함수는 기준 시각을 **인자로 받는다**(테스트용).

**만들기 액션**: Google 확인 **필수**. 서버가 `owner_email`을 박고, **난수 소금값을 서버가 생성**해 `crypto_salt`에 넣고 `crypto_version = 2`로 표시한다. **관리 키도 서버가 발급**한다(길이 확대, 문자집합은 **hex 또는 base64url** — 복사·전달 사고 방지). 앱이 본문에 보낸 `owner_email`·`crypto_salt`는 **무시한다.**

- **소금값의 거처는 엣지 함수 응답에 동봉(A안)으로 못 박는다.** 로컬 저장이나 동기화로 나르면, 옛 백업을 든 기기에서 "일정은 있는데 소금값만 없는" 상태가 만들어진다.

**수정 액션**: `updateSchedule`, `setClosed`, `setArchived`, `setExpiresAt`, `replaceSlots`, `bulkUpdateSlotStatus`, `setSlotBlockedByTeacher`도 이 함수로 옮긴다.

**Google 호출량 완화 3종**

1. 엣지 함수 안에 **`sha256(토큰) → 이메일` 5분 캐시**(토큰 자체는 저장하지 않고 지문만 키로 쓴다).
2. **시간대와 예약을 한 번의 호출로 함께 반환**한다.
3. **자동 갱신 주기 조정** — 상세 화면이 열려 있는 동안은 **30초 유지**(명단 최신성이 중요하다), 배경 재계산만 **60초 + 차단(back-off)**.

**파일**: `supabase/functions/consultation-teacher/index.ts`, `supabase/functions/survey-teacher/index.ts`, 공통 판정 모듈은 `supabase/functions/_shared/`에 별도로 빼서 테스트 가능하게.

**검증**: `supabase/functions/**`는 타입·품질 검사 대상이 아니다. 판정 로직 테스트를 `src/infrastructure/supabase/__tests__/`에 두고 상대경로로 불러온다(`staffroomServerAccess.test.ts` 방식).

**롤백**: 앱이 아직 옛 경로를 쓰므로 이 단계까지는 배포해도 사용자 영향이 없다.

### S3 — 배포·시크릿·실호출 확인

> 엣지 함수는 만들어도 배포·시크릿을 따로 해야 산다. 테스트가 모의값이라 **게이트 4종이 전부 초록인 채 실기기에서만 터진 전례**가 있다.

**조회 확인**

1. 내 계정 → 소유자 있는 시험 일정: 허용
2. 다른 계정 → 같은 일정: `different_account`
3. 토큰 없이: `not_connected`
4. 소유자 없는 옛 일정 + 맞는 키 + 유효 토큰 + 기한 전: 허용
5. 같은 조건, 키만 틀림: `key_mismatch`
6. 소유자 없는 옛 일정 + 맞는 키 + **토큰 없음**: `not_connected` (학부모 시나리오)

**수정 확인** (전부 거부) 7. 토큰 없이 일정 수정 / 8. 마감 / 9. 보관 / 10. 다른 계정 토큰으로 시간대 차단

**기한 판정 확인** — 기기 시계 조작은 서버 시각 판정에서 의미가 없다. (a) 판정 함수에 **기준 시각을 인자로 주입하는 단위 테스트**(§9.1), (b) **전역 기한 상수를 과거로 둔 함수를 잠시 배포해 1회 실호출** → `legacy_closed` 확인 후 즉시 원복.

**(c) 랜딩 암호화 판 — 판 번호를 암호문 자체에 싣는다**

- **판 2 암호문은 `v2:` 접두사 + base64로 저장한다. 앱·랜딩 모두 접두사가 없으면 판 1로 복호화한다.** 판정 단위를 "일정"이 아니라 **"값"** 으로 옮기는 것이다.
- 이유: 캐시된 탭이나 CDN에 남은 **옛 랜딩 번들**, 또는 랜딩만 이전 배포로 내린 상태에서 **판 2 일정에 판 1 암호문이 저장**되면, 신형 앱이 행의 `crypto_version=2`만 보고 판 2로 풀다 실패한다. 이것은 한 방향으로만 생기는 **침묵 결함**이고, "소금값 없으면 판 1" 식의 fallback으로는 막히지 않는다.
- `crypto_version` 칸은 **통계·감사용으로 남긴다**(복호화 판정에는 쓰지 않는다).
- `landing/src/components/booking/bookingApi.ts`: `deriveKey(password, salt, iterations)` 인자화, `ScheduleRow`/`SchedulePublic` 칸·매핑 추가, 소금값이 없으면 판 1로 파생.
- `landing/src/components/booking/BookingPageContent.tsx`: `encrypt` 호출 2곳을 새 시그니처에 맞춘다.
- `src/domain/rules/cryptoUtils.ts`: 접두사로 판을 고르는 복호화, **주석 2곳 정정** — 4행("교사만 아는 문자열")과 18행("로컬 전용이므로 OK" — 랜딩에도 같은 로직이 있어 거짓).

**검증**: 게이트 4종 + `cd landing && npm run docs:check && npm run build`.

> **저장소가 USB 디스크(E:)라 테스트와 코드 품질 검사를 동시에 돌리면 드라이브가 떨어진다. 반드시 하나씩.**

**롤백 (정정)**

- **"클라이언트만 되돌리면 원복"은 거짓이다.** 소유자가 박힌 일정은 071이 옛 RPC에서 거부하므로, 앱을 되돌리면 **071의 RPC 정의 원복과 짝으로** 해야 한다.
- **랜딩 단독 롤백은 원칙적으로 금지**한다. 다만 `v2:` 접두사 채택으로 안전 근거가 생겼다 — 랜딩을 이전 배포로 내려도 판 2 일정의 새 예약은 **접두사 없는 판 1 값**으로 저장되고, 신형 앱은 접두사가 없으므로 **판 1로 읽어 성공**한다. 이 근거를 롤백 절차서에 그대로 적는다.

## 8. 사전 부검

### 시나리오 1 — "명단이 텅 비었어요"

거부를 폴링이 삼켜 빈 명단만 뜬다. 선생님은 예약이 사라졌다고 믿는다. 게이트 4종은 초록.
**막는 법**: 오류를 삼키는 5곳을 **먼저** 고친다. 사유 코드 4종 각각의 화면 문구 테스트 + 회귀 #74.

### 시나리오 2 — "배포한 줄 알았는데 안 됐다"

커밋만 하고 배포 안 함, 또는 시크릿 첫 줄만 저장. 상담 당일 아침에 발견.
**막는 법**: S3 독립 단계, 실호출 10종 통과 전 진행 금지. 시크릿은 JSON API + sha256 대조.

### 시나리오 3 — "학부모가 예약을 못 한다"

071에서 PUBLIC만 걷어야 할 5개에서 anon까지 회수했거나, **스키마 캐시가 갱신되지 않아** 새 칸이 포함된 조회가 실패한다. 랜딩은 실패를 `null`로 삼키므로 화면에는 "일정이 없습니다"로 뜬다.
**막는 법**: §5 12종 체크리스트 실호출 + **캐시 새로 고침 후 200 확인을 배포 순서에 못 박음.** 하나라도 실패하면 즉시 `GRANT` 복구.

### 시나리오 4 — "예약된 시간에 또 예약이 들어왔다"

거부 시 `recomputeSlotAvailability`가 빈 결과를 반환해 **자동 슬롯 차단이 조용히 멈춘다.** 이중 예약.
**막는 법**: 실패를 올리고 시간대 상태를 덮어쓰지 않는다.

### 시나리오 5 — "이름이 깨져 보인다 (편도 침묵 결함)"

판 2 일정인데, 캐시된 옛 랜딩 탭이나 CDN에 남은 옛 번들이 **판 1 암호문**을 저장한다. 신형 앱이 행의 `crypto_version=2`만 보고 판 2로 풀다 실패한다. **판 1 fallback은 이 방향을 못 막는다.**
**막는 법**: **판정 단위를 값으로 옮긴다** — `v2:` 접두사가 없으면 무조건 판 1로 복호화. 옛 앱은 판 2 일정을 만들 수 없다는 구조적 안전장치는 **믿지 말고 e2e로 확인**한다(§9.4). 관측으로 "판 2 일정에서 접두사 없는 값을 만난 건수"를 세어 **옛 번들 잔존 지표**로 쓴다.

## 9. 테스트 계획

### 9.1 단위 — 판정 로직 / 암호화 판

판정 함수는 **기준 시각을 인자로 받는다.**

- 토큰 성공 + 소유자 일치 → 허용 / 소유자 다름 → `different_account`
- **토큰 없음 + 소유자 없음 + 키 일치 + 기한 전 → `not_connected`**(학부모 시나리오)
- 토큰 성공 + 소유자 없음 + 기한 전 + 키 일치 → 허용 / 기한 후 → `legacy_closed` / 키 불일치 → `key_mismatch`
- `legacy_grace_until` 계산: 전역이 이른 경우 / 일정별이 이른 경우 / 날짜 없는 설문 → 전역만
- 이메일 대소문자·공백 차이 → 정규화 후 일치
- 암호화: 판 1 왕복 / 판 2(`v2:`) 왕복 / **접두사 없으면 판 1** / **행은 `crypto_version=2`인데 값에 접두사가 없다 → 판 1로 복호화 성공**

### 9.2 통합 — 앱 클라이언트

- 거부 시 **빈 배열이 아니라 오류를 올린다**
- `recomputeSlotAvailability`가 거부 상태에서 시간대 상태를 **덮어쓰지 않는다**
- 시간표·행사 구독 경로가 거부 상태에서 **재시도를 폭주시키지 않는다**
- 사유 코드 4종 각각에서 `supabaseAccessError`가 "업데이트하세요"로 바꾸지 않는다
- 만들기 순서: 엣지 함수 성공 후에만 로컬 저장·공유 URL 조립, **실패 시 반쪽 일정이 남지 않는다**
- 모바일 설문 스토어가 토큰 게터를 받아 같은 경로를 쓴다

### 9.3 적대 검증

| ------------------------------------------------------------- | ------------------------------- |
| 다른 교사 계정으로 남의 일정 명단 요청                        | `different_account`             |

### 9.4 실기기(e2e)

**교사**: (1) Google 연결 후 새 일정 → 소유자·소금값이 박히고 명단 보임 (2) 연결 끊고 열기 → 사유 표시(빈 명단 아님) (3) 다른 계정 → "만든 계정과 같은 계정" 문구 (4) **구버전 두 번째 기기에서 같은 일정 열기 → "그 기기도 최신 버전으로" 문구** (5) 보관 일정 → 기한 전/후 동작 (6) 모바일 설문 응답 조회
**학부모·학생**: (7) 짧은 링크 예약 (8) 확인→변경→취소 (9) 설문 응답(비밀번호 포함) — **(7)~(9)를 071 직후·072 직후 각각 12종 전부**
**암호화 판**: (10) 판 2 일정 예약 → 앱에서 이름 정상 (11) 판 1 옛 일정 예약 → 현재 버전·v2.4.5 미만 **양쪽** 정상 (12) 랜딩만 새 배포된 상태에서 판 1 일정 예약 → 정상 (13) **판 2 일정 + 옛 랜딩 번들(또는 이전 배포 랜딩) 조합으로 예약 → 신형 앱에서 이름 정상**

### 9.5 관측

- 사유 코드별 거부 건수(개인정보 미기록)
- **생성 단계 `not_connected` 건수·비율을 조회 단계와 분리 계측**(결정 1·6의 판단 근거)
- **복호화 실패 건수**

- Google userinfo 호출 건수, **캐시 적중 통과 건수**(철회된 토큰이 최대 5분 통과하는 창)

## ADR-095 초안

### 결정

상담·설문의 **교사 명단 조회 인증을 관리 키 대조에서 Google 신원 확인으로 전환**한다.

1. 일정·설문에 소유자 이메일 칸을 두고, **만들 때 서버가 검증한 이메일로만** 소유자를 정한다(claim 창구 없음).
2. **옛 조회 RPC 2종을 "소유자가 있으면 거부"로 고친다**(071). **만든 기기 기준으로는 구버전이 깨지지 않는다.** 예외는 (가) 클라우드 동기화로 일정을 받은 **같은 교사의 구버전 두 번째 기기**와 (나) 운영자 수동 결속 대상이며, 화면 문구로 안내한다.
3. 새 조회·수정은 엣지 함수 `consultation-teacher`·`survey-teacher`가 맡는다. **레거시 유예 판정에도 Google 토큰 검증 성공을 필수 조건으로 둔다.**
4. 소유자 없는 옛 일정의 유예 만료일은 **071 시점에 `min(2026-11-30, 마지막 상담일+30일)`으로 계산해 `legacy_grace_until`에 박는다**(스냅샷, 서버 시각 판정). 072에서 옛 권한을 회수한다.
5. 예약자 정보 암호화를 **일정별 난수 소금값(판 2)**으로 올리고, **판 구분은 암호문의 `v2:` 접두사로** 한다. 접두사가 없으면 판 1로 복호화한다. `crypto_version` 칸은 통계·감사용이다. 설문은 평문이라 대상이 아니다.

### 결정 동인

1. 학부모·학생이 겪는 동작은 하나도 바뀌면 안 된다.
2. Google 미연결 교사가 다수다. 즉시 전환은 불가능하다.
3. 각 단계에 명시적 롤백 절차가 있어야 한다.
4. 관리 키가 암호 열쇠·신분증·링크 값 세 역할을 겸해, 링크를 받은 사람이 같은 일정의 다른 예약을 읽을 수 있다.

### 검토한 대안

- **B. DB 함수 안에서 토큰 검증** — Google 호출량은 A안과 같다. 탈락 사유는 **그 부담과 실패 처리를 작은 운영 DB에 얹을 수 없다**는 것.
- **C. 링크용/관리용 열쇠 분리** — 배포된 링크가 깨지고 소유자 개념이 없어 재발.
- **D. 유예 없는 즉시 전환** — 상담주간에 다수 교사가 명단을 못 본다.
- **E. 현상 유지** — 위험이 남고 방침 서술과 어긋난다.
- **F. 일정별 종료만** — 완료 시점 미확정, 설문에 기준 없음. **혼합안+스냅샷으로 부분 채택.**
- **G. claim 계열(TOFU)** — 학부모 선점으로 교사가 영구 배제. **탈락.** 앱 창구 없는 **운영자 수동 결속**만 예외 허용(앱 버전 확인 선행).

### 선택 이유

A안은 세 동인을 모두 만족한다. 옛 RPC를 "소유자 있으면 거부"로 고치는 한 수로 **일정을 만든 기기에서는 구버전을 깨지 않으면서** 새 일정 보호가 배포 즉시 효력을 갖는다. `verifyGoogleIdentity`와 교무실 엣지 함수 8종이라는 검증된 부품·선례를 재사용하므로 새 Google 권한 요청이 없다. 유예 판정에 Google 토큰 검증을 필수로 둬서 링크만 가진 사람이 새 문으로도 못 들어온다. 유예 만료일을 스냅샷으로 박아 남은 anon 수정 권한으로 기한을 늘리는 길을 막았다. 암호화 판을 **값 단위**로 판정해, 옛 랜딩 번들이 만든 판 1 값을 신형 앱이 조용히 못 읽는 편도 결함을 구조적으로 없앴다.

### 결과

**좋아지는 것**

- 소유자가 정해진 일정은 그 계정으로만 열린다(옛 경로 포함).
- 링크만 가진 사람은 새 문으로도 못 들어온다.
- 일정 수정·마감·보관이 소유자만 가능해진다.
- 명단 조회 실패가 이유를 말하고, 자동 슬롯 차단이 조용히 멈추지 않는다.
- 앱이 안 쓰던 anon 권한과 잔류 정책이 즉시 정리된다.
- 새 일정은 일정마다 다른 소금값으로 암호화되고, 판 오인으로 인한 복호화 실패가 구조적으로 막힌다.

**감수하는 것**

- **새 일정·설문을 만들려면 Google 연결이 필요하다**(2주 실측 + 임계치 관문).
- **소유자 없는 옛 일정은 072 전까지 옛 경로로 계속 열린다.**
- **같은 교사의 구버전 두 번째 기기는 소유자 박힌 일정을 못 연다.**
- 매 조회마다 Google 계정 확인 호출이 일어난다(캐시·병합·주기로 완화). **캐시 5분 동안 철회된 토큰이 통과할 수 있다.**
- **캘린더 인증 상태에 종속된다.**
- 구버전 앱 일부가 072 이후 막힌다(실측·승인 필수).
- 유지할 것이 늘어난다(마이그레이션 2, 엣지 함수 2, 암호화 판 2종, 랜딩 2파일).

### 후속

- **운영자 수동 결속 절차 문서화** — 앱 창구 없이 오너가 본인 확인 후 소유자를 기입하며, **대상 교사의 앱 버전 확인이 선행 조건**이다. 다기기·옛 일정 구제의 유일한 탈출구.
- **복수 소유자(한 일정을 여러 계정이 열기)는 이번에 하지 않는다**(원칙 1). 수동 결속이 탈출구이며, 필요가 확인되면 별도 결정으로.
- **유예 종료 후 도달할 수 없게 된 옛 예약·응답 행의 보관 종료(파기) 정책**을 정한다. 아무도 못 읽는 개인정보를 무기한 두지 않는다.
- **옛 번들 잔존 감시** — "판 2 일정에서 접두사 없는 암호문을 만난 건수"를 지표로 두고, 0에 수렴하면 판 1 복호화 경로 정리를 검토한다.
- S6 완료 전까지 개인정보 처리 방침의 접근 통제 문구를 고치지 않는다.
- 관리 키 로테이션은 배포된 링크가 깨지므로 하지 않는다.
- 지난 상담 다시 보기(로컬 사본) 범위는 결정 3에 따른다.
- `not_connected` 거부가 계속 많으면 안내 위치·문구를 다시 손본다.
