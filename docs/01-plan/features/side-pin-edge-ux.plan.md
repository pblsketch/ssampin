## 1. 기능 개요

옆핀의 "잠깐 확인하고 닫는다"는 목적을 유지하면서, 여는 방법과 손잡이의 자리를 개선한다.

| #   | 기능                   | 한 줄 요약                                                                          |
| --- | ---------------------- | ----------------------------------------------------------------------------------- |
| A3  | **단축키 열기/닫기**   | 글로벌 단축키 한 번으로 옆핀을 열고 닫는다. 기존 단축키 체계에 합류한다.            |
| A1  | **손잡이 높이 슬롯**   | 손잡이를 화면 세로 8칸 중 원하는 칸에 두고 드래그로 옮긴다. 창은 하나 그대로다.     |
| A2  | **접힌 rail 클릭통과** | 접힌 상태에서는 손잡이 칩 부분만 클릭을 받고 나머지 투명 영역은 뚫고 지나가게 한다. |

구현 순서는 이 문서 순서대로: **A3 → A2 → A1**. 난이도 낮은 것부터 (아이디어 문서 우선순위 1위가 A3).

## 2. 사용자 가치

- **A3**: 글을 쓰다가 키보드만으로 메모를 꺼내 본다. 마우스를 화면 가장자리까지 보낼 필요가 없다.
- **A1**: 주로 쓰는 위젯이 화면 상단/하단에 있어도 손잡이를 그 근처로 옮겨 둔다. 마우스 이동 거리가 짧아진다.
- **A2**: 최대화한 창의 스크롤바가 화면 오른쪽 끝에 있어도 옆핀 때문에 누르지 못하는 일이 사라진다. v2.3.8 위젯 손잡이 사고("겹쳐 보이는 것보다 안 눌리는 게 컸다")와 같은 계열의 문제를 막는다.

## 4. Phase 구성

### Phase A3 — 단축키 열기/닫기 (가장 먼저)

**범위**

1. `Settings` 도메인: `QuickAddShortcutId`에 `'sidePin:toggle'` 추가, `DEFAULT_SHORTCUTS.bindings`에 `{ combo: 'mod+alt+p', enabled: true }` 추가.
2. `useGlobalShortcuts.ts`: `sidePin:toggle`은 sticker-picker와 같은 방식(메인 IPC 위임 + 렌더러 keydown 이중 경로, debounce 250ms)으로 처리. 단, **렌더러 keydown 경로는 메인 창이 포커스일 때만** 동작해야 한다 — 옆핀 패널 창이 포커스를 갖고 있을 때 메인 렌더러의 keydown은 오지 않으므로 자연히 해결된다.
3. 메인 프로세스: `syncShortcuts` IPC의 globalShortcut 등록에 `sidePin:toggle` 포함. 트리거 시 `sidePinService.dispatch({ type: 'shortcut-toggle' })`.
4. **보호 상태 가드**: `shortcut-toggle` 전이가 이미 `isSidePinResponsive`(enabled + protectedReason null)로 막고 있으므로 잠금·절전·전체화면 중에는 동작하지 않는다. 확인만 하면 된다.
5. **비활성 상태 동작**: 옆핀이 꺼져 있으면(`enabled: false`) 단축키는 아무 일도 하지 않는다(전이 규칙이 이미 무시한다). 단축키로 켜는 것은 범위 밖 — "켜는" 것은 설정이라는 제품 결정 유지.
6. ShortcutsTab: COMMANDS 목록에 "옆핀 열기/닫기" 행 추가 (아이콘: `view_sidebar`, 색: text-sp-accent).

**주의점**

- 충돌 검사: ShortcutsTab의 중복 검출이 자동으로 새 항목을 포함한다. `mod+alt+p`가 기존 6종과 겹치지 않음을 확인했다(t/e/m/n/b/e — p 없음).
- 이중 트리거: globalShortcut(OS 전역)과 렌더러 keydown(메인 창 포커스)이 같은 키로 동시에 잡힐 수 있다. sticker-picker의 250ms debounce 패턴을 그대로 따른다.

### Phase A2 — 접힌 rail 클릭통과

**목표**: 접힌 상태에서 rail 창의 **투명 영역이 클릭을 가로채지 않게** 한다.

**설계**

- Electron `setIgnoreMouseEvents(true, { forward: true })`를 쓴다. `forward: true`면 렌더러로 mouse-move 이벤트는 계속 오므로 호버 감지(칩 위)도 유지된다.
- **토글 지점은 메인의 pointer 폴링 루프**(`sidePinElectron.ts`의 50ms `syncPointerRegion`)에 둔다. 이미 실제 커서 좌표와 `resolveSidePinPointerRegion` 판정이 여기 있으므로, 판정 결과(`outside` vs `rail-widget`/`rail-memo`)에 따라 `setIgnoreMouseEvents`를 켜고 끈다:
  - 판정 = `rail-widget` 또는 `rail-memo` → `setIgnoreMouseEvents(false)` (칩 위, 클릭 받음)
  - 판정 = `outside` → `setIgnoreMouseEvents(true, { forward: true })` (뚫고 지나감)
- **패널 펼침 상태에서는 절대 클릭통과하지 않는다.** 패널 창 자체는 그대로 두고, rail 창이 숨는 구조이므로 자연히 해결된다. 레일이 살아있는 상태(surface: collapsed)에서만 적용.
- **파생 효과 확인 필요**: 클릭통과 상태에서는 칩 위로 마우스가 와도 OS가 칩에 이벤트를 주지 않는다. 단 `forward: true` + 50ms 폴링이 실제 커서 위치를 계속 보고 있으므로 칩 위 진입을 감지하면 즉시 `setIgnoreMouseEvents(false)`로 복귀 → 이후 클릭 가능. 폴링 간격(50ms) 안에서의 클릭 유실 가능성은 있다(칩 진입 후 0~50ms 사이 클릭). 수용한다 — 손잡이는 머무르고 여는 대상이지 즉시 클릭의 대상이 아니다.
- **레거시 창(단일 창 모드)은 건드리지 않는다.** `getSidePinRendererSurface`가 'legacy'를 돌려주는 옛 구성은 지원 범위 밖이되, 동작이 나빠지지 않게 토글 조건에 surface 기반 창 존재 확인을 넣는다.

### Phase A1 — 손잡이 높이 슬롯

**목표**: 손잡이 세로 위치를 8칸 슬롯 중 하나로 골라 두고, 손잡이 드래그로 옮긴다.

**설계**

1. **값 모델**: `railSlot: 0..7` (0=맨 위, 7=맨 아래). 절대 좌표가 아니라 **칸 번호**를 저장한다 — 모니터 구성·해상도가 바뀌어도 칸 번호는 유효하기 때문. 기본값 3 또는 4(현재의 "가운데"와 같은 위치).
2. **기기 전용 저장**: `SidePinDeviceState`에 `railSlot` 추가. **스키마 버전 1 유지 + optional 필드** — `normalizeSidePinDeviceState`가 없는 값(undefined)을 기본 슬롯으로 정규화하므로 마이그레이션 불필요. 도메인 정본(`src/domain/entities/SidePinDeviceState.ts`)과 electron 미러(`electron/sidePinDeviceState.ts`) **양쪽 모두** 수정 — mirror 테스트가 동치를 강제한다.
3. **위치 계산**: `sidePinGeometry.ts`의 `rightEdgeTab()`이 `area.y + railSlot × (area.height - rail높이) / 7` 형태로 y를 계산. `resolveSidePinLayout` 입력에 `railSlot` 추가. clamp: rail 높이(168)가 화면보다 큰 화면에서는 기존 동작 유지.
4. **드래그 UX**: rail 창은 `movable: false`라 OS 드래그가 안 된다. 대신:
   - rail 렌더러에서 칩 영역에 드래그 시작 감지(포인터다운 + 이동 임계값 4px)
   - 이동 중: 렌더러가 커서 화면 좌표를 IPC로 보내고, 메인이 그 y에서 슬롯 번호를 계산해 rail 창 위치를 즉시 옮긴다(`setPosition`만, 창 재생성 없음)
   - 드래그 종료: 확정된 `railSlot`를 `SidePinDeviceState`에 저장
   - 드래그 중에는 호버 펼침(reveal 예약)을 취소한다 — 드래그하다 패널이 펼쳐지면 손잡이를 놓친다. 전이 규칙에 드래그 중 펼침 금지 반영.
5. **패널 위치는 그대로**: 패널은 화면 오른쪽 전체 높이를 쓰는 구조를 유지한다(펼침 시 세로 위치가 바뀌면 열림 애니메이션 좌표가 흔들린다). 이는 아이디어 문서의 "단일 창 안의 배치값" 원칙과 일치한다.
6. **설정 UI**: Phase 1에서는 드래그만 둔다. 설정 패널의 슬롯 선택 UI는 사용자 피드백 후 추가 여부 결정 (안티-범위: 불필요한 설정 증식).

### 11.3 A1 재설계 — 끌기 전용 자리 분리 (사용자 지적으로 발견)

**문제.** 최초 A1 구현은 손잡이 아무 데나 눌러 끌 수 있게 했다. 그런데 손잡이에 커서가 닿는 순간 **180ms 펼침 예약**이 시작되고, 펼쳐지면 rail 창은 `hide()`된다(`sidePinWindow.ts:257`). 반면 끌기는 **눌러서 4px 이동한 뒤에야** 인식돼 예약을 취소했다. 결과:

1. 커서가 닿은 뒤 약 180ms 안에 "누르고 4px 움직이기"를 끝내야만 손잡이를 잡을 수 있었다. 사람이 마우스를 멈추고 버튼을 누르기까지 보통 200~400ms가 걸리므로 대부분 실패한다. 실패하면 **잡으려던 창이 손 밑에서 사라진다.**
2. 끌기를 마치고 손을 떼면 커서는 여전히 손잡이 위 → 다시 180ms 뒤 패널이 펼쳐졌다. 위치만 바꾸려 했는데 창이 열린다.

계획서 §4 A1-4에 "드래그 중에는 호버 펼침을 취소한다"고 적었지만, 구현이 **드래그가 시작된 뒤에야** 취소하도록 되어 있어 생긴 틈이다. 자동 테스트로는 잡히지 않는다(실제 창·타이머·커서가 필요).

**해결 — 여는 자리와 옮기는 자리를 나눈다.** 사용자 결정.

- 포인터 구역에 `'rail-grip'`을 새로 둔다. 위·아래 버튼(각 44 DIP, 손잡이 높이의 25%·75%) 사이에 남는 40 DIP 안에 **32 DIP 전용 자리**를 잡는다(`railGripTarget`).
- **`isPointerInsideSidePin('rail-grip') === false`** — 이 한 줄이 핵심이다. 손잡이 창 위인데도 "밖"으로 쳐서 펼침을 아예 예약하지 않는다. 위 문제 1과 2가 같은 규칙으로 함께 사라진다.
- 클릭 통과(`shouldIgnoreSidePinRailMouse`)는 `outside`에서만 켜지므로, 끌기 자리는 계속 마우스를 받는다.
- 화면에서는 `drag_indicator` 점 표시로 그리고 `cursor-grab`을 준다. 두 구역을 나누던 1px 선을 대신한다. **흐름에서 빼고 가운데에 겹쳐 둔다** — flex 높이를 차지하게 하면 버튼이 밀려 내려가, 메인이 커서로 판정하는 위치(25%·75%)와 화면에 그려진 위치가 어긋난다.
- 4px 임계값과 클릭 억제 로직은 없앴다. 끌기 자리는 여는 기능이 없어 구분할 필요가 없다.
- 버튼 슬롭(2 DIP)과 끌기 자리 슬롭이 맞닿는 한 줄에서는 **여는 쪽이 이긴다** — 옮기기보다 여는 일이 훨씬 잦다.
- 손잡이가 짧아 버튼 사이 여유가 없으면 `railGripTarget`이 `null`을 돌려주고 끌기 자리는 생기지 않는다.

**한계**: 끌기 자리는 마우스 전용이다(`aria-hidden`). rail 창은 `showInactive`로 띄워 포커스를 받지 않으므로 키보드로 도달할 수 없고, 초점을 못 받는 창에 초점 가능한 버튼을 두면 약속만 하고 못 지키는 꼴이라 일부러 버튼으로 만들지 않았다. 키보드로 손잡이 위치를 바꾸는 길이 필요하면 설정 UI 쪽에 두는 것이 맞다(현재 안티-범위).

**신규/수정 테스트 8건** — 끌기 자리 판정 5건(가운데·경계·가로 폭·슬롭 우선순위·짧은 손잡이), 렌더 3건(끌기 시작·**여는 버튼에서는 끌리지 않음**·표시 강조), 전이 2건(끌기 자리는 예약 안 함·버튼→끌기 자리 이동 시 예약 취소).

### 11.3.1 끌기 표시 되먹임 (실기기 1차 확인에서 나온 것)

**증상 보고**: "점 표시가 있긴 한데 클릭 후 드래그해도 아무 변화도 없어."

**진짜 원인은 코드가 아니었다.** 실행 중이던 앱이 08:58에 켠 것이고, 끌기 IPC는 09:58에 들어왔다. 화면은 Vite가 실시간으로 갈아 끼워 점 표시가 보였지만 **main·preload는 앱을 껐다 켜야 바뀐다**(`electron:dev`는 main을 watch하지 않는다). 그래서 `window.electronAPI.sidePin.startRailDrag`가 아직 없었고, 옵셔널 호출(`?.()`)이라 조용히 무시됐다.

> ⚠️ **이 계열 QA 전 필수 절차**: `node scripts/build-electron.mjs` → **앱 완전 종료 후 재시작**. 화면만 바뀌고 동작이 없으면 거의 항상 이것이다. 렌더러가 최신이라는 사실은 main이 최신이라는 증거가 **아니다**.

**함께 고친 진짜 결함**: 끌기를 시작하면 메인이 판정을 `outside`로 고정하는데(끌다가 패널이 펼쳐지는 것을 막으려고), 점 표시가 그 값을 그대로 보고 있어 **누르는 순간 색이 흐려졌다**. 손잡이는 8단계로만 움직여 화면 높이에 따라 한 칸이 100 DIP를 넘으므로, 조금 끌면 창은 그대로인데 표시까지 흐려져 "눌리지 않았다"로 읽힌다.

→ 끌고 있는지는 **화면이 직접 기억한다**(`useState`). 끄는 동안 점 표시는 강조색(`text-sp-accent`)을 유지한다. 메인의 판정값으로 자기 상태를 되읽지 않는다.

### 11.3.2 끌기 모델 재설계 — 끌 때는 따라오고, 놓을 때만 칸에 맞춘다

**증상 보고 3건** (실기기 재시작 후 첫 정상 동작에서): ①손잡이 이동 후 무조건 패널이 열림 ②이동이 잘 안 될 때가 있음 ③이동 후 패널이 열리는 경우가 있음.

**셋 다 원인이 하나다.** 끄는 동안에도 창을 8단계로 반올림해 옮기고 있었다. 작업 영역 1040 DIP 기준 한 칸이 **124 DIP**다. 그래서:

| 보고                  | 실제로 벌어진 일                                                                                                                                                                                                                   |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ② 이동이 잘 안 됨     | 62 DIP 넘게 끌어야 칸이 바뀐다. 그보다 짧게 끌면 창이 그대로다                                                                                                                                                                     |
| ①③ 놓으면 패널이 열림 | 놓는 순간 창이 칸 자리로 튀며 커서 밑에서 **최대 반 칸(62 DIP)** 빠져나간다. 손잡이는 위 버튼 20~64·끌기 자리 68~100·아래 버튼 104~148이므로, 남은 커서는 대개 **여는 버튼 위**가 된다 → 180ms 뒤 펼침. 우연이 아니라 기본값이었다 |
| ② 다음 끌기가 헛나감  | 같은 이유로 끌기 자리가 커서 밑에서 벗어나, 다시 누르면 여는 버튼이 눌린다                                                                                                                                                         |

**해결 두 가지.**

1. **끄는 동안에는 반올림하지 않는다.** `SidePinService.setRailTop`을 `setRailDragTop`(임시 자리) + `commitRailDrag`(놓을 때 칸에 맞춤)로 나눴다. `getLayout()`이 끌고 있는 동안에는 저장된 칸 대신 임시 자리를 돌려주므로 **창도 포인터 판정도 손을 그대로 따라온다.** 손이 멈춰 있으면 다시 옮기지 않는다(50ms마다 같은 자리로 재배치 방지). 화면 밖으로는 `clampSidePinRailTop`이 가둔다. 놓을 때는 칸이 그대로여도 **반드시 다시 배치한다** — 안 그러면 창이 칸과 어긋난 자리에 남아 다음에 켤 때 자리가 달라진다.
2. **놓은 직후에는 그 자리에서 펼치지 않는다.** `resolveSidePinHoverArm` 신규. 놓으면 무장을 풀고, 그동안 손잡이 위 판정은 전부 `rail-grip`으로 바꿔 돌려준다(= 펼침 예약 없음). **커서가 손잡이를 완전히 벗어나야 다시 무장한다.** 클릭 통과는 켜지지 않으므로 클릭으로 여는 길과 다시 끄는 길은 그대로 열려 있다. 패널이 열린 상태의 판정(`panel-*`)은 가로채지 않는다.

**이때 남겨 둔 성질**: 놓을 때 한 번은 칸으로 튄다(최대 62 DIP). "8단계 저장 모델에서는 피할 수 없다"고 판단했다. → **틀렸다. 바로 그 튐이 다음 라운드의 핵심 원인이었다(§11.3.3).** 저장 모델 자체를 바꾸면 되는 것을, 모델을 고정값으로 두고 그 위에서만 답을 찾은 것이 실수다.

**신규 테스트 11건** — 지오메트리 2(가두기·음수 좌표 모니터), 무장 4(평소·놓은 직후·벗어나면 재무장·패널 판정 보존), 서비스 5(따라오기·가두기·놓을 때 저장·같은 칸이면 저장 없이 되돌리기·끌지 않았는데 놓기).

원인 2·3은 교차 검토에서 지적받아 반영했다. 같은 검토에서 제안된 **"놓은 직후 200ms 클릭 통과 유예"는 넣지 않았다** — 그 타이머가 필요했던 이유가 원인 1(튐)이고, 튐을 없애면 판정 좌표와 실제 창이 어긋날 구간 자체가 사라진다. 원인을 지운 자리에 타이머를 덧대면 다음 결함을 가린다.

**저장 이관**: `railSlot`으로 저장된 개발본은 `railSlot/7`로 옮겨 같은 자리를 가리키게 한다(도메인·electron 미러 양쪽). 출시 후에는 지워도 된다.

### 11.4 남은 확인 (실기기 수동)

**먼저 `npm run build:electron` 후 앱을 완전히 껐다 켠다** (§11.3.1). `electron/`은 `npx tsc --noEmit` 검사 대상이 아니고 Electron 런타임 동작은 자동 테스트로 덮이지 않는다. 다음은 실제 Windows에서 눈으로 확인해야 한다.

1. **A3** — 다른 앱에 포커스가 있을 때 `Ctrl+Alt+P`로 옆핀이 열리는가. 잠금 화면 복귀 직후에는 동작하지 않는가.
2. **A3 후속** — 설정에서 키를 바꾸는 중에 그 키가 먼저 실행되지 않는가. 등록 실패 시 토스트가 뜨는가. 단축키를 바꾼 뒤에도 위젯·모달의 다른 전역 키가 그대로 동작하는가(문제 1의 회귀 확인).
3. **A2** — 최대화한 창의 스크롤바가 손잡이 뒤에 있을 때 눌리는가. 칩 위 호버 180ms에 패널이 펼쳐지는가.
4. **A1 끌기** — 끌기 자리(가운데 점 표시)에 커서를 올려도 패널이 열리지 않는가. 누르면 점 표시가 강조색으로 바뀌는가. **끄는 동안 창이 손을 1:1로 따라오는가**(조금만 끌어도 움직여야 한다). **놓아도 창이 튀지 않는가**(§11.3.3 원인 1). **연속으로 대여섯 번 끌어도 계속 되는가** — 이번 보고의 핵심이다. 손을 뗀 뒤에도 패널이 열리지 않는가.
5. **A1 가장자리** — 마우스를 **화면 맨 오른쪽 끝까지 밀어붙인 상태**에서도 끌기와 클릭이 되는가(§11.3.3 원인 3).
6. **A1 저장** — 앱을 껐다 켜도 놓았던 그 자리에 있는가. 배율이 다른 모니터, 해상도를 바꾼 뒤에도 화면 밖으로 나가지 않는가.
7. **A1 시인성** — 32 DIP 점 표시가 손잡이 폭 30~52 DIP 안에서 알아볼 만한가. 여는 버튼 두 개와 헷갈리지 않는가.
