## 1. 왜 하는가

새 기능이 아니라 **빚 갚기다.** 기획서가 1차 포함으로 약속한 두 항목이 옆핀에만 빠져 있었다.

- 본체 메모에는 글자 크기(`Memo.fontSize`)와 이미지 첨부(`Memo.image`)가 이미 있다.
- 옆핀 메모 편집기에는 둘 다 없었다. 색상 4종과 텍스트 편집이 전부였다.
- **목록은 "이미지 있음" 표시까지 이미 그리고 있었다**(`SelectSidePinMemos.ts:95`, `SidePinMemoList.tsx:100`). 즉 본체에서 그림을 붙인 메모를 옆핀 목록에서 알아볼 수는 있는데, 열어도 볼 수가 없는 상태였다.

값은 `Memo`에 이미 있으므로 **저장 구조를 건드리지 않는다.** 본체에서 바꾼 크기가 옆핀에도, 옆핀에서 바꾼 크기가 본체에도 그대로 간다. 복제본을 만들지 않는다는 기획서 §1-2를 그대로 지킨다.

## 2. 사용자 가치

- **글자 크기**: 옆핀은 화면 가장자리에 붙는 좁은 창이라 본문이 작게 느껴진다. 수업 중 멀리서 흘깃 보는 자리라 크게 키울 수 있어야 한다.
- **이미지**: 칠판 사진·안내문 캡처를 메모에 붙여 두고 수업 중 옆핀에서 바로 꺼내 본다. 지금은 본체 창을 열어야만 볼 수 있다.

## 3. 화면 설계와 그 근거

### 3.1 도구 줄을 한 줄로 유지한다

기존 줄은 `[← 목록] [저장 중…] [색상 4개] [🗑]`로 이미 꽉 차 보였다. 그래서 처음에는 팝오버로 접는 안을 생각했으나, **실제로 재어 보니 자리가 남았다.**

| 요소                              | 폭(px, 대략) |
| --------------------------------- | ------------ |
| 목록 버튼                         | 54           |
| 색상 4개                          | 76           |
| 삭제                              | 28           |
| 사이 간격                         | 12           |
| **고정 합계**                     | **170**      |
| 가용 폭 (최소 360 − 좌우 여백 16) | **344**      |

아이콘 버튼 2개(28×2 + 간격 8 = 64)를 더해도 234로, "저장 중…"(약 44)까지 들어간다. **자리가 있는데 팝오버로 접으면 클릭이 한 번 늘고, "잠깐 적고 닫는" 자리에서는 그 한 번이 크다.**

최종: `[← 목록] [저장 중…] [Aa] [🖼] [색상 4개] [🗑]`

### 3.2 글자 크기만 펼침 줄로 뺀다

고를 것이 넷(작게·기본·크게·아주 크게)이라 한 줄에 다 못 넣는다. 그래서 `Aa` 버튼을 누르면 **머리말 아래로 줄이 펴진다.**

순환 버튼(누를 때마다 다음 단계)도 검토했으나 기각했다 — 4단계라 한 단계 되돌리려면 세 번 더 눌러야 하고, 지금 몇 단계인지 눈에 안 보인다.

**이 패널이 이미 쓰는 언어를 따랐다**: 삭제 확인도, `SidePinAppearancePopover`도 띄우지 않고 줄을 편다. 옆핀은 좁고 항상 위에 떠 있어서 그 위에 창을 하나 더 얹으면 어디를 눌러야 할지 알기 어렵다.

### 3.3 이미지는 제자리에서 키운다

본체 메모는 눌러서 원본 크기 뷰어(`MemoImageViewer`)를 띄운다. **옆핀에서는 같은 이유로 하지 않았다.** 대신 썸네일을 누르면 그 자리에서 120px → 260px로 커지고(`object-cover` → `object-contain`), 다시 누르면 접힌다.

## 4. 가장 큰 함정 — 파일 선택 창을 여는 동안 패널이 접힌다

옆핀은 **마우스가 벗어나면 접히는 창**이다. 이미지를 넣으려고 파일 대화상자를 열면:

1. 옆핀 창이 포커스를 잃는다.
2. 마우스가 대화상자 쪽으로 가면서 패널 밖으로 나간다.
3. 패널이 접힌다 → 고른 그림이 붙을 자리가 사라진다.

기존 장치를 그대로 쓴다. `MemoEditorActivity`가 `'idle'`이 아니면 접힘이 막히므로(`isEditorBusy`, `resolveSidePinTransition.ts:167`), 대화상자를 여는 순간 `'dialog-open'`을 건다. 삭제 확인 줄이 쓰던 것과 같은 값이다.

**푸는 쪽이 더 까다롭다.** 취소에는 이벤트가 없다.

| 상황       | 오는 신호                   | 처리                                                              |
| ---------- | --------------------------- | ----------------------------------------------------------------- |
| 고름       | `focus` → 그 다음 `change`  | `change`에서 붙이기 시작하며 `saving`으로 이어 받는다             |
| 취소       | `focus`만, `change`는 빈 값 | `change`(빈 값)에서 바로 풀고, 못 받으면 `focus`가 받는다         |
| 둘 다 유실 | —                           | `focus` 후 400ms(`SIDE_PIN_IMAGE_PICKER_GRACE_MS`) 뒤 강제로 푼다 |

**`focus`에서 곧바로 풀면 안 된다.** `focus`가 `change`보다 먼저 오기 때문에, 즉시 풀면 그 틈에 패널이 접혀 이미 고른 그림이 붙지 못한다. 그래서 한 박자 늦춘다.

> ⚠️ 이 400ms는 **jsdom 테스트로는 검증되지 않는다.** 실제 Windows 파일 대화상자의 focus/change 순서와 시차는 실기기에서 봐야 한다(§7).

## 7. 남은 확인 (실기기 수동)

`electron/`은 건드리지 않았으므로 재빌드는 필요 없다. 다만 **파일 대화상자는 jsdom으로 덮이지 않는 영역**이라 실제 Windows에서 봐야 한다.

1. **접힘 방지** — 이미지 버튼을 누르고 파일 대화상자를 **10초 이상 열어 둔 채** 마우스를 화면 반대편으로 옮겨도 옆핀이 접히지 않는가.
2. **고르기** — 그림을 고르면 대화상자가 닫히는 동안 패널이 접히지 않고 그림이 붙는가 (§4의 focus→change 시차).
3. **취소** — 취소로 닫으면 옆핀이 **정상적으로 다시 접히는가**. 영영 안 접히면 400ms 해제가 안 걸린 것이다.
4. **글자 크기** — 옆핀에서 바꾼 크기가 본체 메모 화면에도 반영되는가. 그 반대도 되는가.
5. **이미지 펼침** — 260px로 키웠을 때 좁은 패널에서 알아볼 만한가. 글 쓰는 칸이 지나치게 눌리지 않는가.
6. **오류 안내** — PDF 등 그림이 아닌 파일을 고르면 안내가 뜨는가. 5MB 넘는 사진은 어떤가.
7. **보호 상태** — 화면 잠금 중에는 첨부한 그림이 옆핀에 보이지 않는가.

## 8. 메모 검색 (B1 저비용 대안)

### 8.1 왜 검색인가

B1(고정 메모 우선)의 목적은 "자주 쓰는 메모를 빨리 찾는다"였는데, 고정 기능은 **메모 데이터에 항목을 새로 만들어야 한다**(§3-B1 정정). 검색은 같은 목적을 **데이터 추가 0으로** 이룬다.

`SidePinPreferences.memoSort`는 이미 있지만 **선언만 되고 아무도 읽지 않는 죽은 필드**다(`'recent'` 하나뿐). 검색은 정렬이 아니라 거르기라 이 필드를 건드리지 않았다.

### 8.2 정한 것과 그 근거

| 결정                                       | 근거                                                                                             |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------ |
| **본문 전체**를 찾는다 (첫 줄만이 아니라)  | 찾는 말이 아래쪽에 있다고 안 나오면, 있는 메모를 없다고 말하는 셈이다                            |
| 걸린 줄을 **미리보기로 보여준다**          | 둘째·셋째 줄을 그대로 보여주면 찾는 말이 안 보이는 결과가 떠서 "이건 왜 나왔지"가 된다           |
| 메모 **5개 미만이면 검색 칸을 안 띄운다**  | 그 정도는 훑는 게 빠르다. 단 이미 찾는 중이면 결과가 줄어도 칸을 유지한다 — 지울 방법이 없어진다 |
| 새 메모를 만들면 **찾던 말을 지운다**      | 안 지우면 방금 만든 빈 메모가 그 말에 안 걸려 목록에서 사라진다                                  |
| 결과 없음은 **"첫 메모 쓰기"와 다른 말**로 | 메모는 있는데 없다고 말하면, 지우면 나온다는 걸 알 길이 없다                                     |
| 거르기는 `selectSidePinMemos`에서          | 조회 규칙의 정본이 이미 거기다. 화면이 따로 거르면 규칙이 두 곳으로 갈라진다                     |

### 8.3 함정 둘

**① 검색 칸도 "쓰는 중"이다.** 옆핀은 마우스가 벗어나면 접히는데, 키보드로 찾는 말을 치는 동안 마우스는 대개 딴 데 있다. **메모 본문과 똑같은 문제**라 똑같이 막았다 — 검색 칸에 포커스가 있으면 `'editing'`. 손을 떼면(`blur`) 푼다. §4의 파일 대화상자와 함께, 이 패널에서 **"접힘"이 세 번째로 문제가 된 자리**다.

**② 잠금 상태에서 검색을 걸면 개수로 내용이 샌다.** `selectSidePinMemos`는 잠기면 내용을 아예 만들지 않는데, **거르기까지 해 주면 남은 개수가 "그 낱말이 든 메모 수"가 된다.** 가리는 것과 세는 것을 함께 막아야 가린 것이 된다 → 잠기면 검색어를 **무시**하고, 화면에서도 검색 칸을 내린다.

### 8.6 남은 확인 (실기기)

1. 찾는 말을 치는 동안 **마우스를 패널 밖으로 빼도 접히지 않는가**. 다 치고 마우스를 움직이면 정상적으로 접히는가.
2. 한글 입력 중(조합 중)에도 검색이 자연스러운가 — 자모가 조합되는 동안 결과가 튀지 않는가.
3. 메모가 수십 개일 때 타자마다 걸러도 버벅이지 않는가.

## 9. 하지 않은 것

- **붙여넣기(Ctrl+V)·끌어다 놓기**: 발견성이 없어 교사 대상 앱에서는 버튼이 먼저다. 나중에 덧붙일 수 있다.
- **원본 크기 뷰어**: 좁고 항상 위에 뜨는 창에 모달을 얹지 않는다(§3.3).
- **목록에서의 글자 크기 반영**: 목록은 훑는 자리라 항목 높이가 들쭉날쭉하면 찾기 어려워진다. 편집기에만 적용한다.
- **고정(pinned) 메모**: 데이터 구조 변경이 필요해 미뤘다(§3-B1). 검색으로 같은 목적을 먼저 덮는다.
- **초성 검색·유사어**: 좁은 보조 화면에 맞지 않는 복잡도다. 단순 포함 검색으로 충분한지 실사용에서 본다.
- **`memoSort` 되살리기**: 검색은 정렬이 아니라 거르기다. 죽은 필드는 정렬 기능을 실제로 할 때 함께 정리한다.
