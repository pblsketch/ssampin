## 2. Principles (원칙)

1. **틀린 짝짓기는 침묵하지 않는다.** 사진↔이름이 어긋날 여지가 있으면 추측해서 넘기지 않는다. 교사가 남의 얼굴로 이름을 외우는 사고는 어떤 편의보다 비싸다.
2. **학생 얼굴은 교사 화면 안에서만 산다.** "지금은 안 뜬다"가 아니라 **"뜨게 만들 수 없다"**가 목표다. 관습이 아니라 빌드 게이트로 강제한다.
3. **새로 짓지 않는다.** 명단 병합·바이너리 저장·파싱 디렉터리는 이미 있다. 형제 디렉터리를 새로 만들지 않는다.
4. **사진은 부가가치이지 전제조건이 아니다.** 사진 0장이어도 가져오기→학습→결과 전 경로가 정상 동작한다.
5. **한 세션 = 한 Phase.** Phase 경계는 "여기서 멈춰도 앱이 정상이고 사용자에게 설명 가능한 가치가 남는가"로 정한다.

### 3.3 지원 포맷 — 실물 검증 결과 (2026-08-19)

**⚠️ `.hwp` 확장자에 서로 다른 두 포맷이 들어온다. 확장자로 판단하지 말고 매직 바이트로 판별할 것.**

### 3.4 O2·O3 확정으로 **필수가 된 대가** (생략 불가)

Architect가 반대한 이유가 사라진 게 아니라, **비용을 우리가 떠안기로 한 것**이다. 아래는 옵션이 아니라 완료 조건이다.

1. **드라이브 파일 단위 삭제 기능을 새로 만든다.** — 현재 `IDriveSyncPort`에는 `deleteSyncFolder(folderId)`뿐이고 **파일 하나를 지우는 수단이 없다**(코드 확인 완료). 이대로 모바일에 사진을 뿌리면 "사진을 지웠습니다"가 거짓말이 되어 **개인정보 처리방침 위반**이 된다. `GoogleDriveClient.trashFile`이 이미 있으므로 포트에 `deleteSyncFile`을 뚫어 배관만 이으면 된다.
2. **모바일에도 삭제 UI를 둔다.** 데스크톱 설정에만 두면 폰 분실 시 지울 방법이 없다.
3. **동기화 실패 격리를 구현한다.** — 현재 `SyncToCloud.ts` 바이너리 루프는 항목별 try/catch 없이 `throw`한다(코드 확인 완료). 사진 1장 실패가 **출결·기록 등 무관한 도메인 동기화까지 중단**시킨다. 사진을 얹기 전에 이걸 먼저 고쳐야 한다.
4. **iOS 스토리지 소멸 대비.** iOS Safari는 7일 미사용 시 저장소를 정리한다 → 방학 지나면 사진이 사라진다. `navigator.storage.persist()` 요청 + 사라졌을 때 재다운로드 경로가 필요하다.
5. **국외이전 고지.** 드라이브 동기화 = 교사 개인 구글 계정(국외 서버)에 얼굴 사진 보관. 개인정보 문서에 **사실 그대로** 적는다. (과거 서식 문구와 실제가 어긋난 전례가 있다 — 홍보 문구를 옮기지 말 것.) **동기화가 기본 켬으로 확정(2026-08-19)됐으므로 이 고지는 전체 사용자 대상이다.**

## 4. 검산 규칙 — D1의 유일한 방어선

### 4.1 규칙 (포맷 무관 공통)

> **좌표 격자 복원 + 전단사(bijection) 성립. 둘 중 하나라도 깨지면 자동 짝짓기를 포기하고 수동 보정 화면으로 강등한다.**

- **전단사**: 모든 사진이 서로 다른 이름 1개에 정확히 매핑되고, 매핑되지 않은 사진이 0장, 사진 2장이 같은 이름을 가리키지 않는다.
- **위치 기반이 기본. 순서 기반은 최후 수단.** 포맷별 좌표원(座標源)은 아래와 같고, **셋 다 좌표를 제공하므로 순서 기반은 구형 `.hwp`에만 남는다.**
  - `.xlsx` — anchor `(row r, col c)` → 이름 `(r+1, 같은 col)`. 병합 셀은 **좌상단으로 정규화**. (실증 완료)
  - `.hwp`(HWPML) — 사진이 표 밖 떠 있는 개체이므로 `<POSITION VertOffset/HorzOffset>`로 **격자를 복원**한다: VertOffset으로 행 묶기 → 각 행 내 HorzOffset 오름차순 = 읽기 순서. 그 순서를 이름 표의 `(RowAddr, ColAddr)` 순서와 맞춘다. (8·8·6 실증 완료)
  - `.xls` — client anchor 셀 좌표.
- **행·열은 하드코딩하지 않는다.** 2019 양식본과 2026 실물의 격자가 우연히 같았지만(§3.3), 28명 반이면 4번째 블록이 생긴다. 사진 좌표에서 행 묶음을 **탐지**하고, 이름 행은 "사진 행 + 1"로 **유도**한다.
- ⚠️ **초판의 "인터리브 블록 검산"은 폐기한다.** HWPML은 사진 22장이 문서 앞쪽에 **한 덩어리로 몰려 있고** 이름과 교차하지 않는다(실측). 구형 OLE2 `.hwp`에만 성립하는 규칙이었다.
- **실패 시 동작**: 사진을 버리고 이름만 반영 — 이 아니라 **수동 보정 화면으로 강등**한다(A′에서 채택). 사용자는 "사진 못 가져옴"이 아니라 "직접 맞춰 주세요"를 받는다. P1을 지키면서 기능이 죽지 않는다.
- **사유 코드**: `PHOTO_ANCHOR_MISMATCH` / `PHOTO_COUNT_MISMATCH` / `PHOTO_DUPLICATE_ANCHOR` / `PHOTO_GRID_MISMATCH` / `NO_DRAWING_RECORDS` / `UNSUPPORTED_FORMAT`. **베타 사용자가 사유 코드만 알려 줘도 원인이 특정돼야 한다.**

### 4.2 왜 "개수 일치"만으로는 안 되는가 (반례)

- **로고 반례(한글)** — `binItemID`는 `DocInfo`의 **전역 인덱스**라 학교 로고·직인도 같은 번호 공간을 쓴다. 로고 1장 + 전학생 사진 1장 누락이면 `23 − 1 = 22 == 22`로 **개수 검산을 통과하면서 전원 한 칸 밀린다.** 실물 파일에서 1:1이 확인된 건 *그 파일에 로고가 없었다*는 뜻일 뿐이다(n=1).
- **병합 셀 반례(엑셀)** — 확보한 양식본에 `MERGECELLS`가 있다. 이름 셀이 병합이면 열 집합이 넓어져 **부분집합 검사가 사실상 항상 통과**한다.
- **행 하드코딩 반례** — 이름 행을 8/11/14로 고정하면 28명 반에서 이름 22명 + 사진 28장이 되어 6명이 조용히 사라진다.

### 4.3 사람 확인 화면은 "확인 가능한 것"만 묻는다

"사진과 이름이 맞습니까?" 체크박스는 **원리적으로 무력하다** — 교사는 아직 얼굴을 모르고, 그게 이 기능을 쓰는 이유다. 대신:

- 교사가 실제 판별 가능한 것만 묻는다: **"학생 수 22명이 맞습니까?"**, **"1번이 `고재우`가 맞습니까?"**(명렬표 첫 줄만 대조)
- 학습 모드 안에 **"이 사진, 이름이 다른 것 같아요" 신고·정정 버튼**을 둔다. 사후 정정 경로가 사전 체크박스보다 실효가 크다.

## 5. Pre-mortem — 6개월 뒤 실패했다면

### S1. "선생님이 3주 동안 남의 얼굴을 외웠다"

사진 1장 누락 또는 로고 1장 혼입으로 짝이 밀렸는데 경고가 없었다. → **방어**: §4 좌표 격자 복원 + 전단사 검산, 탐지 기반 행/열, 수동 보정 강등, 학습 화면 내 정정 버튼.

### S2. "사진 넣은 뒤로 동기화가 이상해졌다"

사진 1장 업로드 실패가 사이클 전체를 예외로 떨어뜨려 **출결·기록까지 멈췄다.** → **이건 가정이 아니라 현재 코드의 실제 동작이다**(`SyncToCloud.ts` 바이너리 루프에 항목별 try/catch 없음, 확인 완료). **방어**: §3.4-3 실패 격리 선행, 일부러 1장 실패시켜 타 도메인 완료를 **테스트로 증명**. 항목 수 폭증(담임 22 + 수업반 8×25 ≈ 220)은 **반 단위 묶음**(`student-photos/{ownerKey}.pack`)으로 220 → 9로 억제. 사진은 학기 초 1회 입력 후 거의 불변이라 교환이 유리하다.

### S3. "학생 얼굴이 교실 화면에 떴다"

다른 세션이 위젯에 자리배치 미리보기를 붙이며 같은 카드 컴포넌트를 재사용했고, 사진 표시가 기본 ON이었다. → **방어**: §6 3단 차단. 그리고 **차단은 Phase 5가 아니라 렌더가 생기는 Phase 4와 같은 작업 단위**여야 한다.

## 6. 학생 노출 차단 — 3단 방어

`surface` prop 규약과 심볼 grep만으로는 **우회된다**(prop 위조 가능, 이미 만들어진 objectURL을 prop으로 넘기면 grep이 못 봄, 위반 시 행동이 "화이트리스트에 추가"가 됨).

- **Tier 1 — 원리적 불가**: `scripts/check-bundle-isolation.mjs`의 `NEEDLE`을 **배열화**하고 `student-photos`·`StudentPhotoRepository`를 추가해 `dist-student`(+ 발표 공유 경로)에 two-way 단언. 학생 SPA는 사진 코드를 **물리적으로 담지 않는다**.
- **Tier 2 — import 그래프 도달성**: 위젯·옆핀은 교사 번들을 공유하므로 번들 격리가 안 된다. `src/widgets/**`·`src/sidepin-main.tsx`에서 `IStudentPhotoRepository`/`useStudentPhotoStore`/`readBinary('student-photos'` 로의 **정적 import 경로가 존재하지 않음**을 단언. 사진 바이트의 **유일한 관문은 리포지토리**이므로 관문을 막으면 prop 우회가 봉쇄된다.
- **Tier 3 — grep 화이트리스트**: 보조로 유지(사람이 읽는 문서 역할).

## 7. Phase 분할

> 각 Phase는 그 자체로 멈춰도 되는 지점이다. 검증 게이트 4종 = `npx tsc --noEmit` → `npm run lint` → `npm run test` → `npm run regression-check`.
> ⚠️ 게이트 4종 중 `electron/`을 보는 건 `npm run test`뿐이다. electron 수정 시 `npx tsc -p tsconfig.electron.json --noEmit` + `npx eslint <파일>` 별도 실행.
> ⚠️ 다른 세션이 `electron/main.ts`·`desktopWidgetBounds.ts`·`screenBoundsClamp.ts` 등 7개 파일 수정 중 — **이 계획은 그 파일들을 건드리지 않는다.** 커밋은 항상 명시 path.

### Phase 0 — 지금 있는 이름 학습 모드부터 고치기

> **무엇을**: 사진과 무관하게 지금도 발생 중인 퀴즈 버그를 고치고 결과 요약을 붙인다. **왜**: 여기서 멈춰도 출시 가능한 가치가 남고, 사진을 얹으면 이 혼란이 더 커진다.

- `NameLearningMode.tsx` quiz 채점 대상 불일치 수정 — `handleCardClick`의 `seatList[index]`(항상 참) → **`seatList[currentIndex]`**
- 마지막 문제 후 **결과 요약 화면** 추가 (`remaining.length === 0` 처리)
  - ⚠️ `recordAnswer`가 `answers` 클로저를 읽어 마지막 판정이 한 틱 늦는다 → **함수형 업데이트 안에서 다음 문제를 결정**하거나 `useEffect`로 분리. 안 고치면 "마지막 1명이 안 나옴"이 생긴다.
- 퀴즈 첫 문제 랜덤화 — ⚠️ `currentIndex`를 `sequential` 모드가 **공유**한다. 무조건 랜덤 초기화하면 순서 모드가 3번 학생부터 시작한다 → **모드 진입 시점에 모드별 초기화**
- 담임 화면 진입점을 `⋯` 더보기 밖 툴바로 노출 (`Seating.tsx`)
- 모드 이름 정리: `자유 · 순서 · 맞혀보기 · 이름 쓰기`
- **완료 기준**: 하이라이트 아닌 카드 클릭이 무반응임을 단언하는 회귀 테스트가 **수정 전 코드에서 실패**함을 실증 / 결과 요약 DOM 단언 / 게이트 4종

### Phase 1 — 파일에서 이름과 사진을 읽어 내는 부품 (UI 없음)

> **무엇을**: 최신 한글(XML)·엑셀 파일을 해석해 (번호, 이름, 사진) 목록으로 바꾸는 순수 부품. **왜**: 화면보다 먼저 "제대로 읽히는가"를 확정해야 한다.

- **형식 판별을 매직 바이트로 한다** — `.hwp` 확장자에 **OLE2와 HWPML(XML) 두 포맷이 온다**(§3.3). `D0CF11E0`=OLE2, `EFBBBF3C3F786D6C`(BOM+`<?xml`)=HWPML, `504B`=zip(.xlsx/.hwpx). 확장자 신뢰 금지.
- **지원 범위는 최신 2종뿐이다(§3.3) — HWPML `.hwp` + `.xlsx`.** 둘 다 실물 검증을 마쳤고 **새 런타임 의존성이 0개**다: HWPML은 평문 XML+base64라 압축 해제가 필요 없고, `.xlsx`는 기존 `exceljs@4.4.0`이 압축 해제·이미지 추출을 모두 처리한다.
  - ✅ **이로써 초판의 압축 해제 블로커(렌더러에 `node:zlib` 없음)가 소멸한다.** `fflate` 승격도 불필요.
- **미지원 형식은 조용히 실패하지 말고 안내로 강등한다** — 구형 OLE2 `.hwp`·`.xls`·`.hwpx`를 만나면 형식을 정확히 식별해 **"나이스에서 최신 형식으로 다시 받아 주세요"**로 안내한다. "열 수 없는 파일"이 아니라 **무엇을 어떻게 하면 되는지**를 말할 것.
- 배치: **기존 `src/infrastructure/parse/`에 넣는다.** 새 `parsers/` 형제 디렉터리 금지(P3). 형식 판별은 `sheetGrid.ts`의 `.xlsx→HTML 폴백` 로직과 중복 구현하지 말 것.
- `src/domain/ports/IRosterParserPort.ts` **신설** — `usecases`가 파서를 직접 import하면 레이어 위반인데 **eslint가 `warn`으로만 잡아 게이트가 막아 주지 않는다**(기존 위반 57건 누적, 확인 완료). DI 주입 필수.
- 순수 짝짓기·검산은 `domain/`에 (`rosterPairing`)
- ⚠️ **`domain/`의 npm import 금지는 기계 검증되지 않는다** — eslint domain 규칙은 레이어 별칭만 막고 npm 패키지는 안 막는다(확인 완료). **메타 테스트로 못 박을 것**(`src/domain/**`의 모든 import가 상대경로 또는 `@domain/*`인지 단언)
- **완료 기준**: §4 검산 규칙 유닛 테스트 전 케이스 통과(정상/사진1장누락/로고혼입/좌표격자 불일치/중복anchor/사진0/이름0/사진>이름) / **미지원 형식 4종이 각각 올바른 안내로 강등되는지** / 실물 2종 골든 테스트 22쌍 1:1 / 게이트 4종

### Phase 2a — 사진 로컬 저장 (동기화 없음)

> **무엇을**: 사진을 이 PC에만 저장한다. **왜**: 클라우드로 나가기 전은 전부 되돌릴 수 있다. 되돌리기 비싼 건 업로드부터다.

- 저장 키는 **`Student.id`(불변)** — ❌ `studentKey`/학번 금지. 학번은 변경·전학·학년도 전환 때 **다른 학생을 가리킨다**(이 프로젝트에 "담임 출결 학번 뭉개짐" 사고 전례 있음). 선례 `obs-attachments/{id}.{ext}`도 불변 id를 쓴다.
- 리사이즈: 긴 변 320px, JPEG 0.8, 장당 상한 80KB. ⚠️ **업스케일 금지** — `min(원본 긴 변, 320)`
- `IStoragePort.writeBinary/readBinary` 사용 (모바일 IndexedDB 포함 4종 구현 완료 — 어댑터 추가 불필요)
- 반별 일괄 삭제 경로 **선구현**
- **완료 기준**: 저장→읽기 왕복 / 반별 삭제 후 잔여 0 / 게이트 4종. **여기서 멈추면 "사진이 이 PC에만 있는 상태"로 완결된다.**

### Phase 3 — 가져오기 화면

> **무엇을**: 파일을 고르고, 결과를 눈으로 확인하고, 명단에 반영한다. **왜**: 부품이 실제로 쓰이는 첫 지점.

- ⛔ **기존 명단 가져오기 파이프라인을 재사용한다**(P3). `rosterImportRules`(`ImportReadyStudent`) → `rosterImportPlan`(`planImport`) → `ConflictResolveModal` → `applyImportPlan`. **병합 규칙을 새로 만들지 말 것** — 두 벌이 되면 유지보수가 갈라진다. (3개 파일 모두 실존 확인)
- 사진은 **최종 id 확정 이후**에 붙는 사이드채널. ⚠️ `applyImportPlan`의 `addNew` 분기는 **새 `Student.id`를 발급**한다 → 저장은 반드시 그 뒤.
- 검산 실패 시 **수동 보정 화면**(§4.1) — 사진 누락 학생 개별 첨부 포함(기각한 Option C의 폴백 흡수)
- 사진 없는 엑셀 안내: "사진 명렬표가 맞는데 사진이 들어 있지 않아요. 나이스에서 **한글(hwp)** 형식으로 받으시면 사진까지 들어옵니다. 지금은 이름만 가져올게요."
- 자리배치 없이 **명단만으로 열리는 입구** 신설
- **완료 기준**: 4형식 각각 가져오기→명단 반영 통합 테스트 / 검산 실패 시 보정 화면 진입 / 게이트 4종

### Phase 4 — 사진 학습 모드 + "이름 쓰기" + 노출 차단

> **무엇을**: 얼굴을 띄우고 이름을 맞히게 한다. 동시에 학생 화면에 못 뜨게 막는다. **왜**: 렌더가 생기는 순간 차단도 같이 생겨야 한다(S3).

- `LearningCard`에 사진 표시 — **사진 모드에서는 학번을 가린다**(학번이 보이면 얼굴을 안 보고 맞힌다)
- **"이름 쓰기"(주관식)** 모드: 사진 1장 → 이름 입력 → 자동 채점 → 결과 요약
  - 공백 제거 후 비교, **완전 일치만 정답**
  - **재시도·부분점수 없음** — 틀리면 바로 오답 처리하고 정답을 보여 준다(오너 확정). `김민수`/`김민서`가 한 반에 공존할 수 있어 유사도 인정은 애초에 위험하고, 규칙이 단순할수록 학습 신호가 정확하다.
  - 같은 반 동명이인은 양방향 정답
  - 힌트: 초성 보기 / "모르겠어요"(오답 기록 후 넘김)
  - 한 바퀴 후 **틀린 학생만 재출제**
  - ⚠️ **한글 IME**: 조합 확정 Enter가 제출로 새지 않게 `compositionstart`/`compositionend` 처리. **jsdom으로 완전 검증 불가 → 실기기 필수**
- **§6 Tier 1 + Tier 2 차단을 이 Phase 안에서 구현**
- ⚠️ UI 작업은 frontend-design 에이전트 협업 의무. `sp-*` 토큰만, 하드코딩 HEX 금지, `rounded-sp-*` 금지
- ⚠️ objectURL 언마운트 시 `URL.revokeObjectURL`
- **완료 기준**: 사진 모드 앞면에 학번·이름 DOM 부재 단언 / 채점 규칙 유닛 전 케이스 / **번들 격리 게이트가 사진 심볼에 대해 실제로 빨간불** / 게이트 4종

## 10. ADR — 사진 명렬표 기반 얼굴-이름 학습

**Decision** — 나이스 사진 명렬표 **최신 2종(HWPML `.hwp` + `.xlsx`)**에서 이름과 사진을 자동 추출해, 기존 이름 학습 모드를 얼굴 기반으로 확장한다. 사진은 바이너리로 분리 저장하고 반 단위로 묶어 구글 드라이브에 동기화하며 모바일에서도 사용한다. 주관식 "이름 쓰기" 모드를 추가한다.

**Drivers** — D1 잘못된 짝의 무증상 전파 / D2 얼굴 사진이라는 새 개인정보 등급 / D3 다중 포맷 파싱 유지보수 비용.

**Alternatives considered** — B 외부 파싱 라이브러리(시트 그림 추출 미지원으로 무용) / C 학생별 수동 첨부(단독 무효, Phase 3 폴백으로 흡수) / D dataURL JSON 인라인(동기화 전량 전송·충돌 사고 재발 위험) / **E 이미지·PDF 격자 크롭** 및 **A′ 종합안**(D1·D3 모두에서 우수하나 **오너가 O2로 자동 추출을 확정**하여 기각. A′의 "실패 시 수동 보정 강등" 아이디어만 채택).

**Why chosen** — 최신 2종 모두 실물 파일로 **22쌍 전단사 짝짓기까지 검증**됐다. HWPML은 평문 XML이라 파싱만으로 끝나고, `.xlsx`는 기존 `exceljs`가 압축 해제·이미지 추출을 다 해 준다 → **새 런타임 의존성 0개, 미검증 코드 0건.** 무엇보다 **오너가 "파일을 넣으면 자동으로"라는 사용 경험을 제품의 핵심 가치로 확정**했다.

**Consequences**

- (+) 교사는 파일 하나로 학기 초 준비가 끝난다. 모바일에서도 연습 가능.
- (+) **최신 나이스 산출물 2종(HWPML·`.xlsx`)이 실물로 검증됐다** — 22쌍 전단사 성립. 초판의 최대 위험이었던 "실물 미검증"이 주 경로에서 해소됐고, 주 경로는 **압축 해제조차 필요 없어** 새 런타임 의존성이 0개가 될 수 있다.
- (+) **범위를 최신 2종으로 확정(2026-08-19)** → 미검증 코드 0건, **새 런타임 의존성 0개**, 압축 해제 블로커 소멸.
- (−) 구형 `.hwp`(OLE2)·`.xls`·`.hwpx`를 쓰는 교사는 **최신 형식으로 다시 받아야 한다.** 그래서 미지원 형식을 정확히 식별해 안내하는 경로가 필수다(무언 실패 금지). 신고가 나오면 Q6으로 재검토.
- (−) `.hwp` 한 확장자에 두 포맷이 있어 **매직 바이트 판별이 영구 요구사항**이 된다.
- (−) **O3 확정으로 §3.4의 5가지가 필수 작업이 됐다** — 드라이브 파일 삭제 포트 신설, 모바일 삭제 UI, 동기화 실패 격리, iOS 스토리지 대비, 국외이전 고지. 특히 실패 격리는 **기존 관찰 첨부 동기화 동작도 바꾸는 변경**이다.
- (−) 개인정보 표면이 넓어진다(로컬 + 드라이브 + 모바일 IndexedDB 3사본).

**Follow-ups**

1. ~~실제 나이스 사진 파일 확보 후 검증~~ → **완료(2026-08-19)**: HWPML·`.xlsx` 각 22쌍 실증. 남은 건 `.xls` 하나뿐이고 Q5에서 제외가 기본값.
2. Q1~Q5 확정 (**Q5 = `.xls` 지원 여부, 범위에 가장 큰 영향**)
3. 학년도 전환 시 `Student.id` 유지 여부 확인(`ExecuteYearTransition.ts`) — 안 유지되면 사진 재매핑 절차 필요
4. `usecases → infrastructure` eslint 규칙을 `error`로 승격하는 장기 과제(현재 위반 57건)
