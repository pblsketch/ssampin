# ADR-078: 발표 중 옆핀 가리기는 "순한 등급"으로 한다 — 추측으로 판단하는 감지기에 최대 반응을 물리지 않는다

> 2026-08-31 · 관련 계획서 `docs/01-plan/features/sidepin-privacy-guard.plan.md` §5 (1단계) ·
> `electron/platform/win32Presentation.ts` · `electron/sidePinProtection.ts` ·
> `src/domain/services/resolveSidePinTransition.ts`

### 무슨 일이 있었나

옆핀은 **항상 맨 위에 뜨는 창**이라 파워포인트 F5 슬라이드쇼 위에도 그대로 남는다(오너 실측).
수업 중 화면을 띄우면 급식·할 일·일정이 교실 전체에 보인다.

숨기는 장치는 **이미 다 만들어져 있었다** — `SidePinProtectReason` 에 `'fullscreen'` 이
선언까지 돼 있는데 **어디에서도 쓰이지 않았다.** 진짜 작업은 두 가지였다:
**알아채기**(윈도우에 묻기)와 **반응을 작게 만들기**.

### 결정

1. **감지는 `SHQueryUserNotificationState`**(shell32, koffi, 3초 폴링). 후보였던 "맨 앞 창 크기 재기"는
   **최대화한 크롬·탐색기도 전체화면으로 오인**해 탈락시켰다. 오탐하면 옆핀이 이유 없이 사라지고,
   선생님은 고장으로 여겨 기능을 꺼 버린다 → **보호가 0이 된다.**
2. **새 보호 등급 `soft-protect`.** 기존 `force-protect` 를 재사용하지 않는다.
   그것은 `editorActivity` 를 `'idle'` 로 밀고(쓰던 글을 버린다) `hide-all` 로 패널을 파괴하고
   손잡이까지 숨긴다. 잠금·절전은 선생님이 확실히 자리에 없으니 맞지만, **전체화면은 추측이라
   오탐 한 번에 쓰던 메모가 날아간다.** `soft-protect` 는 **손잡이까지 감추되 패널 창은 살려 둔다**
   — 새 창 명령 `conceal-all`(§"명령이 세 개인 이유").
3. **보호 이유에 등급을 둔다** — `force`(잠금·절전) > `soft`(전체화면). 남은 이유 중
   **최고 등급**을 항상 돌려준다. 안 그러면 절전이 풀리는 순간 등급이 내려가
   **아직 잠금 화면인데 손잡이가 다시 뜬다.**
4. **"즉시 가리기"는 새 단추를 만들지 않는다.** `SidePinPanel` 의 기존 [닫기]를
   `visibility_off`/"지금 가리기"로 바꾸고, `close-requested` 에 `force` 를 더해
   **쓰는 중이어도 접히게** 했다(직접 누른 경우만).
5. **끄는 스위치는 기기 전용 파일**(`SidePinDeviceState.hideOnPresentation`, 기본 켜짐)에 둔다.
   동기화하면 학교(모니터 두 대)와 집(한 대)이 서로의 값을 덮어쓴다.
   **끄는 스위치는 그 기능과 같은 단계에 출시한다** — 다음 단계로 미루면 그 사이에
   끌 방법 없는 자동 숨김이 배포된다.

### 🚨 명령이 세 개인 이유 — 실기기에서 두 번 고쳤다 (2026-09-01)

처음에는 `soft-protect` 가 기존 `collapse-panel` 을 재사용했다. **틀렸다.**
그 명령은 이름과 달리 **손잡이를 보이게 한다**(`sidePinWindow.ts` 의 `collapsePanel` 이
`rail.showInactive()` 를 부른다 — 원래 용도가 "펼친 패널을 접어 손잡이로 되돌리기"다).
그래서 오너가 PPT 로 확인했을 때 **손잡이가 화면에 그대로 남았다.**
"전체화면일 때 옆핀을 숨긴다"는 목적 자체가 달성되지 않았다.

| 명령                    | 손잡이     | 패널     | 쓰던 글                         |
| ----------------------- | ---------- | -------- | ------------------------------- |
| `collapse-panel`        | **보인다** | 숨김     | 살아 있다                       |
| `hide-all`              | 숨김       | **파괴** | **날아간다**                    |
| **`conceal-all`**(신설) | **숨김**   | 숨김     | **살아 있다**(창을 안 파괴한다) |

⚠️ "쓰던 글이 살아 있다"는 **패널 창을 파괴하지 않는다**는 뜻이다. 편집기가 닫히면서
아직 저장 안 된 마지막 몇 글자(저장 지연 이내)는 잃는다 — 잠금·절전에서도 원래 같았고
발표 감지가 만든 문제가 아니다. 제대로 고치려면 저장을 effect 바깥으로 옮겨야 한다(후속).

가운데가 비어 있어서 새로 만들었다.

**근본 원인은 D2("되돌아올 수 있는가")를 잘못된 곳에 적용한 것이다.**
자동으로 걸린 보호는 **자동으로 풀린다** — 발표가 끝나면 `protect-released` 가 `ensure-rail` 로
손잡이를 되돌린다. D2 가 진짜 필요한 곳은 **사람이 직접 누르는** [지금 가리기] 쪽이고,
거기는 접기라서 이미 손잡이가 남는다.

★ **교훈**: 명령 이름을 믿지 말고 **그 명령이 창에 실제로 무슨 일을 하는지** 읽을 것.
도메인 테스트로는 절대 안 잡힌다 — 창을 다루는 것은 `electron/sidePinWindow.ts` 층이다.
재발 방지 테스트를 `sidePinWindow.contract.test.ts` 에 넣었다.

### 🚨 "최소 유지 시간"은 넣었다가 뺐다 — 다시 넣지 말 것 (2026-09-01)

흔들림을 막으려고 "한 번 숨겼으면 최소 30초는 숨긴 채로 둔다"를 넣었다. **두 가지가 틀렸다.**

1. **해로웠다.** 발표를 30초 안에 끝내면 손잡이가 남은 시간 동안 사라진 채로 남아
   **"손잡이가 돌아오지 않는다"로 신고됐다.** 선생님 눈에는 고장이고, 그러면 기능을 꺼서
   보호가 0이 된다.
2. **필요도 없었다.** 흔들림을 막는 것은 **확인 횟수의 비대칭**(가릴 때 1회 · 되돌릴 때 2회)이다.
   값이 한 칸씩 번갈아 튀면 "아니오"가 두 번 연속 나오지 않아 **되돌아가는 일 자체가 없다.**

**되돌리는 것은 빨라야 한다.** 늦게 되돌리는 대가(고장으로 보임 → 기능을 끔)가
일찍 되돌리는 대가(잠깐 잘못 나옴, 그나마 2회 확인이 막는다)보다 훨씬 크다.

★ 이 판정을 처음에 `main.ts` 안에 두었더니 **어떤 테스트도 보지 못했고** 실기기에서야 나왔다.
순수 함수 `stepPresentationWatch`(`win32Presentation.ts`)로 빼고 테스트를 붙였다 —
`sidePinProtection.ts` 가 "창을 다루지 않고 판단만 한다"로 얻은 것과 같은 이점이다.

### 등급이 겹칠 때 — 내려오는 것은 허용하되, 추적기가 아는 이유에서만

잠금과 발표가 겹쳤다가 **잠금만 풀리면** 추적기는 `fullscreen`(soft)을 돌려준다.
이때 전이 함수가 등급을 안 낮추면 `protectedReason` 이 `'lock'` 에 멈춰,
**발표가 끝나고 추적기가 `release('fullscreen')` 을 보내도 이유가 안 맞아 안 풀린다.**
화면에서 보이는 모습은 두 등급이 같지만(둘 다 손잡이까지 감춘다) **대가가 다르다** —
force 는 패널을 파괴하고 soft 는 살려 둔다. 그래서 **내려오는 것을 허용한다.**

내려와도 안전한 근거: 이 이벤트는 추적기가 **남은 이유 중 최고 등급이 soft일 때만** 보낸다.
여기 도달했다는 것 자체가 잠금·절전이 이미 다 풀렸다는 뜻이다. 잠금이 살아 있으면
추적기가 force 를 돌려주므로 이 자리에 오지 않는다(`sidePinProtection.test.ts` 가 못박는다).

**단, 추적기가 모르는 이유에서는 내려오지 않는다.** `adapter-unhealthy` 는 전이 함수가 직접
세우는 이유라 바깥의 등급 판단이 그 사정을 모른다. 그걸 낮추면 **어댑터가 고장 난 채로
손잡이를 다시 내보낸다.** 그래서 내려오기는 `lock`·`suspend`·`fullscreen` 세 가지에서만 허용한다.

### 알고 받아들이는 한계 (릴리즈 노트에 그대로 쓴다)

- **창 모드 앱을 프로젝터에 띄운 경우는 안 막힌다.** 이 API 는 창 모드에 반응하지 않는다.
  한국 교실에서 더 흔한 쪽이 이것이다. 그 경우는 [지금 가리기]와 2단계(PIN 잠금)가 담당한다.
- **모니터 구분이 없다.** 세션 단위 API 라 프로젝터에서 발표하면 **노트북 옆핀도 함께 숨는다.**
  v2.4.6(ADR-075)에서 모니터별 배치를 낸 터라 이 조합은 실재한다. 끄는 스위치가 회피 수단이다.
- **macOS 는 여전히 무보호다.** 감지가 Win32 전용이라 `'fullscreen'` 은 macOS 에서 도달 불가 상태다.
- 폴링이라 **최대 3초 지연**된다(감시를 시작하는 순간에는 곧바로 한 번 확인하므로 0초).
  가릴 때는 한 번만 보고 바로 가리고, 되돌릴 때만 두 번 연속을 확인한다 —
  **기다리는 시간이 곧 학생 정보가 화면에 떠 있는 시간**이라 방향마다 기준을 다르게 뒀다.
  순한 등급이라 헛짚어도 손잡이가 남고 쓰던 글도 안 지워지므로 빨리 가리는 쪽이 싸다.

### ★ 교훈 세 가지 (전부 이번에 실제로 겪었다)

**① 외부 API 의 상수값은 리뷰로 안 잡힌다.** 계획서가 적어 둔 `QUNS_*` 숫자가 **전부 1씩 어긋나
있었다.** Architect·Critic 두 번의 리뷰를 통과했는데, 둘 다 계획의 *논리*를 봤지 남의 문서를
대조하지 않았기 때문이다. 그대로 구현했다면 `5`(= 실제로는 **평상시** 상태)에서 숨어
**아무 일도 안 하는 동안 옆핀이 계속 사라졌을** 것이고, 정작 전체화면 앱(`7`)에서는 안 숨었을 것이다.
구현 단계에서 원문을 확인한 것이 잡았다.

**② 도메인만 고치고 통로를 안 이으면 게이트가 전부 초록인 채 기능이 죽는다.** `force` 를
도메인에 넣고 도메인 테스트 97개가 통과했는데, `preload → main → 화면` 배선이 없어
**단추는 그대로 아무 반응이 없었다.** `tsc` 는 `electron/` 을 안 보므로 타입으로도 안 걸린다.
→ 재발 방지로 `electron/sidePinHideNow.wiring.test.ts` 를 만들어 네 곳의 연결을 소스로 확인한다.

**③ 같은 값을 두 곳에 두면 반드시 어긋난다.** `SidePinDeviceState` 는 도메인과 electron 에
미러가 있는데(rootDir 제약), 도메인만 고쳤더니 미러 테스트가 16건으로 잡아냈다.
그 테스트가 없었으면 **설정을 저장해도 안 읽히는** 상태로 나갔을 것이다.
