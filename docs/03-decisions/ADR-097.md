# ADR-097 · 학생 번호는 배열 위치가 아니라 명렬표의 실제 출석번호다 — 제출물 연결도 소속을 먼저 본다 (2026-09-08)

- 상태: 채택 · 로컬 구현 완료(게이트 4종 통과). **운영 적용(마이그레이션 067)·배포는 미승인 상태로 대기.**
- 관련: 분석 [student-number-integrity-20260908.analysis.md](../03-analysis/student-number-integrity-20260908.analysis.md) · 핸드오프 [student-number-integrity.handoff.md](../03-analysis/student-number-integrity.handoff.md)
- 앞선 사례: v2.4.9 상담 예약 결번 밀림 수정(같은 원인, 상담만 고쳤다)

## 배경

v2.4.9 에서 상담 예약의 "결번 뒤 번호 밀림"을 고쳤다. 2026-09-08 검토에서 **같은 원인이 과제·설문·
생기부 근거에 그대로 남아 있는 것**을 실행으로 재현했다(재현 스크립트
`docs/03-analysis/student-number-audit-20260908.cjs`, 결함 5건 + 상담 대조 1건).

뿌리는 두 가지다.

1. **배열 위치를 학생 번호로 썼다.** 비활성 학생을 걸러낸 뒤 `index + 1` 을 번호로 삼는 코드가
   과제 명단·설문 CSV·격자·조회·발표 순서에 흩어져 있었다. 2번이 전출하면 3번이 2번이 된다.
2. **번호만으로 학생을 이었다.** 과제 조회는 학생 id·학년·반이 명시돼 있어도 마지막에 번호만
   비교해, 1학년 1반 3번의 제출물을 1학년 2반 3번 칸에도 붙였다. 생기부 근거 후보도 같았다.

설문은 여기에 더해 **인원수를 마지막 번호로 취급**했다. 33번까지 있는 반에 결번 2명이면 재학생은
31명이고, 학생 화면은 `1~31번` 버튼만 그렸다. 32·33번 학생은 자기 번호가 없어 응답을 못 하고,
빠진 번호는 반대로 열려 있었다. PIN 도 같은 기준이라 32·33번에게는 PIN 이 없었다.

## 결정

### 1. 번호의 단일 출처는 `rosterNumbering` 한 곳이다

`src/domain/rules/rosterNumbering.ts` 를 새로 만든다.

- 담임은 `studentNumber`, 수업반은 `number` — 필드 이름 차이를 여기서만 흡수한다(`rosterNumberOf`).
- 유효하고(>0) 그룹 안에서 유일한 번호는 **절대 바꾸지 않는다**. 번호가 없거나 겹친 학생만
  "그룹 안 가장 작은 미사용 번호"로 채운다(기존 `reassignConflictingNumbers` 재사용).
- **번호 계산은 전체 명렬표에서 먼저 하고 그다음에 비활성 학생을 거른다**(`numberActiveRoster`).
  그래야 전출 학생이 쓰던 번호가 빈 자리로 남고, 번호 없는 다른 학생에게 넘어가지 않는다.
- 번호가 아예 없는 명렬표는 예전처럼 1..N 이 된다(하위 호환 — 이름만 붙여넣은 명단).

★배열 위치·정렬 순서·활성 학생 수를 학생 식별자로 쓰지 않는다. 이것이 원래 사고의 원인이다.

적용처: 과제 대상 명단(`useStudentLists`) · 설문 CSV/클립보드(`surveyRules`) · 담임 격자
(`StudentGrid`) · 기록 조회(`SearchMode`) · 발표 순서(`PresentationMode`) · 생기부 초안 행
(`HomeroomRecordDraftTab`) · 설문 응답 현황과 PIN 표(`SurveyStudentDetail`).

### 2. 제출물 연결 규칙도 한 곳이다 — 소속이 어긋나면 번호를 무시한다

`src/domain/rules/submissionMatching.ts` 를 새로 만든다. 판정 순서는 이렇다.

1. 학생 id 일치
2. 양쪽에 학년·반이 있으면 **학년·반·번호가 모두** 일치
3. 한쪽에 학년·반이 없으면(담임반·구형 제출물) 번호 일치 — 단 **그 번호를 쓰는 학생이 명단에
   한 명뿐일 때만**
4. 양쪽에 학년·반이 있는데 다르면 번호가 같아도 **절대 잇지 않는다**
5. 제출물 하나는 학생 한 명에게만 붙는다

**추측하지 않는 쪽을 고른다.** 소속이 어긋나거나 같은 번호 학생이 둘 이상이면 붙이지 않고
`unmatched` 로 돌려준다. 과제 상세 화면이 "명단과 연결하지 못한 제출 N건"으로 교사에게 알린다 —
조용히 사라지지 않고, 남의 칸에 붙지도 않는다.

적용처: 과제 상세(`GetSubmissions`) · 미제출 복사(`CopyMissingList`) · 모바일 제출 현황
(`ToolAssignmentPage`, `useMobileAssignmentStore`) · 새 제출 알림(`useAssignmentStore`, 번호 대신
학생 id 로 대조).

### 3. 근거 후보는 "과제가 겨냥한 반"까지 확인한다

`collectEvidenceCandidates` 의 제출물 갈래를 `isSubmissionOfStudent` 로 옮긴다.

- 담임: 명단 학생 id 가 같아야 한다. `studentId` 가 없으면 후보 0건(추측하지 않는다).
- 수업반: 과제 대상이 `type === 'teaching'` 이고 `teachingClassId === classId` 여야 한다.
  그다음 그 과제 명단에서 제출자를 찾아 `studentKey`(학년-반-번호)로 사람을 가른다.
- 반 id 가 없는 구형 과제는 관문을 통과시키되 명단의 `studentKey` 로만 가른다.
- 과제를 목록에서 찾지 못하면 확인할 방법이 없으므로 연결하지 않는다.

### 4. 설문은 인원수와 **응답 가능 번호 목록**을 분리한다

- `Survey.targetNumbers?: readonly number[]` 를 추가한다. `targetCount` 는 진행률 분모로 남긴다.
- `generateStudentPins(count)` → `generateStudentPins(studentNumbers)` 로 **시그니처를 바꾼다**.
  인원수를 받는 문법을 남겨 두면 같은 사고가 다시 난다.
- 새 함수 `surveyAnswerableNumbers(survey)` 하나가 학생 화면·교사 화면·PIN 의 기준이 된다.
  `targetNumbers` 가 있으면 그것을, 없으면 `1..targetCount` 를 쓴다(구형 설문 하위 호환).
- DB: 마이그레이션 067 이 `surveys.student_numbers INT[]` 를 추가한다. NULL 이면 구형 설문이다.

### 5. 기존 자료는 자동으로 고치지 않는다

이미 만든 과제·설문은 **만들 당시의 명단을 그대로 갖고 있다.** 현재 명렬표 번호로 과거 데이터를
일괄 덮어쓰지 않는다 — 그 사이 명렬표가 바뀌었으면 멀쩡한 기록을 망가뜨리고, 서버·드라이브에 이미
저장된 사본과도 어긋난다.

대신 **읽기 전용 점검 도구**를 둔다: `scripts/student-number-audit-existing.mjs` 가 저장된
과제 명단의 학생 id 를 현재 명렬표와 대조해 어긋난 항목만 표로 찍는다(쓰기 없음). 어긋난 과제·
설문은 **새로 만들어 링크를 다시 나눠 주는 것**이 정본 절차다. 이미 받은 제출물·응답과 드라이브
파일은 그대로 남는다.

### 6. 학생 id 를 학생 화면으로 내려보내지 않는다

제출 폼이 `studentId` 를 함께 보내면 연결이 가장 정확해진다. 그러나 `get-assignment-public` 은
의도적으로 명단에서 id 를 뺀다 — 링크를 가진 누구에게나 학생별 고정 식별자를 주게 되기 때문이다.
**이번 작업에서는 넣지 않는다.** 필요하면 서버(`submit-assignment`)가 자기가 들고 있는
`student_list` 에서 학년·반·번호로 id 를 찾아 저장하는 쪽이 맞다 — 클라이언트에 아무것도
노출하지 않는다. 이건 엣지 함수 배포가 필요하므로 별도 승인 항목으로 남긴다.

## 되돌리기

- 앱: 커밋 되돌리기. 마이그레이션 067 이 이미 적용됐어도 `student_numbers` 를 안 쓸 뿐 깨지지 않는다.
- DB: `supabase/migrations/067_survey_student_numbers.rollback.sql`.
  ⚠️ 컬럼을 지우면 그 사이 만든 설문의 응답 가능 번호가 사라진다. **앱을 먼저 되돌린 뒤** 실행한다.
- 적용 순서는 **마이그레이션 → 앱 배포**다. 반대로 하면 새 앱이 없는 컬럼에 쓰려다 설문 생성이 400 으로 실패한다.

## 남은 위험

- 소속 정보가 없는 구형 제출물이 같은 번호 학생 여러 명과 겹치면 이제 "미연결"로 뜬다. 예전에는
  아무에게나 붙었으므로 **겉보기 제출 인원이 줄어 보일 수 있다.** 이건 정보 손실이 아니라 감춰져
  있던 모호함이 드러난 것이다.
- 학생이 이미 받은 옛 설문 링크·과제 링크는 옛 번호 방식 그대로다(결정 5).
- 실기기(설치본)·운영 DB 확인은 하지 않았다.
