# ADR-087: 온라인 교무실 제출 과제 — 취합은 부장만 하는 일이 아니고, 이름은 필요한 사람에게만

- 일자: 2026-09-07
- 상태: 채택 (계획 `.omc/plans/staffroom-submission-plan.md` v4 · 명세 `.omc/specs/deep-interview-staffroom-swl.md`)
- 관련: ADR-062(교무실 격리 두 겹) · 계획서 `docs/01-plan/features/online-staffroom.plan.md` §8-B·§8-E
- 출처: [school-work-links](https://github.com/cando8442/school-work-links) (MIT, 서울세종고 교사 제작) — **설계 판단만 참고, 코드 이식 없음**
- 마이그레이션: `066_staffroom_submission.sql`

### 발단

부서 업무(`staffroom_tasks`, M4)는 **한 사람이 맡는 일**이다 — "출결 관리". 그런데 학교
업무의 상당수는 다른 모양이다 — "2학기 수행평가 계획을 **과목별로** 내주세요". 여럿이
각자 내고 한 사람이 취합하며, 다 내면 끝난다. 담을 자리가 없었다.

같은 오픈소스를 읽다 업무분장에 **인수인계 지식**(반복 주기·처리 절차·주의사항)을 담는
칸이 있는 것도 발견했다. 쌤핀 교무실은 M6에서 "학년도 인수인계"를 최대 차별점으로 잡아
뒀는데, 넘기는 것이 **파일뿐**이었다. 2월에 넘어가야 하는 건 파일이 아니라 아는 것이다.

## 결정 1 — 제출 과제 만들기는 **멤버 누구나**. 업무분장은 현행 유지

취합은 부장만 하는 일이 아니다. 교과 협의회 간사·학년 담당·행사 담당 누구나 "이거 다들
내주세요"를 띄울 수 있어야 하고, 관리자만 만들 수 있으면 나머지는 결국 단톡방으로 돌아간다.

| 하는 일                      | 누가                            | 쓰는 판정                        |
| ---------------------------- | ------------------------------- | -------------------------------- |
| 제출 과제 **모듈** 켜고 끄기 | 관리자                          | `canManageModules`               |
| 제출 **과제 만들기**         | **멤버 누구나**                 | `canWritePost` 와 같은 결        |
| 과제 고치기·지우기           | 만든 사람 · 관리자              | `canEditRoomItem`                |
| 미제출 명단 보기             | 만든 사람 · 관리자              | `canSeeUnsubmittedList` (신설)   |
| 남의 칸 체크                 | 만든 사람 · 관리자              | `canToggleSubmissionDone` (신설) |
| 내 칸 체크                   | 본인                            | 〃                               |
| **업무분장** 만들기·고치기   | **멤버 누구나 / 만든이·관리자** | 기존 그대로                      |

★ **"만든 사람"은 권한 등급이 아니다.** 그 과제 한 건에 대한 관계일 뿐이고, 교무실은
계획서 §2대로 **관리자/일반 2단계**를 그대로 유지한다. 다음 사람이 `role: 'collector'` 로
정규화하지 말 것.

★ 업무분장 권한을 좁히려다 **되돌렸다.** 명세 초안이 "기존 `canEditTask` 유지 = 관리자"라고
적었는데 **사실이 아니었다** — `staffroom-plan/index.ts:326` 의 `addTask` 에는 권한 검사가
없고 `canEditTask` 는 만든이·관리자다. 그대로 갔으면 v2.4.4로 이미 출시된 기능에서
**지금 자기 업무를 고치던 일반 선생님이 조용히 손을 잃을 뻔했다.** 데이터는 남으니 아무도
못 알아챈다. 오너 결정으로 현행 유지.

## 결정 2 — 진행률은 전원이, **명단은 만든이·관리자만**

교무실 화면에 미제출자 이름이 회색으로 남아 있는 것은 부장에게는 편하지만 그 사람에게는
다른 뜻이다. 계획서 §8-E(사람별 누적 표시 금지)와 같은 결이다.

- 일반 멤버: `7 / 12` 진행률 + **내 상태만**
- 만든이 · 관리자: "안 낸 분 보기"로 명단

### 왜 "권한 없으면 이름을 지운다"가 아니라 **통로를 나눴나**

두 방식의 차이는 왕복 수가 아니라 **실수의 방향**이다.

- 목록에 담되 지우기 — `if (권한없음) name = null` 한 줄을 **빠뜨려서** 샌다
- 통로를 나누기 — 익명 타입에 담을 칸이 **없어서**, 담으려면 **일부러 해야** 샌다

사람은 빠뜨리고, 검증 게이트 4종은 빠뜨림을 못 잡는다. 그래서 `toSubmissionSummary` 의
반환 타입에 제출 주체 칸을 **아예 두지 않았다.** 부서 멤버의 지메일을 정당하게 돌려주는
함수는 `toTargetsList` **하나뿐**이고, 그 자리에서만 권한을 판정한다.

`authorEmail` 은 **의도된 유일한 예외**다 — 화면이 "내가 만든 과제인가"를 판정해 "안 낸 분
보기" 단추를 그릴지 정해야 한다. `authorName` 은 담지 않는다.

## 결정 3 — 필독 글 읽음 명단도 같이 좁힌다

구현 중에 발견했다: `staffroom-posts` 의 `readers` 에 **권한 검사가 없어**, 필독 글의
"안 읽은 사람" 명단이 **부서 전원에게 이름째로** 나가고 있었다.

제출 과제 명단만 가려도 같은 부서에서 필독 글 하나면 옆문으로 그대로 새므로, 오너 결정으로
이번에 함께 좁혔다(쓴 사람·관리자만). **서버·스토어·화면을 한 묶음으로 배포해야 한다.**

## 결정 4 — 개인 화면에서 체크하되, 완료분은 **14일**만 남긴다

`StaffRoomPlanOverlay` 는 "여기 있는 것은 전부 읽기 전용이다"를 설계 원칙으로 못박아 뒀다.
이번에 **내 칸의 완료 표시 하나만** 예외로 연다.

부서 업무와 제출 과제의 계약이 **다르다**:

|           | 부서 업무                              | 제출 과제                                   |
| --------- | -------------------------------------- | ------------------------------------------- |
| 완료한 것 | 화면에서 거른다(사라짐)                | **안 거른다**(체크된 채 남음)               |
| 왜        | 여기서 체크할 수 없으니 되돌릴 게 없다 | **여기서 체크하므로 되돌릴 수 있어야 한다** |

그런데 제출 과제는 학년도 전환·보관함 대상이 아니라 계속 쌓인다. 전부 남기면 1년 뒤
개인 화면이 완료된 과거 과제로 덮이고 `PAGE_SIZE` 에서 조용히 잘린다. **되돌릴 필요가
있는 것은 방금 누른 것뿐**이므로 서버가 **미완료 전부 + 최근 14일 완료분**만 보낸다.

예외가 번지는 것은 **주석이 아니라 회귀 검사 REGRESSION #68-3** 으로 막는다.

## 결정 5 — 부서를 나간 멤버는 분모에서 뺀다

안 빼면 그 과제는 `11/12` 에서 영원히 안 채워져 "끝났다"를 말할 수 없다. **분자에서도**
빼야 한다 — 한쪽만 빼면 `12/11` 같은 숫자가 나온다.

이름은 `staffroom_members` 에 남아 있으면 산 값, 없으면 `display_name_snapshot`(걸 때
복사해 둔 값), 그것도 없으면 화면이 대신 그린다. `049` 의 멤버 표에는 "나갔다"를 표시하는
칸이 없고 내보내기가 행을 통째로 지우므로, 스냅샷이 없으면 이름을 복원할 길이 없다.
`staffroom_members` 로 **FK 를 걸지 않는다** — 걸면 CASCADE 로 제출 이력까지 사라진다.

## 결정 6 — 서버는 `staffroom-rooms`, 순수 판정은 `_shared`, 개인 화면은 `staffroom-plan`

- **CRUD 는 `staffroom-rooms`** — 모듈 소속 엔티티(`staffroom_discussions`·`staffroom_minutes`)를
  이미 그 함수가 맡고 있고, 제출 과제도 `module_id` 소속이다. `staffroom_events`·
  `staffroom_tasks` 는 `department_id` 직속이라 `staffroom-plan` 이 맡는다
- **순수 판정·투영은 `_shared/staffroomSubmissions.ts`** — ★ **import 는 `./staffroomAccess.ts`
  하나만.** `staffroomDb.ts` 를 값으로든 `import type` 으로든 참조하면 `https://esm.sh/...`(TS2307)와
  `Deno`(TS2304)가 딸려 와 **프로젝트 타입 검사가 깨진다**(실측). 그러면 `src/` 테스트가
  이 파일을 못 불러 CI 방어선이 사라진다. 이 규칙은 드리프트 메타 테스트가 강제한다
- **`mine` 은 `staffroom-plan`** — 개인 화면 왕복은 한 번만 유지한다

**대가:** `staffroom-rooms` 를 되돌리면 회의록·토론방까지 함께 되돌아간다. 새 함수(A안)를
탈락시킨 이유였던 "미배포 위험"은 `scripts/verify-staffroom-submission.mjs` 가 이미 막으므로
결정적 근거가 아니었다 — **순수하게 일관성으로 고른 것이고 그 대가를 받아들였다.**

## 결정 7 — 붙여넣기 파싱은 앱이, 검사는 서버가 다시

사람이 미리보기로 확인하고 올리는 것이 이 기능의 안전장치인데, 미리보기마다 서버를
부르면 글자를 고칠 때마다 왕복이 생긴다. 파서는 `domain/rules/staffRoomSchedulePaste.ts`
순수 함수이고 **기준 학년도를 인자로 받는다**(domain 은 외부를 import 할 수 없다).

읽지 못한 줄은 **조용히 버리지 않고 수를 센다.** 20줄을 붙여넣었는데 12줄만 들어가면
아무도 알아채지 못한다.

## 검토 과정에서 바로잡은 사실 오류 (기록으로 남긴다)

계획을 4번 다시 썼다. 명세·계획이 **사실이라고 적었다가 코드로 반증된 것**들이다.

| 적었던 것                              | 실제                                                |
| -------------------------------------- | --------------------------------------------------- |
| "업무분장은 관리자만 만든다"           | `addTask` 에 권한 검사 없음 — 멤버 누구나           |
| "필독 읽음 확인과 같은 규칙(관리자만)" | `readers` 에 검사 없음 — **전원 공개**              |
| "별도 엣지 함수로 빼면 왕복 2번"       | 엣지 함수는 이미 남의 표를 직접 읽는다              |
| "모듈 종류는 두 곳"                    | **여섯 곳**. DB CHECK 와 이름·아이콘 맵이 게이트 밖 |
| "`_shared` 면 CI 테스트가 된다"        | import 그래프가 `Deno`·URL 에 닿으면 tsc 가 깨진다  |
| "오래된 일정이 잘린다"                 | 오름차순+limit 이라 **날짜가 늦은 것**이 잘린다     |

## 결과

- 마이그레이션 `066` · 엣지 함수 3개(`staffroom-rooms`·`staffroom-plan`·`staffroom-posts`)
- 회귀 검사 3건 신설 — #68-1(목록 투영에 주체 신원 없음) · #68-2(명단 두 통로가 판정 호출) ·
  #68-3(개인 화면 예외가 안 넓어짐). **셋 다 변조 테스트로 실제로 무는 것을 확인했다** —
  #68-3 은 처음에 괄호를 요구해 셀렉터로 넓히는 실제 경로를 못 잡아 고쳤다
- 메타 테스트 2건 — 격리(RLS·REVOKE·§8-E 칼럼·UNIQUE·FK 부재) · 모듈 종류 여섯 곳 드리프트

## 남은 것

- **배포 4회**(S3 `staffroom-rooms`+`staffroom-plan` 동시 → S4-6c `staffroom-posts` →
  S5·S6 `staffroom-plan` 재배포). 매번 **서버를 먼저**
- **운영 DB 적용 확인** — `SELECT pg_get_constraintdef(...)` 로 CHECK 에 `submission` 이
  들어갔는지 보고 출력을 진행 기록에 붙인다. 파일에 적어 두고 실행을 안 하면 게이트 4종은
  전부 초록인데 실기기에서만 500 이 난다
- `scripts/verify-staffroom-submission.mjs` 실호출
- 실기기 확인 E1~E12

## 의도적 비목표

- 제출 과제는 **학년도 전환·보관함 대상이 아니다**(`archiveScope.ts`·`ExecuteYearTransition.ts` 에
  staffroom 참조 0건). 교무실 목록에는 과거 과제가 계속 쌓이고, **개인 화면만 14일 창으로 막았다**
- 모듈 삭제 확인은 **화면 전용**이다. `canDeleteModule` 은 게시판·자료실만 보호하고 서버는 CASCADE
- "안 낸 분 보기"는 **한 과제 안에서만** 센다. 여러 과제를 가로질러 "이 분이 N개 안 냄"이
  되면 §8-E 위반이다

## 함께 발견한 별건 (이번 범위 밖)

**`sp-danger` 토큰이 `tailwind.config.js` 에 없다.** 그런데 교무실 화면 **7개 파일**이 쓰고
있어 CSS 규칙이 아예 안 만들어진다 — 오류 문구와 경고 테두리가 지금 빨갛게 안 보인다.
이번에 손댄 `StaffRoomPlanOverlay.tsx` 한 곳만 `sp-error` 로 고쳤고, 나머지 6개
(`DiscussionView`·`GalleryView`·`LibraryView`·`MinutesView`·`ModuleTabs`·`PlanView`)는
**별건으로 남겼다.** 실기기에서 "원래 빨갛던 것이 안 빨갛다"를 먼저 확인하는 편이 순서다.
