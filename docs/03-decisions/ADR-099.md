# ADR-099 · 작성 방식은 선생님이 고른다 — 공통 규정과 작성 구성을 가르고, 순서는 요청서가 정한다 (2026-09-09)

- 상태: 채택 · **구현·운영 적용 완료(2026-09-09)**. 커밋 `c59f1acd`. 서버 규정 판본 3 적용·재배포 완료.
- 바꾸는 결정: **ADR-094**(교사 평가 맨 앞 = 고정 → **기본값**) · **ADR-085**(형광펜 순서 = 글 순서 → **색은 고정, 순서는 구성이 정함**).
- 관련: ADR-072(규정 서버 배급 · 막는 자리는 프롬프트가 아니라 입력) · ADR-088(분량) · ADR-089(배급 한도) · ADR-093(실행 상태는 스토어).
- 근거 조사: `docs/03-analysis/record-draft-template-library-v2-research-20260909.md`(대학 가이드북 4종·서울대 공개 사례 2건·교육청 연수 도움자료·동국대 수행평가 영역명 가이드북).

## 배경

지금까지 생기부 초안은 **골격이 하나**였다. 교사 평가 → 동기·질문 → 과정 → 결과, 그리고 "모든 근거를
하나의 탐구 흐름으로 이어라". 수업이 다르고 학생에게 남은 근거가 다른데 뼈대가 같으면, 읽는 사람에게
먼저 도착하는 것은 학생의 차이가 아니라 뼈대다.

오너 판단: 초점을 고르게 하자. 여러 구성 중 하나를 고르고, 요소를 조합하고, 자기 지시를 더할 수 있어야 한다.

## 이 결정의 핵심 — 화면만 만들면 안 된다

같은 순서를 **세 곳이 동시에** 요구하고 있었다.

1. 서버 1층 규정(`RECORD_PROMPT_L1` 판본 2): "골격: 교사의 평가적 기술 → 수업 장면 → 호기심 → …",
   "평가가 맨 앞이고", "**이 순서를 바꾸지 마십시오**", "질문 없이 이어 붙이면 실패한 기록입니다".
2. 앱이 매 요청 끝에 붙이는 표식 지시(`NARRATIVE_MARK_INSTRUCTION`): "순서는 반드시 [평가] → [동기]
   → [과정] → [결과] 입니다. 첫 문단은 교사 평가이고 '~하는 학생임.' 으로 끝냅니다."
3. 요청서 마지막 줄(`recordDraftPack`): "활동을 나열하지 말고 **하나의 탐구 흐름**으로 이어 주세요."

여기에 선택 단추만 붙이면 **서로 싸우는 두 지시**를 함께 보내게 된다. 모델은 둘 중 하나를 버리고,
어느 쪽을 버릴지는 우리가 못 정한다. 그래서 이 작업의 본체는 UI 가 아니라 **층 가르기**다.

## 결정

### 1. 공통 규정(1층)과 작성 구성(2층)을 가른다

- **1층(서버 규정, 못 끔)**: 사실 창작 금지 · 시점 · 문체 · 관찰 가능한 표현 · 기재 금지 · 하지 말 것 · 마지막 점검.
- **2층(요청서, 선생님이 고름)**: 무엇을 어떤 차례로 쓸지 · 시작 방식 · 근거를 묶는 방식 · 요소 · 추가 지시.

1층 규정은 판본 **3**으로 올려 "글의 구성·순서·시작 방식은 요청서의 「작성 구성」을 따른다"고 넘긴다.
**1층에는 선택으로 바뀌는 문장이 하나도 남지 않아야 한다.**

### 2. 세 가지를 따로 고른다

| 설정      | 선택지                                                     | 기본값             |
| --------- | ---------------------------------------------------------- | ------------------ |
| 작성 초점 | 기존형 + T1~T8 + 생활·관계 종합(행특)                      | 기존형             |
| 시작 방식 | 교사 판단 먼저 / 수행·장면 먼저 / 질문·문제 먼저           | 교사 판단 먼저     |
| 근거 묶기 | 대표 장면 하나 / 실제로 이어진 과정 / 독립 수행을 성취별로 | 실제로 이어진 과정 |

**ADR-094 는 폐기되지 않는다.** "교사 평가가 맨 앞, 첫 문장은 '~하는 학생임.'" 은 **기본값**이 되고,
그 조합을 고르면 어미 요구까지 그대로 나간다. 다른 시작 방식을 고르면 교사 판단이 맨 뒤로 가고
어미 요구는 빠진다. ADR-094 §4(평가를 끝에서 되풀이하지 않는다)는 그대로 산다 — 교사 판단 요소는
어느 구성에서도 **한 번만** 놓인다.

### 3. 기본값이면 요청서가 예전과 글자 하나까지 같다

고르지 않은 선생님에게는 「작성 구성」 블록이 **아예 붙지 않는다**. 이 기능이 생겼다고 기존 초안 품질이
조용히 달라지면 안 된다. 검사로 못 박았다(`recordDraftPackStyle.test.ts` 첫 묶음).

### 4. 형광펜 어휘는 늘리지 않는다 — 바뀌는 것은 순서뿐

요소가 40여 개여도 색은 `평가·동기·과정·결과` 넷뿐이다. 옛 초안의 `roleMarks`·파서·범례가 그대로 산다.
`NARRATIVE_ROLES` 는 이제 **범례를 그리는 차례**일 뿐 글의 차례가 아니다(ADR-085 수정).

### 5. 규정 판본 문지기 — 승인 전에는 아무것도 달라지지 않는다

`RECORD_STYLE_MIN_PROMPT_VERSION = 3`. 서버가 준 판본이 3 미만인데 기존형이 아니면
**기존형으로 되돌려 실행하고 화면에 그 사실을 적는다.** 판에도 되돌린 뒤의 구성이 남는다.

- 운영은 지금 판본 2 를 준다 → 새 구성은 **아무에게도 나가지 않는다.** 화면은 보이되 실행이 기존형이다.
- 되돌리기: 시크릿을 판본 2 본문으로 되돌리고 함수를 판본 2 로 재배포 → 모든 앱이 자동으로 기존형만 쓴다.
  앱 재설치도, 설정 삭제도 필요 없다.
- 캐시(1시간 TTL + 24시간 만료 유예) 때문에 배포 직후 최대 1시간은 옛 판본으로 되돌려 실행된다.
  **틀린 글이 나오는 게 아니라 옛 글이 나온다.**

### 6. 분량 조절과 [다시 표시]는 순서를 요구하지 않는다

이미 쓰인 글에 손대는 자리다. 순서를 다시 못 박으면 다른 구성으로 쓴 초안을 줄이라고 했을 때 모델이
글을 통째로 다시 짠다. `narrativeMarkInstruction({ keepExistingOrder: true })` 를 쓴다.
([다시 표시]는 원래도 "한 글자도 바꾸지 말라"면서 순서를 강제하던 자기모순이었다.)

### 7. 저장은 설정에 얹고, 프리셋에 학생 자료를 담지 않는다

새 JSON 파일을 만들지 않는다. `Settings.recordWritingStyles`(영역별 마지막 선택) ·
`Settings.recordStylePresets`(내 작성 방식, 상한 30). 둘 다 선택 필드라 옛 설정 파일이 그대로 읽힌다.

판(`RecordAiDraft.style`)에는 재현 정보를 남기되 **추가 지시 본문은 넣지 않는다** — 판 파일은 Drive 로
동기화되는데 지시문에는 선생님이 학생 이름을 적었을 수 있고, 마스킹은 보낼 때만 걸린다.

### 8. 검사는 앱이 셀 수 있는 것만 한다

"근거에 질문이 있는가" 같은 의미 판정은 못 한다. 근거 건수·서로 다른 날짜 수·영역처럼 **셀 수 있는 것**만
보고 6종을 알린다. **막지 않는다**(판본 문지기만 예외이고 그것도 적는다). 못 하는 판정을 하는 척하지 않는다.

## 왜 이 설계가 "선택만 있고 결과는 같다"를 피하는가

프롬프트 한 곳만 고치는 방법은 이미 실패한 전례가 있다(ADR-072: "프롬프트로는 규정을 못 막는다").
그래서 이 결정은 **같은 것을 요구하던 세 자리를 전부 손댄다.**

| 자리                  | 전                                     | 후                                                                             |
| --------------------- | -------------------------------------- | ------------------------------------------------------------------------------ |
| 서버 1층 §6·§8·§9·§11 | 골격·첫 문장·순서를 못 박음            | 구성·순서를 요청서로 넘김(판본 3)                                              |
| 표식 지시             | "순서는 반드시 [평가] → …" 고정 문자열 | `narrativeMarkInstruction(옵션)` — 구성이 있으면 "위 「작성 구성」을 따릅니다" |
| 요청서 마지막 줄      | "하나의 탐구 흐름으로 이어 주세요"     | 구성을 실었으면 그 문장을 빼고, 묶는 방식은 구성 블록이 말함                   |

세 자리 중 하나라도 놓치면 서로 싸우는 지시가 나간다. 회귀 검사 **#79·#80** 이 두 자리를 글자로 박는다.

## 구버전 앱 호환 — 1층에서 순서를 빼도 구버전 결과는 안 바뀐다

v2.5.0 이하 앱은 요청서에 「작성 구성」을 못 싣는다. 그런데 그 앱들도 표식 지시
(`NARRATIVE_MARK_INSTRUCTION`)를 **매 요청 끝에** 보내고, 그 문장이 순서와 첫 문장 어미를 **전부**
말한다. 그래서 1층에서 순서를 빼도 구버전 앱의 결과는 그대로다. 이 상수의 값은 글자 하나까지
예전과 같게 유지했고, 검사로 고정했다.

## 미해결 · 남은 위험

- **서버 규정 판본 3 은 아직 적용하지 않았다.** 시크릿 교체 + 함수 재배포는 오너 승인 뒤에 한다.
  적용 전까지 새 구성은 아무에게도 나가지 않는다(문지기가 기존형으로 되돌린다).
- **실제 모델이 고른 구성을 얼마나 지키는지는 표본 20건으로만 봤다**(가상 근거, Claude 한 공급자).
  Codex 쪽은 이번에 재지 않았다.
- 카탈로그의 초점 이름·요소 구성은 대학 가이드북과 연수자료를 읽고 만든 **쌤핀의 제안**이다.
  공식 지정 양식이 아니고, 현행 기재요령과의 상세 대조는 여전히 남아 있다.
- 초점을 바꾸면 요소 조정(뺀 것·더한 것)은 버린다. 다른 초점의 요소 id 를 들고 가면 뜻이 없어서인데,
  선생님이 공들여 고른 조정이 사라지는 순간이므로 실사용 반응을 볼 것.

## 보강 1 — 초점 7종으로 줄인다 (2026-09-09, 오너 검토)

오너가 실제 생성 20건을 읽고 판단했다: **"결과물이 비슷한 템플릿은 하나로 추려라. 기존형이 더 낫다.
10개는 선생님께 복잡하다."**

측정부터 했다. 기존형과의 대조가 B1 하나뿐이어서 B2·B3·B4 에도 기존형을 돌려 3건을 추가 생성한 뒤 견줬다.
결과: **성취·수행 · 질문·검증 · 개념 적용** 셋이 세 묶음 모두에서 기존형과 거의 같은 글을 냈다.
질문·검증의 유일한 차별점(질문으로 열기)은 **이미 「시작 방식」이라는 독립 설정으로 가능**하다.

### 결정

1. **초점은 7종이다**: 기존형 · 근거 비교·판단 · 피드백·수정 · 설계·창작 · 협업·기여 · 관심 탐색 · 생활·관계 종합.
2. 합쳐진 셋의 **지침은 버리지 않고 기존형의 세 요소로 옮긴다**(개념은 이름보다 쓰인 방법 · 조사·실험·증명
   구별 · 결론 강도 · 성취기준 문구 그대로 옮기지 않기 · 참여만으로 숙달 단정 금지).
3. 쓸모 있던 선택 요소는 **기존형의 「더 넣을 수 있는 요소」**로 살린다: 사용한 개념 · 적용 범위·한계 · 한계·추가 검토.
4. 없어진 세 값은 `RECORD_FOCUS_ALIASES` 로 **명시적으로** 기존형에 매핑한다. 조용히 기본값으로 떨어뜨리지
   않는다 — 어디로 갔는지 표가 정하고 그 표를 테스트가 지킨다. 카탈로그 판본은 2로 올린다.
5. 카탈로그에 **죽은 요소를 남기지 않는다**(어느 초점도 안 쓰는 요소 = 0). 테스트로 고정.

## 보강 2 — 문장 잇기·평가 키워드·근거 활용 (같은 검토)

| 지적                                                          | 반영한 자리                                     | 왜 그 자리인가                                                                            |
| ------------------------------------------------------------- | ----------------------------------------------- | ----------------------------------------------------------------------------------------- |
| 연결어미·접속부사가 없어 문장 관계가 안 드러난다(많아도 문제) | **1층 규정 §3** + 「작성 구성」 블록            | 기본값(기존형)은 구성 블록을 안 붙이므로 1층에 없으면 대부분의 선생님에게 적용되지 않는다 |
| 평가 문장에 강점·역량 키워드가 안 보인다                      | **1층 §3** + `teacherJudgement` 요소            | 같은 이유. 오너가 든 나쁜 예를 1층에 ✗ 예시로 박았다                                      |
| 행특에서 근거가 충분히 안 쓰인다                              | 「작성 구성」 블록 + `lifeScenes` 요소 + 1층 §8 | 행특은 기본값이 아니므로 구성 블록이 붙는다                                               |

★**"더 쓰라"는 지시는 반드시 "늘리지는 말라"와 짝으로 넣는다.** 근거 활용 지시만 넣었더니 한 장면을
세 문단으로 늘렸다(실측). "같은 장면을 여러 문단으로 나누지 말라 · 근거가 적으면 글도 짧아야 한다"를
함께 넣자 원래 분량으로 돌아왔다. 연결 표현 지시에도 같은 이유로 "필요한 자리에만 · 한 문단에 한두 번"을 붙였다.

## 보강 3 — 1차 보고의 정정

1차에서 "행특이 근거 3건 중 1건을 안 썼다(AI 손실)"고 적었다. **틀렸다.** 그 근거에 '대회'라는 낱말이
있어 **기재 금지 필터가 요청서에서 아예 빼 버린 것**이다(`detectProhibitedTerms` → `대회·수상`).
ADR-072 의 의도된 동작이며 화면은 "제외됨 1건"으로 알린다.

다만 **'체육대회 준비물을 빌려준 장면'은 수상 기록이 아니다.** 이 필터의 과탐지는 이 결정의 범위 밖이고,
느슨하게 하면 진짜 수상 기록이 새므로 **오너 판단 대상으로 남긴다.**

★교훈: "AI 가 빠뜨렸다"고 판정하기 전에 **요청서에 그 근거가 실렸는지부터 본다.**

## 보강 4 — 금지어는 낱말만 걸린 경우 대체어로 살린다 (2026-09-09, 오너 요청)

오너: "체육대회는 '체육행사'처럼 대체어를 써서 근거로 쓸 수 있게 해야 한다."

### 확인한 규정 (2026-09-09)

- 학교생활기록부 종합지원포털 Q&A: **'대회'는 수상경력을 제외한 어떤 항목에도 입력하지 않는다.**
  다만 창의적 체험활동 **누가기록**에는 '체육대회' 같은 명칭을 쓸 수 있다.
- 같은 포털: 학교가 주최한 **행사**(의식행사·발표회·**체육행사**·현장체험학습)는 성격에 맞는
  창의적 체험활동 영역에 넣어 입력할 수 있다.
- 울산 NEIS 자문단 Q&A(전담자 답변): **'운동회' 또는 '체육행사'** 로 명칭을 계획해 운영하면 문제없고,
  **교내상이 계획되지 않은** 프로그램이면 관찰한 사실로 특기사항을 쓸 수 있다.

### 결정

1. **대체는 아주 좁게 한다.** 지금 표에 있는 것은 `체육대회 → 체육행사` **한 짝뿐**이다.
   공식 안내가 대체 명칭을 명시한 것만 넣는다.
2. **일반 규칙(`대회` → `행사`)은 두지 않는다.** 처음에 넣었다가 **테스트가 바로 잡았다**:
   그러면 '경진대회'가 '경진행사'가 되어 필터를 통과한다. **시상을 전제한 이름을 말만 바꿔
   내보내는 것은 규정 우회다.**
3. **수상 결과를 가리키는 말이 함께 있으면 하나도 바꾸지 않는다**(수상·입상·최우수상·우승·1등·메달 등).
   그건 진짜 수상 기록이다. 이 목록은 금지어 목록과 **따로** 둔다 — '우승'·'1등'을 금지어로 올리면
   다른 자리에서 오탐이 는다.
4. **조용히 바꾸지 않는다.** 무엇을 무엇으로 바꿨는지 미리보기에 적고, **"시상이 계획됐던 행사라면
   이름을 바꿔도 기재할 수 없어요"** 를 함께 띄운다. 시상 계획 여부는 앱이 알 수 없다.
5. **선생님이 적어 둔 원본 근거는 바뀌지 않는다.** 대체는 보낼 때만 일어난다(마스킹과 같은 자리).
6. 살릴 수 없는 `대회` 근거에는 **고쳐 적는 법을 알려 준다**(`rewriteHintFor`).
   앱이 대신 판단하지 않고 선생님이 고치도록 한다.

## 보강 5 — 초점 이름·문장 명료성·모델의 자기 정정 (같은 검토)

### 초점 이름을 특징이 드러나게 바꾼다

오너: "기존본이라고 이름 짓지 말고 이 템플릿의 특징이 드러나는 이름을 적어라."

| 전                       | 후                                    |
| ------------------------ | ------------------------------------- |
| 기존형: 하나의 탐구 흐름 | **질문에서 출발한 탐구 흐름 (기본)**  |
| 근거 비교·판단 중심      | **자료를 견주어 판단한 과정**         |
| 피드백·수정 중심         | **피드백을 받아 고쳐 쓴 과정**        |
| 설계·창작·문제 해결 중심 | **직접 설계하고 만든 과정**           |
| 협업·기여 중심           | **함께한 일에서 맡은 몫**             |
| 관심 탐색·선택 중심      | **관심 분야를 넓혀 간 탐색**          |
| 생활·관계 종합           | **한 해 생활과 관계 종합 (행동특성)** |

### 뜻이 한 번에 통하게 쓴다

오너 지적: "근거가 많은 학생이 그렇게 느낀다는 인상에 머물렀고" 는 '근거가 많은 학생'으로 읽힌다.

1층 규정 §3 과 「작성 구성」 블록에 넣은 것:

- 수식 관계가 두 가지로 읽히는 문장 금지. 근거의 말을 명사 앞에 그대로 끼워 넣지 말고 **따옴표로 인용**.
- **비유·은유 금지**(밀고 가다·벼리다·갈아 끼우다·~하는 자리에 서다·닿게 하다).
- 주어 없이 서술어만으로 말이 되는지 확인.
- **근거에 붙은 날짜를 본문에 옮기지 않는다**(실측: Luna 가 "2026년 4월 2일"을 본문에 적었다).

### ★모델이 자기 정정을 본문에 끼워 넣는다 — 새 결함과 그 방어

"내보내기 전에 마지막으로 확인하라"를 §11 에 넣자, Claude 가 **초안 → "…이 표현은 금지된 비유이므로
다시 씁니다. 아래가 초안입니다." → 다시 쓴 초안** 을 통째로 내보냈다(실측). 그 설명 줄은 표식이 없는데,
`judgeNonDraftReply` 는 **글 전체가 설명일 때만** 걸러 내므로 통과했고, 그대로 생기부 칸에 들어갈 뻔했다.

두 겹으로 막는다.

1. 규정(§11): "이 확인은 머릿속으로만 하고 **완성된 글 하나만** 내보낸다. 고쳤다는 말·앞서 쓴 문장을
   함께 쓰지 않는다. 표식 없는 줄을 끼워 넣지 않는다."
2. 코드(`dropUnmarkedParagraphs`): **표식이 하나라도 있으면 표식 없는 문단을 버린다.**
   표식이 하나도 없으면 아무것도 버리지 않는다(옛 초안·다른 모델 호환).

★프롬프트만으로 막지 않는다 — ADR-072 의 원칙이 여기서도 그대로다.
★남은 위험: 자기 정정 시 **평가 문단이 두 번** 나올 수 있다. 표식이 있어 버려지지 않는다.
미리보기에서 눈에 띄므로 이번에는 두지 않았다.

## 보강 6 — 각 문단은 사실과 교사의 해석을 함께 담는다 (2026-09-09, 오너 검토 3)

오너: "코덱스 모델로 쓸 때도 교사의 해석 부분이 있으면 좋겠다."

Codex Terra 의 행특 초안이 근거를 거의 그대로 옮기기만 했다("…치우고 가는 모습이 여러 차례 확인됨."
"…먼저 빌려주고 마지막에 챙김."). 사실은 맞지만 교사가 무엇을 봤는지가 없다. 기록부가 아니라 관찰 메모다.

### 결정

각 문단은 **학생이 한 일 + 그 일에서 교사가 읽은 것**을 함께 담는다. 해석 문장의 어미는
`~확인됨`·`~드러남`·`~관찰됨`·`~판단됨`. 1층 규정 §6 과 「작성 구성」 블록 **양쪽**에 넣는다
(기본 초점은 구성 블록을 안 붙이므로 1층에 없으면 대부분에게 적용되지 않는다).

### ★함께 넣은 제약 4개 — 이것이 이 결정의 핵심이다

"더 해석하라"만 넣으면 지어내기와 되풀이가 는다. 이번 작업에서 **세 번** 겪었다
(근거 활용 → 한 장면을 세 문단으로 / 연결 표현 → 남발 / 해석 → 요약 문단 추가).

1. 해석은 **그 문단의 사실에서 곧바로 읽히는 것만.** 성격 전체·가치관·미래를 넘겨짚지 않는다.
2. **첫 문단의 총평을 문단마다 되풀이하지 않는다.** 문단마다 읽은 것이 달라야 한다(ADR-094 §4 연장).
3. 읽을 것이 없으면 **해석을 쓰지 않고 사실만** 남긴다.
4. **이미 쓴 사실을 다시 모아 요약하는 문단을 만들지 않는다.** ← 1차 반영 뒤 Luna 가 실제로 저지른 것.

★**원칙으로 굳힌다: 생성 지시를 더할 때는 그 지시가 과해지는 방향을 함께 막는다.**

### 확인

세 공급자(Claude · Codex Terra · Codex Luna) 모두 문단마다 해석이 붙고 되풀이가 없는 것을 실측했다.

### 미해결

Codex Terra 는 따옴표 인용 지시를 **4회 중 1회만** 지켰다(Luna·Claude 는 2/2). 규정 §3 예시와
§11 점검 두 곳에 넣었는데도 그렇다. 사실 왜곡은 아니고 읽기 어려울 뿐이라, **모델 차이로 기록하고
지시를 더 얹지 않았다** — 지시를 늘리면 다른 규칙이 밀린다.

## 보강 3 — 상단 정보 바의 범례를 "작성 방식 배지"로 (2026-09-09, 오너 요청)

### 문제

작성 방식이 일곱이 되었는데 초안 화면 상단 정보 바의 형광펜 범례는 `교사 평가 · 동기·질문 ·
과정 · 결과` 로 **고정**이었다. 무엇을 골랐는지, 그 방식이 어떤 순서로 쓰는 글인지 알려면
오른쪽 패널의 [자세히]를 펴서 「적용될 설정」을 봐야 했다. 고르는 화면만 만들고 **고른 결과가
보이는 자리를 만들지 않은 것**이다.

### 결정

범례의 성격을 "색 안내"에서 **"지금 고른 작성 방식 요약"** 으로 바꾼다.

1. 방식 이름을 늘 보여준다. 형광펜 스위치와 무관하다 — 작성 방식은 형광펜을 꺼도 적용된다.
2. 구성 요소를 화살표로 이어 **순서대로** 보여준다. 값은 「적용될 설정」과 **같은**
   `resolveComposition(style).modules` 다. 둘이 갈리면 화면이 거짓말을 한다.
3. 색점은 형광펜을 켰을 때만 붙는다. 껐을 때는 본문에 칠해진 색이 없어 색 안내가 뜻을 잃는다.
4. 좁아지면 요소를 **줄바꿈하지 않고 접는다**(이름 + 단계 수). 상태 막대가 두 줄이 되면 아래
   본문이 출렁인다.
5. 누르면 오른쪽 AI 패널의 작성 방식 고르기를 편다. 패널을 새로 만들지 않는다(도크와 배타).
   갈 곳이 없는 상태(대상 학생 없음)에서는 단추가 아니라 표시로만 둔다.

### 바꾸지 않는 것

형광펜 **4색과 모델에게 나가는 표식(`[평가][동기][과정][결과]`)은 그대로**다. 방식마다 색이나
표식을 늘리면 이미 저장된 초안의 `roleMarks` 와 파서가 깨지고, 모델이 표식을 틀릴 확률도 오른다.
바뀌는 것은 **이름과 순서**뿐이다.

같은 색이 잇달아 나오는 방식이 있다(행동특성은 과정 셋, 자료 비교는 과정 둘·결과 둘). 색을
늘리지 않고 화살표와 요소 이름으로 가른다. 색만으로 뜻을 전하지 않도록 순번·이름·역할 이름을
`sr-only` 문장으로 함께 읽어 준다.

### 구현

| 자리                                          | 한 일                                                               |
| --------------------------------------------- | ------------------------------------------------------------------- |
| `RecordDraft/RecordStyleLegend.tsx` (새 파일) | 배지 본체. 도메인의 `focusById`·`resolveComposition` 만 읽는다      |
| `RecordDraft/RecordDraftView.tsx`             | 영역별 작성 방식을 고르는 자리와 **같은 곳에서 읽어** 배지에 넘긴다 |
| `RecordDraft/RecordDraftAiPanel.tsx`          | `openStyleSignal` 을 고르개로 전달                                  |
| `RecordDraft/RecordStylePicker.tsx`           | `openSignal` 이 오르면 펴고 고르는 칸에 초점                        |

않는 결함이 생긴다. 0 은 "아직 누른 적 없음" 이라 패널을 열 때마다 저절로 펴지지 않는다.
