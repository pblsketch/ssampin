# ADR-079: 교무실 계측은 "부서 단위 행"을 만들지 않는다 — 화면에서 가리는 게 아니라 SQL 에서 안 꺼낸다

> 2026-08-31 · 관련 계획서 `docs/01-plan/features/staffroom-survival.plan.md` §6-P0 ·
> 마이그레이션 `064_staffroom_health.sql` · REGRESSION #66

### 배경

온라인 교무실은 v2.4.4(2026-08-24)에 실험실 기능으로 나갔는데 **계측이 0건**이다.
부서가 몇 개인지, 그중 **관리자 구글 연결이 끊긴 부서가 몇 개인지** 아무도 모른다.
그런데 교무실은 §3.2.1 대로 **읽는 길까지 관리자 한 사람의 구글 계정을 지나므로**, 그 사람이
전출하면 자료실 전체가 부서 전원에게 안 열린다. "끊긴 부서 수"는 관리자 넘겨주기·공동 관리자
같은 후속 작업의 **긴급도를 재는 유일한 숫자**다.

문제는 이 숫자를 재려면 **여러 학교의 부서를 가로질러 읽어야 한다**는 것이다. 쌤핀에서 처음이다.

### 결정

**집계 함수(`staffroom_health_v1`) 단계에서 부서를 식별할 수 있는 칸을 아예 만들지 않는다.**
숫자·날짜·구간 히스토그램만 내보내고, 부서 이름·교사 이메일·글 제목은 물론 **부서 id 조차**
선택하지 않는다. 두 겹으로 못박는다:

1. **타입** — `RETURNS TABLE` 19칸이 `bigint`·`timestamptz`·`date` 뿐이다. `uuid`·`text`·`jsonb` 0개.
2. **카디널리티** — **바깥 `SELECT` 에 `FROM` 이 없다**(스칼라 서브쿼리만). 그래서 구조적으로
   **항상 정확히 1행**이다. 히스토그램의 `GROUP BY` 는 CTE 안에 갇혀 밖으로 새지 않는다.

### 왜 이렇게까지 하는가 (드라이버)

- **오너 대시보드는 다른 학교 선생님들의 부서 내용을 볼 자리가 아니다.** 부서별 표를 만들면
  id 만 있어도 "이 부서가 크다/죽었다"가 보이고, 결국 이름을 붙이고 싶어진다.
- **화면에서 가리는 방식은 실질 방어가 아니다.** 관리자 화면 인증은 `landing/middleware.ts` 에서
  **쿠키 값을 `ADMIN_PASSWORD` 와 그냥 비교**하는 구조다(비밀번호가 곧 세션 토큰). 그 경계 위에서는
  "안 띄운다"보다 **"DB 밖으로 안 나간다"** 가 훨씬 무겁다. 화면에 안 보여도 네트워크 응답 본문에
  남으면 실패다.
- **긴급도를 재는 데 필요한 건 분포지 명단이 아니다.**

### 대안과 기각 사유

| 대안                                       | 기각 사유                                                                                                                                                                       |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 부서별 표를 만들고 화면에서 가린다         | 네트워크 응답 본문에 그대로 남는다. 방어가 아니다                                                                                                                               |
| 부서 이름을 해시로 바꾼다                  | 여전히 부서 단위 추적이 되고, 오너는 자기 학교 부서를 알아서 짚을 수 있다                                                                                                       |
| `RETURNS TABLE` 에 타입 검사만 건다        | `RETURNS TABLE(members_count bigint, files_total bigint, last_activity_date date)` 같은 **부서당 한 행**이 타입 검사를 통과하며 되살아난다 → 그래서 카디널리티 계약을 함께 둔다 |
| 기존 `staffroom_storage_usage`(051) 재사용 | **부서 단위 행**(`department_id UUID`)을 돌려준다. 전체를 세려면 모든 부서 id 를 넘겨야 해서 이 결정이 금지한 모양이 그대로 생긴다                                              |

### 함께 정한 것

**(1) `SECURITY DEFINER` 를 고른 이유 — 061 과 다르게 간다.**
`061_analytics_rollups.sql` 의 데이터 RPC 16종은 전부 `STABLE SECURITY INVOKER` 다. 그런데
**교무실 도메인의 선례는 정반대로 3/3 이 `SECURITY DEFINER`** 다(`050:256`·`051:242`·`052:256`).
같은 도메인에 정반대 관례를 넣지 않는다. 기능적으로는 둘 다 돌지만(service_role 은 BYPASSRLS),
`INVOKER` 에는 **"대시보드 키가 언젠가 service_role 이 아닌 것으로 바뀌면 RLS 가 조용히 0행을
돌려주고 `fetchRpc` 가 그걸 빈 배열로 만들어 탭이 빈 화면이 된다"** 는 실패 경로가 붙는다.
대신 `REVOKE ALL ... FROM PUBLIC, anon, authenticated` 를 테스트로 못박는다.

**(2) P0 에서 개인정보처리방침을 개정하지 않는 이유.**
새로 저장하는 것은 `last_broken_at`·`broken_kind` **두 칸뿐이고, 이건 관리자 본인의 구글 연결
상태에 대한 운영 메타데이터**다. 교사·학생 개인정보가 새로 수집되지 않고, 집계는 기존 데이터를
개수로만 센다. (공동 관리자에서 **관리자 토큰을 여러 개 보관하게 되면** 그때는 제11조를 다시 본다.)

**(3) ★ 분리선 — 이 결정이 "그런 능력이 어디에도 없다"로 읽히면 안 된다.**
**대시보드는 부서를 절대 보지 않는다.** 운영상 특정 부서에 연락해야 할 일이 생기면
**일부러 불편하게 만든 일회성 운영 스크립트로만** 본다. 상시 화면으로 만들지 않는다.

**(4) 성공은 기록하지 않는다.**
`adminAccessToken` 은 모든 읽기·쓰기가 지나는 뜨거운 길이고 빠른 경로는 지금 쓰기가 0회다.
"정상"은 **이미 있는 `staffroom_admin_tokens.updated_at`** 으로 소급해서 구한다(갱신 성공·재로그인
양쪽에 기록된다). 그래서 새 표도, 성공 경로 쓰기도 필요 없고, **배포 첫날부터 소급된 진짜 숫자**가 나온다.
기록은 `staffroom-library` 의 `list` 가 **실패했을 때만** 한다.

### 결과 (좋은 것과 나쁜 것 둘 다)

- ✅ 다른 학교 부서 내용이 오너 화면에 **구조적으로** 닿지 않는다.
- ✅ 뜨거운 길에 쓰기가 늘지 않아 자료실이 느려지지 않는다.
- ❌ **어느 부서가 크고 어느 부서가 죽었는지 개별로는 못 본다.** 분포로만 본다.
- ❌ **"끊김 0"이 진짜 0인지 계측이 멈춘 것인지 화면만으로 구별할 수 없다** — 정상 상태에서는
  아무것도 기록하지 않기 때문이다. 확인하려면 관리자 토큰을 일부러 끊고 자료실을 열어봐야 한다.
- ❌ **서버 설정(`STAFFROOM_ENCRYPTION_KEY`)이 잘못된 날은 지표가 "정상"이라고 말한다** —
  키 부재는 "토큰 행 없음"과 같은 종류로 와서 원리적으로 못 가른다. 진단은 Edge Function 로그로 한다.
- 🔒 나중에 개별 부서를 보고 싶어지면 **SQL·메타 테스트·회귀검사 셋을 함께 고쳐야 한다.**
  이 마찰은 **의도된 것**이다(`staffroomHealthPrivacy.meta.test.ts` · REGRESSION #66).

### 후속

- **새 판 grants 미갱신 결함(계획서 §11)** — 새 판을 올리면 `staffroom_files.drive_file_id` 가
  갈아끼워지는데 `staffroom_file_grants` 는 `(file_id, member_email)` 로만 조회·유일 인덱스라
  v1 을 받아 본 멤버가 v2 권한을 못 받는다. 이번 범위 밖. 고치려면 `insert` → `upsert(onConflict)`
  전환과 error 확인이 함께 필요하다(단순히 조회 조건만 더하면 유일 인덱스에 걸려 조용히 실패한다).
- 부서 수가 늘어 "조용함"의 사각이 문제가 되면 일회성 점검 스크립트를 만든다.
