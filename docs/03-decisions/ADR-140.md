# ADR-140 — Analytics 롤업을 증분 갱신으로 바꾼다 (구체화 뷰 9종 → 일반 표, 새 행이 닿은 날짜·기기만 다시 계산)

- 날짜: 2026-09-30
- 상태: 채택 · 운영 DB 적용 완료(마이그레이션 `078_analytics_rollup_incremental.sql`, `schema_migrations` 기록)
- 결정자: 오너 (2026-09-30 대화 — 원인 보고 뒤 "증분 롤업 vs 컴퓨트 승격" 중 "전자로 조치")
- 관련: 061(롤업 도입) · 065(모바일 분리) · 076(시간 초과 복구) · 2026-09-09 주기 결정(`5 1-21 * * *`, 바꾸지 않음)

## 발단

Supabase 가 "Disk IO Budget 이 바닥난다"는 경고 메일을 5번 보냈다(마지막 2026-09-30). 컴퓨트 add-on 이 없어
Nano(메모리 0.5GB, 디스크 기준 5MB/s·250 IOPS, 넘치면 버스트 예산에서 깎인다)로 돈다.

## 조사 결과 (읽기 전용, 2026-09-30)

- pg_stat_statements(9/8 재시작 뒤 22일): `select analytics_refresh_rollups()` 가 DB 가 디스크에서 읽은 블록의 약 60%,
  임시 파일 쓰기 거의 전부를 차지했다(temp 170GB, 하루 약 7.7GB). work_mem 4MB 를 넘친 정렬·중복 제거가 원인.
- 호스트 지표(`/customer/v1/privileged/metrics`): 메모리 여유 6.6MB·스왑 약 0.5GB 사용. 롤업이 없는 시간에도 시스템
  디스크(스왑·페이지 재적재)가 초당 4~8MB·IOPS 약 250 을 읽는다. **옛 롤업이 도는 3분 동안은 IOPS 약 3,000·스왑 읽기
  15MB/s 로 12배 뛰었다** — 예산을 한꺼번에 깎는 것은 이 폭주다.
- 트래픽 급증은 없었다(앱 기록 저장 하루 2천여 건).

## 결정

1. 롤업 9종을 구체화 뷰에서 **같은 이름의 일반 표**로 바꾼다. 컬럼·색인·권한(anon·authenticated 없음, service_role
   조회)을 그대로 두어 `*_v2` RPC 14개는 고치지 않는다. 새 표에는 RLS 를 켠다(Supabase 기본 권한 방어).
2. `analytics_refresh_rollups()` 는 **직전 갱신 뒤 새로 들어온 행(app_analytics.id 기준)이 닿은 날짜·기기만** 지우고 다시 계산한다.
   - 날짜 단위 6종은 그 날짜의 created_at 범위만, 기기 단위 3종은 그 기기의 전체 기간을 다시 집계한다.
   - 기준을 created_at 이 아니라 id 로 잡는다. created_at 은 앱이 보낸 값이라 오프라인으로 쌓였다가 늦게 들어오는 행이
     있다(실측: 5월 28일 날짜 행이 9월 말에 들어옴). "최근 N일만 다시 계산"은 이런 행을 놓친다.
   - 직전 max(id) 에서 1000 행을 겹쳐 다시 본다(아직 커밋 안 된 행 대비). 다시 계산은 멱등이다.
   - 집계식은 운영 `pg_matviews` 정의를 그대로 옮겼다.
3. 원본 행 삭제는 반영하지 않는다(지금 원본을 지우는 정기 작업이 없다). 집계식을 바꾸거나 원본을 지우면
   `analytics_rebuild_rollups()`(옛 REFRESH 와 같은 무게)로 한산할 때 전체를 다시 만든다.
4. 주기·크론 명령·"지금 갱신" 경로는 바꾸지 않는다.

## 확인 (운영)

- 적용: 트랜잭션 한 번 6.8초. 9개 모두 `relkind=r`, RLS 켬, anon·authenticated 권한 없음, 색인 18개.
- 한 번 갱신 비용(pg_stat_statements 차이): 디스크 읽기 30블록(옛 방식 평균 약 3,850) · 임시 쓰기 3,555블록(옛 약 57,000) ·
  21~50초(옛 130~280초). 소요가 들쭉날쭉한 것은 스왑 때문이다.
- 동등성: 기준 id 이하 행으로 옛 정의를 다시 계산해 9종 전체를 `EXCEPT ALL` 양방향 대조 → 7종 0건 차이.
  device_event·device_profile 은 1행씩 달랐는데 **갱신 도중 들어온 id 1112115·1112116 두 행이 새 표에 먼저 반영된 것**이라 정상.
  hour_day·device_prop 은 관리 API 2분 한도 때문에 날짜·기기 구간으로 나눠 대조했고 전부 0건.
- 정기 갱신(첫 cron 회차)과 그 시간의 IOPS 는 [진행 기록](../progress/2026-09.md)에 적었다.

## 남는 것 · 하지 않은 것

- **롤업과 무관한 상시 스왑 IO 는 그대로다.** 경고가 계속 오면 원인은 메모리 부족이고, 처방은 컴퓨트 승격(Micro,
  월 약 $10, 메모리 1GB)이다. 오너 판단 사항.
- 기기 단위 3종은 한 시간에 기록을 보낸 기기(약 50대)의 전체 기록(약 19.5만 행)을 다시 읽는다. 더 줄이려면
  기기×이벤트×일자 중간 표를 두는 방법이 있다 — 지금은 디스크 읽기가 거의 0 이라 하지 않았다.
- 되돌리기: 운영 정의로 구체화 뷰를 다시 만들고(당시 `pg_matviews` 정의 = 061+065) 076 의 함수 본문을 다시 적용한다.
